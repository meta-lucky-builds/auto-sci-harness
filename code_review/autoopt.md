## 1. What the code actually does (architecture map)
This repo is **not a software system that runs the pipeline**. It is (a) eight "agent skill" folders (`Skills/`, duplicated with small drifts in `plugins/autoopt/skills/`), i.e. markdown instructions plus a few helper scripts for a host coding agent (Codex / Claude Code), and (b) two finished Lean 4 / mathlib projects (`Lean-Related/ITEM-f`, `Lean-Related/LemniAcc`) holding the paper's two verified results. The README states "agent skills + Lean verification projects only" (consistent with the task brief).
- `auto-opt` (`Skills/auto-opt/SKILL.md`): a "thin pipeline controller" that is explicitly "not an autonomous agent" (`SKILL.md:10-16`). Stage 0 repo grounding -> Stage 1 BnB-PEP numerics -> Stage 2 symbolic fitting by LLM -> Stage 3 Lean -> closeout. A human approval gate sits at every boundary (`SKILL.md:209-235`, gate-brief template `stage-handoff-protocol.md:152-165`).
- `research-repo-manager`: scaffolds a repo of fixed markdown ledgers (`GOALS/SOURCES/FINDINGS/EXPERIMENTS/ARTIFACTS/REPRODUCIBILITY/NEXTSTEP/OPTIONAL_GOALS`), an immutable `RawSources/`, and `scripts/audit_sources.py` (sha256 drift detector against `sources.lock.json`).
- `bnb-pep-skill`: instructions for turning a function class + FSFOM + metric into a PEP derivation (markdown, human-approved) and then Julia/JuMP code. **No BnB-PEP solver or certificate-extraction code exists in the repo.** The only `.jl` file is `check_julia_environment.jl`; `find -name "*.jl"` returns only copies of that. The "numerical certificates" of the paper are produced by code the host agent generates at run time, outside this repo.
- `frontier-llm-consult` / `chatgpt-pro-session` / `chatgpt-pro-handoff`: route Stage 2 either to a human-in-the-loop ChatGPT Pro web session (zip upload + marker-delimited response pasted back, `chatgpt_handoff.py`; it uses `pbpaste`, `chatgpt_handoff.py:511`, so it is macOS-only) or to `solve-with-highest-reasoning`.
- `solve-with-highest-reasoning`: a long-horizon (default 8 h wall + 28,800 s active) native campaign with a machine-validated run record (`validate_campaign.py`).
- `lean-verify`: Lean/Lake formalization workflow with a hygiene script and Comparator closeout.
- Lean projects: each has `Spec/` (proof-free definitions + result types), internal proof modules, `Challenge.lean` (the Spec import + `by sorry` theorems), `Solution.lean` (same signatures discharged from the internal proofs), `config.json` (Comparator config), `AxiomAudit.lean` (`#print axioms` for every public theorem).

## 2. Core loop, step by step (with file:line citations)
There is no code loop; the "loop" is a protocol the host agent follows.
1. Stage 0: `research-repo-manager` Initialization / Status Refresh / Session mode (`research-repo-manager/SKILL.md:8-21`); user must approve `GOALS.md` text before it is written (`:53`).
2. Stage 1: `bnb-pep-skill` formalizes the instance, writes a Markdown derivation, **stops for human approval, only then generates Julia** (`bnb-pep-skill/SKILL.md:63-80`). Default is local Stage 1/2 only (dual SDP for a feasible point, then a warm-started local NLP); spatial B&B / Gurobi is opt-in and forbidden by a regex linter unless `--allow-stage3-global` (`validate_generated_instance.py:36-65, 149`).
3. Stage 2: LLM symbolic fitting. Output "candidates" enter the ledger as `Conjectured` or `Needs check` only (`auto-opt/SKILL.md:242-244`). Verify-on-return is by the researcher; "model re-examination is not verification" (`:172-179`).
4. Stage 3: `lean-verify`. Formalize lemma-by-lemma, `lake build`, hygiene scan, optional Comparator replay of `Challenge.lean` vs `Solution.lean` (`lean-verify/SKILL.md:132-183`). Stop rule: block rather than weaken the theorem; two failed focused repair attempts on one obligation => ask a human (`lean-build-loop.md:332-340`).
5. Closeout: route conclusions to the ledgers, set exactly one next full-workday session (`research-repo-manager/SKILL.md:121-128`).

## 3. Paper/summary vs code discrepancies
- **"BnB-PEP numerical certificates" are not in the repo as code.** Summary says Stage 1 "Fully automated... generates convergence certificates" (summary, Level of Autonomy). The code is only instructions to a host LLM plus a static linter whose docstring admits "document-wide phrase-presence checks (static lint), not per-section structural validation and not computational verification" (`validate_generated_instance.py:3-4`). `smoke-tests.md:164`: "Do not claim computational validation when only static lint was possible." So the claim is not reproducible from this repo.
- **"Fully automated" Stage 1/2/3 vs mandatory human approval.** The summary lists stages as automated, but the skill files make every boundary an explicit human gate and say outright that it is not an autonomous agent (`auto-opt/SKILL.md:10-16, 235`). Comparator replay itself needs human approval of the wrapper surface (`lean-verify/SKILL.md:56-59`).
- **BnB-PEP "Stage 3" (global certification) is deliberately excluded from the default pipeline** (`auto-opt/SKILL.md:263-265`; `bnb-pep-skill/SKILL.md:10, 97-100`). The summary's "three-stage process ... spatial branch-and-bound certification" is therefore only an opt-in lint target here, and "solver output is not a theorem or Lean proof" (`stage3-global-optimization.md:85-89`).
- **Lean evidence is asserted, not shipped.** `LemniAcc/README.md` says "This public directory is build-only. It does not include project-local validation scripts or recorded build, hygiene, axiom-audit, or Comparator artifacts." `ITEM-f/README.md` is a 4-line stub with a dangling sentence. I found no recorded `lake build` output, no `#print axioms` output, no Comparator log in the repo. [inference] The "formally verified" status in the paper cannot be checked from repo artifacts alone; one must rebuild.
- **The paper's "claims and evidence are kept" mechanism is markdown tables, not enforced data.** Only `solve-with-highest-reasoning` has a machine validator for its ledger; `research-repo-manager`'s FINDINGS ledger has no validator (see section 6).
- **`Skills/` vs `plugins/autoopt/skills/` drift.** `diff -rq` shows differing `chatgpt-pro-session/SKILL.md`, `chatgpt-pro-handoff/SKILL.md`, `bnb-pep-skill/references/{composite-primitives,onboarding}.md`, and `research-repo-manager/agents/openai.yaml`. The `Skills/` copy of `chatgpt-pro-session/SKILL.md` hard-codes the author's path `/Users/shuvo/My Drive/GitHub/Shuvos_Skills/...` (the plugin copy uses `<chatgpt-pro-session-skill-dir>`), and `Skills/research-repo-manager/scripts/__pycache__/` was committed.
- "No autonomous self-improvement" (summary) is confirmed: nothing in the repo modifies skills, prompts or policies from results. The skills do contain a human-gated "self-extension rule" for new interpolation conditions with provenance labels (`bnb-pep-skill/SKILL.md:29-38`), which is the closest thing.

## 4. Mechanisms worth adopting into custom-harness (ranked by expected value)
Our current state: `tiers.py:12-21` has T0 Formal ("Lean / SMT") as a single label, `chain_tier` = weakest link (`tiers.py:24-27`), `DEFAULT_POLICY` (`tiers.py:41-48`); evidence/claims are in `store/` (STATUS.md: claims only from evidence, I1/I2/I4 audit).

1. **Trusted-surface split for T0: `Challenge` (proof-free Spec + `by sorry`) / `Solution` / `config.json` (theorem names + `permitted_axioms`) / Comparator replay, plus `AxiomAudit`.** Evidence: `ITEM-f/Challenge.lean:1-49` imports only `ITEMf.Spec` (comment: "proof-free `ITEMf.Spec` tree"), `Solution.lean` repeats signatures and discharges from `ITEMf.Internal.*`, `config.json` lists 14 theorem names and `permitted_axioms: [propext, Quot.sound, Classical.choice]`, `AxiomAudit.lean:10-23` prints axioms for each. Why better: it shrinks what a human must trust to ~670 lines of definitions (`wc` of `ITEMf/Spec/*.lean`) instead of 15k proof lines, and it closes the "theorem was quietly weakened / definitions redefined" hole, which `tiers.py` does not address (we currently have no notion of statement fidelity). Layer: L3 verifier registry (T0 verifier = `lean_comparator`), with the human-approved spec surface hash stored as Evidence; L9 approval record for the statement. Effort: M (needs Lean toolchain + Docker/gVisor sandbox; do not run Landrun on native Windows, they say the same). Copy-vs-reimplement: reimplement the protocol; the two Lean projects are un-licensed -> ideas only.
2. **Split T0 into two evidence labels, `Lean build+hygiene verified` vs `Lean+comparator verified`, with a required evidence record.** `lean-verify/SKILL.md:185-201`, `comparator-platforms.md:190-205` (host OS, kernel, sandbox backend, tool revisions + hashes, wrapper hashes, exact command, exit status, final verdict). Why better: our `Tier.T0_FORMAL` is one bucket; a `build` alone does not bind the theorem statement. Concretely: `T0a_LEAN_BUILD`, `T0b_LEAN_COMPARATOR` (or a sub-field on the Evidence record) and `PUBLISH_VERIFIED` policy requires T0b for "verified". Layer: L3 + `tiers.py`. Effort: S. Reimplement (idea).
3. **Statement-fidelity gate with named "blocked" outcome.** `lean-build-loop.md:229-245, 325-340`: preserve raw blueprint, diff generated statements against the source proof, reject silent weakening / changed index ranges, mark `blocked/stubbed` rather than weaken after 2 repair attempts; `lean-verify/SKILL.md:200-201`: "If the formal theorem differs from the paper theorem, record the difference explicitly". Our PLAN has no equivalent of a "statement correspondence" check for T0/T1 claims. Layer: L2 audit (new integrity item, e.g. I5 "formal statement matches claim text, signed off by human or by an independent model panel") feeding L3. Effort: S-M. Reimplement.
4. **Machine-validated, hash-pinned independent-audit records for a claim.** `validate_campaign.py:1172-1392`: each audit must carry candidate/contract sha256 that match the files on disk (`:1263-1275, 2139-2181`), `authoring_involvement == false`, a fresh context whose agent record started after `last_material_repair_at`, scope in a fixed set (`REQUIRED_AUDIT_SCOPES`, `:28-31`), distinct auditors and contexts, and `audits.completed_fresh` must equal the number of qualifying records (`:1370-1377`). Completion requires both scopes (`:1380-1390`). Why better than ours: our T5 judge panel has agreement stats planned (STATUS next #4) but no staleness rule; "audit invalidated by any later material repair" is the cheap, valuable part. Layer: L2 claim graph + L3. Effort: M. Reimplement (Apache-2.0 would let us copy, but the logic is tied to their YAML run-record layout).
5. **Claim status taxonomy with hard anti-promotion rules.** `claim-evidence-protocol.md:7-19`, `auto-opt/SKILL.md:239-257`: Proven / Derivation checked / Computed / Literature / Conjectured / Refuted / Needs check; model output, duration, subagent agreement, validator pass and self-review "do not promote a candidate"; solver output is never an "exact certificate" unless status, tolerances, gap and logs justify it (`verification-profiles.md:73-76`, `stage3-global-optimization.md:67-89`). This maps cleanly to our tiers: Proven->T0, Computed (full provenance) ->T1/T2, Literature -> a citation tier we lack, Conjectured/Needs check -> T5/T6. The useful addition for `tiers.py` is an explicit **"numerical-certificate evidence checklist"** (solver+version, termination status, incumbent, best bound, gap, feasibility+optimality tolerances, time limit, seed, threads, log path: `stage3-global-optimization.md:69-83`) that a T1 numerical-certificate Evidence record must satisfy before it can count as T1, else it falls to T2/T5. Layer: L3. Effort: S. Reimplement.
6. **Immutable-source hash lock + drift report.** `audit_sources.py:18-139`: sha256 + size per file under `RawSources/`, classify new / missing / hash-changed / possible-renames (by matching hash), `merged_lock` assigns stable `S###` IDs. Equivalent to what our content-addressed blobs already do for runs, but for **human-supplied inputs** (problem statements, reference papers, datasets) we have nothing; needed for time-split rediscovery freeze (PLAN §8/D4) and discovery-mode problem suites. Layer: L2/L5. Effort: S. Copy is allowed (Apache-2.0, keep NOTICE) but it is 213 lines; reimplementing is as easy.
7. **Ledger-as-schema fields for experiments: "supports claim IDs", status in {reproduced, partial, failed, stale, not attempted}** (`reproducibility-protocol.md:103-117`, `evals/experiment_claim_missing_seed.md`). The eval cases are a good template for **our own tests of the integrity audit** (e.g. a `Computed` claim with missing seed/solver version must be downgraded). Layer: L2 audit. Effort: S.
8. **Approve-before-send egress manifest for any external model call** (`chatgpt_handoff.py:40-135` excluded dirs, key/secret globs, sensitive-extension warnings, per-file sha256, sizes; `auto-opt/SKILL.md:128-135`; prompt-injection line at `chatgpt_handoff.py:382`). We already redact secrets in the gateway; the new thing is a **content manifest with hashes shown to the human before data leaves the machine**, relevant to our BYOS/§14 gate. Layer: L0 gateway + L9. Effort: S. Reimplement.
9. **Public-retrieval restriction for open-problem work** (`validate_campaign.py:32-56`, `verification-profiles.md:78-88`): the agent may only look up background and named theorems, never the exact problem/solution/open-status; enforced by regex over logged retrieval records. Relevant to our Phase 7 discovery mode and the contamination problem in the time-split design. The regex approach is weak (see §6) but the policy and the logged retrieval class are worth having. Layer: L4 literature module. Effort: S-M.
10. **Time-boxed campaign floors with active-work accounting** (`campaign.yaml:157-165`, `COUNTABLE_WORK_KINDS` / `EXCLUDED_WORK_KINDS`, `validate_campaign.py:25-26`): minimum wall-clock and active-seconds before an agent may self-declare done, plus a mandatory "exact remaining gap" report on incomplete (`:2230-2240`). Low value for us; the "incomplete must name the exact remaining gap, not 'open'" rule is the transferable bit for discovery-mode null results (PLAN Phase 7 exit: "documented null result"). Effort: S.

## 5. Things custom-harness already does better (with evidence)
- **Autonomy and self-improvement.** AutoOPT has no outer loop, no budget ledger, no trace store, no racing/gating; it is a human-driven protocol. We have L0 graph runtime with checkpoints/forks, budget ledger, append-only evidence store, evolve/ with held-out gate (STATUS.md "Done").
- **Enforcement by code rather than prose.** Their claim ledger (`FINDINGS.md`) is a free-text markdown table with no validator; claims are "traceable" only by instruction (`research-repo-manager/SKILL.md:383-385, 420-426`). Ours: claims can only be created from Evidence rows (STATUS L2) and chain tier = weakest link in code (`tiers.py:24-27`) with a deterministic policy (`tiers.py:57-65`). `solve-with-highest-reasoning` validator is the only enforced ledger and it validates self-reported logs (see §6).
- **Sandboxing.** AutoOPT never sandboxes generated Julia; it relies on human approval gates and explicitly allows an *unsandboxed* macOS Comparator route that "qualifies" (`comparator-platforms.md:134-151`). Ours: Docker with no network/caps/read-only rootfs, local sandbox refused unless flagged (STATUS L0).
- **Statistics.** AutoOPT reports one theoretical constant and no replication; our T2 has seed bootstrap + paired bootstrap + Bradley-Terry (`verify/`).
- **Domain generality.** AutoOPT's verification is domain-locked (first-order methods, `lean-verify` described as "intentionally scoped to optimization theorem verification", `lean-verify/SKILL.md:24-28`). Our verifier ladder is domain-agnostic.

## 6. Pitfalls, bugs, or anti-patterns seen in their code (cite) that we must avoid
1. **Their own hygiene checker would reject their own flagship projects.** `check_lean_project.py:18-19` forbids `sorry` and scans every `.lean` file under the root (`:82-109`), but `ITEM-f/Challenge.lean` (14 `by sorry`, e.g. `:49, 53, 60`) and `LemniAcc/Challenge.lean` (10) contain `sorry` by design. [inference, script not executed] Running the documented command on the project root fails; the closeout recipe works only if the wrapper files are excluded, which the script does not support (no `--exclude`). Lesson: a verifier policy must model the legitimate placeholder file explicitly (our T0 wrapper must whitelist the `Challenge` module by hash, not by blanket regex).
2. **Regex hygiene is not a verifier.** `strip_comments_and_strings` (`:22-79`) handles `--`, nested `/- -/` and `"..."` but not Lean raw strings (`r#"..."#`), char literals such as `'"'` (would flip `in_string`), nor tokens like `native_decide`, `implemented_by`, `extern`, `macro`/`elab` that can smuggle in trust. Since it only blocks four words, the real guard is `#print axioms` + Comparator `permitted_axioms`, which is correct but only recorded as "when the project requires" (`lean-verify/SKILL.md:169-171`). Lesson: T0 acceptance must be derived from the kernel/axiom report, never from source-text scanning.
3. **Axiom audit output is never parsed.** `AxiomAudit.lean:7-8` says "The local acceptance gate checks that every printed dependency set is contained in {propext, Quot.sound, Classical.choice}", but no such gate exists in the repo (`LemniAcc/README.md`: no validation scripts shipped). The check is a comment. Lesson: if the checker is not code we run, it does not exist.
4. **`validate_generated_instance.py` is substring theatre.** Requirement checks are `re.search` over the whole document (`:20-36, 97-130`), so a derivation that mentions "dual SDP", "strong duality", etc. anywhere passes; the Stage-3 block lint is by Julia regex (`:36-65`). It is explicitly labeled as such, but `bnb-pep-skill/SKILL.md:86` still says to run it "before claiming the skill output is ready". Do not let a lint pass promote evidence.
5. **Validator checks consistency of self-reported logs, not truth.** `validate_audits` demands `fresh_context: true` and `authoring_involvement: false` fields (`:1227-1245`), which are written by the same agent being audited; independence of auditors is by declaration. The skill itself warns that the validator "checks protocol structure only and is not mathematical verification" (`stage-handoff-protocol.md:257-258`). Also, "two fresh audits" are the same model family on the same host (`auto-opt/SKILL.md:67-68` admits the native route "cannot satisfy provider diversity"). Lesson: for our T5/replication, require different model families and record that; correlated-error warning from SDE applies.
6. **The public-search ban is a regex over free text** (`PUBLIC_RETRIEVAL_BANNED_PATTERNS`, `:36-56`) and trivially evaded by paraphrase. Treat it as logging, not enforcement; enforce by network allow-listing in the sandbox.
7. **Human gates as the only safety, in prose.** Everything (derivation approval before Julia, upload approval, Comparator surface approval) is an instruction to the host agent, not code the harness enforces. A non-compliant or injected agent can skip them. Our L9 must make approval a persisted record that downstream actions check (`tiers.decide` already does this shape: `tiers.py:57-65`).
8. **Verification claims depend on human reading Spec.** The Lean statements use structure-typed models (`SmoothConvexModel` with `lower`/`upper` fields, `Spec/Model.lean:21-29, 50-61`) and algorithms defined in the Spec (`Spec/Algorithm.lean:100-135`). That is a sound design, but the *result types* (`OneStepMapResult`, `TargetAngleResult`, `ExplicitRateResult` in `Spec/Construction.lean:143-196`) hide the actual claim inside structures; a reviewer must read them, not just the theorem line. [inference, I did not audit these for vacuity] Statement fidelity is therefore not mechanically checked anywhere.
9. **Operational debris:** committed `__pycache__` (`Skills/research-repo-manager/scripts/__pycache__`), hard-coded `/Users/shuvo/...` paths in `Skills/chatgpt-pro-session/SKILL.md`, `Skills/` and `plugins/` diverging copies, macOS-only clipboard helper. Single squashed commit means no history to audit.
10. **Skill length as risk.** SKILL.md files of 280-467 lines of dense gating prose (e.g. `solve-with-highest-reasoning/SKILL.md`, `research-repo-manager/SKILL.md` 454 lines) are hard to follow reliably by an LLM; the gating rules that matter (gate before send/replay) are duplicated across 4+ files, a drift hazard that already shows up in the Skills/plugins diff.

## 7. Verifier / evaluation / safety handling (how they check results, handle exploits, sandbox code)
- Verification ladder in their terms: numerical (BnB-PEP solver evidence; never promoted to theorem) -> symbolic candidate (LLM; `Conjectured`) -> Lean `build+hygiene verified` -> `Lean+comparator verified` -> human interpretation (`lean-verify/SKILL.md:185-201`, `auto-opt/SKILL.md:237-257`). This matches our T1 -> T0 direction: a numerical certificate gives a *conjecture with evidence*, and the formal proof is what establishes the claim. In `tiers.py` terms: BnB-PEP output is T1 only if the evidence checklist in §4.5 is complete; the Lean artifact is T0; the derived claim is T0 only if the formal statement is approved to match the paper statement.
- Soundness anchors actually used: Lean kernel via `lake build`; axiom whitelist via Comparator `permitted_axioms` (`config.json`); Comparator replays Challenge vs Solution to bind the proof to the pre-agreed statement. Sandbox for Comparator: real Landrun on Linux / WSL2, or an unsandboxed official shim on macOS, treated as qualifying (`comparator-platforms.md:113-121, 134-151`). The Comparator sandbox protects against hostile *Lean* code in the proof-building step; the Julia code the agent generates and runs has no sandbox in this repo.
- Reward hacking / exploits: addressed only by process rules (never weaken the target, no `sorry/axiom/admit/unsafe`, theorem-change must be recorded, `lean-build-loop.md:257-259`), not by an adversarial evaluator or exploit quarantine. The Comparator design is the one structural defense against "agent redefines the theorem to make the proof go through". The paper itself concedes "the formal theorem statement may encode a claim weaker than the paper's natural-language statement" (summary, Limitations).
- Prompt injection: `chatgpt_handoff.py:382` tells ChatGPT to treat attached files as data; `solve-with-highest-reasoning/SKILL.md` section 3 treats source-file instructions as quoted research material. Prose only.
- Cost/time: only a per-execution 180-minute ceiling and a campaign duration floor; no token/$ ledger (`campaign.yaml:156`).

## 8. Bottom line (5 lines max)
- AutoOPT is a gated protocol + skill text, not an engine: its real verifier contribution is the **Challenge/Solution/config + Comparator + axiom-whitelist** pattern, which we should adopt as our T0 definition (split into build vs comparator).
- Its BnB-PEP "numerical certificates" are not in the repo, and its hygiene regex would fail its own `Challenge.lean`; do not copy the lint-as-verifier idea.
- Adopt: statement-fidelity gate + blocked outcome, hash-pinned audits invalidated by later repairs, numerical-certificate evidence checklist for T1, source hash-lock, egress manifest. All are S-M effort and reimplementable.
- Phase 7 (discovery mode) should target "numerical T1 candidate -> LLM symbolic fit -> Lean T0 with approved spec" and treat any claim lacking an approved formal statement as T1 at best.
- Licensing: only the `plugins/autoopt` skills are provably Apache-2.0; the Lean projects have no license; no root LICENSE. Prefer reimplementation.
