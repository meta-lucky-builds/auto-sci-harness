## 1. What the code actually does (architecture map)
Four packages + a workflow script, glued by subprocess calls and JSON files on disk:
1. `eval/` — runs a Harbor/pytest TB2 harness per case (`run_harbor_eval.py`), `repeats=2` per split (config example line `repeats = 2`; `load_config` line 122), writes `result.json` with `splits: {split: [{repeat, passed, total,...}]}` (`aggregate_results` 468-482). The agent under test is `FixedHarnessWrapper` (`harbor_wrapper.py:254`) which imports `repo_baseline` from `SELF_HARNESS_CANDIDATE_WORKSPACE` if set (`_candidate_import_context` 33-46, `_candidate_surface_paths` 49-64). Tasks run in the Harbor container via `HarborSandbox`.
2. `diagnosis/` — `trace.py` runs one LLM call per failed trace producing per-stage analysis items (fields below); `integrated.py` clusters failed cases by an exact-string triple and renders a markdown brief.
3. `proposer/` — builds a prompt (`build_multi_proposer_prompt`, multi_proposer.py:65-164), parses JSON (`parse_multi_proposer_response`), maps a single "virtual hook" value to a source edit of `repo_baseline.py` (`hooks.py`), writes candidate directory (`materialize.py`).
4. `acceptance/run_acceptance_gate.py` — the gate.
5. `workflow/run_self_harness_loop.py` — queue + branch-state machine: baseline eval once, diagnosis → prompt → proposer response → parse → enqueue → per candidate: materialize, eval, gate → merge accepted siblings → eval merged → gate → child branch.
The "harness" being evolved is ONE Python file (`repo_baseline.py`, 240 lines) that exposes `build_*` functions (`build_system_prompt`, `build_subagents`, `build_skills`, `build_permissions`, `build_interrupt_on`, `build_*_instruction`, `build_*_middleware`) consumed by `build_agent_kwargs` (repo_baseline.py:201-236) to `create_deep_agent(...)` from the DeepAgents SDK.

## 2. Core loop, step by step (with citations)
1. **Baseline**: if no `baseline_eval/result.json`, run eval once (`main` 57-58, `run_baseline_eval` 262-274). This single result (2 repeats × train + heldout) is the comparison baseline for ALL candidates of that branch (`parent_baseline_result`, enqueue_candidates 427).
2. **Diagnosis** (external): brief file `branches/<id>/diagnosis/diagnosis.md` (`BranchPaths` 170-181; `resolve_diagnosis`).
3. **Proposer prompt**: `run_build_proposer_prompt` → `run_multi_proposer.py` without `--response` writes the prompt (lines 69-71). Prompt says "Use only train-side evidence. Do not use or mention holdout/private/test-set evidence" (multi_proposer.py:107) — an instruction only, not a technical barrier (the held-out results are in the same work dir).
4. **Proposer response** (external LLM), parse with `require_one=False` (run_multi_proposer.py:63-67). NOTE: the slot-by-slot generation with "already generated proposals" context (`generate_multi_proposals`, `build_multi_proposer_prompt` slot args) is NOT used by the workflow — the workflow's prompt asks for `route_count` (default 4, main line 28) proposals in one shot (multi_proposer.py:106 "Generate exactly {route_count}").
5. **Enqueue**: skip proposals whose `selection_decision == decline` (loop:415-416); status `pending_eval` (417-432). Dedupe key = (parent_branch_id, proposal_id) (399-413).
6. **Per candidate** (`process_pending_candidates` 437-497): `materialize_candidate` → `run_candidate_eval` (candidate dir passed through env var) → `run_acceptance_gate` → status `accepted_pending_merge` or `rejected` (480).
7. **Merge** (`finalize_merge_groups` 500-593): when all siblings of one proposal bundle are evaluated: 1 accepted → child branch directly (529-544, **no extra re-eval**); ≥2 accepted → `create_merged_candidate` (640-737) AST-merges changed top-level functions, re-evaluates the merged candidate against the parent's baseline, gates it again; accepted → child branch, else all become `accepted_merge_rejected` (583-587). So accepted siblings are *not* individually kept if the merge fails (no fallback to best single, no subset search) — [inference from code: lines 583-587 set all to merge_rejected].
8. **New branch baseline = the candidate's own eval result** (`create_child_branch` passes `baseline_result=eval_result`, 631). Subsequent rounds gate against that same noisy 2-repeat measurement.

## 3. Paper/summary vs code discrepancies
| Claim (paper summary 2606.09498.md) | Code reality |
|---|---|
| Gate: Δin≥0, Δho≥0, max>0 | Implemented exactly as strict float compare of the 2-repeat mean pass-rate per split: `delta>0` improved, `<0` dropped, else unchanged (run_acceptance_gate.py:130-136); `accepted = not dropped and bool(improved)` (line 99). Split names are `train` and `heldout` (DEFAULT_SPLITS line 11). Matches the paper formula; no tolerance/CI/significance. |
| "Same model proposes" | Not enforced; proposer is an arbitrary shell command (loop:330-356). |
| VGFS clusters by (terminal cause, causal agent behavior, exposed *harness* mechanism) | Code triple is `(terminal_cause, criticality, agent_mechanism)` (integrated.py:111-115, 25). The third element is an *agent behavior* pattern ("reusable behavior pattern observed in the agent trace", trace.py prompt ~line 352), not a harness feature; "criticality" replaces "exposed harness mechanism". Harness-mechanism mapping is left to the proposer (brief line 77: "Proposal surfaces, hook names, patch text... selected by the proposer"). |
| Clustering is "automatic" | The three fields are all free-form snake_case strings written by an LLM per trace; clustering is **exact string equality** on the triple (defaultdict by tuple, integrated.py:55-57). No normalisation, embeddings, or merging. Different LLM wordings → separate clusters. [inference] likely fragments clusters; paper does not discuss. |
| "K mutually distinct candidates" | Distinctness = prompt text asking for it + (in the unused slot generator) rejecting duplicate `(cluster_id, mechanism_family, exact_hook)` tuples (`_proposal_signature` 318-323, used 216-220). In the workflow's single-shot path (`parse_multi_proposer_response` with require_one False) there is NO distinctness check at all, only proposal_id dedupe at enqueue. |
| Edits "bounded"/"typed" | Real: each eval candidate must change exactly ONE virtual hook (`apply_candidate_values` 94-95; `_validate_mechanism_contract` 298-315), the hook must belong to the declared mechanism_family (`HOOKS_BY_MECHANISM_FAMILY` hooks.py:56-64). |
| Multi-candidate merging | Implemented via AST function-level merge (loop 640-960); conflict = two candidates changing the same function → RuntimeError (apply_function_definition 82-91), which would crash the whole run rather than be handled [inference: no try/except around `create_merged_candidate` in finalize_merge_groups 546-550]. |

## 4. Mechanisms worth adopting (ranked by expected value)
Current custom-harness refs: `evolve/evaluate.py:49-71` (regex-normalised error-string signatures), `evolve/selection.py:75-104` (CI gate), `evolve/edits.py` (typed JSON-pointer edits), `evolve/propose.py:19-42` (Counter clustering).

1. **LLM-produced causal failure signature with criticality filter (L6; effort M; reimplement — no license).**
   What: per failed trace, one LLM call over normalized steps + raw verifier evidence outputs stage items with `terminal_cause`, `criticality ∈ {root_cause, contributor, non_terminal_friction, recovered_friction, unknown}`, `agent_mechanism`, `incorrect_step_ids`, `terminal_link`, `causal_weight` (trace.py ~278-358, validation 429-456). The primary item is chosen by: has incorrect steps first, then causal_weight, then terminal_link, then earliest stage (integrated.py:191-209). Clusters sorted by criticality then size (integrated.py:178-181) and "recovered friction is evidence, not a repair target" (184-188). Key prompt rule: "Root cause means the first unrecoverable critical failure, not the first visible recovered tool error" (trace.py prompt).
   Why better than ours: our `failure_signatures` (evaluate.py:57-71) lists EVERY step error string, including recovered ones, and `diagnose` counts a signature once per run (propose.py:25) with no notion of terminal causation or recovery; it also has no verifier-evidence input (only step.error/run_error/route). Their approach separates symptom from cause and de-prioritises already-recovered noise. Caveat: the fields are LLM-labelled and clustered by exact string (see §6), so adopt the schema but add a canonicalisation step.
   Where: L6 diagnosis, fed by L3 verifier output (our `verdict`/`audit`).
2. **Verifier evidence bundle as first-class diagnosis input (L3→L6; effort S).** `load_tb2_verifier_evidence` extracts reward text, ctrf test summary, failed tests with trace excerpts and failure snippets from the verifier directory (tb2.py:9-39) and the brief prints `terminal_summary`, `reward_text`, up to 3 failed-test excerpts per case (integrated.py:226-244). Our `diagnose` passes only our own step errors; our hidden-test `verdict` (evaluate.py:80-87) never reaches the proposer. Cheap, high-value (respecting our private-data guard: only summaries, not test data).
3. **Brief contract text: "Passing cases are regression tests", "Select one high-confidence cluster", "prefer no-op" (integrated.py:79-84) plus explicit `expected_affected_cases`, `protected_passing_cases`, `skipped_clusters`, `decline_reason`, `why_not_noop` in the proposal schema (multi_proposer.py:106-137, `strict_noop` 97-103).** We have `PredictedEffect` (edits.py:35-39, with `tasks_at_risk`) but no decline path; a proposer forced to output something will emit junk edits and burn eval budget. A first-class "decline" saves evaluations. Effort S (add to `EDIT_SCHEMA` in propose.py:45+).
4. **Mechanism-family ↔ hook contract with exactly-one-hook-per-candidate (L6; effort S).** Forces single-factor candidates so a gate result is attributable (hooks.py:94-95, multi_proposer.py:298-315). Our `Edit` (edits.py:49-55) allows multiple `ops` of different paths in one edit; adding "one mechanism target per candidate" gives cleaner credit assignment for the harness-science ledger. Ours is a typed JSON-pointer spec edit, theirs is source-code function-body replacement; ours is the better representation (see §5) but should adopt their one-hook discipline and the family taxonomy (prompt_instruction/subagent/skill_procedure/tool_configuration/middleware/runtime_control/permission_interrupt) as a coverage check on our `EditType`.
5. **Sibling-merge-then-re-gate protocol (L6; effort M).** Accepted siblings are merged and the *merged* harness is re-evaluated and gated (loop 546-588) — interactions are checked rather than assumed. Our loop has `racing` then selects `keep` survivors (selection.py:`race`); I did not find an equivalent merge-and-recheck (loop.py grep for "merge" returned nothing). Improve over theirs by falling back to best-single or subset search if the merge fails (they discard all, 583-587) and by handling merge conflicts instead of raising (apply_function_definition 82-91). With JSON-pointer edits, conflicts are detectable by path overlap.
6. **Strict acceptance with verification of denominator equality (gate hygiene; effort S).** `assert_same_denominators` (gate lines 180-189) and fixed repeat count validation (156-157) refuse non-comparable results instead of silently computing. Add the same sanity check (same unit set, same seeds) to our `gate()` — currently it takes bare `list[float]` diffs (selection.py:75) with no unit-alignment check.

## 5. Things custom-harness already does better (with evidence)
- **Gate statistics.** Theirs is `delta>0` / `delta<0` on a mean of 2 repeats over 43 / 21 tasks (gate 130-136): any 1-task fluctuation in either direction decides. With 21 held-out tasks and run-to-run LLM noise, a harmless edit can be rejected by a random −1 task drop, and a neutral edit accepted by +1 noise on one split. Ours uses paired bootstrap CI: evolve CI lo>0, gate mean>0 and CI lo ≥ −eps (selection.py:75-104), on paired (task, seed) units (selection.py:13, 27-37). No unit-level pairing in theirs (only split aggregate means; per-case results exist in files but are not used by the gate).
- **Held-out leak control.** Theirs: "do not use holdout" is a prompt sentence (multi_proposer.py:107); the held-out results sit in the same work dir and `current_eval_observations` is a free-text pass-through (multi_proposer.py:59, 157). Ours: separate evolve/gate/sealed splits plus static leakage patterns in edits (edits.py:63, 109-112) and `_private*` render guard (STATUS.md L4).
- **Protected surfaces and invariants.** Ours: protected nodes (setup/verify/audit), reachability, audit-only terminal (edits.py:107-151). Theirs: no protection — an edit could change any `build_*` function including `build_permissions`/`build_interrupt_on` (hooks.py:28-34), i.e. could weaken the agent's own guardrails; the only static check is function-level shape (`_validate_subagents`, skill name regex, `_validate_relative_component_path` hooks.py:185-196, 258-261).
- **Edit representation.** Ours: structured, validated against a pydantic `HarnessSpec` after application (edits.py:133-136), with declared type, rationale, evidence refs, predicted effect. Theirs: source-text surgery on a Python file via `ast` line spans and `repr()`-embedded strings (hooks.py:414-440), brittle — it depends on fixed marker strings in the baseline (e.g. `'        build_multimodal_middleware,\n    ):\n'` hooks.py:334 and `'    if skills:\n        kwargs["skills"] = skills\n'` line 388); returns None → "could not apply hook" if the file is touched by a prior edit. Merge relies on the same AST function-level diff.
- **Cost-aware evaluation.** Ours: successive-halving race with paired CI elimination (selection.py:40-72), `evaluations_fixed_k` accounting. Theirs: evaluates every candidate fully on all 64 tasks × 2 repeats (run_harbor_eval.py:73-90); no cost tracking at all.
- **Lineage of rejects & calibration.** Ours has predicted-effect calibration and ledger (STATUS.md L6). Theirs records accept/reject reasons in `acceptance.json` and queue (loop 480-484) but never compares predicted vs actual effect (their `net_gain_hypothesis` is stored as free text only, materialize.py:123-127).

## 6. Pitfalls, bugs, anti-patterns seen (must avoid)
1. **Baseline drift / winner's curse.** The child branch baseline is the accepted candidate's own single 2-repeat eval (loop 631). Selection is made on noise ("max over K candidates of noisy delta>0") and then that same noisy number becomes the next baseline, biasing every later gate. Our paired CI + fresh units avoids part of this; we should also re-evaluate accepted harnesses on fresh seeds before using them as parents.
2. **Exact-string clustering of LLM-written labels** (integrated.py:55-57). Near-duplicate labels fragment clusters; a "cluster" is as likely a wording artifact as a mechanism. Add embedding/LLM canonicalisation and report cluster purity.
3. **Fail-hard diagnosis**: any failed case with no LLM analysis raises RuntimeError (integrated.py:51-52, 110, 121); one bad JSON stops the whole round. Prefer degrade-to-"unknown" with a counter.
4. **Gate tie semantic**: `unchanged` on both splits → rejected (build_reason "no split improved"); fine. But `dropped` on a 1-task difference rejects; and with `max_candidates` default 1 (main line 34-38) candidates are processed one at a time per invocation — the research protocol (K candidates + merge) only happens if the user passes `--max-candidates 0`.
5. **No exception handling around merge** — a function conflict aborts the process mid-queue state (queue is written after each candidate 485-486, so state survives, but `finalize_merge_groups` will re-raise on every re-run [inference]).
6. **Candidate code executes in the host/eval process**: harness is a Python module imported by the eval harness (`importlib` + `sys.path` injection, harbor_wrapper.py:33-46) and skill bundles write files next to the module (`_build_skills_function_body` hooks.py:344-359). Strings are `repr()`-quoted so injection via prompt text is not trivial, but any `build_tools`/`build_permissions` literal returned is evaluated Python. Our harness spec is data, not code — keep it that way.
7. **Prompt-only held-out protection and non-enforced "same model"** (see §3).
8. **Single-shot K proposals contain no distinctness check** (workflow path) — the slot-wise distinct generator is dead code in the workflow.
9. **`harnesses/qwen_tb2_final/repo_baseline.py` shows what accepted edits look like**: sizeable prompt text edits (diff vs baseline: "CRITICAL: Before executing any task, verify required Python modules...", "Do not perform more than 3 consecutive 'explore' or 'execute' steps...", "do not retry the exact same command") and one `ArtifactCreationMiddleware` predicate=_has_tool_error. These are mostly generic hygiene prompts; combined with an eval of two repeats, the evidence that each is individually causal is thin (no ablation, as the paper summary already notes). Treat the paper's per-model "adaptations" as hypotheses.

## 7. Verifier / evaluation / safety handling
- Verifier: TB2 deterministic pytest checks inside Harbor containers (reward.txt, ctrf.json, test-stdout.txt parsed in tb2.py:21-24). The harness never touches the verifier; verifier evidence is read after the run and used only for diagnosis (good separation, equivalent to our T1 hidden tests).
- Eval isolation: agent tool actions run in the Harbor container (`FixedHarnessSandbox(HarborSandbox)` harbor_wrapper.py:232-251, 284). Timeouts: per-case `timeout_s=43200` (config) and hard per-task timeouts from `task.toml` (harbor_wrapper.py:205-229). We did not read `backend_bridge.py` so cannot comment on exploit handling.
- Reward-hacking/exploit handling: none seen in the code read (no quarantine, no check that a pass came from legit behavior). Gate counts pass/fail only.
- Safety of edits: structural validators only (hooks.py:185-196, 213-261, 264-292); no edit protection list; no review of weakened permissions.
- Statistics: none (no CI, no test, no noise estimate). The author-stated limitation "higher stakes need stronger gates" is the only acknowledgment.

## 8. Bottom line
- Adopt the *idea* (not the code; no license): LLM-labelled (terminal_cause, criticality, mechanism) signatures with recovered-friction filtering, verifier-evidence input to the proposer, and a first-class decline/no-op path with expected/protected case lists.
- Their gate is exactly the paper's rule but is statistically naive (mean of 2 repeats, strict float sign, noisy baseline reused as parent); our paired-CI gate + sealed split is stronger — keep ours, add their denominator-equality check and merge-then-regate step.
- Their edit representation (one Python file, AST/regex source surgery, one virtual hook per candidate) is brittle; our typed JSON-pointer spec with protected nodes is better — borrow only the one-mechanism-per-candidate rule and family taxonomy.
- Repo is a partial release: no license, no benchmark, no round driver, no diagnosis/proposer glue, no run data, no tests; "same model" and held-out separation are conventions, not enforced.
