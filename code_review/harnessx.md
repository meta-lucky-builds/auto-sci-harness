## 1. What the code actually does (architecture map)
- **Substrate** (the "9 dimensions"): `docs/architecture.md:7-23` lists nine "slots" (Model, Context, Memory, Tools, Sandbox, Evaluate, Control, Observe, Train). In code these are *packages of processors* (`harnessx/processors/{context,memory,tools,control,evaluation,observability,multi_model}`, `harnessx/sandbox`, `harnessx/rl`), composed with a `HarnessBuilder` and `|` operator that raises `HarnessConflictError` on `_singleton_group` collisions (architecture.md:~38-47). Processors are `MultiHookProcessor` subclasses on 8 hook points. "Typing" is therefore mostly Python class/hook structure plus run-time contract checks (`core/processor.py::check_post_hook_invariants`, line 243), not a typed edit schema.
- **The evolver ("AEGIS") is NOT a four-stage pipeline in code.** `MetaAgent` (`meta_harness/agent.py:493`) is *one* ordinary HarnessX agent (tools Read/Write/Edit/Glob/Grep/Bash/WebSearch/WebFetch + `spawn_reflect_worker`, agent.py:130-215) whose workflow is a prose loop in `workspace/SOUL.md` (steps 1-7) and four skill files (`analyze`, `validate`, `reference`, `journal`). I grepped `planner|critic` across `harnessx/` and `recipe/`: no Planner or Critic component exists (only unrelated hits in cli.py, sycophancy_detector.py, a tau2 playbook). The only separate sub-agent is the **trajectory-digester worker** (`workers/trajectory_digester.py:42-88`: read-only tools Read/Glob/Grep/Bash, 20 steps, $0.5, returns a <=1500-word markdown summary). The "Planner" is the `analyze` skill text (lens x lever x intent framework) and the "Critic" is a leakage self-check processor (`processors/leakage_guard.py`, one injected user message when the agent tries to end its turn, lines 29-45, 96-110) plus the post-flight validator.
- **Evolver output** is a whole `config.yaml` (HarnessConfig) plus optional authored `tools/*.py`, `processors/*.py`, `templates/*.j2` (agent.py `_render_task_brief`, ~lines 719-815). There is no typed edit/patch object; the change set is *derived afterwards* by `compute_changeset` (agent.py:439-490: tools added/removed, processors added/removed/kwargs-changed, templates by sha256 of file). The paper's "typed builder operations" and "change manifest" correspond only to this post-hoc diff plus the free-text `candidates.md`.
- **Recipes** own the outer loop: `recipe/gaia_evolver/run.py` (flat), `run_meta.py` (per-domain), `tau2_evolver`, `tb2_evolver`. Cross-round memory is `learnings.md` (journal, `meta_harness/journal.py`) rendered into `CONTEXT.md` (lever scoreboard, per-task matrix, changesets).
- **RL side**: `recipe/verl_harnessX` (vendored veRL GRPO + HarnessX multi-turn agent loop) and `recipe/slime` (Slime integration capturing token ids and logprobs via a SGLang provider). `harnessx/rl/{builder,config,task}.py` is the training bridge.

## 2. Core loop, step by step (with file:line citations)
Per round, in `recipe/gaia_evolver/run.py` main loop (lines ~660-925):
1. Run all tasks under `current_config`, per-task `.md` trajectories with frontmatter (behaviour, `eval_passed`, LLM-judge verdict/cause/missing). Evaluator output (expected answer, reason) is deliberately withheld from the frontmatter (digester prompt, trajectory_digester.py:~63; `GAIAPipelineEvaluator.evaluate_answer`, evaluator.py ~line 190, "keeps evaluator outputs off the per-task trajectory").
2. **Gate the finished round** against best-so-far with `_score_and_gate` (run.py:1174-1257, details in section 4). Return REVERTED sets `current_config = best_cfg` (run.py:812-820).
3. Journal back-fill (run.py:828-895): `compute_attribution` (journal.py:605) labels each task in the entry's `predicted_affected` as flipped / still_F / regressed / still_T / absent; `regressed_unpredicted` = tasks that passed in prev round, absent from cur pass set, not in predicted (run.py:857-859). This is **bookkeeping only; it does not feed back into the accept/revert decision.**
4. `MetaAgent.evolve(...)` (agent.py:538): materialise TASK.md + CONTEXT.md, run the meta-agent under an `asyncio.wait_for` wall clock (agent.py ~line 612; timeout -> RuntimeError and a TIMEOUT.md), then `EvolveValidator.run` (validate_workflow.py:890):
   - validity: `canonicalize` (YAML parse + eager Jinja template render, :944), `contract` (custom processors' hook-mutation contract, :1045, blocking), changeset diff (:987), `replay` = ONE tiny synthetic task through the real run loop, fail on exception/timeout/exit_reason=error (:1011; replay.py docstring says the earlier `task_replay` mode was removed);
   - policy (only if diff non-empty): `novelty` (re-proposal of a journal hypothesis marked `reverted`, by id or by (lever, predicted_affected) signature, :694; also a 0.85 SequenceMatcher soft warning, :804-850) and `evidence` (candidates.md must exist, contain `## Candidate C-N` headings, and the latest journal entry's `cited_candidates` must be a subset of those ids, :1110-1220);
   - advisory: `literals` scan, non-blocking (:1222). The only default pattern is a UUID regex (`_DEFAULT_LITERAL_PATTERNS`, :568-576), scanning only `tools/*.py` and `processors/*.py` (not templates, not config).
5. Next round runs the new config. Byte-identical config.yaml == explicit no-op (run.py:~955). A crashed evolve keeps `current_config` and sets status "crashed" (run_meta.py ~lines 650-660).
6. Stop: `run_meta.py` stops after **2** consecutive no-ops (run_meta.py, `noop_streak >= 2`); `run.py` I found no early-stop (grep for noop/early/consecutive hits only the no-op status at 955). The paper says 3 consecutive rounds without shipped edits.

## 3. Paper/summary vs code discrepancies
1. **Four-stage digest -> plan -> evolve -> critic pipeline**: not implemented as stages. One agent + skills + one read-only digester worker; no Planner, no Critic (grep above). `trajectory_digester.py:11-13` says `artifact-auditor` and `processor-probe-dryrun` worker kinds are "reserved but not yet available."
2. **"Deterministic seesaw gate: no regression on previously passing tasks"**: the string "seesaw" appears nowhere in the repo (case-insensitive grep over all files returned empty). The implemented gate is an aggregate pass-rate comparison with tolerance and a noise threshold, and it is **post-hoc** (runs after the new config has already been evaluated on the full task set), not a pre-ship per-task check. Per-task regression info (`regressed_unpredicted`) is only logged to the journal. So the "Pareto" language (SOUL.md "Pareto thinking rule", agent.py brief "Global optimization constraint") is an instruction to the LLM, not code. `pareto_archive.json` is advertised in the brief (agent.py:756) as a read-only artifact "marked stuck/fragile/solved", but no code in the repo writes it (grep for `pareto_archive|stuck|fragile` hits only agent.py:756).
3. **"Manifest completeness" / "configuration normalization" / "build tests"**: map to evidence-gate structural checks, `canonicalize`, and the 1-task synthetic smoke. The evidence gate verifies only that id strings cross-reference (validate_workflow.py:1196-1218), not that the claims are true or that the diff matches the candidate.
4. **Variant isolation (per-task routed harness versions)**: not a routing mechanism. `run_meta.py` splits GAIA tasks by the dataset's static `category` label (`_load_classified_tasks`, :126-170) and evolves an independent config per domain starting from the same `original_base` (main(), `scope_dir = RUN_DIR/"domain"/domain_name`). There is no runtime router that picks a variant per task, and no classifier for unseen tasks. The final report just sums each domain's *best round* (`best_idx = max(curves by passed)`, run_meta.py ~line 665; "AGGREGATE" in the report) which is best-of-N selection on the same tasks used for evolution.
5. **Harness-model co-evolution via cross-harness GRPO with FIFO replay buffer and importance ratios**: not found. `recipe/verl_harnessX` is stock veRL GRPO (`algorithm.adv_estimator: grpo`, group size `rollout.n=8`, README table) over a *fixed* harness; `recipe/slime` is a rollout adapter. grep for `replay|buffer|harness_version|co-evol|offline` in these recipes finds only logprob capture. No code interleaves harness evolution rounds with weight updates, groups by task across harness versions, or applies an off-policy correction. I did not read the vendored `verl/` tree; a buffer could exist there, but nothing in the recipe wires harness versions into it. Treat the +4.7% co-evolution claim as unreproducible from this repo.
6. **Reward-hacking defense "Critic compares manifests to trace evidence"**: only the LLM self-check `LeakageGuardProcessor` (templates only, one-shot, advisory text) and the (non-blocking) UUID literal scan. The GAIA verifier-format exploit the paper reports is not specifically handled (section 7).
7. **Early stop**: paper "3 consecutive rounds with no shipped edits"; run_meta.py uses 2; run.py has none that I found.
8. **Held-out evaluation**: absent in code (grep heldout/holdout in recipe/ and meta_harness/ empty), matching the paper's own admitted limitation.

## 4. Mechanisms worth adopting into custom-harness (ranked by expected value)
1. **Journal with outcome attribution and lever scoreboard** (`journal.py::compute_attribution` :605, `fill_gating` :271, `build_context` :366; run.py:828-895). Each hypothesis declares `predicted_affected` tasks; after gating, each is labeled flipped/still_F/regressed/still_T/absent, `regressed_unpredicted` records collateral damage, and the next proposer sees a rendered per-lever precision scoreboard and per-task history matrix. Better than ours: our `PredictedEffect` (evolve/edits.py:35-39) records `tasks_at_risk` and `expected_delta` but I found nothing in `evolve/` that scores predictions per task and feeds a per-lever precision table back; our `proposer_calibration` (evolve/loop.py:138) is aggregate. Add the *collateral* (`regressed_unpredicted`) term. Layer L6 (evolve), calibration tie to PLAN §8.5. Effort S-M. Reimplement from the idea (MIT: copying with attribution is allowed, but our data model differs).
2. **Novelty gate against reverted hypotheses by (lever, predicted-set) signature** (validate_workflow.py:694-850). Deterministic check that blocks re-proposing a reverted bet, plus a soft similarity warning. Ours: `check_edit` in edits.py:107 has only leak and protected-node checks, no memory of reverted edits. Add a (EditType, op-path-prefix, predicted-cluster) signature check against the ledger. L6. Effort S. Reimplement.
3. **Evidence-linking gate** (candidates.md ids <-> journal `cited_candidates`, :1110). Cheap structural proof that every shipped change cites evidence. Ours has `Edit.evidence` as an unchecked `list[str]` (edits.py:54). Upgrade: require each evidence ref to resolve to a real trace/failure-cluster id in the store (stronger than theirs, which only matches id strings). L6. Effort S.
4. **Read-only worker sub-agent with fixed allow-list and no overrides** (trajectory_digester.py header, :1-30). Digestion is isolated from the authoring agent; the tool exposes only `kind`, never `tools`/`system_prompt`/`model` overrides, so the digester cannot become an artifact writer. Matches our digest->propose split (`propose.diagnose`, propose.py:19, is deterministic digest) — adopt the "no free-form override" capability design for any LLM digester we add. L6/L2. Effort S.
5. **Hold-out of evaluator output from proposer-visible trajectories** (digester prompt, `evaluate_answer`). The proposer sees `eval_passed` and behaviour but never the expected answer or evaluator reason. Check our `store`/`diagnose` path enforces the same (our protected `verify` node and `_LEAK_PATTERNS`, edits.py:62-63, cover edits, not necessarily what the proposer reads). L3/L6. Effort S.
6. **Best-so-far baseline that cannot drift** (run.py:1174-1257): tolerated regressions never lower the reference (`new_best` only on strict `score > best_score`, tested in `tests/unit/test_gaia_gating.py::test_baseline_cannot_drift_over_many_tolerated_regressions`). Our gate compares each candidate against its parent (evolve/selection.py `gate`), so a chain of individually non-regressing edits can erode the lineage; keep a lineage-best anchor and require candidates to be non-inferior to it, too. This also addresses the paper's own admitted "sub-threshold coupling from consecutive edits." L6.5. Effort S.
7. **Wall-clock + step + cost caps on the evolver itself, "analysis-only end_turn = failed round", explicit no-op as byte-identical copy** (agent.py:~612, brief "Decision contract"). We should treat a no-op as a first-class outcome and stop after K consecutive no-ops. Effort S.
8. **Synthetic-task smoke gate through the real run loop** (replay.py) as the cheapest pre-evaluation filter: our `check_edit`/`apply_edit` validate the spec structurally but do not run the harness once before spending paired evaluations. Add a 1-task smoke before racing in `evolve/selection.py`. L6. Effort S.
9. **Four-lever taxonomy with lens x lever x intent tagging and 3-variant retroactive check** (analyze SKILL.md; description at line 3, variants A/B/C lines 196-250). Notably *preservative* (success-lens) candidates that lock in or transfer winning habits. Our EditType has 11 types but no "intent" (corrective vs preservative) axis; adding intent to `Edit` would let the gate treat preservative edits as higher-risk-of-nothing and feed calibration. Effort S. Idea only.
10. **Per-domain evolution scopes** (run_meta.py). Not worth copying as written (see section 6), but the idea of clustering tasks and evolving per-cluster specs maps to our `EditType.ROUTING` (edits.py:31). Do it with a *learned/derived* cluster key plus a runtime router and hold-out validation. L4/L6. Effort M-L. Reimplement.

## 5. Things custom-harness already does better (with evidence)
- **Gate is statistically principled, paired, and uses a never-shown split.** `evolve/selection.py::gate` requires paired-bootstrap CI lower bound > 0 on the evolve split and non-regression plus mean > 0 on a gate split the proposer never sees; `race` does successive halving on paired (task, seed) units. HarnessX's gate is an unpaired aggregate pass-rate threshold (`score < best_score - tolerance`, run.py:1223) with a hard-coded 0.03 tolerance and a `pass_count_noise_threshold=3` that, when |delta passed| < 3, *accepts* a regressed config without promoting it as best (run.py:1224-1237). On a 6-task default (`--max-tasks` default 6 per README) that means a 2-task regression is accepted and becomes `current_config`, which then seeds the next evolve round.
- **Typed, JSON-pointer edits with predicted effect and protected nodes.** `evolve/edits.py` rejects edits to `setup/verify/audit`, leaks of `_private`/`test_y`, protected-node unreachability and alternate terminal nodes (`apply_edit`, :124-151). HarnessX's meta-agent can write arbitrary Python (`processors/*.py`, `tools/*.py`) into the next harness and edit the whole config; its write-scope gate only restricts *where the meta-agent writes* (write_scope_gate.py), not what the evolved processors may do, and it does not protect the evaluator wiring in the evolved config itself [inference: I did not find a check that the evolved config preserves the evaluator/judge processor; run.py injects the judge into the config as a serialisable dict that the meta-agent can see and modify, run.py ~lines 619-641].
- **Held-out discipline.** Ours has an evolve/gate split by construction; HarnessX evaluates and evolves on the same tasks (paper admits; code has no hold-out).
- **Verifier-integrity**: we have verifier tiers and an integrity audit node that a run must end on (edits.py `terminal_required`); HarnessX has none (section 7).

## 6. Pitfalls, bugs, or anti-patterns seen in their code (cite) that we must avoid
1. **Gate runs after the full evaluation, and the "noise" rule accepts regressions.** run.py:1224-1237: regression within |delta|<3 returns ("ACCEPTED", ..., best, None): config kept, best not updated. Over repeated rounds this can ratchet through sub-threshold regressions while the reference stays at the old best (only that reference is protected, the live config is not). Also `run_meta.py` hard-codes `tolerance=0.03, cost_weight=0.0` (its `_score_and_gate` call) so cost is never penalised there.
2. **Duplicate gate implementations.** `_score_and_gate` is copy-pasted in run.py, run_meta.py (simplified), tau2_evolver/run.py (different semantics: `accept` if `adjusted >= best_adjusted - tolerance`, no count-noise guard, `best_cost` handling differs). Three gates with different rules under one paper claim; avoid by keeping a single tested gate.
3. **Selection bias in reported results.** run_meta.py reports each domain's best round by passed-count on the evolution tasks and sums these ("AGGREGATE"); with ~6-15 tasks per domain this is best-of-N on noise. Never report max-over-rounds on the evolve set.
4. **Prose-only "Pareto" rule.** SOUL.md and the brief tell the LLM not to regress passing clusters, but no code enforces per-task non-regression; `pareto_archive.json` is promised but never produced (agent.py:756, no writer). Do not claim a property in prompts that no code checks.
5. **Evidence gate is checkable by string-stuffing.** It validates only heading ids via regex `^##\s+Candidate\s+(C-\d+)\b` and set containment (validate_workflow.py:1171-1218); a meta-agent can write a vacuous candidate to pass.
6. **Leakage/literal defenses are weak.** Literal scan only matches UUIDs in `tools/` and `processors/` (`_DEFAULT_LITERAL_PATTERNS`, :568-576) and is advisory (:1222-1280); templates are covered only by an LLM self-check (`LeakageGuardProcessor`) that the same agent answers about its own work. Task-specific knowledge in a Jinja prompt or a config kwarg passes the deterministic checks.
7. **Smoke gate is 1 synthetic task, 20 s cap** (`replay_timeout_s=min(replay_timeout_s, 20.0)`, agent.py `EvolveValidator(...)` call). It catches crashes, not behavioural regressions.
8. **Authored code executes in the evaluation environment with no static restrictions** beyond the dry-fire/contract checks (`run_processor_dry_fire` :234, `run_tool_dry_fire` :361). Meta-agent also has Bash + WebFetch + WebSearch with an absolute-path write gate (write_scope_gate.py parses shell redirections, `tee`, `cp`, `mv`), which is a pattern-matching approach to shell writes and is inherently bypassable [inference].
9. **Evaluator leniency doubles as a reward-hacking surface** (section 7).
10. Meta-agent budgets are large and default high (run_meta.py: `EVOLVE_COST = 50.0`, 200 steps, 10000 s wall; agent.py defaults $5/500 steps/900 s).

## 7. Verifier / evaluation / safety handling
- **GAIA scoring** (`benchmarks/gaia/evaluator.py`): answer extraction takes the first line after "FINAL ANSWER:" (regex with `re.DOTALL`, then `.split("\n")[0]`), else an "answer is:" line, else the *last non-empty line of the last assistant message* (`_extract_answer_from_messages`). Matching `_answers_match` (evaluator.py, last function) accepts in order: exact; normalised (lowercase, strip markdown/articles/quotes/trailing punctuation, hyphens -> spaces, strip `$ , %`, number words -> digits); numeric tolerance (1% for integers, 3% for decimals, computed after `re.sub(r"[^\d.\-]","",...)` which discards all non-numeric characters); **fuzzy SequenceMatcher >= 0.9 for answers >=5 chars**; **multi-part containment** (every comma-separated part of the gold answer appears as a substring of the agent answer); and **word-boundary containment** of the gold answer inside the agent answer when the gold answer is <=30 chars. With no ground truth it falls back to an LLM judge whose prompt shows only the final answer (`_judge_fallback_raw`), and "PASS" prefix parsing (`text.upper().startswith("PASS")`).
- **Exploit surface (the "verifier-format exploit")**: the containment rules mean a hedged/enumerated final answer (e.g. listing several candidates in one line, or an answer with the gold string embedded in extra words) passes; the numeric stripping lets decorated numbers pass; fuzzy 0.9 passes near-miss strings. This matches the paper's report of the evolver "exploiting verifier format" [inference: the paper summary does not say which rule; the repo does not contain the exploit trace]. The repo's `gaia-playbook` even recommends a "forced FINAL ANSWER: format guard" processor (+2-4pp claim), which is legitimate formatting but shows the optimisation pressure is on the extraction rule. **No defense exists in the repo**: no strict-mode evaluator for headline numbers, no check that evolved configs/prompts do not mention the answer format rules, no second independent verifier, no exploit quarantine. The LLM judge (`LLMJudgeProcessor`) is used for behavioural diagnosis (cause/missing), while `eval_passed` is the authoritative gate; the digester prompt says so explicitly.
- **Info hiding**: gold answers and evaluator reasons are kept out of proposer-visible trajectories (digester prompt; evaluator "external path"). Good practice, but the proposer sees `eval_passed` per task, which is enough to overfit a small fixed set.
- **Sandbox**: meta-agent runs in a `LocalSandbox(root="/", mode="isolated")` subclass that defaults cwd to output_dir (agent.py:69-90) plus `WriteScopeGate`/`ReadScopeGate` processors (`read_scope_gate` hides harnessx source; hint text at agent.py ~lines 197-205). It is a *policy* sandbox, not an OS isolation boundary [inference from reading `_MetaAgentSandboxProvider` and the gate processors only]. Task-agent code execution uses separate sandbox providers (Docker/E2B per README), which I did not audit.
- **No tiered verifier policy, no integrity audit, no spec-conformance check, no replication, no seeds/CI.** Pass@k variants and noise handling are ad hoc (threshold 3 passes).

## 8. Bottom line (5 lines max)
- The repo is a single LLM meta-agent plus a post-hoc best-so-far pass-rate gate; the paper's four stages, per-task seesaw rule, router-style variant isolation and cross-harness GRPO co-training are not in the code.
- Adopt: journal attribution with collateral term, reverted-hypothesis novelty gate, evidence-ref resolution, lineage-best anchor, 1-task smoke before racing, read-only worker with fixed allow-list.
- Our paired-CI + hidden gate split, typed protected edits, and held-out discipline are stronger than anything they ship.
- Avoid: accepting "noise-level" regressions into the live config, best-round-on-train reporting, prose-only invariants, and lenient containment/fuzzy verifiers (their GAIA exploit surface).
- MIT licensed: code may be copied with attribution, but only ideas are worth taking.
