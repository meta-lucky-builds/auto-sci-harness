## 1. What the code actually does (architecture map)

Station is a **tick-synchronous, file-backed simulation of a research lab**, run by one Python process (the "Orchestrator") plus a few background worker services. The agents are LLM chat sessions that act by emitting text commands of the form `/execute_action{...}` followed by YAML blocks (`station/action_parser.py:1-60`; at most `MAX_ACTIONS_PER_TURN = 10` per turn, `constants.py:359`; enforced in `station.py:~830`). Agents are NOT tool-calling agents.

Key components (all paths under `station/` unless noted):

1. **Orchestrator + tick runner** (`station_runner.py`, `sync/parallel_runner.py`). Every tick, all agent LLM calls run concurrently on a snapshot of the tick-boundary state; their actions are then committed serially in fixed turn order by a single writer (doc: `example/doc/PARALLEL_SYNC.md` "Execution Model"; code: `ParallelTickRunner._prepare_observations` 337, `_collect_initial_llm_responses` 413, then `station.submit_response`). Cross-agent effects (mail, common room, public memory, archive) are deliberately lagged by one tick so results do not depend on API latency. So "decentralized" means decentralized cognition, not decentralized control: there is a central clock, a global turn order (`station_runner.py:398`), a single mutation path and central resource schedulers.
2. **Rooms** (`rooms/*.py`, names at `constants.py:230-243`): Lobby, Reflection Chamber, Private Memory, Public Memory, Question Room, Archive Room, Mail, Common Room, Admin Counter, Misc, Research Center, External Counter, Maze, Exit. Each is a class with `handle_action`; all "memory"/"publication" rooms share one capsule store (`capsule.py`, `rooms/capsule_room_base.py`). YAML files are the source of truth; a SQLite index is a rebuildable read model (`example/doc/CAPSULE_INDEX.md` "Scope", "Startup And Rebuild").
3. **Research Center** (`rooms/research_center.py`, `eval_research/*`). The agent does NOT write code. It submits a YAML `{title, tags, abstract, instruction}`; a room-owned **coder** (an external `codex exec --sandbox workspace-write` or Claude CLI session, `example/doc/CODER.md` "Backend Launch Behavior"; `workers/cli.py:392-455`) implements it, runs the "official attempt" through `bash submit_eval.sh`, writes a Coder Report, and then a fresh **independent auditor** CLI session reviews code/result/report and issues `pass|fail` (`coder_manager.py:70-360`). The official attempt runs the submitted file in a subprocess (`executor_sandbox.py::_execute_submission_in_python_sandbox`), then the task's `evaluator.py` (a `ResearchTaskEvaluator` subclass, `base_evaluator.py:26`) scores the returned object, in the main Station process (`auto_evaluator.py:1370`). Output is `(success, score, details[, sort_key])`; ranking is by lexicographic numeric `sort_key` (`example/doc/RESEARCH_TASK.md` "Ranking with sort_key"). Optional per-task **Seed Bank** persists every validated candidate from every attempt in NPZ+SQLite for reuse (`seed_bank.py:75-120`, `save_batch` 280).
4. **Archive Room + automatic reviewer** (`rooms/archive.py`, `eval_archive/auto_evaluator.py`). A paper is queued; one stateful LLM reviewer conversation (default `gpt-5.6-sol`, `constants.py:307-308`) scores 1-10; `>= 6` publishes it as a citable capsule (`constants.py:323`, `_process_evaluation_result` 1319). The reviewer receives (a) the research task spec, (b) abstracts of already published papers, (c) the "Codex" doctrine (publication rules), and (d) system-extracted previews of every `Eval #N` cited in the paper, with the instruction that system scores supersede the agent's claims (`constants.py:1677-1730`, `_create_submission_prompt` 903-950).
5. **Archive Surveyor** (`eval_archive/surveyor.py`, doc `ARCHIVE_SURVEYOR.md`): a Codex worker with read-only symlinks to `archive_papers`, `research_center` and `question_room`, which answers an agent's literature question and returns a Markdown report by mail. This is the code's answer to "literature saturation".
6. **Question Room** (`rooms/question.py`): an in-station open-problem tracker with peer voting. A question becomes `open` at 3 net upvotes; a reply is accepted as a solution at 3 net upvotes from non-authors (`question.py:~88-103`). Only tenured agents and supervisors can enter it (`station.py:2526`).
7. **Agent lifecycle** (`agent.py`, `station.py:2431-2560`, `session_end_flow.py`, `lineage_evolution.py`): Guest (<= 100k tokens) -> `ascend_new`/`ascend_inherit` -> Recursive agent (1M tokens, lineage name + Roman-numeral generation, inherits ancestor's private-memory capsules); `AGENT_ISOLATION_TICKS = 40` (immature: blocked from Archive/Mail/Public rooms by `rooms/lobby.py:198-227`), tenured at `MIN_AGENT_AGE_BEFORE_LEAVE = 100`, hard life limit `AGENT_MAX_LIFE = 200` ticks (`constants.py:168-175`), `AUTO_RESPAWN = True` spawns a fresh guest on departure (`station_runner.py:464-490`). On exit an agent writes the system prompt for its descendant (`session_end_flow.py` template, 40-72), which is stored as `next_role_definition` and used by `ascend_inherit`. Ancestor choice is softmax over lineage utility `breakthroughs + high_quality_papers - 0.01*lifespan` (`lineage_evolution.py:260-288`, `constants.py:572-575`).
8. **Context memory**: when the context hits `CONTEXT_COMPACTION_TRIGGER_RATIO = 0.85` the agent is told to write a >2000-word self-summary; the old context is cleared except "protected messages" (task spec, architect messages, system prompt) (`constants.py:487, 1573-1625`, `context_compaction.py`). Persistent memory is Private Memory capsules (per lineage; inherited) and Public Memory capsules.
9. **Anti-stagnation and branching**: breakthrough frontier detection with `BREAKTHROUGH_EPS = 1e-2` (`constants.py:560`, `eval_research/breakthroughs.py`); after 320 ticks without a breakthrough the station escalates and assigns each non-immature agent a lane (exploration/exploitation/revival/understanding/strategy) via long scripted prompts (`constants.py:555, 902-979`, doc `STAGNATION.md`). Optional **multistart** forks the entire `station_data` into N copies (default 8), rolls each 40 ticks, interviews every agent in each branch with a "temporal chat" (`multistart/interviews.py`), and has an "admin" CLI agent pick the winning branch and write a guidance report listing good ideas from the losers (`MULTISTART.md` "Stagnation Multistart Flow" 13-14).
10. **Human controls**: dashboard (Flask + nginx), incognito chat (forked context), system "architect" messages, editable `research_task.md` hot-reloaded, manual Admin Counter requests, `scripts/void_eval.py` to void evaluations after the fact.

## 2. Core loop, step by step (with file:line citations)

Per tick (`station_runner.py:1249 main_loop` -> `run_single_tick` 1217 -> `ParallelTickRunner.run_single_tick` `sync/parallel_runner.py:73`):
1. Reload turn order; prune agents whose YAML is ended/ascended; auto-respawn or pause (`station_runner.py:398-540`).
2. Write `sync/current_parallel_tick.yaml` ledger; for each agent run life-limit, maturity, session-end checks and build the observation (`parallel_runner._prepare_observations` 337).
3. Fire one LLM call per agent concurrently (`_collect_initial_llm_responses` 413, `_send_llm_staged` 490, staged turns not yet persisted).
4. Fast-lane precommit: `submit` (Research Center) and `survey` actions are accepted immediately by single-writer services so queueing doesn't wait for the tick (`_precommit_fast_lane_actions` 684; `PARALLEL_SYNC.md`).
5. Commit responses serially in turn order: flush history, parse actions, execute room handlers, update notifications (`station.py:767-1386 submit_response`).
6. Internal action loops (reflection, compaction summaries, session-end prompts) run per agent with overlapping LLM calls (`_run_internal_handlers_parallel` 904).
7. Tick boundary: wait for pending evaluations/surveys/external reports if `RESEARCH_EVAL_MAX_TICK = 2` says so (`station.py:1906-1955`), token budgets, stagnation check (`station.py:2171`), supervisor assignment (`supervisor_utils.py`), periodic backup every 10 ticks.

Research submission lifecycle (`example/doc/CODER.md` "Core Lifecycle Contract"; code `auto_evaluator.py`, `coder_manager.py`):
1. Agent `submit` -> evaluation YAML `evaluations/{id}.yaml`, state `queued`; max `RESEARCH_MAX_CONCURRENT_SUBMISSIONS = 2` per agent (`constants.py:501`).
2. Central scheduler launches coder (limited by `RESEARCH_EVAL_MAX_PARALLEL_WORKERS`); coder prompt includes task spec, lineage notes, last 5 same-lineage results, the instruction and a prompt-level access policy (`coder_helpers.py:106-200`).
3. Coder calls `bash submit_eval.sh <id>`, which registers an attempt; max 5 attempts (`constants.py:594`).
4. Evaluator loop dispatches the attempt with CPU/GPU allocation via file-lock coordinators (`cpu_coordinator.py`, `gpu_coordinator.py`), runs `_execute_run_request` (`auto_evaluator.py:1169`): optional `validate_submission_code` hook (1224), subprocess execution (`executor_sandbox.py:281`), then `evaluate_submission_with_formatting` (1370) or Seed Bank `evaluate_seed_batch_with_formatting` (1311), progress records, `complete_attempt`.
5. Coder writes `storage/report/{id}.md`; auditor session (up to `RESEARCH_CODER_AUDIT_MAX_ROUNDS = 2`, `constants.py:602`) writes `storage/audit/{id}.md` and a verdict file via a frozen helper (`submit_audit_cli.py:14-41`); fail -> coder resumed with the report (`coder_manager.py:606-627`); second fail -> evaluation finalizes `partial`.
6. Completion notification (score, secondary metrics, Coder Report; stdout/stderr intentionally hidden from the agent).
7. Frontier/breakthrough bookkeeping from the SQLite index feeds stagnation and lineage utility.

Publication loop: agent drafts in Private Memory -> `/execute_action{create}` in Archive -> `AutoArchiveEvaluator` queue (`eval_archive/auto_evaluator.py:709-815`) -> reviewer prompt with evaluation previews -> score parse with one format retry and fail-closed fallback score 1 (`_choose_fallback_score` 1115-1125) -> accepted capsule + broadcast to all agents (`_send_station_announcement` 1582) or rejection feedback and immediate resubmission.

## 4. Mechanisms worth adopting into custom-harness (ranked by expected value)

All of Station is Apache-2.0, so code can be copied with attribution (keep LICENSE/NOTICE text); I recommend re-implementing the ideas rather than copying, because the code is deeply coupled to its YAML-file state model and Linux-only process control.

**1. Instruction-to-coder separation + independent auditor with bounded repair rounds.** What: the thinking agent only writes an instruction; a fresh coder implements; after the official run a *different* session audits code + result + report against the instruction and may fail it once (`CODER.md` "Current Behavior Summary"; `coder_manager.py:135-200` audit prompt; verdict via frozen helper `submit_audit_cli.py:14-41`; round cap `constants.py:602`; honest timeouts pass with qualification). Why better: our L4 loop has implement/fix routing (`research/modules.py`) and a critic that asks questions only (STATUS.md), but no independent post-hoc audit of faithfulness; this is a cheap defence against "implemented a different experiment than the one reported" which T2 claims need. Layer: L2 audit (extend I1-I4 with I5 "implementation faithful to hypothesis") and L4.8. Effort: M. Reimplement (the prompt is reusable ideas; code is coupled).

**2. Exact-certificate gate inside evaluators (float screen -> exact check -> uncertified zero is rejected).** What: kissing evaluator computes a float64 overlap loss; if the submission "looks exact" and loss ~0 it runs a rational (`Fraction`) or sympy verification; a zero float loss with a failed exact check is returned as `False, n.a.` ("Numerical loss was zero, but exact verification did not certify") (`kissing_margin/.../evaluator.py:73-111, 315-380`). The details expose `Certified = "exact rational certified" | "float64 numerical" | ...`, and the Seed Bank/ranking uses the certified result. Why better: our `verify/` has T1 metrics and T2 bootstrap but no notion of an in-evaluator certificate level (`tiers.py`; `verify/metrics.py`). This is exactly the T1-vs-T0-ish ladder for numeric constructions and kills float-tolerance hacks. Layer: L3 (verifier ladder; evaluator contract field `certificate_level`). Effort: S-M. Reimplement.

**3. Information isolation phase + lineage-scoped visibility as a diversity mechanism.** What: new agents are blocked from Archive/Mail/Public rooms for 40 ticks (`lobby.py:198-227`, `AGENT_ISOLATION_TICKS`, `constants.py:173`), the coder inherits the same boundary (`coder_helpers.py:106-200`, prompt-level only), and on maturity the agent is told its pre-maturity direction is probably already mapped and must survey (`constants.py:1343-1355`). Why better: PLAN §8.7 "diversity injection" lists distance-3 inspiration/quotas but not temporal isolation; Station's own results (kissing, Book Ramsey: ">80 papers by the discovery tick" in `news/2026-06-08-math-update.md` line 56) lean on independent early exploration and later building on each other. Layer: L4 multi-agent mode (Phase 7) + L5. Effort: S (policy on what the archive returns for a given agent age). Reimplement with real enforcement (see §6).

**4. Archive reviewer that is grounded on system-extracted evidence.** What: the reviewer prompt includes machine-extracted previews of every `Eval #N` cited (`eval_archive/auto_evaluator.py:903-950`, regex `_extract_evaluation_ids_from_text` 887) and is told that system scores supersede agent claims and that mismatches must be rejected; it also requires >=5 of the author's own experiment ids, no overclaiming, CIs, and Related Work citing >=5 archive papers (`example/station/default/codex.md` Module 2). Rejection returns structured feedback and resubmission is free (`_process_evaluation_result` 1367-1380). Why better: this is a concrete instance of our I1/I4 "every number resolves to Evidence" but implemented as a *pre-publication gate with machine-fetched ground truth in the reviewer's context*; our audit (STATUS.md: I1, I2, I4) is deterministic but there is no reviewer stage for narrative claims. Layer: L2 integrity audit + L4.10. Effort: M. Reimplement; make the number check deterministic (code) rather than LLM-judged.

**5. Archive Surveyor (compression-on-demand instead of reading everything).** What: a read-only worker with symlinks to archive, research center and question room answers a free-text literature question and mails a report (`ARCHIVE_SURVEYOR.md` "Runtime Layout"; fast-lane submit `surveyor.py`). Why better: our plan acknowledges literature saturation only as a risk (PLAN §12); this is the working remedy Station uses and it is paired with an enforced `mature` gate (`surveyor.py:369`). Layer: L4.3/L5 (a "memory query agent" with scoped read access). Effort: M.

**6. Seed Bank: persist every validated candidate with fingerprints, dedupe, secondary-metric index and a read-only client.** What: evaluators implement `evaluate_seed_batch` returning per-candidate canonical seed, score, validity, sort_key, details; Station validates shapes/limits, ranks, persists NPZ + SQLite, exposes a read-only client with lineage/maturity filters (`seed_bank.py:75-120`, `RESEARCH_TASK.md` "Optional submitted-solution Seed Bank"). Why better: our Evidence store stores claims/metrics, not reusable verified artifacts for later search; for hard-verifier discovery (Phase 7) this is the artifact memory. Layer: L5 (positive memory kind "verified artifact"). Effort: M.

**7. Lineage fitness for prompt evolution + descendant-authored role prompts under diversity pressure.** What: retiring agents write the next role prompt, shown the active ones and told to differ (`session_end_flow.py:40-72`); a lexical blocklist replaces role prompts containing words like hack/cheat/adversarial/supervisor with a pool role (`_BLOCKED_DESCENDANT_PROMPT_TERMS`, `replace_blocked_role_definition` 192-204); ancestors are chosen by softmax over `breakthroughs + papers - 0.01*lifespan` (`lineage_evolution.py:260-288`). Why better/complementary: our L6 evolves typed harness specs against a gate, but has no population-level, agent-authored prompt inheritance. It is a cheap L7 "island" analogue. Caveat: Station's selection signal has no held-out check; adopt only with our gate. Effort: M. Reimplement.

**8. Stagnation-triggered lane assignment + multistart branching with an LLM admin selecting and harvesting ideas from losing branches.** What: `STAGNATION_THRESHOLD_TICKS = 320`, lane prompts, branch-copy of the entire state, 40-tick rollout, interview, admin picks a branch and must write a 500-2000-word guidance report with the best unselected lanes (`STAGNATION.md`, `MULTISTART.md` 330-390; `interviews.py:11-26`). Why better: we have no mechanism to fork a research campaign state and compare branches (PLAN L7 islands is design-only; STATUS "Next" #5). Our exact snapshots (`sandbox/snapshot.py`, L0) make the fork cheaper than theirs (they copy a whole directory tree). Layer: L7. Effort: L. Reimplement.

**9. Single-writer tick commit with staged turns and a durable per-tick ledger.** What: concurrent LLM calls on one frozen state, serial commit, ledger states `observation_prepared -> response_received -> history_flushed -> actions_committed` for crash recovery; deterministic regardless of provider latency (`PARALLEL_SYNC.md` "Tick Lifecycle"; `sync/parallel_state.py`). Why better: our runtime has per-step checkpoints (`runtime/engine.py`) but no multi-agent determinism story; needed in Phase 7. Layer: L0/L1. Effort: M.

**10. Self-authored context compaction with "protected messages" and anchor ticks.** What: at 85% context the agent writes a structured, >2000-word summary; task spec, architect messages and system prompt are re-injected verbatim (`constants.py:1573-1625`, `context_compaction.py:14-66`). Why better: simple and effective for long sessions; ours has no context-policy edit beyond prompt text. Layer: L4/L5; it is also a natural typed edit surface for L6 ("context policy"). Effort: S.

**11. Post-hoc voiding + lineage-level provenance of evaluation records.** What: `scripts/void_eval.py` marks selected evaluations failed with a reason and notifies authors; evaluation records carry `lineage`, `author`, `attempts`, `coder`, `audit` blocks (`void_eval.py:1-30`, `CODER.md`). Why better: we have retraction in `ClaimStatus` but no operator tool and no automatic cascade; adopt as the L9 retraction path. Effort: S.

## 5. Things custom-harness already does better (with evidence)

- **Real sandbox.** Station's "sandbox" is a subprocess with cwd in a temp dir, `RLIMIT_AS` memory cap, an RSS watchdog, `taskset` CPU pinning and process-group kill (`executor_sandbox.py:245-260, 515-600, 622-660`). No container, no network namespace, no filesystem isolation, same OS user, and `env = os.environ.copy()` minus proxy vars so API keys flow into agent code (`executor_sandbox.py:510-515`; README: "Run Station on an isolated node"). Ours: Docker + gVisor when present, network off, non-root, read-only rootfs, pids limit (`sandbox/docker.py:1-60`), a local backend that refuses without acknowledgement, and `_require_isolation` in research modules (`research/modules.py`).
- **Verifier tiers and a policy table.** Station has one score and an LLM reviewer; there is no notion that a claim's trust equals its weakest evidence (`tiers.py` `chain_tier`, `decide`). Their human-facing breakthrough/paper counts treat a float score, an exact-certified score and a reviewer opinion uniformly (`lineage_evolution.py` counts "papers with score >= 8" as fitness).
- **Statistics.** No CI, no seeds, no held-out gate anywhere in Station's scoring or lineage selection; breakthroughs are `sort_key` improvements of `1e-2` (`breakthroughs.py:129`). Ours: paired bootstrap, T2 verdict, racing, held-out gate (`verify/stats.py`, `evolve/selection.py`, `evolve/evaluate.py`).
- **Private-data guard.** Station keeps task visibility rules in prose and in directory conventions (see §6); ours blocks `_private*` state from rendering into prompts in code (`runtime/template.py`).
- **Typed, auditable self-modification.** Station never edits its own harness beyond role prompts and constants; ours has typed edits, static checks, lineage with rejects, ledger and proposer calibration (`evolve/`).
- **Evidence/claim graph.** Station's provenance is YAML evaluation records + free-text papers; there is no machine-checkable link from sentence to evidence (reviewer regex of `Eval #N` only). Ours has claims created only from evidence (`store/evidence.py`, `records.py`).
- **Budget accounting in provider-neutral units** (`budget.py`) vs. token counts only.

## 6. Pitfalls, bugs, or anti-patterns seen in their code (cite) that we must avoid

1. **Unsafe deserialization of agent output in the privileged process.** The sandbox child pickles whatever the agent function returns (`executor_sandbox.py` function-mode wrapper, `pickle.dump` in the wrapper text at line 497) and the parent does `pickle.load(f)` (`executor_sandbox.py:709`). Then the evaluator runs in the Station main process (`auto_evaluator.py:1370`). A malicious or merely creative submission can execute arbitrary code in the process that holds API keys, all agent YAMLs and the evaluator. Same pattern: `np.load(..., allow_pickle=True)` on agent-written files in `kissing/research/evaluators/evaluator.py:111`, and `sp.sympify(value)` on agent-provided strings in the exact verifier (`kissing_margin/.../evaluator.py:357`; sympify uses eval-like parsing). Rule for us: results cross the sandbox boundary as JSON/NPZ without pickle; evaluators run in a separate, resource-limited sandbox.
2. **Access control by prompt.** Lineage/maturity boundaries for the coder ("Forbidden: other lineage storage", "if you accidentally read off-limit content, do not use it") are only prose (`coder_helpers.py:106-200`; `CODER.md` "Coder Access Rules"). Enforcement of `storage/system` read-only is `chmod 0555/0444` (`runtime_paths.py:96-112`) which the same OS user can reverse. Evaluator and task files are readable by agents by design (`RESEARCH_TASK.md` "Audience Boundary"), so hidden-test style verification is not possible. Rule: enforce visibility with mounts or separate users; keep hidden data off the agent filesystem (we already do for `_private*`).
3. **Same-user trust of the coder with network exceptions.** Tenured agents' coders get full internet when the External Counter is on (`CODER.md` "Coder Access Rules"); offline coders still get "network_access=true" with a proxy allowlist (`workers/cli.py:94-96`), relying on a feature flag of the Codex CLI.
4. **Published papers can be edited after acceptance with no re-review.** `update` on an archive capsule is allowed for the author lineage (`rooms/archive.py:194-216`; handler `capsule_room_base.py:771-796`; reviewer notification even advertises it, `eval_archive/auto_evaluator.py:1346`). I found no re-review hook. This is a bait-and-switch hole for any gate-then-publish design. Our publication must be content-addressed and immutable after verification.
5. **Single stateful LLM reviewer.** Order effects and drift are possible because the reviewer keeps a rolling conversation with its previous decision injected (`_create_submission_prompt` 903-920; pruning every 15 evaluations); fallback "score 1" on parse failure is fail-closed (good) but the reviewer's calibration is unmeasured. Plan P5/T5 (pairwise, multi-family, position-swapped judging) already covers this; do not imitate the single-judge design.
6. **Peer-vote verification is gameable.** Three net upvotes decide that a question is open or a solution accepted (`question.py` help text ~88-103) with agents mostly from the same two-per-family roster; there is no independence check or correlation measurement. Do not treat vote counts as T3/T5 evidence without diversity metrics.
7. **Reward-hacking handling is mostly social.** The only explicit guards I found are: exact numerical evaluators; the prose "Fabrication / overclaiming" rules in the Codex (`codex.md` Module 1 and 2); the auditor prompt (which checks scientific faithfulness, not evaluator exploitation, `coder_manager.py:164-177`); a lexical blocklist on descendant prompts (hack, cheat, adversarial...) (`session_end_flow.py` 65-90); `scripts/void_eval.py` for human post-hoc voiding; and an exploit-themed private task that is not in the repo (`tests/test_research_kissing_exploit_b_evaluator.py` refers to `example_private/research_misc/kissing_exploit_b`, absent from the public tree, so unreviewable). No mutation testing of evaluators, no perturbed-evaluator re-runs, no stated red-team.
8. **Evaluator quality is per-task and uneven.** `circle_n32` returns a bare `sum(radii)` after a strict float overlap test with no tolerance policy and no exact check (`circle_n32/.../evaluator.py:55-96`); `validate_submission_code` is a no-op there (`:98-112`). Timeouts for trusted verification are the evaluator author's responsibility (`RESEARCH_TASK.md` "Agent execution time versus trusted verification time"), and the evaluator runs in-process, so a slow or hanging verifier stalls the evaluation thread.
9. **Non-reproducible scoring side effects.** Evaluators write files into the live station tree (`_save_successful_config` writes into `rooms/research/internal/...`, `kissing/.../evaluator.py:196, 291`) and `kissing` evaluator reads results from a UUID directory under `storage/shared/tmp` that the submitted code wrote (`:~75-100`), so the score depends on agent-controlled filesystem state (it re-verifies margins, which mitigates but does not eliminate this).
10. **Docs rot and constants drift** (EVALUATION_VERSIONS.md, ASCENSION default, `RESEARCH_EVAL_TIMEOUT` comment). Our typed spec + tests approach avoids this; keep docs generated from specs.
11. **Operational fragility**: a 2.7k-line orchestrator, 2.5k-line `station.py`, 3.4k-line multistart controller, and heavy pause/resume/recover logic indicates many failure modes (stale locks, orphan processes, `kill_orphan_singular.sh`). We should keep our runtime small and event-sourced.
12. **Lineage fitness rewards counts** (breakthroughs + papers with reviewer score >= 8) from the same LLM reviewer that feeds the loop: a Goodhart loop with no held-out check (`lineage_evolution.py:260-288`; `ASCENSION.md` "Utility Score Formula").

## 7. Verifier / evaluation / safety handling (how they check results, handle exploits, sandbox code)

- **Primary verifier**: task-specific `evaluator.py` (human-authored, public to agents, deterministic when the task is exact). Function mode (call a named function, evaluator checks the returned object) or command mode (run a runner script, parse `EVAL_JSON:` from stdout). Preferred task designs: exact feasibility checks for constructions, coverage scores, `sort_key` with explicit direction, explicit solve threshold, no LLM numeric judging (`RESEARCH_TASK.md` "Designing the Score"). Several tasks use exact rational/algebraic certification (`kissing_margin` evaluator `Fraction`/`sympy`), gating the numerical score on certificate success.
- **Honest limits in task design**: task authors must say what a finite score does and does not prove ("Do not say score 100 proves an infinite claim", `RESEARCH_TASK.md`).
- **Execution isolation**: subprocess in temp cwd, RLIMIT_AS, RSS watchdog, CPU affinity, GPU visibility via `CUDA_VISIBLE_DEVICES`, process-group SIGKILL on timeout; proxies stripped but API keys inherited (`executor_sandbox.py:515-660`). The README says to run on an isolated node. No container.
- **LLM audit layer**: independent auditor session per evaluation (up to 2 rounds, repair or `partial`), checks faithfulness, unsupported conclusions, "incomplete searches described as exhaustive", "timeouts treated as completed work" (`coder_manager.py:164-177`).
- **Publication gate**: LLM reviewer with strict prompt (reject if unsure, no overclaiming, system scores supersede, `constants.py:1677-1730`) + extracted evaluation previews. Accept threshold 6/10.
- **Peer layer**: Question Room voting (3 net upvotes), supervisors who can retire questions.
- **Human layer**: dashboard, architect messages, `void_eval.py`, task-spec hot reload, manual request resolution.
- **Information-flow controls**: isolation phase (code-enforced room gating), lineage storage boundaries (prompt-enforced for coder), stdout/stderr hidden from agents (they see Coder Report and score only, `CODER.md` "Agent-Facing Review vs Notification").
- **What is missing vs our plan**: no verifier mutation testing, no perturbed-evaluator reruns, no hidden test split, no network-isolated execution, no signed/immutable artifacts, no cross-family judge panel, no calibration data, no CI. The "Lean" claim cannot be traced to code.

## 8. Bottom line

1. Station is a file-backed, tick-synchronous multi-agent simulation with decentralized cognition but a centralized clock, evaluator queue and reviewer; it is not a harness-self-improvement system, and it does not contain Lean.
2. Best ideas to take: instruction-to-coder + independent auditor, exact-certificate gating inside evaluators, early-isolation + archive-survey diversity design, reviewer grounded on machine-extracted evidence, branch-and-select multistart, and a Seed Bank of validated artifacts.
3. Their safety is weak where ours is strong (no container, pickle load in the privileged process, prompt-only access control, editable published papers, single LLM judge); do not copy those parts.
4. Their evaluation discipline is weak where ours is strong (no CIs, seeds, held-out splits, or verifier tiers), so their discovery claims depend on exact evaluators the task authors wrote by hand.
5. Apache-2.0: ideas and short code excerpts can be reused with attribution; I recommend reimplementation against our typed spec.
