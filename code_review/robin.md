## 1. What the code actually does (architecture map)
Robin's repo is NOT an agent framework; it is ~3.5k lines of glue that (a) calls an LLM through LiteLLM (`o4-mini` default, `configuration.py` `llm_name`) for query generation / proposal / pairwise judging / data interpretation, and (b) calls FutureHouse's hosted, closed-source "Edison platform" agents over an API (`EdisonClient`, `edison_client`): Crow (`JobNames.CROW`) for literature queries and Falcon (`JobNames.FALCON`) for deep reports, and the "data-analysis-crow-high" job (Finch) for notebook-based analysis. The literature agents (PaperQA2-based) and the data-analysis agent's internals (`edit_cell`, `submit_answer`, Docker image) are NOT in this repo; the repo only submits a text query and polls (`utils.py:70-237` `call_platform`, `create_task` at 85, polling at 31-59). Verified in README: "The data analysis portion of this repo requires access to the Edison platform."

Three public async functions (`__init__.py`): `experimental_assay`, `therapeutic_candidates`, `data_analysis`. They are chained by a human in a notebook (`robin_full.ipynb` cells 6, 8, 13, 15); there is no orchestrating loop, no state object, no resume. Configuration: `RobinConfiguration` (`configuration.py` ~266-330 in the file) holding num_queries/num_assays/num_candidates, agent assignment per stage (`AgentConfig`: assay lit search=CROW, assay report=CROW, candidate lit search=CROW, candidate report=FALCON), and a `Prompts` pydantic model that validates `str.format` placeholders at load time (`configuration.py` `validate_all_prompts`).

The only experimental feedback path is human lab work -> raw files -> `data_analysis` -> text dict -> re-run `therapeutic_candidates(..., experimental_insights=...)`.

## 2. Core loop, step by step (with file:line)
### Stage A: "hypothesis" generation = assay/strategy selection (`assays.py:27-277`)
1. LLM generates `num_queries` literature queries, separated by `<>` (assays.py:36-66; split on `<>` at 59).
2. Crow runs each query remotely (72-76), results saved, concatenated into text (`output_to_string`, utils.py:334).
3. LLM proposes exactly `num_assays` strategies as a JSON array `{strategy_name, reasoning}` (92-129; prompt at prompts.py:392-417 says "mechanistic hypotheses tested via cell-culture assays"). JSON parse fallback via regex `\[.*\]` (123).
4. One Crow report per strategy (`assay_hypothesis_queries`, 154-187), formatted Assay Overview / Biomedical Evidence / Previous Use / Overall Evaluation (prompts.py:440-456).
5. Tournament (201-243), details in section 2.1. Winner's `hypothesis` string (strategy name) is the top assay (243).
6. LLM synthesizes a one-string "candidate generation goal" from the winning assay (249-275).

### Stage B: candidates (`candidates.py:30-548`)
1. Query generation (45-97) -> Crow lit search (103-107). Query prompt asks for `2*num_queries`: half therapeutic landscape, half disease biology (prompts.py:559-590).
2. LLM generates exactly `num_candidates` candidates in a custom `<CANDIDATE START>/<CANDIDATE END>` + `KEY:` text format, parsed by hand-written regex (172-235). Blocks missing CANDIDATE/HYPOTHESIS/REASONING are silently skipped with a warning (221-227).
3. Falcon report per candidate (273-311), then an LLM reformat pass (`format_final_report`, utils.py:858).
4. Tournament (334-548), section 2.1.
5. If `experimental_insights` is passed, it is appended (as prose) to both the query-generation system message (55-69) and the candidate-generation user message (148-162), and output files get an `_experimental` suffix. That is the whole feedback mechanism.

### 2.1 The Bradley-Terry-Luce tournament, exactly
- **Pair schedule**: `uniformly_random_pairs(n_hypotheses, seed=621, n_games=None)` (utils.py:422-453). It calls global `random.seed(621)` (426), computes `max = n(n-1)/2` (438), default `n_games = min(300, max)` (441), enumerates `itertools.combinations(range(n),2)` and `random.sample(..., n_games)` (452-453). So: pairs are sampled WITHOUT replacement, uniformly, non-adaptive, fixed seed; each pair judged exactly once. For the full run (`robin_full.ipynb` cell 3: 10 assays, 30 candidates): assays -> all 45 pairs (round robin); candidates -> 300 of 435 pairs (69%), ~20 games/candidate on average.
- **Position order is not randomized**: every pair is `(i, j)` with `i<j` (from `combinations`), and `process_comparison_pair` (utils.py:594-617) always puts `i` as "Candidate 1" and `j` as "Candidate 2". The paper/summary says BTL "addresses positional bias"; the code contains no swap, no double-ordering, no bias estimate. Candidate index = order of `Path.iterdir()` over report files (utils.py:881, 929) which is filesystem-dependent; so any bias is systematic against/for whichever candidates land at low indices. [inference: BT cannot remove a bias that is correlated with index.]
- **Judge call**: one LLM call per pair (`client.call_single`, utils.py:624) with system prompt = detailed committee rubric (prompts.py:458-476 assay; 691-760 candidate: evidence 1st, MoA 2nd, safety, feasibility/delivery, novelty "balanced") and user prompt = both full Falcon/Crow reports + a JSON schema asking for `Analysis`, `Reasoning`, `Winner` as `(name, id)`, `Loser` (prompts.py:478-497, 762-783). Order of output keys puts Analysis/Reasoning before Winner (reasoning-before-verdict). Concurrency via semaphore of 100 (utils.py:705, 710). Temperature/model from `llm_config` (default; get_default_llm_config at configuration.py:62, not fully read).
- **Parsing**: JSON braces located by first `{`/last `}` (629-638); required keys checked (642-650); failures return an "error" dict and are dropped, NOT retried (733-737). Results are written to CSV, then re-read and the `Winner`/`Loser` strings regex-parsed back into `(name, id)` (`processing_ranking_output`, utils.py:456-570). Round-tripping through CSV + regex + `ast.literal_eval` fallback is fragile (see section 6).
- **Fitting**: `choix.ilsr_pairwise(n_items, [(winner, loser), ...], alpha=0.1)` (candidates.py:469-471; assays.py:232). That is the third-party `choix` library's Iterative Luce Spectral Ranking with L2 regularization alpha=0.1 (the MLE of BTL with a ridge prior). Output is log-strengths (`strength_score`), sorted descending (519-521; assays.py:239-241). No confidence intervals, no ties, no multiple judges, no repeated games, no model-agreement stat, no check that fit converged other than try/except (468-503). I did not read `choix` source; the description of ILSR's regularization is from its API name/arg and is `[inference]`.
- **Validation before fit**: candidates.py:403-436 range-checks IDs and rejects self-pairs, but does NOT check that winner/loser are the two members of the pair actually presented (the pair is not carried to this stage; `Game Score` is derived only from the LLM's echoed IDs). The assay path (assays.py:230-232) skips even the range check and passes `n_items=configuration.num_assays` regardless of how many rows survived.
- **Decision**: top of the sort is taken as the experiment/candidate to run. The paper's top-ranked picks (RPE phagocytosis assay; ripasudil) are downstream of this.

### Stage C: data analysis (`analyses.py:17-202`, `multitrajectory_runner.py`)
1. Step 1: submit the same prompt (`ANALYSIS_QUERIES[type]`, prompts.py:279-330: flow cytometry gating strategy with DMSO control, plate effects, one-sided test, adj p) to the remote data agent `PARALLEL_ANALYSIS=5` times in parallel (analyses.py:290, 332-341; `[TaskRequest]*task_count`, multitrajectory_runner.py:189-195: identical prompts, so diversity is from agent stochasticity only). Language R, max_steps 30, timeout 15 min per step (339).
2. Step 2 ("consensus"): a second agent run reads the 5 `flow_results` CSVs and does a meta-analysis (`CONSENSUS_QUERIES`, prompts.py:331-365; for RNA-seq: "mode of log2FC and adjusted p values"). Output `consensus_results.csv` (344-354).
3. A plain LLM (not an agent) reads the consensus CSV rendered as HTML (`read_and_process_csv`, utils.py:946-975; warns but does not truncate beyond 30,000 chars, 958-963) and emits four `<>`-separated parts: drugs tested, summary, questions raised, mechanistic insights (analyses.py:407-447; prompt prompts.py:110-137). If it is not exactly 4 parts, all four fields become the string "Error in the LLM response parsing." and the pipeline continues (432-442), which would then be fed into the next candidate round as if it were data insights.
4. Second LLM call suggests follow-up assays (`FOLLOWUP_*`, prompts.py:139-179); "none" allowed.
5. Anti-repeat: the summary gets " These drugs have already been tested: ... DO NOT SUGGEST THESE DRUGS AGAIN." appended (467-472). Prompt-level only; nothing programmatic filters re-proposed candidates.

## 3. Paper/summary vs code discrepancies
(Compared to `autoresearch_survey/nature_s41586-026-10652-y.md`, read lines 1-80 only.)
- Summary: "Identifies 10 candidate disease mechanisms ... ranked with BTL." Code: there is no mechanism-ranking stage. The tournament in `assays.py` ranks **assay strategies** (`num_assays`, 10 in `robin_full.ipynb`), whose prompt asks for "mechanistic hypotheses tested via cell-culture assays" (prompts.py:392-396). The mechanism "RPE phagocytosis" would be output of that step. `[inference]` the paper's "mechanism" is this assay/strategy.
- Summary: "Claude 3.7 Sonnet pairwise adjudication" and o4-mini for synthesis/ranking. Code: one LLM client (`llm_name="o4-mini"`, `RobinConfiguration.llm_client`, configuration.py ~54, 80-84) does queries, proposals, pairwise judging, formatting, and data interpretation. No second judge family, no Claude path exists in the repo (`grep` of README/config shows only LiteLLM defaults). Judge diversity is a paper claim, not code.
- Summary: BTL "addresses positional bias and stochasticity." Code: no position swap and one sample per pair (section 2.1). Stochasticity is not averaged; BT only smooths across different pairs.
- Summary: "distributed tournament." Code: single-process asyncio fan-out, no adaptive/active pairing.
- Summary: Finch "operates via two tools: edit_cell and submit_answer", Docker with R/Python stack. Code: not present; only a remote job name (`job-futurehouse-data-analysis-crow-high`, analyses.py:333) and `environment_config={"eval":..., "language":...}` (multitrajectory_runner.py:217-224). Cannot be verified from this repo.
- Summary: "closed-loop." Code: loop is manual; experimental results are text-injected into prompts for a re-run. No code ingests lab results automatically, links candidates to measured outcomes, or updates rankings with measured effects (BT is never refit with experimental data).
- Summary: "~551 papers analyzed in 30 min", cost $10.76/cycle: not checkable from code.
- Summary: "multi-layer verification." Code verification is: JSON key checks, ID range checks, 5x repeated data-analysis + consensus (a replication layer), and an LLM interpreting the CSV. No statistics checks on the final claims are performed in code.

## 4. Mechanisms worth adopting into custom-harness (ranked by expected value)
Our current state: `verify/ranking.py:9-39` (K-way rankings -> pairwise wins -> BT via MM, symmetric prior 0.5, 200 iters, no uncertainty) and `research/modules.py:118-157` `research.tournament` (3 rounds of full K-way ranking, order shuffled per round at 133-134 with one `random.Random(state["_seed"])`, invalid permutations rejected 145-148, no per-pair rationale, single judge role `"judge"`).

1. **Consensus/replicated analysis agent with meta-analysis step** (analyses.py:290-356; prompts.py:331-365). What: run the same analysis N=5 times in independent trajectories, then run a second agent that combines p-values/effect sizes into one consensus table. Why better than ours: `research/modules.py` `verify` (217-288) and our T2 bootstrap rely on one implementation run per candidate; Robin treats agent-written analysis code as a noisy instrument and replicates it. Layer: L3 verifier ladder (an "analysis-replication" tier) + L4 research loop. Effort: M. Reimplement (Apache allows copying prompts, but our pipeline is code-execution-in-sandbox, not a remote API). Improvement over theirs: make the N runs differ (different seeds/prompt paraphrases; theirs are identical prompts, multitrajectory_runner.py:189-195) and compare numerically against a deterministic reference, not LLM-merged.
2. **Experimental-results-to-structured-insight object** (analyses.py:407-479; prompts.py:110-179). What: after results, produce {tested items, summary, questions raised, mechanistic insights, follow-up suggestions} and inject into the next generation round with an explicit "already tested, do not repeat" list. Why: our L5 memory (negative memory, dead-ends) is still "next" in STATUS.md; this is the minimal version. We should do it better: store as typed records in L2 (claims-from-evidence), and enforce the do-not-repeat as a programmatic dedup against the evidence store rather than a prompt sentence (their weakness, section 6). Layer: L5 memory + L4 hypothesize prompt. Effort: S-M. Reimplement.
3. **Pairwise A-vs-B judging with rubric and reasoning-before-verdict, as a SECOND judge mode** (utils.py:584-695; prompts.py:691-783). What: head-to-head comparison where the judge sees the full evidence dossier of both items and a weighted rubric that explicitly down-weights persuasion and prefers strong existing evidence/safety. Why: our tournament lists all K items in one prompt (modules.py:134-138) with only idea+rationale; for K large a single long listing degrades; pairwise gives per-pair rationales for audit. Add (and Robin lacks) both-orders evaluation, repeats, and adaptive pair selection by BT uncertainty. Layer: L3/L4.5 (tournament), L9 audit trail. Effort: M. Reimplement.
4. **Ridge-regularized BT fit** (`choix.ilsr_pairwise(..., alpha=0.1)`, candidates.py:469). We already regularize via a symmetric pseudo-win prior in `bradley_terry` (ranking.py:29); equivalent in spirit. Nothing to copy. Possible upgrade (ours, not theirs): bootstrap over games for rank CIs, which Robin does not do either.
5. **Query-split literature strategy** (prompts.py:559-590): generate 2N queries, half "therapeutic landscape" and half "disease biology", each 30+ words, covering target validation / efficacy in relevant models / mechanism confirmation / PK-safety. For our future literature module (STATUS Next #6): a fixed coverage template for query generation so literature retrieval spans complementary facets. Layer: L4 literature module. Effort: S. Prompt idea, Apache so copyable.
6. **Prompt-placeholder validation at config load** (`Prompts.validate_all_prompts`, configuration.py, `_get_prompt_args` at 71): fail fast if a template's `{vars}` do not match expected. We already have a template renderer with a private-state guard (`runtime/template.py`); worth confirming we have an equivalent unknown/missing-variable check. Effort: S.

## 5. Things custom-harness already does better (with evidence)
- Tournament position bias: ours shuffles presentation order every round (modules.py:133-134) and rejects non-permutation outputs rather than guessing (145-148). Robin never randomizes order (section 2.1).
- Determinism/traceability: ours seeds from `state["_seed"]` locally (modules.py:123); Robin calls global `random.seed(621)` which mutates process-wide RNG (utils.py:426) and keeps no trace beyond CSVs.
- Failure handling: ours raises when no valid ranking (modules.py:149-150) and records `rejected_rounds`; Robin drops failed comparisons silently with only a log count (utils.py:739-741) and, on all-bad parse, returns early with a "choix_error" CSV (candidates.py:444-503) while the notebook continues.
- Typed, checkpointed runtime (L0), budget ledger (L1), evidence store with claims-from-evidence (L2), integrity audit (L4), tier policy (L3): Robin has none; its state is a folder of text files and CSVs, `results_<timestamp>.json` for agent runs (multitrajectory_runner.py:118-156).
- No private/held-out separation or exploit handling in Robin; ours has hidden-test verify + private-data guard.
- Sandbox: Robin executes nothing locally; ours has Docker sandbox for agent code (STATUS).
- Closed loop: Robin's loop is a human re-running notebook cells; ours is a graph interpreter.

## 6. Pitfalls, bugs, or anti-patterns seen in their code (cite) that we must avoid
- **Free-text delimiters as the data format**: `<>`-split query lists (candidates.py:92; assays.py:59), `<>`-split 4-field interpretation (analyses.py:426, 432) and `<|>`-joined records parsed with `.split("<|>")` index access (candidates.py:257-260). A stray `<>` in an LLM answer shifts every field. Use JSON-schema outputs (we do: modules.py:127).
- **Parse failure becomes data**: if the interpretation LLM does not produce exactly 4 parts, the returned dict contains literal "Error in the LLM response parsing." strings (analyses.py:437-442) that the next stage would paste into the prompt as "experimental insights" (candidates.py:55-69, 148-162). Failures must raise or be typed.
- **Judge output not tied to the presented pair**: Winner/Loser IDs are taken from the model's echo and re-parsed from CSV text by regex (utils.py:468-518, 550-563); candidates.py:413-417 only checks range and self-pairs. A model that names a wrong-but-valid ID adds a phantom game. Keep the pair context and verify membership.
- **Assay path lacks validation and has a count mismatch hazard**: assays.py:219 uses `num_assays` (configured) not the number of reports actually produced; `n_items=configuration.num_assays` at 232 vs `assay_hypothesis_df` built from whatever `results` returned (201), which may include error dicts without an "answer" column (utils.py:152-160, 208-216 emit error rows). If an assay task failed, `get_candidate_info` raises KeyError/ValueError (utils.py:399-413) or choix gets mismatched sizes. No range filtering at all (230-232), unlike candidates.py.
- **Variable leak in error path**: `call_platform` timeout/gather-error branches reference `hypothesis` (utils.py:116, 124), a loop variable from the submit loop (79), i.e. an arbitrary last query; and returns a dict without a `"results"` key, which callers index with `["results"]` (assays.py:78; candidates.py:110, 307), so a timeout crashes as KeyError. Also `await fh_client.get_task(...)` (utils.py:111) while elsewhere `get_task` is called synchronously (38, 178): inconsistent [inference: one of the two is wrong depending on client version].
- **No position-bias control, single sample per pair, one judge model** (section 2.1): rankings from a single stochastic judge presented as BTL-calibrated. Don't copy the "300 random pairs" schedule without both-order swaps and repeats.
- **Report-length confound**: each side of the pair is the full Falcon report (utils.py:600-611); judges favor longer/more confident text; rubric tells it not to (prompts.py:699 "not on persuasive quality") but nothing normalizes length. Our judge should see length-normalized or structured fields.
- **Unseeded, unconverged claims**: no convergence check on ILSR, no CI, so the "top-ranked" pick can be within noise of #2; downstream (human wet-lab) cost depends on it.
- **Global state**: `random.seed(621)` at utils.py:426 resets module-global RNG each call.
- **Anti-repeat only in prompt** (analyses.py:467-472): the LLM may re-propose tested drugs; nothing checks.
- **Silent skipping of malformed candidate blocks** (candidates.py:178-184, 221-227): could return fewer than `num_candidates` and break `n_items` assumptions; only logs.
- **Hardcoded input path comment** `input_files={data_path: "flow_250508/"}` (analyses.py:336) and flow-cytometry-specific Alexa Fluor 647 / RPE phagocytosis wording baked into the "generic" analysis prompt (prompts.py:279-300): the data-analysis stage is domain-hardwired.
- No tests in repo; entire verification is by humans reading outputs.

## 7. Verifier / evaluation / safety handling
- No sandbox, execution, or exploit handling in this repo: code execution happens inside FutureHouse's remote Finch environment (not inspectable here). Our L0 sandbox has no counterpart to learn from.
- Result verification layers actually in code: (i) JSON/keys/ID-range checks on judge output; (ii) 5x parallel analysis + consensus meta-analysis; (iii) an LLM judge for candidate quality; (iv) human lab experiment as the real verifier (paper's wet-lab validation, outside code). There is no check that the data agent's reported p-values correspond to the raw files (no recomputation), no hidden-test, no anti-leakage. Prompt wording tells the agent "Do not give up" / "Do not stop early" (prompts.py ANALYSIS_QUERIES) which can encourage p-hacking-by-persistence for the gating strategy; the gating is judged by the agent itself ("Adjust the gating if the percentage gated population is too high or too low", prompts.py:~300). This is a verifier-exploit surface: agent tunes gating until the answer "makes sense".
- Safety: no domain safety filtering in code (drug candidate generation); `.env` keys only.

## 8. Bottom line
- Robin's "BTL tournament" is simple: random sample of up to 300 distinct unordered pairs, one fixed-order LLM judgment each, `choix.ilsr_pairwise(alpha=0.1)`; no position swap, repeats, uncertainty, or second judge despite the paper's framing. Our K-way shuffled-order BT (`verify/ranking.py`, `research/modules.py:118`) is already methodologically safer; add pairwise mode with both orders + BT bootstrap CIs.
- The real value is the closed-loop scaffolding idea: replicated (5x) analysis + consensus step, structured "insights/questions/do-not-repeat" feedback into the next generation round; implement these as typed L2/L5 records with programmatic dedup, not prompt strings.
- Literature (Crow/Falcon) and data agent (Finch) are remote and unavailable in code; nothing to copy but prompt designs (Apache-2.0, copyable with attribution).
- Avoid: delimiter-parsed LLM output, failures converted to prompt text, judge IDs not bound to the presented pair, and domain-hardwired analysis prompts.
