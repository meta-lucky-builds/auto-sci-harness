## 1. What the code actually does (architecture map)
SIA is a small orchestration shell around **two coding agents (Claude Code SDK or OpenHands/pydantic-ai) that write files**. There are no learned components inside the repo. The "meta-agent" and "feedback agent" are the same configured profile (`meta_profile`, `orchestrator.py:~690-700, 874-945`) and are given a text prompt, a working directory and `bypassPermissions` over Bash/Read/Write/Edit/Glob (`agent_impls/claude.py:35-45`).
- Run = `setup_run_directory` (venv + `runs/run_N/gen_k/`) → meta-agent writes `gen_1/target_agent.py` (`orchestrator.py:~905-925`) → loop `for current_gen in 1..max_gen: run_generation(...)` (`orchestrator.py:930-955`).
- `run_generation` (`orchestrator.py:~645-740`): (1) run `target_agent.py` as a subprocess (venv python or `docker run --network none --memory --cpus`, `_run_target_agent_sandboxed`), (2) run the task's `data/public/evaluate.py --gen-dir` which writes `results.json` (`run_evaluation`, `orchestrator.py:~195-260`), (3) append metrics to `context.md` (`ContextManager.add_generation`), (4) if not last gen, build feedback context and run feedback agent which writes `improvement.md` + the next `target_agent.py` (or `train.py`).
- **Harness-vs-weights is a run-level CLI flag**, `--focus {harness,weights}` (`cli.py:84-90`, default `harness`), threaded through every function as `focus`. In weights mode the "agent" file is `train.py` (a tinker-cookbook GRPO config: Env/EnvGroupBuilder/RLDataset/RLDatasetBuilder; `prompts.py:480-585`), run on Tinker + Modal/SandboxFusion (`orchestrator.py:822-845`).
- Feedback context = source of current agent, first 3 trajectories truncated + path to all of them, execution status, full `results.json` JSON (`_build_feedback_context`, `orchestrator.py:~455-545`), plus pointer to `context.md` (history).

## 2. Core loop, step by step (with citations)
1. `main()` parses args, loads profiles, checks `TINKER_API_KEY`/`MODAL_TOKEN_ID` only if `--focus weights` (`orchestrator.py:822-845`).
2. Meta prompt chosen by `focus` (`prompts.py:619-640`; weights variant `_build_weights_meta_prompt` at `prompts.py:39-612`).
3. Per gen: run target/train script → `run_evaluation` → `context_mgr.add_generation` → `_build_feedback_context` → `_run_feedback_agent` (`orchestrator.py:~700-760`).
4. `_run_feedback_agent` reads `gen_{current_gen}/target_agent.py` or `train.py` by `focus` (`orchestrator.py:~575-582`) — i.e. **always edits the latest generation, never the best one**. `ContextManager.finalize` merely prints "Best Performance: Generation X" (`context_manager.py:275-311`); no rollback/selection of the best generation as the output.
5. Early stop only in weights mode: loop breaks if file `COMPLETED` exists in next gen dir (`orchestrator.py:947-953`). **`COMPLETED` appears nowhere else in the repo** (grep of the whole tree): no prompt tells the feedback agent to create it, so this branch is effectively dead/undiscoverable.
6. Harness feedback prompt (`prompts.py:790-945`) tells the agent to read `context.md`, "don't repeat failed approaches", write exactly two files; says "Don't optimize for this specific task" and "Focus on agent structure". Weights feedback prompt (`prompts.py:773-880`) says to rewrite `train.py` for reward shaping/stability.

## 3. Paper/summary vs code discrepancies (the important section)
| Paper / summary claim | Code reality |

| Feedback-Agent "dynamically decides whether to update harness or weights" each generation (Aₘ₊₁ = ℱ(Aₘ, τₘ, ℰₘ, 𝒰)) | **No such decision exists in the released code.** `focus` is a single CLI arg fixed for the whole run (`cli.py:84-90`, passed unchanged at `orchestrator.py:943`). The feedback prompt never mentions the other lever. There is no decision rule, heuristic, or prompt text that chooses between levers (grepped `prompts.py`, `orchestrator.py`). |
| Single self-improving loop updating scaffold and weights (SIA-W+H) | Two disjoint modes. In weights mode the artifact is `train.py` and the harness (prompt/parsing) is whatever the reference agent contains; in harness mode no training happens. No code hands a trained checkpoint URL from a weights run to the next harness generation (grep for `checkpoint`, `tinker://`, `sampler`: only a prompt line at `prompts.py:440,601` asking train.py to save checkpoint paths to `results/`). SIA-W+H [inference] was likely produced by manual/sequential runs outside the released orchestrator. |
| Adaptive algorithm selection among PPO/GRPO/entropic/BC/DPO/REINFORCE | Weights prompt hard-wires GRPO: "Tinker-cookbook uses GRPO" (`prompts.py:238`), "DO NOT write local training code or custom loops… Everything else must match the template" (`prompts.py:480-585`). The feedback agent can only change reward/Env/dataset components; it cannot switch algorithm. |
| Feedback agent sees "per-instance reward scores from a deterministic verifier" | It sees `results.json` as written by `evaluate.py` (aggregate fields; LawBench includes `per_class` accuracy, `lawbench/evaluate.py:34-47`) and 3 truncated trajectories plus a folder path. Per-instance rewards only if the task's evaluator emits them (docs recommend `details`, `docs/evaluator_design.md`). |
| Coupled Goodhart acknowledged as limitation | Confirmed: no mitigation anywhere (see §7). |
| README claims "56.6% gain… 502%" etc. | Benchmarks are images (`docs/*.png`); no script in repo reproduces them. | Weights mode "task-agnostic" | Weights meta prompt is a tinker-cookbook tutorial (`prompts.py:51-402`); depends on Tinker + Modal accounts. |

## 4. Mechanisms worth adopting into custom-harness (ranked)
Honest note: the headline mechanism (lever-selection by feedback agent) is NOT in the code, so there is little here to copy for the L7/L8 decision rule. What remains is modest.
1. **Reward-variance / zero-signal debugging guidance for RL environments** (`prompts.py:188-193, 313, 349-402`): warns that hidden/missing ground truth gives constant reward → zero GRPO variance, that Tinker centers advantages per group (don't normalize), and mandates a train/eval split inside the RLDataset. Useful as a checklist for our L8 environment builder (also matches PLAN AWorld-RL "reward-variance gaps"). Layer L8; effort S; reimplement as our own guard (an automated check that group reward variance > 0 before launching training), text is MIT so may copy with attribution.
2. **Evaluator design checklist** (`docs/evaluator_design.md`: private/public split, robustness slices, "treat evaluator as adversarial surface", determinism). Maps to our L3 T1 and the integrity audit. Largely already covered by our tiers (`tiers.py`, `verify/`), but the "robustness slices" (rare/common, paraphrased, previously-failed vs new) could be added to T2 reporting. S; reimplement.
3. **Weights-vs-harness as an explicit, logged, per-generation `lever` field** — not in SIA code, but SIA's failure to log one shows what we should do: record `lever ∈ {harness, weights, none}`, the predicted effect, and the evidence that triggered it in the L5 lineage/ledger so we can later calibrate the L7 decision (§8.5 decision observability). Our design, not theirs.
4. **Trajectory folder + truncated sample in feedback context** (`orchestrator.py:~455-500`, `TRAJECTORY_PREVIEW_LIMIT`): include 3 samples inline + path to all. We already have full traces (L0) and trace-grounded diagnosis (`evolve/`); nothing to adopt beyond confirming the pattern.
5. Docker target-run flags (`--network none --memory --cpus`, `:ro` data mount; `orchestrator.py:~290-325`): we already exceed this (`sandbox/`).

## 5. Things custom-harness already does better (with evidence)
- Held-out gate and racing (successive halving + paired CI) in `evolve/` vs SIA's "always take the newest generation" (`_run_feedback_agent` reads current gen, `orchestrator.py:~575`); SIA has no accept/reject and no rollback to best.
- Typed edits + static checks (protected nodes, leakage patterns) vs SIA's free-form "rewrite the whole file", with the feedback agent running under `bypassPermissions` (`agent_impls/claude.py:38-45`).
- Private-data guard (`runtime/template.py`) vs SIA's "convention" that `data/private/` is unreadable, which SIA's own doc admits is not a security boundary in `--sandbox none` (`docs/evaluator_design.md` §1; `SECURITY.md` Direct Mode).
- Lineage including rejects, proposer calibration, budget ledger (`budget.py`): SIA has none; only a `context.md` text log and an LLM-written summary.
- State-exact snapshots, hard sandbox for agent-written code; SIA default is `--sandbox none` (`cli.py:~72-77`, SECURITY.md).

## 6. Pitfalls, bugs, anti-patterns (cite) to avoid
- **Test-set-as-training-signal every generation**: LawBench `evaluate.py` scores the same 913 cases the agent is told to predict (`task.md`: "913 cases to predict") against `data/private/test.csv` (`evaluate.py:15,23`), and the full result including `per_class` accuracy is injected into the feedback prompt each generation (`orchestrator.py:~500-520`). The feedback agent therefore adaptively overfits the "private" test set; reported 70.1% is a selection-on-test number [inference: the paper's numbers come from this setup, but I did not verify how the paper's final numbers were measured]. Our L3 sealed score must never be shown to the proposer.
- Information leak via file system: feedback and meta agents run with Bash, cwd inside `runs/`, host FS access, in the same repo tree as `sia/tasks/*/data/private/` (`claude.py:38-45`). A feedback agent can trivially `cat` private labels. Nothing prevents it.
- `evaluate.py` runs in the host venv with `subprocess.run` (`orchestrator.py:~220`) and reads `results.json` written into a directory the agent can write to; if the target agent pre-writes `results.json` and the evaluator crashes/skips, stale or forged results could be read (`run_evaluation` returns "warning" and `_build_feedback_context` still reads whatever `results.json` exists, `orchestrator.py:~500`). The docs themselves list this risk ("accidentally read the agent's old `results.json`", `evaluator_design.md` §6).
- Dead early-stop (`COMPLETED`, §2 item 5).
- Metric extraction by regex over stdout as fallback (`context_manager.py:385-400`, "accuracy[:\s=]+(\d+...)"): the agent controls stdout, so it can print a fake accuracy that lands in `context.md` and steers later feedback.
- Best-gen is only reported, never restored (`context_manager.py:275-311`) — final artifact can be worse than an earlier gen.
- Metric hardcoded to the key `accuracy` in finalize (`context_manager.py:279`); tasks with other metrics (TriMul runtime, mse_norm) get "N/A".
- Feedback prompt says "Don't optimize for this specific task" (`prompts.py:~875`) while the loop optimizes literally against that task's test score: contradictory instruction, no enforcement.

## 7. Verifier / evaluation / safety handling
- **Verifiers used**: per-task `data/public/evaluate.py` against `data/private/*` (LawBench exact-match label accuracy `lawbench/evaluate.py:23-30`; GPQA diamond answers `gpqa/evaluate.py:6,277`); deterministic, single, fixed. In weights mode the RL reward is supposed to come from that same `evaluate.py` ("use it in your EnvGroupBuilder.compute_group_rewards()", `prompts.py:~593`) — the **same verifier is the training reward, the harness-selection signal and the reported score**. This is exactly the coupled-Goodhart configuration; there is **no safeguard**: no disjoint verifier sets, no sealed held-out split, no perturbed evaluator, no adversarial verifier, no generalization check across generations. The only mitigation is the weights prompt's request to split train/eval inside the RLDataset (`prompts.py:193,597`), which is advisory and generated by the LLM, and a docs checklist for the human evaluator author.
- **Co-evolution loop**: not implemented as a single loop (see §3). So no synchronization between lever timescales, no data provenance from harness gens to weights training, no rollout re-collection after a harness change.
- **Sandbox**: optional Docker (no network, mem/cpu caps, ro data) for target agent only; meta/feedback agents always on host with `bypassPermissions`; default is no sandbox (`SECURITY.md`). Training runs on Modal/SandboxFusion (`cli.py:91-96`).
- **Reward hacking handling**: none in code; only the evaluator checklist doc.

## 8. Bottom line
- The released SIA does NOT implement the paper's per-generation harness-vs-weights decision: `--focus` is a static run flag (`cli.py:84-90`); no decision rule exists to port to our L7 — we must design it ourselves (use PLAN §8.8 plus logged lever choices).
- No Goodhart safeguards at all: one verifier is training reward, selection signal, feedback input and reported score; our disjoint-verifier two-timescale design (§8.8) is genuinely novel relative to this code, and the "A-score vs sealed gap" test is the right experiment.
- Do copy-adapt (MIT, attribution): the RL zero-variance/reward-centering checklist and the evaluator-design checklist; nothing else is worth copying.
- Avoid: showing the scored test set to the proposer each generation, host-level agents with bypassPermissions, regex-scraped metrics, "latest gen wins" with no rollback.
- Treat SIA's reported 70.1% as likely test-adaptive and the SIA-W+H pipeline as not reproducible from the repo.
