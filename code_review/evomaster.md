## 1. What the code actually does (architecture map)
- Generic agent framework: `BasePlayground` (evomaster/core/playground.py, 1,891 lines) wires LLM + tools + skills + session (local or Docker) + MCP into `BaseAgent`/`Agent` objects and `BaseExp` runners. A "playground" is a subclass with a hand-written pipeline (e.g. ml_master_2: prefetch, draft, research, parallel improve, knowledge promotion).
- Innermost loop = `BaseAgent.run` (agent/agent.py:145-203): a `for turn in range(max_turns)` loop calling `_step`, which does context prep, one LLM call, tool execution, trajectory append (agent.py:331-498). The `finish` tool or a no-tool text answer ends it (agent.py:408-430, 366-378).
- "Evolution loop" = `evomaster/evolution/` (optional `--evolve` flag, run.py:112-135, 548-573). It is a post-run wrapper that shells out to `run.py` as a subprocess (manager.py:161-200), builds a compact `TraceDigest` (collector.py:181-294), asks one LLM call for skills / prompt patches / tool proposals (analyzer.py:151-209), writes them as a YAML config overlay plus SKILL.md files plus appended prompt text (applier.py:55-119), and re-runs the same task.
- Skills = directories with `SKILL.md` (YAML frontmatter name/description/license) + `scripts/` + `reference/` (skills/base.py:20-226). Progressive disclosure through one tool `use_skill` with actions get_info / get_reference / run_script (agent/tools/skill.py:20-47). Frontmatter is parsed by a hand-rolled line parser, not a YAML library (skills/base.py:57-119).
- Memory: there is NO persistent agent memory module in the core. What exists: (a) context compaction (agent/context.py), (b) a RAG skill over a hand-built vector store (`evomaster/skills/rag`, used by ml_master_2 prefetch), (c) per-node "memory" strings inside ML-Master v1's UCT tree (uct.py:349-402), (d) `research_plan_and_result` list in ml_master_2 (playground.py:64, 317-333). `on_before_compaction` is declared as a "memory extraction" hook (context.py:102, 333) but nothing in the repo sets it (grep: only context.py).
- Evaluation: there is no benchmark harness for the paper's headline benchmarks (see Section 3). Only the ML-Master playground ships a grading path (`mlebench grade-sample`, mlebench_grade.py) and a batch script with a hard-coded author path (`playground/ml_master/scripts/mlmaster_test.py:15-19`, `/data/bingzehao/...`).
- Docker/MCP: `DockerEnv` shells out to `docker run -d ... tail -f /dev/null` then `docker exec` (env/docker.py:473-620, 694+). MCP via `MCPToolManager` with stdio/SSE/HTTP connections (agent/tools/mcp/mcp_connection.py:95-156), each remote tool wrapped as an `MCPTool` (mcp.py:21-150). ml_master_2 explicitly refuses Docker (ml_master_2/core/playground.py:88-89).

## 2. Core loop, step by step (with citations)
### 2a. Execution loop (agent/agent.py)
1. `_initialize`: build Dialog [system, user] + tool specs, new `Trajectory` (agent.py:287-329).
2. `_step` (331-498): `context_manager.prepare_for_query` (two-tier: >=100% usable => LLM summary compaction, >=80% => prune old tool outputs as a non-persistent view; context.py:393-443); LLM query; on `ContextOverflowError` do emergency `truncate` and retry once (agent.py:343-354); proactive compaction if usage near limit (agent.py:362-374); execute each tool call (`_execute_tool`, 500-542, with 30k-char head/tail truncation at 505-520 and again at 454-460); append trajectory entry every step (`_append_trajectory_entry`, 819).
3. Terminates on `finish`, on `ask_user` (pause, returns status "waiting_for_input"), on text-only reply if `finish_on_text_response`, or after `max_turns` ("failed: max_turns_exceeded", agent.py:187-193).
4. The "self-critique" claimed in the summary is not a distinct code step in this loop. There is no critique node in `_step`; critic roles exist only as separate agents in some playgrounds (x_master Solver/Critic/Rewriter/Selector, x_master README; I only read the README and the method list of x_master/core/playground.py).

### 2b. Exploration loop (per-playground, hand-coded)
- ml_master_2 (playground/ml_master_2/core/playground.py:174-370): watchdog thread (86400 s, ctypes `PyThreadState_SetAsyncExc`, watch_dog.py:1-40), prefetch via RAG (196-200), draft with debug retries (204-213), then `for reseach_round in range(20)` (215): research agent proposes `{direction: {idea: ...}}` (221-233), each idea is implemented in a parallel improve exp on a copy of the direction's best solution (254-272), scored, greedy update of `best_solution`/`best_score` (277-313), then a knowledge-promotion agent summarizes the round and its text is appended to `research_plan_and_result` fed back to the next research prompt (321-333). This is greedy hill-climbing with LLM-written lessons; no tree.
- ml_master v1 (playground/ml_master/core/utils/uct.py): real UCT tree. `select_next` (480-500), `ingest_result` (502-556), rewards -1 for buggy, +1 valid, +1 if parent was buggy (debug fixed), +1 if new global best (`_get_node_reward`, 695-731); backprop up the tree (678-693); exploration constant with decay schedules (828-859); stagnation cut-off via `metric_improvement_threshold` and `max_improve_failure` (753-802). Final hidden-test grade runs once after search via `mlebench grade-sample` (ml_master/core/playground.py Step 4; mlebench_grade.py:35-99).

### 2c. Evolution loop (evolution/manager.py:51-136)
1. Run baseline: `iterations/iter_000_baseline` via subprocess `python run.py --agent ... --task ... --run-dir ...` (manager.py:72-73, 161-200).
2. `collect_trace_digest`: reads `trajectories/**/trajectory.json`, counts tool calls and errors, regex-flags "issues" (collector.py:17-22: `error|failed|timeout|not found|invalid|...` over any tool output), pulls a score from `*grade*.json|*metric*.json|result.json` or from log lines matching `score|metric: <num>` (collector.py:23-26, 105-158), lists workspace files (161-178).
3. `EvolutionAnalyzer.analyze`: one LLM call (temperature 0.2, `tools=[]`), JSON schema of {skills, prompt_patches, tool_proposals} (analyzer.py:26-71, 181-199); falls back to a canned heuristic skill if the LLM fails or returns invalid JSON (274-390); normalizes names/lengths (skill body <=8000 chars, patch <=4000; 247-272). The system prompt tells the model to be "aggressive about turning ... single-run knowledge into agent-local skills" (analyzer.py:29).
4. `EvolutionApplier.apply`: writes `iter_NNN/skills/<slug>/SKILL.md` (applier.py:121-151), adds the dir to `skills.extra_roots` and appends the name to the agent's `skills` list (163-214), appends "# EvoMaster Evolution Notes" blocks to the original system/user prompt file and points the agent config at the new file (216-264), writes tool proposals to JSONL, never enabled (278-291).
5. Re-run with the overlay config into `iter_NNN_evolved`, collect digest, compute a deltas dict (`score_delta`, `step_delta`, `tool_error_delta`, `issue_delta`; manager.py:206-217), and set `current_config = overlay.config_path` UNCONDITIONALLY (manager.py:132). Next iteration analyzes the evolved run and stacks more patches on the patched prompt.
- Net effect: one task, serial only (run.py:548-557), the same task is re-run after learning from it.

## 3. Paper/summary vs code discrepancies
Summary file: `autoresearch_survey\gh_EvoMaster.md` (a Haiku summary of README/paper).
- **Benchmarks not reproducible from code.** The summary's numbers (58.02% average, MLE-Bench Lite 75.76, PaperBench 74.40, BrowseComp 74.25, BrowseComp-ZH 73.36, Codex/OpenHands/OpenClaw baselines 40.29/39.84/32.39, 9 of 10 wins, 35.6% lower cost) have no counterpart in the repo. A repo-wide grep for BrowseComp / PaperBench / FrontierScience / HLE hits only data CSVs (false positives) and README; the README shows the benchmark results only as two PNGs (README.md:22-30). No eval harness, task lists, graders or result files exist for BrowseComp, BrowseComp-ZH, PaperBench, HLE or Frontier Science. The only evaluable pieces: (i) MLE-Bench-style grading for ML-Master v1 via the external `mlebench` CLI (mlebench_grade.py:35-99; needs mle-bench and datasets installed; a 24-competition list is in `scripts/mlmaster_test.py`), whose per-competition scores could in principle be aggregated into an MLE-Bench Lite figure, but no aggregation or medal logic is in the repo; (ii) a single demo task for ml_master_2 (`detecting-insults-in-social-commentary`) with its gold file checked in. The "~60-65% Frontier Science" and "~50% HLE" values in the summary are labelled "inferred" by the summary itself and are unsupported.
- **"Persistent integration across future runs / evolution persists to future runs."** Code: evolution is a single-task wrapper that stacks overlays over iterations of the SAME task and run directory (manager.py:72-133; docs/evolution.md "run-local ... does not overwrite ... built-in skill directory"). Nothing is promoted to a shared skill library or reused on a different task. The "evolve" gain on a task is therefore measured on the very task it learned from (see Section 6).
- **"Tracked as reviewable proposals"**: only tool proposals are review-only (JSONL, never applied). Skills and prompt patches are applied automatically with no review gate or A/B acceptance (applier.py:84-93; manager.py:132).
- **"Failure attribution" / "trajectory analysis"**: implemented as one LLM call over a truncated JSON digest (<=120k chars, middle cut; analyzer.py:103-107; collector step cap 120 and issue cap 160, collector.py:289-290). Per-step summary only inspects `steps[0]` of each trajectory entry (collector.py:211-213). No structured attribution, no clustering, no counterfactual.
- **"Self-critique" in the execution loop**: not present in `BaseAgent._step`. Only separate critic agents in specific playgrounds.
- **"LLM-based dynamic summarization to prevent bloat"**: true, but the DEFAULT strategy is `latest_half` (context.py:74-77, config examples), not summary; summary mode needs `set_summary_llm`, falling back to latest_half if unset (context.py:108, 275-285). Note the 80%-prune/100%-compact design is directly lifted from OpenCode (context.py comments 395-401, 459-466).
- **ML-Master 2.0 "Hierarchical Cognitive Caching" / wisdom accumulation**: wisdom promotion runs ONLY inside the `GlobalTimeoutInterrupt` handler (ml_master_2/core/playground.py:339-357), i.e. only after the 24 h watchdog fires, not after normal completion of 20 rounds (334-338 returns without it). Its output is parsed and merely logged; no code writes it into `db.json` / `nodes.jsonl` / `embeddings.npy` (grep: those names appear only in docs and the rag skill reference). The shipped wisdom DB is one hand-built entry for the same competition the demo runs on (`example_wisdom/db.json` has exactly one key `detecting-insults-in-social-commentary`; nodes.jsonl has 1 line). Prefetch hardcodes `top_k 1 --threshold 0.7` (prefetch_exp.py:92-94), so the demo effectively retrieves the answer distilled from the same task. The long-term cross-task memory loop is not closed in code.
- **Six agents / MagiClaw**: MagiClaw lives in a separate repo (README.md:71). PhysMaster and EmboMaster are "Coming Soon" (README.md:113-114). mat_master exists as a playground; I did not read it.
- **"~100 lines of code to build an agent"**: plausible for the minimal playgrounds; not evaluated by me.

## 4. Mechanisms worth adopting into custom-harness (ranked by expected value)
1. **Failure-grounded skill distillation with a staged overlay (idea only; our version must add a gate).**
   - What: skills are generated from a trace digest, written as an isolated overlay dir with an evidence section, and activated by pointing the config at the overlay (applier.py:121-151, 163-214, 253-264; run-local, original untouched). Analyzer prompt explicitly bans secrets, gold labels and one-off paths (analyzer.py:29).
   - Why better than ours: custom-harness has typed edits, racing and gates (`evolve/edits.py`, `evolve/loop.py`, `evolve/selection.py`) but no reusable "skill" object type; PLAN §3 lists `Skill` and `MemoryEntry` but STATUS.md shows L5 memory/skill library not built. EvoMaster supplies a minimal skill format and an overlay-as-diff pattern.
   - Where: L5 (skill library) + L6 (as a new EditType: `add_skill`). Our gate must apply: candidate skills only enter after held-out non-regression and quarantine (PLAN §8.4).
   - Effort: S-M. Copy-vs-reimplement: Apache-2.0, may copy with attribution, but the code is ~100 lines of YAML/file plumbing; reimplement against our typed-edit spec instead.
2. **SKILL.md progressive-disclosure format (3 levels).** Level 1 name+description always in the tool description, level 2 body on `get_info`, level 3 `reference/` and `scripts/` on demand (skills/base.py:33-47, agent/tools/skill.py:61-85). Compatible with Anthropic-style skills. Gives a cheap context policy for large skill libraries. Layer L5 + L0 gateway tool. Effort S. Reimplement (use a real YAML parser, see Section 6). Dead-simple to interoperate with the 3-level format so we can import community skills.
3. **Two-tier context management with a non-persistent prune view.** Prune old tool outputs into a throwaway view above 80% of usable context, and write back a permanent LLM summary only at 100% (context.py:393-443, 458-518); reserve output tokens (20k) and use real `usage.prompt_tokens` + incremental estimate instead of re-tokenizing (context.py:116-130, 423-436). Keeps raw tool outputs available for later summarization. Our `runtime/engine.py` has no context-policy layer (STATUS: contracts + retries, not compaction); PLAN §8 treats "context policy" as an edit type, so this is a good seed baseline and a typed parameter set (thresholds, strategy). L0. Effort S-M. Copy ok (Apache-2.0), but note the code is itself derived from OpenCode's logic.
4. **MLE-Bench-style UCT search over (draft/debug/improve) nodes with reward shaping** (uct.py:320-336, 695-731, 753-802): -1 buggy, bonus for debug-recovery, bonus for global best, exploration decay, local-best stagnation counter. Useful as a ready L4 search policy for ML tasks; our L4 uses a K-way tournament + deterministic routing (`research/modules.py`, STATUS). Only worth it if the node score comes from a hard verifier (their score comes from an LLM, see Section 6). L4/L7. Effort M. Copy ok, reimplement preferred (the file is 859 lines with heavy docstrings and several coupled guards).
5. **Grading-server format guard + metric sanity guards**: reject nodes whose submission format is invalid before they can be best (uct.py:595-626), reject metric-direction flips (558-577) and implausible metric ratios (733-751). Cheap exploit and bug filters. In ml_master v1 a grader failure marks the node buggy (fail-closed, uct.py:620-626), which is the right default. L3. Effort S. Reimplement.
6. **Parallel idea fan-out with per-experiment workspaces and CPU/GPU pinning** (ml_master_2 playground.py:372-490, core/playground.py `_per_exp_docker_resource_allocation`, 799-935). Operational pattern for L0 sandboxes; ours has Docker sandboxes and snapshot (`sandbox/docker.py`, `snapshot.py`) but no parallel resource allocation. Effort M. Not a priority until we have real GPU runs.
7. **Round-level "knowledge promotion" text fed back into the next research prompt** (playground.py:317-333). This is a minimal negative+positive memory per run. We should implement the same idea with evidence IDs and negative memory as first-class (PLAN P6), not free text.

## 5. Things custom-harness already does better (with evidence)
- **Acceptance gating.** EvoMaster accepts every evolved overlay unconditionally (manager.py:132) and only logs deltas (206-217). Ours has racing with paired bootstrap CIs, a held-out gate and rejected-candidate lineage (`evolve/selection.py:18-87`, `evolve/loop.py:71-136`, STATUS L6).
- **Typed, bounded edits with static checks.** Theirs is free-text appended to the prompt + free-text skill bodies (applier.py:243-262); ours is JSON-pointer ops with protected nodes, leakage-pattern checks and "audit must be the only terminal" (`evolve/edits.py:107-152`).
- **Predicted vs actual effect, proposer calibration.** Absent in EvoMaster; ours: `evolve/propose.py`, `evolve_generation`, `proposer_calibration` (loop.py:138).
- **Held-out / leakage discipline.** EvoMaster's evolve loop re-runs the same task it learned from (run.py:556 one task only; manager.py:91-133). Ours separates evolve/gate/sealed splits (PLAN P2, `evolve/driver.py`) and has a private-data guard (`runtime/template.py`).
- **Evidence store and claim provenance.** Theirs is directories of JSON and logs; digest regexes over free text (collector.py:17-26). Ours: content-addressed Evidence store, claims only from evidence (`store/evidence.py`).
- **Statistical honesty.** Theirs reports single-run deltas; ours has seed bootstrap, paired test-example bootstrap, Bradley-Terry (`verify/stats.py`, `verify/ranking.py`).
- **Sandbox default.** Theirs defaults to host-local execution for ML-Master 2 (Docker explicitly unsupported, playground.py:88-89) and Docker `network_mode` defaults to bridge, no cap-drop/read-only/non-root flags in `docker run` (env/docker.py:520-610; session/docker.py:93-96). Ours: no-network, caps dropped, non-root, read-only rootfs, gVisor if present (STATUS L0 sandboxes).
- **Spec-driven reproducibility.** Their pipelines are bespoke Python classes per playground; ours is a typed harness spec + graph interpreter with per-step checkpoints and exact fork/backtrack (`runtime/engine.py`, `runtime/spec.py`).

## 6. Pitfalls, bugs, or anti-patterns seen in their code (must avoid)
1. **Same-task learn-and-rerun = self-contamination.** The evolved run is scored on the task whose trajectory generated the skills; the analyzer is explicitly told to be "aggressive" about converting single-run knowledge to skills (analyzer.py:29). Any reported evolve gain here is not generalization evidence. Do not copy this evaluation design.
2. **No accept/reject, no rollback.** `current_config = overlay.config_path` always (manager.py:132); a worse evolved run still seeds the next round, and each round stacks more prompt text (applier.py:253-258 appends to the already-patched file). Prompt grows monotonically; no dedup or cap beyond per-patch 4000 chars (analyzer.py:263).
3. **Likely bug: evolved skills can hide all other skills when config uses the list form `skills: ["*"]`.** Applier only skips agents whose raw value is the string `"*"` (applier.py:205); configs in the repo use the list form (`configs/minimal_skill_task/deepseek-v3.2-example.yaml:91-92`). The applier then appends the evolved name giving `["*", "evo-..."]`; the playground exposes all skills only when the list is exactly `["*"]` (core/playground.py:978-983), so exposure becomes the explicit list (the `*` entry matches nothing). Inference from reading both code paths; not executed (we may not run third-party code).
4. **Noisy "issue" detection and gameable score.** Any tool output containing the word "error", "failed", "invalid", etc. counts as an issue (collector.py:17-22, 229-236). The run's "score" is the last number matching `score|metric: x` in log text or any `score` key in a `*metric*.json` / `result.json` in the workspace (collector.py:23-26, 128-158). Agent-written code can print or write such a file, so the evolve comparison (`score_delta`) is trivially spoofable by the agent being evolved.
5. **LLM-extracted validation scores drive search.** ml_master_2 asks a metric agent to read the terminal output and emit `\boxed{score}` (improve_exp.py:154-180); parse failure only flags unsuccessful. The score is whatever the agent's own code printed; hallucination or deliberate printing is possible. ml_master v1 uses an LLM review too (`build_review`, orchestrator.py:407; exp/__init__.py:114). The hard hidden-test grade happens only after search (ml_master v1) or never in the loop (ml_master_2: the grading server only validates submission FORMAT, improve_exp.py:45-77).
6. **Verifier fails open in ml_master_2.** If the grading server is unreachable the submission is "treated as valid by default" (improve_exp.py:67-72, and `_HAS_GRADING=False` returns True at 54-55). ml_master v1 fails closed (uct.py:620-626). Fail-open verifiers are an anti-pattern.
7. **Agent-written code runs on the host.** ml_master_2 `execute_bash` runs `python run.py` with a 86400 s timeout in the local session, no Docker allowed (improve_exp.py:123-131; playground.py:88-89). The repository also ships the competition's private `gold_submission.csv` and `private/test.csv` in the tree used as the run's data root (ml_master_2/data/.../prepared/private/*; `ground_truth_dir = os.getcwd()/data_root` playground.py:69). With no isolation, an agent can read the labels. [inference: depends on session symlink layout in `env/local.py`, which I did not read]
8. **Timeout via `PyThreadState_SetAsyncExc`** injecting a `BaseException` into worker threads (watch_dog.py:1-40; playground.py:478-484). Fragile: cannot interrupt blocking C/IO calls and can leave state inconsistent. Prefer subprocess + kill with checkpoint.
9. **Wisdom promotion only on timeout and never persisted** (Section 3). Anti-pattern: the "memory" step is on the failure path only, so successful runs teach nothing.
10. **Hand-rolled YAML frontmatter parser** (skills/base.py:57-119): a value containing `:` in a nested structure, lists, or quotes is parsed naively; the applier even writes the literal `license: null` (applier.py:135-140), which the parser reads as the string "null". Use a real YAML loader.
11. **Config-by-subprocess evolution** (manager.py:161-200) and stdout piping into the logger loses structured run results (return code only; digest is rebuilt by regex-scraping logs). Use in-process state objects/Evidence records.
12. **Prompt-injection surface**: evolved skill bodies and prompt patches come from an LLM reading raw tool outputs and workspace content (collector.py `log_excerpt` up to 80k chars, analyzer user prompt) and are then injected into the agent's SYSTEM prompt (applier.py:253-259) with no quarantine. An adversarial web page or file seen in a run could persist itself as a "skill". Our plan's skill quarantine (PLAN §8.4) is the right counter.
13. **Hard-coded paths and demo leakage**: `scripts/mlmaster_test.py:15-19` has the author's absolute paths; `prefetch_exp.py:86-91` leaves a commented hard-coded descriptor from the demo task; `run()` hard-codes `playground/ml_master_2/example_wisdom` (playground.py:200). No tests exist for the evolution package (`git ls-files | grep test`: only `agent/test_agent_context.py`, `pdf` helper and bench scripts).
14. **Tool-call bug risk**: in `_step`, if a `finish` call appears after other tool calls in the same assistant message, earlier calls run and the loop `break`s (agent.py:420-445) while later calls in the message get no ToolMessage; combined with the `ask_user` break (447-470) this can leave unmatched tool_call ids in the dialog. [inference; the code does add ToolMessages for the break cases themselves, but not for skipped sibling calls]

## 7. Verifier / evaluation / safety handling
- Evolution: no verifier. Compares digest metrics (status, score, step_count, tool/issue counts) between consecutive runs and logs them (manager.py:206-217); no decision depends on them.
- ML-Master v1: LLM-extracted validation metric per node (orchestrator.py:407 `build_review`), guards for metric direction and ratio bounds (uct.py:558-577, 733-751), format validation by an embedded Flask grading server (`grading_server.py`, `grading.py`; not read in depth), fail-closed. Final hidden-test grade by `mlebench grade-sample` is outside the search loop (good, no leakage into search) and best-effort ("mlebench grading failed (ignored)", ml_master/core/playground.py Step 4).
- ML-Master 2: LLM metric agent; grading server for format only, fail-open; no hidden-test grading in the code path I read.
- Sandbox: DockerEnv supports memory/cpu/cpuset/gpu limits, `--network` mode (default bridge), bind mounts, env vars, `--rm` (env/docker.py:520-610). No `--cap-drop`, `--read-only`, `--user`, `--security-opt`, no seccomp. Passing `env_vars` as `-e KEY=VALUE` in the command line exposes secrets to `docker ps`/logs (docker.py:593 plus the INFO log of the full command at 603-607 prints them). That log line is a secret leak.
- MCP: stdio/SSE/HTTP connections, path adaptor hook to rewrite args (mcp.py:96-120); no allowlist, no per-tool permissioning, no output sanitization beyond formatting (mcp.py:182). x_master / browse_master ship an `mcp_sandbox` (Python servers; not read).
- Exploit handling: none (no reward-hack detection, no quarantine of generated skills, no tamper checks on scorers).

## 8. Bottom line
- EvoMaster's "evolution" is a thin, single-task, un-gated overlay loop (LLM writes SKILL.md + prompt patches, rerun the same task); the paper's cross-run persistence and the headline benchmark numbers (58.02 avg, 75.76 MLE-Bench Lite, BrowseComp, PaperBench, HLE, Frontier Science) are NOT reproducible from this repo.
