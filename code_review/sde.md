## 1. What the code actually does (architecture map)
- `sde_harness/` is a small generic LLM-iteration library: `Generation` (LiteLLM wrapper), `Prompt` (templates + history), `Oracle` (registry of metric callables), `Workflow` (iterate: prompt -> generate -> oracle -> feedback). It is a scaffold, not a benchmark. There is NO question set in this repo.
- `projects/` holds nine separate project-level tasks, each with its own CLI and its own oracle subclassing `Oracle`: bio-discovery-agent (CRISPR gene screens, ground-truth CSVs), chat-mof, llmeo (transition-metal complexes, 1M-space CSV), llmsr (symbolic regression on llm-srbench via HuggingFace), matllmsearch (crystal structures, CHGNet e_hull), molleo (TDC molecule oracles), proteinoptimizer, synplanner (retrosynthesis), xray-spectral-fitting. The paper lists 8 projects incl. "Ising model solving"; I found no Ising project dir (grep "ising" hits only unrelated files: chat-mof/molleo prompts, sascorer, examples). [inference] the paper's project list and the repo's project list do not map 1:1 (repo has chat-mof and xray-spectral-fitting that the paper summary does not list).
- Question-level benchmark (1,125 Qs / 43 scenarios) lives elsewhere: per paper HTML data-availability, datasets at huggingface.co/deep-principle (science_chemistry/biology/physics/materials; HF org page shows 276/200/163/486-ish entries per download counts; license NOT stated on the org page) and eval code at github.com/deepprinciple/lm-evaluation-harness (a fork of EleutherAI's harness). I did NOT clone or read that repo; I did not verify the HF files.

## 2. Core loop, step by step
`Workflow.run` (`sde_harness/core/workflow.py:100-260`):
1. init history dict of lists (prompts, outputs, scores, raw_outputs, metadata, timing) (:140-150).
2. `for iteration in 1..max_iterations` (:170): build prompt (static or callable(iteration, history)), `generate`, record text.
3. `_execute_evaluation` (:370-409): `oracle.compute_with_history` (multi-round) or `oracle.compute` on (text, reference).
4. optional `stop_criteria(context)` callback (:238); else `_apply_iteration_feedback` writes `last_score/last_output/iteration_number` into the prompt vars (:433-450).
So the "closed discovery loop" in the generic harness is single-candidate prompt refinement with score feedback — not the evolutionary parent-sampling/crossover described in the paper. The evolutionary population logic must live in the per-project modes (e.g. `projects/llmsr/src/modes/evol.py`, molleo `ga/`); I did not read them. Oracle (`oracle.py:114-143`) dispatches registered callables; multi-round metrics (improvement_rate, consistency, convergence — :218-290) are trivial statistics over score history (convergence = word-overlap Jaccard of last 3 outputs, :258-275).
`Workflow.optimize_workflow` (:889-936) and `_generate_*_optimizations` are template recommendation stubs, not real optimization [inference from reading :889-936 only].

## 3. Paper/summary vs code discrepancies
- Summary says the harness "implements the iterative discovery loop" with mutation/crossover over sampled parents; the core `Workflow.run` is a single-chain prompt refinement (workflow.py:170-258). Population search is project-specific, not in core.
- Summary's 8 projects (incl. Ising) vs repo's 9 dirs without Ising (see §1).
- The repo contains no question-level benchmark, no SDE-Hard (86 Qs) list, no scoring scripts for the 1,125 questions. The summary conflates "SDE framework" with this repo; the benchmark data is in deep-principle HF + a lm-evaluation-harness fork.
- LICENSE is an unfilled template; citation bibtex in README is a placeholder ("SDE-Harness Team", year 2024) rather than the arXiv paper; README docs badge points to `https://your-docs-link`.

## 4. Mechanisms worth adopting — as a BENCHMARK for custom-harness (PLAN §10 axis E; §8.3)
1. **Question-level SDE set as an axis-E "scenario knowledge" probe (priority 1, effort S-M).** Access: HF `deep-principle/science_*` (public per org page; license unverified — we must read each dataset card before any redistribution; treat as eval-only, never train/evolve on it). Format [from paper summary + HF structure, not verified]: expert-written scenario-grounded questions, per-domain files, scored through lm-evaluation-harness YAML tasks (exact/multiple-choice style; the paper reports accuracy). Use: run frozen-model single-agent vs custom-harness-wrapped on the 1,125 Qs; report accuracy + CIs per domain, and the 86-question SDE-hard subset. Honest caveat: it is mostly knowledge QA, so it measures the base model more than harness quality; harness gains should be small, so use it as a no-regression sentinel and for cross-vendor error-correlation analysis (paper: Spearman > 0.8), which supports our judge-panel diversity requirement (PLAN §8.7). Layer: L3 eval adapter (`verify/`), L9 reporting. Copy-vs-reimplement: reimplement a tiny loader/scorer; do NOT vendor the lm-eval fork.
2. **Project-level oracle tasks as axis-D/E candidate tasks (priority 2, effort M-L).** Several have genuinely hard, non-LLM verifiers: llmsr (NMSE via BFGS-fitted parameters on llm-srbench, `projects/llmsr/src/core/oracle.py:_calculate_nmse`), matllmsearch (CHGNet e_hull, `materials_oracle.py`), molleo (TDC oracles), llmeo (lookup in a 1M TMC space; "find optimum in 100 proposals from 1.37M" is a clean sample-efficiency metric). Each is a T1-trusted-metric task in our tier model (`tiers.py`). Fit: yes for axis D ("improvement over best-known/baseline under a fixed proposal budget"). Heavy deps (CHGNet, pymatgen, RDKit, GPU, 100+ MB data) mean these run only inside our Docker sandbox; effort L each. License MIT repo-wide, but each project inherits upstream licenses ("follows the corresponding license" in llmeo/molleo READMEs, Apache-2.0 Potts code in proteinoptimizer, snap-stanford MIT in bio-discovery-agent LICENSE) — copy glue code with attribution only after checking each project's upstream license; data files need separate checks.
3. **Time-split rediscovery set (§8.3): SDE is NOT a source.** The tasks are expert-written and have no publication dates or "later literature" ground truth. No use beyond the methodological lesson (scenario-grounding + expert vetting). Do not claim SDE supports T4.
4. **Cheap borrowable idea (effort S):** report "optimization-trajectory" metrics (best-so-far vs #proposals, improvement rate) for project-level tasks. We already have racing/CI; adopt only the metric definitions. Do not copy their `improvement_rate` (`oracle.py` improvement_rate_metric: `(last-first)/n`, not best-so-far, ignores non-monotone runs).

## 5. Things custom-harness already does better
- Verifier rigor: SDE oracles are raw callables with no tier labels, CIs, seeds or paired tests; we have T0-T6 tiers, bootstrap + paired test-example bootstrap (`verify/`, STATUS L3).
- Budgeting/cost: SDE core logs timing and Weave traces only; no budget ledger or hard caps; we have L1 (`budget.py`).
- Sandboxing: see §7; we use Docker with no network, read-only rootfs.
- Trace/fork/checkpointing (L0 `runtime/`) vs. SDE's in-memory history dict with no resume.

## 6. Pitfalls / anti-patterns in their code
- `Oracle.compute` catches `TypeError` from a metric and silently re-calls it without kwargs (`oracle.py:~143-150` and compute_with_history `~177-181`): a real TypeError bug inside a metric is masked and rerun with different arguments. Avoid.
- `exec(equation_code, exec_globals)` on LLM-written code in the host process (`projects/llmsr/src/core/generation.py:161`), with a hand-built globals dict but no `__builtins__` restriction, no timeout, no resource limits: not a sandbox. `exec_globals` leaves builtins available by default, so arbitrary code (file I/O, imports) is reachable. Never reuse this path outside our Docker sandbox.
- Failure encoded as `float('inf')` (nmse oracle returns inf for unparsable/failed code) mixes invalid outputs with scores; downstream aggregation can produce inf/NaN means.
- Repo size: ~97 MB of datasets/results (e.g. `synplanner_results.tar.gz`, molleo 94 MB) in git; third-party data mixed with MIT code.
- Reproducibility: paper itself admits provider-side drift; no seeds/temperature pins enforced by the harness [paper-stated limitation; not checked in generation.py].
- Placeholder LICENSE holder/citation/docs link (see §3).

## 7. Verifier / evaluation / safety handling
- Question level: delegated to lm-evaluation-harness fork (not read). Project level: domain oracles (RDKit/TDC, CHGNet, NMSE fit, TMC lookup, gene-screen ground-truth CSV). Oracles are "hard-ish" (computational) but are surrogate models (CHGNet, TDC predictors), so they can be exploited (generate structures/molecules that fool the surrogate); no exploit quarantine or perturbed evaluator. No held-out/sealed split concept; no contamination defenses (paper's own analyst limitation: benchmark capture risk).
- Code execution: in-process `exec` (see §6); no isolation.

## 8. Bottom line
- SDE is mostly two things we can use: (a) public question sets on HF (license unverified; eval-only, knowledge-heavy, good for a no-regression sentinel + error-correlation study), (b) a handful of oracle-backed project tasks that are real axis-D/E material but heavy to set up.
- The repo itself is a thin, loosely-engineered scaffold: do not adopt its Workflow/Oracle code; adopt only task definitions and metrics, behind our sandbox and tiers.
- It cannot seed the time-split rediscovery set (no dates, no later-literature ground truth).
- Before any use: read each HF dataset card for license, and re-check deep-principle/lm-evaluation-harness (unread by me).
