## 1. What the code actually does (architecture map)
**Headline: this repo is not the paper's research pipeline.** It is a general-purpose "self-evolving research agent" product: a LangGraph/deepagents CLI+TUI+WebUI with chat-channel bridges (`channels/`), an MCP client, scheduled tasks, and an "EvoMemory" subsystem. The paper's named components (Researcher / Engineer / Evolution Manager agents, ideation memory M_I, experimentation memory M_E, Elo tournament, four-stage experiment loop) do not exist as code here (section 3).

What does exist:
- **Orchestrator + subagents** declared in YAML: `subagents/{research,code,data_analysis,debug,planner,writing,scheduler}.yaml`. Orchestration is prose in `prompts.py` ("Experiment Workflow", lines 44-120): the LLM is told to plan, delegate through the `task` tool, and optionally follow a skill sequence `research-ideation -> paper-planning -> experiment-pipeline -> paper-writing -> paper-review -> paper-rebuttal` (`prompts.py`, "Research Lifecycle"). Those skills live in a separate repo (EvoSkills, installed on demand: `commands/implementation/skills.py:145,170`); only `skills/find-skills` and `skills/skill-creator` are bundled. So the ideation, ranking and experiment-pipeline logic is NOT in this repo and I could not review it.
- **EvoMemory**, file-backed (markdown + YAML frontmatter), no database, no embeddings:
  - Profile memory: `/memories/profile/{SOUL,USER_PROFILE,RESEARCH_TASTE}.md` plus a per-project profile (`middleware/memory.py:53-77`).
  - Observation memory: one small markdown file per observation under `/memories/observations/global/` or `/projects/<id>/` (`store.py` `_memory_path`).
  - Execution summaries per subagent run under `/executions/<session>/...` (`memory_worker.py` `_write_subagent_summary`).
- **Background LLM workers** (`memory/agents/`): turn worker and subagent worker (decide whether to call `record_observation`), observation linker (adds typed edges), AutoSkills agent (clusters observations, drafts skills for human approval).
- **Observation schema** (`store.py:92-146`, `types.py`): `id` (`O-` + 16 hex of sha256), `created_at`, one-line `summary`, `memory_type` in {semantic, procedural, episodic}, `scope` in {global, project}, `project_id`, `source{type, agent, session_id}`, `related_observations[{id, relation, reason, linked_at}]` with relation in {complements, contradicts, supersedes} (`types.py` `ObservationRelation`). Body sections: "Observation", "Why It Matters", optional "Evidence" (`store.py` `_format_observation_markdown`).

## 2. Core loop, step by step (the memory loop is the only self-improvement loop in the code)
1. **Write trigger**: after an orchestrator turn or a subagent run, a background memory-worker LLM reviews a sanitized trajectory; the turn worker deliberately does not see subagent transcripts (`memory_worker.py` `_review_scope`). Scheduling is in `memory/scheduler.py` (not read); `middleware/memory.py:586` calls `scheduler.record_observation_created`.
2. **Admission is a prompt policy only**: save "durable, non-obvious, evidence-backed, not already present in memory, likely to change future behavior" (`memory_worker.py` `_goal`; `middleware/memory.py:102-118`). Failed approaches are in scope only as one clause: "failed approaches future agents might repeat" (`memory_worker.py:176`, `middleware/memory.py:105`). There is no negative/dead-end type, no outcome or validation field, and no link from an experiment result to a memory write. Nothing verifies that an observation is true.
3. **Dedup**: id = sha256 of (type, scope, whitespace-normalized lowercase observation, why_it_matters) (`store.py:148-170`); `record_observation_file` (line 682) skips the write if the file exists. Catches only near-verbatim duplicates.
4. **Linking**: a second LLM agent reads new ids, searches/reads candidates, and calls `link_observations` with a relation and reason (`observation_linker.py` prompt). `supersedes` is directional and never mirrored (`relations.py:30`); `complements`/`contradicts` are written on both files by default. Superseding does NOT remove or demote the old observation from search or from the index (I read `search.py` and `index.py`: no relation-aware filtering); the edge only appears as `related_observations` on hits.
5. **Read path**: an injected `<observation_memory>` block lists every observation as `id [type/scope] path: summary`, newest first, truncated to 12,000 chars (`index.py` `DEFAULT_MAX_INLINE_OBSERVATION_INDEX_CHARS`, `_truncated_observation_index_context`). Tools `search_observations` (ranked or regex) and `read_memory` are provided. A "Required memory preflight" is instructed in the prompt, including stating which observation ids were used (`middleware/memory.py:84-99`); it is not enforced in code.
6. **Ranked search** (`search.py`): no embeddings. ASCII words >=3 chars plus CJK bigrams; smoothed IDF over the current corpus (`_token_idf`, line 153); score = sum over query tokens of IDF x {5.0 id, 3.0 summary, 1.0 body else 0.5 metadata} (`_ranked_score` line 165; constants lines 18-21). Whole corpus is re-scored each query; parsed files are cached in an LRU keyed on (mtime_ns, size), cap 2048 (`store.py:393`, `settings.py:369`).
7. **Distilling into skills (AutoSkills)**: connected components of the observation link graph (all three relations treated as undirected) with >=3 observations and >=2 procedural become candidates (`candidates.py:20-21,180-182`); cluster hash = hash of sorted ids; an LLM drafts a skill folder; `submit_autoskill_proposal` (`proposals.py:394`) creates a `pending` proposal; a human approves or rejects (`approve_skill_proposal`, line 563). Approved/rejected/processed cluster hashes are not re-proposed.

## 3. Paper/summary vs code discrepancies
| Paper / summary claim | Code reality |
|---|---|
| Three agents RA / EA / EMA | None. Subagents are code, data_analysis, debug, planner, research, writing, scheduler (`subagents/`). Memory workers are not an Evolution Manager with idea/validation/strategy modes. |
| Ideation memory M_I, embedding-similarity retrieval | No ideation-specific store. Retrieval is IDF-weighted keyword overlap (`search.py`). I grepped for embedding/cosine/faiss/bm25/fts5 and found no retrieval use. |
| Experimentation memory M_E retrieved by proposal content | No separate M_E. Nearest analogue is `MemoryType.PROCEDURAL`; retrieval is by queries the agent chooses, not keyed on the proposal. |
| Idea Direction / Idea Validation Evolution (failed directions recorded when validation fails) | Not implemented. No path from an experiment outcome or review result to a memory write. Failed approaches appear only as a prompt hint (`memory_worker.py:176`). |
| Experiment Strategy Evolution from successful code trajectories | Not as described. Closest is AutoSkills clustering of procedural observations (`candidates.py`), human-approved. |
| Elo tournament on novelty / feasibility / relevance / clarity | Not in this repo. The only mention is a sentence in the system prompt suggesting `task()` fan-out for "ELO-style tournaments" (`prompts.py:346`). No rating code. The `research-ideation` skill that may implement it is in the external EvoSkills repo, which I did not read. |
| Four-stage engineer loop with execution feedback | Not in code. "More Effort" mode delegates to an external `experiment-iterative-coder` skill (`prompts.py`, "Code Generation Mode Selection"). Not reviewed. |
| Execution success improves after evolution | No evaluation of this in the code I read (tests not read). |
| Cross-task memory improves later tasks | Mechanism exists (global-scope observations), but nothing measures whether retrieval helped. |

For our focus (idea memory, experiment memory, Elo), the interesting science is in the paper, not the repo. The repo is a generic agent-memory substrate.

## 4. Mechanisms worth adopting into custom-harness (ranked by expected value)
Our state: `MemoryEntry` exists only as a PLAN line (PLAN.md:70); L5 is "Next" item 3 in STATUS.md; no memory code exists in `src/custom_harness/`. Our tournament is `research/modules.py:118-157` (K-way shuffled rankings to `verify/ranking.py` `bradley_terry`).

1. **Typed entry with summary, why-it-matters and a content-hash id** (`store.py:148-170`, `_format_observation_markdown`). Forces each entry to state the decision it changes; dedup is free and race-safe. PLAN's `MemoryEntry` has kind/content/evidence_ids but no searchable summary or why field, and no global-vs-task scope. Layer: L5 over L2 `records`. Effort S. Reimplement (Apache-2.0 would allow copying with attribution, not needed).
2. **Typed relation edges with reason: complements / contradicts / supersedes** (`types.py` `ObservationRelation`, `relations.py:30,62-156`). PLAN L5 has no contradiction or supersession handling, which revivable dead-ends need (a dead-end re-scored when new evidence arrives). Improve on theirs: make `supersedes` demote the target in retrieval, and let a `contradicts` edge connect a dead-end to the evidence that revived it. Layer: L5. Effort M. Reimplement.
3. **Inlined compact index plus on-demand `search`/`read` tools, truncated by budget** (`index.py`). Cheap, auditable, no embedding infrastructure. Pair it with our read-audit (PLAN L5) by logging every read and search hit; EvoScientist has no usage counters (grep for read_count/last_read/hit_count found nothing). Layer: L5 + context policy. Effort S. Reimplement.
4. **IDF field-weighted keyword ranker as the zero-dependency baseline** (`search.py:153-190`, weights 5/3/1/0.5). Gives a deterministic baseline to ablate embeddings against, which PLAN section on required ablations demands. Layer: L5. Effort S (about 60 lines of core logic). Copy with Apache-2.0 attribution or reimplement; CJK bigram code is not needed.
5. **Cluster the link graph, then propose a playbook, human-gated, with processed-cluster hashes to avoid re-proposing** (`candidates.py:20-21,134-221`, `proposals.py:394,563`). Maps to our playbook-with-maturity kind. Improve: gate promotion on exploit quarantine and the tier floor (PLAN L5 admission rule) and require evidence ids, not just observation ids. Layer: L5/L6. Effort M. Reimplement.
6. **Memory-writer isolation**: writers see a sanitized trajectory and have execution/delete/task tools removed (`memory_worker.py` `_MEMORY_WORKER_EXCLUDED_TOOLS`, `_review_scope`, `_subagent_guardrail`). Keep the idea, but where possible write memory deterministically from our own typed outcomes (verdicts, tiers) rather than from an LLM reading a transcript. Layer: L5 admission. Effort S.
7. **What the paper claims but the code lacks, which we should build ourselves** (paper summary only, unverified in code): outcome-conditioned writes (failed validation creates a dead-end entry; top-ranked ideas create direction entries) and retrieval keyed on proposal content. We already own verifier tiers and an evidence store, so the rule can be: a dead-end entry is created automatically when a hypothesis fails its tier floor, linked to the Evidence id and snapshot, and retrieved into the hypothesize prompt and the tournament prompt (L4 steps 4-5). This beats prompt-hint admission. Layer: L5 + L4. Effort M.

Elo: nothing to adopt, since their tournament is not in the repo. Our batch Bradley-Terry on shuffled K-way rankings is order-independent and better founded than online Elo. The paper's four criteria (novelty, feasibility, relevance, clarity) could be ranked as separate judge calls and aggregated; [inference] cheap to add, but the paper's evidence of benefit is unverified.

## 5. Things custom-harness already does better (with evidence)
- **Ranking**: batch Bradley-Terry with a prior, shuffled presentation, rejection of non-permutation outputs (`modules.py:134-147`, `ranking.py`). EvoScientist's code has no ranking.
- **Evidence-grounded records**: claims only from evidence, failed attempts costed (STATUS.md L0/L2). Their memory writes are unverified LLM judgments with an optional free-text evidence field (`tools.py` `RecordObservationArgs`).
- **Exact snapshots and revivable dead-ends** (PLAN L5, STATUS L0): they have no run-state restoration tied to memory.
- **Private-data guard, held-out gate, exploit awareness** (STATUS L4/L6): nothing equivalent in their memory path.
- **Read-audit design** (PLAN L5): theirs tracks no usage, so low-value observations accumulate until the 12k-char index truncation drops the oldest.
- **Sandbox**: ours is Docker, no network, non-root (STATUS L0); theirs is a command-string blocklist on the host (section 7).

## 6. Pitfalls, bugs, or anti-patterns seen in their code that we must avoid
- **Paper-code gap**: the self-evolving idea/experiment memory is carried by prompt text, not mechanism (section 3). Do not build L5 as a prompt telling the LLM to remember.
- **Retrieval depends on the agent choosing to search**: the preflight is instructed only (`middleware/memory.py:84-99`); no enforcement and no hit-rate measurement. Our L5 must inject retrieved entries through the node input contract and log reads.
- **Recency-only index truncation** drops the oldest entries past 12k chars (`index.py` `_truncated_observation_index_context`), so early high-value negative results vanish from the prompt. Order by importance/outcome, not just recency.
- **Cosmetic supersession**: `supersedes` does not hide or demote the old entry (`search.py`, `index.py` have no relation filtering); contradicted entries rank equally.
- **Exact-text dedup** (`store.py:148`): paraphrases proliferate, and the id also hashes `why_it_matters`, so the same fact with a different rationale is a separate entry.
- **Keyword-only retrieval with hand-set weights**, full-corpus re-score per query, no synonym handling; differently phrased dead-ends will not match.
- **LLM-judged admission** has no ground truth; a hallucinated "verified outcome" can be stored. Evidence is optional free text.
- **Two YAML writers for one format** (`_format_frontmatter` string building vs `yaml.safe_dump` in `write_observation_document`), and link updates rewrite whole files under an in-process `threading.Lock` (`relations.py` `_link_write_lock`), which does not protect against multiple processes.
- **Human approval is the only gate for distilled skills** (`proposals.py` `approve_skill_proposal`): no quarantine or test before install, which is the poisoning/reward-hack path our PLAN section 8.4 closes.

## 7. Verifier / evaluation / safety handling
- No result verifier, held-out evaluation or exploit handling for research results in the files I read; tests were not read, so I cannot rule out test-level checks.
- Code execution: `CustomSandboxBackend(LocalShellBackend)` (`backends.py:1628`) runs on the host and pre-validates the command string: `..` traversal, forbidden path regexes, destructive patterns, a `BLOCKED_COMMANDS` set, absolute-path extraction, workspace-rooted virtual paths (`backends.py:990-1030`, `prepare_sandbox_command` 1551, `execute` 1766-1795). This is a string blocklist, not isolation; I saw no container or network restriction in the lines read, so "sandbox" overstates it. `dangerous` and `auto_approve` modes loosen it, and with HITL suppressed "the backend is the only gate" (`_effective_guard_dangerous` docstring, ~line 1805).
- HITL approval interrupts exist for risky tool calls and are suppressed under `auto_mode`/`auto_approve` (`backends.py:365-452`).
- Injection hygiene: memory workers are told to treat tool and subagent output as data and have execute/delete tools removed (`memory_worker.py`). The AutoSkills agent runs `execute` in a proposal-scoped backend (`AutoskillProposalSandboxBackend`, `backends.py:1982`; not read in depth).
- Honesty norms ("never invent data, citations, or results") are prompt-level only (`prompts.py`).

## 8. Bottom line
- The repo is a product shell (CLI, channels, MCP) around a keyword-searched markdown memory; the paper's M_I/M_E, Elo tournament, four-stage engineer and failed-direction recording are not in the code (ideation skills sit in an unread external repo, EvoSkills).
- Take: typed entries with summary + why-it-matters + hash id; complements/contradicts/supersedes edges; inlined index + search/read tools; IDF keyword baseline; gated promotion of memory clusters to playbooks. All small; reimplement (Apache-2.0 permits copying with attribution).
- Do better: automatic failed-direction writes from verified outcomes with evidence ids, supersession/contradiction that affects ranking, enforced and logged reads (read-audit), keep our Bradley-Terry tournament (no Elo needed).
- Do not rely on the paper's numbers or the "self-evolving" claim; nothing in the repo measures memory benefit.
