## 1. What the code actually does (architecture map)

Prime Agent is a coding-agent product (TUI + background daemon + Python REPL kernel), not a research-experiment framework. The repo contains **no code for any experiment in the paper**: a word-boundary grep for factorio / nanogpt / rcon / arc-agi / emulatorbench / speedrun finds nothing (the only "oolong" hits are a test string "All about oolong brewing" in `prime-agent-runtime/test/test_harness.py:1384`). There is no benchmark runner, no verifier for nanoGPT records, no RCON anti-cheat heartbeat. The 85.5 h / Factorio results cannot be reproduced from this repo.

Process model:
- `pa-daemon` runs a **supervisor** (`supervisor/`) plus one **worker** process per session (`worker/`), each hosting an `AgentSession` (`pa-core/src/session_engine`). Worker descriptors let a restarted supervisor adopt live workers or revive ones that crashed mid-turn (`supervisor/adoption.rs:20-63`: `AdoptionBoot::PlainStartup` revives only "journal-proven live work"; outcomes AdoptedLive / Revived / SkippedIdle / Stopped / Failed).
- Each session owns an IPython **kernel** (Python). The only built-in model tool is the Python REPL (README "Everything is programmatic"). Subagents, messaging, refine, compact, goal, heartbeat are all Python calls through `host_request(...)` (`rlm/repl.py:166`) to the Rust host.
- Memory hierarchy as realized in code (our mapping of the paper's L0-L3):
  - L1 context = the model's token window, managed by compaction: `DEFAULT_RESERVE_TOKENS=16_384`, `DEFAULT_KEEP_RECENT_TOKENS=20_000` (`compaction.rs:9-10`), LLM summary in a fixed format `## Goal / Constraints / Progress / Key Decisions / Next Steps / Critical Context` (`compaction_utils.rs:457`), plus a 2000-char "recent state anchor" (`compact_session/recent_state_anchor.rs:8`).
  - L2 = the persistent kernel namespace (`rlm/repl.py`) and child sessions. Kernel survives compaction; on session resume the namespace is rebuilt from a per-variable `dill` snapshot (`kernel-state.dill` + `.json` manifest, `kernel/state_snapshot.rs:12-14,36-40`; caps 256 MiB total / 16 MiB per variable). Unpicklable or oversized variables are skipped and reported (`repl.py:845-864`), and a compaction-time snapshot can PRUNE oversized live variables (`repl.py:764-770`, `session_engine/ipython_state.rs:181-218`), which is the "agentic garbage collection".
  - L3 = disk: (a) the append-only JSONL session tree with per-row sync (`session/window_cache.rs:203 sync_data`, `session/manager/persist.rs:148-171` temp + fsync + rename); (b) the **continual harness** `harness_state.json` (global at `<agent_dir>/harness/`, local per session) holding five entry kinds: prompt, memory, skill, subagent, factory (`refinement/mod.rs:11,57-75`); (c) `refinement_history.jsonl` global log (`mod.rs:415-430`).
- There is no promotion/eviction policy between tiers beyond: (i) compaction when the window crosses a threshold, (ii) the refine pass, and (iii) top-k relevance ranking of harness entries into the system prompt (below). No frequency/recency/importance score, no TTL, no read counting.

Harness entry representation (`HarnessEntry`, `refinement/mod.rs:57-75`): `id, kind, title, content, path, scope(local|global), reference{}, arguments{}, metadata{}, source, created_at, updated_at, version:u64`. Exact text is stored in full on disk; what the model sees is lossy: the digest renders only the top `DEFAULT_OVERVIEW_ENTRY_LIMIT=3` entries per kind, each content truncated to 140 chars (`mod.rs:19-21`, `ranking.rs:200-375`). Ranking is lexical IDF-weighted term overlap against goal/recent messages (`ranking.rs:112-179`; Python twin in `harness.py:1141-1206` adds `updated_at` recency as tie-break). No embeddings. The model is told to call `harness.search` / inspect for detail.

Skills: two different things share the word.
1. File skills (`SKILL.md` directories, Agent-Skills standard). Loaded from project / user / package / built-in dirs; first name wins; validation is name-format and non-empty description only (`skills/mod.rs:12-15`, `skill-creator/SKILL.md` Frontmatter table). Python-backed skills are `uv`-installed into the kernel venv; the "hash" logic in `kernel/bootstrap/venv/skills.rs:16,45-81` and `venv.rs:185-224` is `pyproject_hash` for cache invalidation, not an integrity or admission check.
2. Harness `skill` entries (created by `/refine` or by kernel code). These are **descriptors** (title, content, `reference={"type":"python","import":..,"callable":..}`, `arguments`), rendered into the prompt as `ref=... args=...`. README line 102 states explicitly that refine "does not replace packaging and reviewing new executable skills". So an auto-refined skill entry names a callable; it does not by itself add code. But it persists a procedure ("how to do X, call this") into every future prompt.

Recursion and messaging:
- `rlm.spawn(prompt, name=, model=, thinking=)` sends host request `rlm.run` and returns once the child is *admitted*, not finished (`rlm/__init__.py:170-193`). Each child is a full session (own worker, kernel, session dir): `create_child` passes `rlmDepth`, `rlmMaxDepth`, `sessionDir`, `parentSessionPath` (`rlm_children/lifecycle.rs:56-125`). **`DEFAULT_RLM_MAX_DEPTH = 2`** (`rlm_children.rs:42`), settable via settings (`settings/types.rs:309`), persisted per session as `rlm_max_depth_state` (`agent_engine/goalcore.rs:12-30`).
- Spawn topology is an append-only JSONL **ledger** (`rlm_ledger.rs`: spawn/rename/delete records, `RLM_LEDGER_MAX_BYTES=32 MiB`, `MAX_RECORDS=100_000`, replay skips malformed lines, `rlm_ledger/replay.rs`), so non-resident children stay visible after passivation.
- `agent_message.send(message, receiver_role=parent|sibling|child, receiver_name)` goes through the daemon; sender identity is daemon-derived (`skills/agent-message/SKILL.md` Safety); limits `DEFAULT_AGENT_MESSAGE_MAX_CHARS=16_384`, `MAX_PENDING_PER_SESSION=20`, token bucket capacity 3 refilling 1/s (`session_engine/agent_messaging.rs:19-27`). Delivery is always "steering" (a busy target sees it mid-run); sending to an idle completed child wakes it for a follow-up turn. Reach is nuclear family only (parent, siblings, direct children).
- `rlm.factory` (`rlm/factory.py`, 4729 lines) runs declarative state-machine workflows of subagents (guards, joins, foreach, retries, `failure_policy` fail_fast/continue/escalate default escalate, `max_parallel` default 8, `budget_ms` per state and run). Opt-in, default off (`refinement/mod.rs:145-176`). **Runs live in kernel memory only** (docstring at `factory.py` near line 560: "Runs live in kernel memory only; children stay supervisor-owned"). Budgets are wall-clock `budget_ms`, not tokens.

Long-run control: three layers. `/goal` (persisted `thread_goal_state` entries, token budget, `budget_limited` state, `goal_driver.rs`), `/autonomous` (limits `DEFAULT_MAX_CONTINUATIONS=3, MAX_TURNS=12, MAX_TOKENS=80_000, TIMEOUT=30 min`, `autonomous/mod.rs:23-28`; user-defined shell gates run via `bash -c` in the session cwd, `gates.rs:57-65`; gate pass stops the run; retries default 3), and heartbeats / cron (`cron/`, `skills/rlm-heartbeat`). These defaults are tiny; the 85 h run necessarily used overrides (`UNLIMITED_AUTONOMOUS_LIMIT` sentinel exists, `mod.rs:33`), and the repo gives no recipe for them.

## 2. Core loop, step by step (with file:line citations)

Session turn (our reading; the turn loop itself is spread over `pa-agent`, `agent_engine/turn/`, which I only skimmed):
1. Build system prompt = immutable base prompt + skill list (names/descriptions only, per `skill-creator/SKILL.md` intro) + harness digest (`format_harness_state_for_prompt`, `ranking.rs:200`) with query terms from goal and recent messages.
2. Model emits Python cells; kernel executes in the persistent namespace (`repl.py:646 _handle_execute`).
3. After each settled turn, `AutonomousDriver::after_turn` (`autonomous/driver.rs:66,107`) runs gates then checks limits (`gates.rs:80-120`): gates passed => stop; retry-exhausted => stop; limit reached => stop; else inject the continuation prompt.
4. If context crosses the threshold (`compaction.rs:146-193`), compaction runs: LLM summary replaces older rows (the JSONL keeps them, `first_kept_entry_index`, `compaction.rs:378`), the kernel prunes oversized variables and writes a snapshot, and on success arms the compact-trigger auto-refine (`auto_refine_trigger.rs:67-90`).

Continual-harness refine (the self-improvement step):
1. Trigger paths: user `/refine`; model-called `await refine.run(instructions, global_)` (`skills/refine/src/refine/__init__.py:28-50`, runs at turn end, never mid-cell); automatic: after compaction, every `turn_interval=25` turns, with 20 min cooldown (`session_engine/refine.rs:37-53`, **defaults enabled=true, compact=true**). Only depth-0 sessions with a local harness dir may auto-refine (`auto_refine_trigger.rs:60-62`, `wiring.rs:179`); child sessions do not.
2. Review gate: an LLM call (`review_auto_refine`, `refinement/executor.rs:361-400`) with `AUTO_REFINE_REVIEW_SYSTEM_PROMPT` (`planner.rs:13`): "Reject one-off noise, unsupported hypotheses, and transient tool outputs... approve when the trajectory contains evidence useful to this session's future turns." Same model family as the agent; sees the last 40k chars of the conversation + harness overview + last 20 history items (`executor.rs:369,92-99`).
3. Plan: second LLM call returns JSON `{summary, rationale, expectedOutcome, edits[{action,kind,id,title,content,path,reference,arguments,metadata,reason}]}` from `REFINEMENT_SYSTEM_PROMPT` (`planner.rs:11`), conversation tail-capped to 80k chars (`executor.rs:230`). Prompt tells it: prefer small evidence-backed edits, local by default, global only for stable cross-session lessons; "never edit source files".
4. Apply (`planner.rs:318-509`): per edit, `validate_edit` (`planner.rs:198-290`) checks only structure (base prompt not editable; id/title/content present; skills need `reference.type=="python"` + import + callable and an `arguments` object; factory needs exactly one of dag/machine objects). Then an optimistic-concurrency check: if the entry changed since planning started (`baseline_state`), the edit is rejected "entry changed during refinement planning" (`planner.rs:371-380`). Then create/update/delete with `version+1`, `source:"refine"`.
5. Persist: atomic write of the store, append to `refinement_history.jsonl` (global scope only; local history lives in session rows), append a `REFINEMENT_AUDIT_CUSTOM_TYPE` session row with full before/after snapshots, an outcome row for the TUI, and a model-visible notice row (`refine.rs:438-475`).
6. Rollback: `/refine` with `rollback_id` builds the inverse proposal from stored before/after snapshots (`planner.rs:513-555`), applies it through the same path; the inverse is itself a recorded refinement.

Kernel-direct path (important, bypasses steps 2-3): the model can call `rlm.harness.create_memory / create_skill / create_prompt_note / create_subagent(..., global_=True)` directly (`rlm/__init__.py:622,681`; `harness.py:712-960`). These write through `_validate_entry_shape` (types/non-empty strings, Python reference for skills, factory opt-in gate; `harness.py:301-357`) and `save()` (atomic, 0600; `harness.py:521-553`). No review model, no evidence requirement, no scope restriction (a local-scope agent can write global).

Resilience mechanics: multi-process write safety via `_sync_from_disk` mtime check before every kernel write (`harness.py:421-433`); host side applies "baseline" CAS (above); state file loads degrade to empty on corruption (`mod.rs:178-232`) so "prompt builds run on every turn" never throw.

## 3. Paper/summary vs code discrepancies

| Paper / summary claim | What the code shows |
|---|---|
| "Each update creates a versioned artifact enabling rollback and A/B testing" | Versioning exists: `version` counter per entry, before/after snapshots in the refinement result, rollback via inverse proposal (`planner.rs:513`, `mod.rs:307-354`). **A/B testing: not implemented.** Nothing evaluates a refinement's effect; `expectedOutcome` is stored text only and never checked. The history shows the prompt asks the model to "validate" but no code does. |
| L2/L3 hierarchy with "agentic garbage collection" | L2 persistence exists and is real (dill snapshots, prune of >16 MiB variables). GC is only size-based pruning at compaction (`repl.py:764-870`); the model's "garbage collection" is its own discretionary `del`. |
| "Background model calls: trajectories converted to state without blocking execution" | Auto-refine runs at quiescent turn boundaries and holds the session lock during apply (`refine.rs:408-424` comment: "the refine arm holds the session lock across this whole call"); an approved review during streaming is deferred (`AutoRefineRound::Deferred`). Not concurrent with a running turn. |
| Anti-cheating heartbeat / RCON skill capture (paper: agent "preserved it as a reusable skill") | No skill-admission check, no exploit detection, no human-review gate on refine in the repo. The only safety text is README warnings (README:84-85, 102). Nothing Factorio-related exists here. See section 7. |
| "Agents View lets humans attach/inspect/redirect" | Present (`pa-tui/src/agents_view*.rs`), not read by me beyond file names. |
| "Unified accounting: single ledger across root and descendant sessions" | Partially. Child usage is attributed post hoc by polling the child's session JSONL and writing `child_usage_attributed` rows into the parent (`rlm_children/usage.rs:1-60`; goal driver comments mention "child-usage attribution landing late", `goal_driver.rs:35-40`). So budgets are eventually consistent, not preemptive across the tree. The RLM ledger records topology and deleted-child usage snapshots (`rlm_ledger/replay.rs:19-70`), not a global spend ledger. |
| "Append-only event histories recording all model calls" | Session JSONL is append-only per session (`append.rs:11-40`); I did not find an immutable content-addressed event log across sessions. Rewrites (compaction/repair) use temp+fsync+rename (`persist.rs:148`). |
| "Transparent verifier handling: standardized processing of test outputs" | The only verifier concept is the autonomous shell gate (`gates.rs`): exit code of user commands, output capped at 6000 chars to the model (`gates.rs:14`). No test-output parsing standardization seen. |
| 85.5 h nanoGPT run, 19 validated records | Not reproducible from repo; default autonomous limits (12 turns, 80k tokens, 30 min) are far below that; the repo does not ship the evaluation configuration. |
| Experiments with three named models | Out of scope for code; model selection is generic provider plumbing. |
| Heartbeats as cron, goals, autonomous mode | Implemented (`cron/`, `goal_driver.rs`, `autonomous/`). |

## 4. Mechanisms worth adopting into custom-harness (ranked by expected value)

All MIT: code may be copied with attribution, but it is Rust/Python-glue tightly coupled to their daemon, so reimplementing the small ideas in our Python core is cheaper than porting.

1. **Optimistic-concurrency baseline on memory/skill edits** (`planner.rs:365-380`, `harness.py:421-433`). Plan against a captured baseline state, re-read the store after the (long) LLM call, reject any edit whose target changed ("entry changed during refinement planning"). Our `MemoryEntry` (PLAN §3) and L6 spec edits will have the same race with multiple islands/agents. Ours: nothing yet (no L5 code; `evolve/edits.py` applies edits to a spec, grep shows no memory module). Layer: L5/L6. Effort S. Reimplement.
2. **Before/after snapshot + inverse-proposal rollback as a first-class operation** (`mod.rs:307-354`, `planner.rs:513-555`). Every applied edit stores `before` and `after` entries; rollback is just another auditable edit, recorded with `rollback_of`. Better than ours as far as lineage goes only if we store before/after; our lineage plan records rejects but the Edit record in PLAN §3 has `diff` only. Layer: L5 + L6 (and the harness-science ledger). Effort S. Reimplement.
3. **Scope split (local = session, global = cross-session) with read-only global from local planning** (`planner.rs:11` prompt policy; `mod.rs:241-283` merge with `local:`-prefixed collisions; `executor.rs:231-235`). Gives a built-in blast-radius control for memory: nothing becomes cross-campaign without an explicit promotion. Note their enforcement is prompt-only on the LLM path and absent on the kernel path (see section 6), so we should enforce in code. Maps onto PLAN L5 "admission rule" and our promotion step (positive memory -> playbook). Effort S. Reimplement.
4. **Typed per-kind entries with a Python-reference contract for skills** (`planner.rs:227-261`, `harness.py:207-224`): a skill must name an import and callable and declare an `arguments` schema; subagent specs and factory specs are first-class. A cheap structural precondition we can *extend* with our tier gate (their validation stops at structure). Layer: L5 Skill record (PLAN §3). Effort S. Reimplement.
5. **Content-addressed state-exact snapshot of the interpreter namespace with per-variable fault isolation** (`repl.py:764-870,1063-1125`, `state_snapshot.rs:12-40`): per-variable dill with per-variable and aggregate size caps, skipped-and-reported list, atomic temp+rename, framed records so corruption is a restore error, never a partial namespace (`repl.py:724-760`). Directly relevant to PLAN B4 "state-exact, not process-exact" and revivable dead-ends (§8.9). Our `sandbox/snapshot.py` snapshots the filesystem only; this adds the in-memory interpreter state for REPL-style agents. Caveat: dill.loads executes arbitrary code (see section 6). Layer: L0 + L5. Effort M. Reimplement in Python (idea is Python-native already; could copy with MIT attribution).
6. **Append-only spawn ledger for agent topology with tombstoned usage** (`rlm_ledger.rs`, `replay.rs:19-70`): spawn/rename/delete JSONL, single `O_APPEND` writes, size/record bounds, malformed-line skip, delete records carry a final usage snapshot so billing survives deletion. A clean pattern for our multi-agent mode (Station-style) cost attribution and for L1 budget ledger across descendant sessions. Effort S-M. Reimplement.
7. **Daemon-derived sender identity, family-scoped addressing, and rate/size/pending limits for agent-to-agent messages** (`agent-message/SKILL.md` Safety; `agent_messaging.rs:19-27`). Cheap defenses against agent message storms and spoofing in L4 multi-agent mode. Effort S. Reimplement.
8. **Steering delivery + "wake idle child" semantics** (`SKILL.md` API) for asynchronous coordination: a message lands during an active run when the target allows. Useful pattern for L1 control plane (supervisor nudges). Effort M; low priority for us now.
9. **Auto-review gate plus cooldown and turn-interval throttling for memory writes** (`refine.rs:37-53` defaults, `auto_refine_trigger.rs:15-26`: every attempt, success or failure, stamps the cooldown so persistent failure cannot retry every boundary). Good throttle design. But their gate is an LLM judging itself; ours must be L1-deterministic plus tier gate (P7). Adopt the throttling only. Effort S.
10. **Compaction as a structured, section-fixed summary with a recency anchor and preserve-verbatim instructions** (`compaction_utils.rs:457-483`, `recent_state_anchor.rs`). Reasonable template for our context-policy edit type (L6) and L1 compaction. Effort S. Copy text with attribution or reimplement.
11. **Per-row fsync of the session log and torn-tail repair** (`persist.rs:148-171`, `window_cache.rs:203`): relevant to our 85 h durability goal; our SQLite evidence store should set WAL + synchronous=FULL for step rows (check `store/evidence.py`; I did not verify our current pragma). Effort S.

Not worth adopting: lexical IDF ranking of entries (`ranking.rs:112-179`; we should use embeddings plus read-audit), the 3-entries-per-kind, 140-char digest (a lossy view that hurts recall; our L5 should keep exact content and rank by evidence tier), TUI/Agents View.

## 5. Things custom-harness already does better (with evidence)

- **Admission is tier-gated and deterministic.** Ours: `tiers.py:28-48` has `Action.ADMIT_SKILL` with `DEFAULT_POLICY[ADMIT_SKILL]=T1_EXECUTABLE`, "Changing this table is a human-only action". Theirs: structural checks only (`planner.rs:198-290`, `harness.py:301-357`), plus an LLM self-review (`planner.rs:13`).
- **Claims only from evidence; claim tier = weakest link** (`store/evidence.py:103-118`, `tiers.py:24 chain_tier`). Prime Agent has no notion of evidence, tier, or claim; "evidence" in `HarnessRefinementEvent.evidence` is a free-text string (`mod.rs:77-90`).
- **Typed, statically checked harness edits with predicted effect, held-out gate, and racing** (`evolve/` per STATUS.md; `edits.py`, `selection.py`). Prime Agent's refinements are unevaluated: no gate, no held-out split, no effect measurement, no calibration.
- **Immutable, content-addressed records and exact fork/backtrack** (`records.py content_hash`, `sandbox/snapshot.py`). Prime Agent's entries are mutable JSON with a version integer; history is a log of before/after snapshots rather than a content-addressed DAG.
- **Private-data guard so held-out/test material cannot render into prompts** (STATUS.md L4 note, `runtime/template.py`). Prime Agent has no equivalent; the whole harness store renders into the system prompt.
- **Statistical honesty**: seed bootstraps, paired CIs (`verify/stats.py`). Prime Agent has none.
- **Sandboxed execution by default** (Docker, no network, read-only rootfs, optional gVisor per STATUS.md/`sandbox/docker.py`). Prime Agent explicitly is not a sandbox (README:84-85).

Where Prime Agent is ahead of us today: a working persistent REPL kernel with state restore, a real multi-process daemon with crash adoption, an actual recursive-spawn/messaging runtime, a goal/autonomous/heartbeat stack, and months of production hardening. Our L5, L7 and multi-agent modes are not built.

## 6. Pitfalls, bugs, or anti-patterns seen in their code (cite) that we must avoid

1. **Self-review gate = same-model approval of persistent writes** (`planner.rs:13`, `executor.rs:361`). The model that may have discovered an exploit (the RCON case) is asked "does the trajectory contain evidence useful to future turns?" and the prompt rewards approving ("approve when the trajectory contains evidence useful"). A discovered shortcut that scored well looks like exactly such evidence. Avoid: never let an LLM reviewer be the last gate for memory/skill admission (PLAN P7).
2. **Kernel-direct writes bypass refine entirely** (`harness.py:712-960`, exposed as `rlm.harness` at `__init__.py:622,681`). The model can `create_skill/create_memory(..., global_=True)` with only a type check; a local session writes straight into the cross-session store. Prompt-level scope policy (`planner.rs:11`) does not bind this path. Avoid: put admission in the store layer, not in one caller.
3. **Persisted entries become system-prompt text for every future session** (`harness.py:301-312` docstring: "crashing the host digest that renders every session's system prompt"; `ranking.rs:200-375`). An exploit or poisoned instruction stored once is replayed with instruction authority in every later session. Avoid: render memory as untrusted data with provenance, not as prompt policy; quarantine before render.
4. **`expectedOutcome` is never validated** (`planner.rs:499-508`, `mod.rs:93-101`). Refinements accumulate with no effect check, no demotion on failure, no read-audit; history only feeds the next refine prompt (`executor.rs:92-128`, last 20). Avoid: record predicted vs actual (our §8.5).
5. **Lossy digest hides what is active**: 3 entries per kind, 140 chars each (`mod.rs:19-21`) means a human reviewing the digest or the model itself cannot see a malicious entry past rank 3; the full entry is only visible through `harness.search`.
6. **Gate/agent share the workspace** (`gates.rs:57-65` runs `bash -c` in the session cwd with the agent's permissions). [inference] An agent that can edit files and run bash can edit the thing a gate checks, or the gate script itself; the gate's snapshot optimization (`gates.rs` header: re-run suppressed over an unchanged worktree) additionally reasons about workspace state, not gate integrity. Avoid: gates and verifiers run outside the agent's writable tree (our hidden-test verify already does).
7. **`dill` snapshot restore is arbitrary code execution** (`repl.py:1063-1125`, `dill.loads`). Safe only because the snapshot is the agent's own, same-trust-domain file. If we adopt it, treat snapshots as trusted-only and content-hash them; never restore snapshots that crossed a trust boundary (e.g. a quarantined run).
8. **Default autonomy limits are tiny and silently require tuning for long runs** (`autonomous/mod.rs:23-28`: 3 continuations, 12 turns, 80k tokens, 30 min), with an "unlimited" sentinel (`:33`). The continuation prompt says "Do not end the session yourself; the verifier/evaluator decides" and "keep looking for safe progress while budget remains" (`:21`), which pushes an agent toward doing something after it has hit a wall: a documented incentive to find shortcuts. Avoid emulating that prompt without a verifier-tier policy.
9. **Factory runs are kernel-memory only** (`factory.py` ~line 560) and budgeted only in wall-clock `budget_ms`. A kernel crash loses in-flight workflow state; there is no token cap per state. For 85 h runs this is a durability hole [inference: the repo has no persistence of factory run state that I found; I read only the docstring, not the full run store].
10. **Post-hoc, eventually consistent cost accounting across the agent tree** (`rlm_children/usage.rs:1-60`, `goal_driver.rs:35-40`). A runaway child can overspend before attribution lands. Avoid: enforce budgets preemptively in L1 (our `budget.py` plans this).
11. **Time accounting bug history in code comments** (`goal_driver.rs:44-55`): a goal's elapsed time read 73 h for a 2 h goal and 242.8 h for a 1.4 h goal across 388 rows before they replaced the anchor model with creation-based age. Lesson for our ledgers: derive wall clock from immutable timestamps, never accumulate deltas.
12. **Message-queue limits are small and per-sender** (`agent_messaging.rs:19-27`: 20 pending, burst 3). Fine as a guard, but 16 KiB messages from child to parent are an unmonitored channel through which an exploit description can propagate between agents; no content screening exists.
13. **Mostly a ported codebase with divergence comments referencing TS parity** (e.g. `mod.rs:655-659`, "TS default no fsync") makes behavior depend on a reference we cannot see. Treat any "matches TS" claim as unverified.

## 7. Verifier / evaluation / safety handling

- **Verification**: none beyond (a) JSON-shape validators for harness entries and factory machines, (b) the user-defined shell gate in autonomous mode (`gates.rs`), whose passing is explicitly weak: README says "A passed gate checks only what that gate verifies; reaching a limit does not imply task success" (README Built for Long-Running Work). There is no tiering, no statistics, no held-out check, no mutation test of gates.
- **Sandboxing**: none. README:84-85 states the worker/kernel processes "are **not** a security sandbox" and tells users to use external sandboxes. Orphan-process journal reaps leaked `bash()` process groups only (`kernel/orphan_journal.rs`).
- **Exploit handling and the RCON case, answered directly: is there any skill admission check? No.**
  - LLM path: the only filters are the review gate (an LLM, same trajectory, self-reporting; `planner.rs:13`) and structural validation (`planner.rs:198-290`). The paper's story (agent used RCON despite an anti-cheating heartbeat, then "preserved it as a reusable skill") fits this path precisely: nothing in `validate_edit` or `apply_refinement_proposal` examines what the procedure does or whether the achieving trajectory was legitimate. The grep for exploit/cheat/reward-hack/anti-cheat across all `.rs`, `.md`, `.py` found only an unrelated hit in `vendor/crossterm`.
  - Kernel path: `rlm.harness.create_skill(...)` writes with type checks only (`harness.py:867-925`, `301-357`), global scope allowed.
  - File skills: an agent can write `~/.prime/agent/skills/<name>/` itself via skill-creator (`skill-creator/SKILL.md` "Pick the location"), `/reload` loads it; Python-backed skills are pip/uv-installed into the kernel venv. The only gate is the user's attention. Name/description lint only.
  - What stops an exploit skill from spreading: (1) only depth-0 sessions auto-refine (`auto_refine_trigger.rs:60-62`) and children cannot, reducing but not eliminating spread; (2) local scope by default; (3) rollback exists and the audit row keeps full before/after, so a human can undo it after noticing; (4) README tells users to review skills. These are post hoc and human-dependent.
- **Reversibility**: good. Atomic writes, versioned entries, audit rows, rollback by id (`mod.rs:307-354`, `planner.rs:513`). Rollback restores the store, not any irreversible world effects (the paper's Factorio "destroyed progress" point has no code mitigation).
- **Relevance to our L5 and exploit quarantine (PLAN §8.4, §5)**:
  - We should treat Prime Agent's refine pipeline as the reference for what *not* to do at the admission step, and keep their good parts (CAS baseline, before/after snapshots, rollback, scope split).
  - Concrete design implied by their gap: `Skill`/`MemoryEntry` writes go through one store API that (1) requires `evidence_ids` and a tier >= floor, (2) runs exploit quarantine (rerun under perturbed evaluator, hidden invariants) before any entry with `kind in {positive, playbook, skill}` becomes readable by prompts, (3) records the originating trajectory hash so a later-discovered exploit can revoke every entry derived from it (their history stores trigger/evidence text only, not a derivation graph), (4) refuses writes from agent code paths that did not pass through the gate (their kernel-direct path is the anti-example), (5) renders memory as quoted data with provenance and tier.
  - Planted-exploit test (PLAN §8.4 "RCON-like"): a faithful reproduction here would be: have an agent perform a shortcut that scores well, call `refine.run()`, and observe it admitted. I did not run this (no execution allowed), and by code reading it would be admitted whenever the review LLM judges the trajectory "useful".
  - For our L5 hierarchy: keep their tier idea of L2 (live state) vs L3 (disk), but add explicit promotion rules from "working notes" to "admitted memory" keyed on verifier tier. They have no demotion/eviction of harness entries at all (only the model can delete); we need read-audit retirement (PLAN L5).
  - Their message channel (parent<->child, 16 KiB) is a propagation path for exploit descriptions; our multi-agent mode should route inter-agent text that could become memory through the same quarantine.

## 8. Bottom line
- Prime Agent is a strong runtime (persistent REPL, daemon, recursive spawn, durable sessions) and a weak safety/evidence layer: refine admits memories, skills and prompts on structure plus a same-model review, and the kernel API bypasses even that. There is no skill admission check, so the RCON-as-skill failure reproduces by construction.
- Adopt: CAS baseline on edits, before/after snapshots with inverse rollback, local/global scope split enforced in code, spawn ledger with tombstoned usage, per-variable-isolated state snapshots, message size/rate limits, throttled review cadence.
- Avoid: LLM self-approval of persistence, kernel-direct writes to shared stores, memory rendered as prompt authority, unvalidated `expectedOutcome`, same-workspace gates, accumulating-delta timers, kernel-memory-only workflow state in long runs.
- The paper's 85 h and Factorio results are not reproducible from this repo (no benchmark or experiment code, default autonomy limits 12 turns / 80k tokens / 30 min); treat those numbers as unverified, and treat their L0-L3 as an informal practice (compaction + dill + JSON store), not a measured hierarchy (no ablations).
