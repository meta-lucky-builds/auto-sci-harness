## 1. What the code actually does (architecture map)
- The "Refiner" is `HarnessEvolver` (`agents/utils/harness_evolver.py:53`). It is NOT a separate agent/model: it creates a second tool-less `VLM` with the same backend+model as the agent (`prompt_optimizer.py:60-66`, reused at `harness_evolver.py:70`). Each "pass" is one single-shot text prompt that returns JSON (or markdown for the prompt), applied directly to stores.
- Four editable components, each a different representation:
  - **System/strategy prompt `p`**: ONE markdown string held in memory (`PromptOptimizer.current_base_prompt`, `prompt_optimizer.py:68-80`); rewritten wholesale by an LLM call ("IMPROVED BASE PROMPT:", `prompt_optimizer.py:181-211`). The fixed *system* prompt (tool list/hard rules) is shown to the optimizer but is not editable (`prompt_optimizer.py:172-178`). Saved per window to `run_dir/prompt_evolution/meta_prompts/steps_A_to_B.md` (`:321-347`).
  - **Subagents `G`**: `SubagentStore` (JSON file `subagents.json`, ids `sa_NNNN`), entries = {handler_type one_step|looping, max_turns, available_tools, system_instructions, directive, return_condition, importance, source} (`utils/stores/subagents.py:24-44`). Char caps 12k enforced in add/update (`subagents.py:142-208`); built-ins can't be deleted (`subagents.py:208-213`). Created subagents are executed by a generic looping executor with a `return_to_orchestrator` tool injected and a safety cap (`agents/subagents/utils/executor.py:300-404`, skimmed).
  - **Skills `K`**: `SkillStore` (`skills.json`, `skill_NNNN`), entry = {path (hierarchy), name, description, `code` (optional inline Python), effectiveness low|medium|high, importance, source, mutation_history} (`utils/stores/skills.py:17-31`). Executable skills run via `run_skill` (`PokeAgent.py:421-518`).
  - **Memory `M`**: `MemoryStore` (path-hierarchical entries with title/content/importance/location/tags; `utils/stores/memory.py:105-207`). Agent writes memory itself via `process_memory`; the Refiner only "curates" 3-5 changes (`harness_evolver.py:483-500`).
  - All three stores share `BaseStore` (`base_store.py:44`): JSON-file persistence rewritten in full on every mutation (`save()` `:306-316`), per-entry `mutation_history` of {timestamp, field: {old,new}} diffs (`:110-133`), tree-overview rendering capped at 200 entries sorted by importance (`:185-241`), recent-access subtree promotion (`:243-256`).
- Agent-facing edit surface ("meta-tools"): `process_memory`, `process_skill`, `process_subagent`, `run_skill`, `run_code`, `execute_custom_subagent`, `process_trajectory_history` (name list `harness_evolver.py:37-50`; HTTP routes `PokeAgent.py:119-123`). The *agent itself* can create/edit skills/subagents/memory at any step with these; the Refiner is a second, periodic editor over the same stores. Plus a single on-demand tool `evolve_harness(reasoning, num_steps)` that fires the Refiner (`registry.py:559-593`, `PokeAgent.py:521-540`).
- Bootstrapping: `utils/stores/bootstrap.py` copies another run's `memory/skills/subagents.json` into the new cache, re-paths every entry under `bootstrapped/` and tags `source="bootstrapped"` (`:166-175`), merges ids with `bs_` prefix on collision (`:203-206`), and optionally runs ONE LLM call to strip run-specific "current state" text from the evolved prompt (`:62-129`).

## 2. Core loop, step by step (with citations)
1. Agent step finishes and its trajectory line is written (`PokeAgent.py:2028-2038`, `_log_trajectory_for_step`).
2. Right after, `if self.optimization_enabled:` -> `harness_evolver.should_evolve(active_step, window)` (`PokeAgent.py:2043-2046`; duplicated for the text-response branch at `:2104-2107`).
3. `should_evolve` (`harness_evolver.py:98-109`): warmup 25 steps; every 25 steps while step<=200, then every 100. **The `--optimization-window-length` / `frequency` argument is explicitly ignored** (`:104`, docstring) — it only sets how many trajectory steps are shown (`PokeAgent.py:2051`). README says `--optimization-window-length 50` controls refinement; it actually controls only the window size.
4. `evolve()` (`:115-148`): loads last N trajectory JSONL lines; runs four **independent, sequential** passes — prompt, subagents, skills, memory — each in its own try/except; saves `evolution_log.jsonl`.
5. Diagnosis input = `_format_trajectories_for_analysis` (`prompt_optimizer.py:249-319`): per step reasoning (full), tool names, args/result truncated to 300 chars only for 5 meta-tools, location/coords/context, and two hard-coded heuristic flags: "movement attempted but coordinates unchanged" and "same coords as 2 steps ago (possible loop)". Plus `_extract_tool_failures` (`harness_evolver.py:166-196`; string-matches `"success": false` / `"error"` in tool results). Skill pass adds an anti-pattern detector: `run_code>=3 && run_skill==0` -> "CRITICAL ANTIPATTERN" text forcing skill creation (`:341-357`). These are the only "failure signatures"; there is no clustering, no persisted failure taxonomy, no cited trace ids in outputs.
6. Edits are applied **immediately and unconditionally** to the live stores (`store.add/update/remove`, e.g. `:282-321`, `:431-454`, `:535-557`); new prompt replaces `current_base_prompt` (`prompt_optimizer.py:233`) and `_load_base_prompt` hands it to the agent on the next step (`PokeAgent.py:333-336`). No candidate evaluation, no A/B, no rollback, no gate (I grepped the evolver: none exist). The only "gate" is JSON-parse success, tool-name filtering for subagents (`:277-280`), `max_turns<=50` (`:287`), and char caps.
7. `_inject_evolution_summary` (`PokeAgent.py:2229-2252`) puts a human-readable change list + "Reason: <analysis[:200]>" into the agent's next-step context (kept in a 3-item `recent_function_results` buffer, `:2254-2262`). So the agent is *told* what changed (nice).
8. Loop continues; agent may also call `evolve_harness` on-demand (`PokeAgent.py:411`, `:521`).
- DAgger + PRM: **NOT in this repo.** `grep -riE "dagger|\bprm\b|process reward|gemma"` over all .py/.md/.toml returns only the single README sentence (README.md line 5). No training code, no PRM, no teacher relabeling, no SFT, no Gemma config. See §3.

## 3. Paper/summary vs code discrepancies
- **DAgger + PRM co-learning with weights: absent.** The README claims "The same loop extends to joint training ... online DAgger + process-reward-model pipeline" but the repo contains zero implementation. Everything we know about K=256 DAgger iterations, pairwise PRM, Gemini-3.1-pro relabeling, soft SFT comes from the paper only — cannot be verified or copied. (For our L8: nothing to reuse; treat as a paper-only design.)
- **Refinement frequency "F" is tunable in the paper/README; in code it is hard-coded** (25 steps early / 100 later, `harness_evolver.py:26-33,104`; `--optimization-window-length` ignored for scheduling).
- **"Refiner role uses the same model as the agent"** — true (`prompt_optimizer.py:61-66`); but the paper's summary calls out a distinct Refiner "component" with failure-signature diagnosis; in code it is four prompt templates, not a diagnoser. The "failure signatures" in the README (navigation loops, tool-call failures, stalled objectives, missed exploration) are only partly operationalized: loops/blocked-move and tool-failure are string heuristics; "stalled objectives" and "missed exploration" have no code (grep of evolver/optimizer shows none).
- **"CRUD edits ... executable code repair"**: skill `code` is dropped on creation — see §6 bug B1; creation of executable skills by the Refiner effectively only works via `update`. In the shipped bootstrap artifacts all 13 skills are `source="orchestrator"` (agent-authored), 0 are `source="evolved"` (computed from `PokemonRed-GBC/bootstrap_source/skills.json`), consistent with the Refiner contributing skills mostly through updates/none. (Subagents: 7/7 `evolved`.) [inference: skills' main author in practice is the agent, not the Refiner — matches paper's "skills carry most improvement" only if one counts agent-side authoring.]
- **Reset-free is real**: harness state mutates in place, no episode restart (`PokeAgent.py:2043-2056`). However "diagnose before agent re-invokes the affected component" is just timing luck, not an enforced property.
- **Paper's "sub-agent regression when newly authored subagents replace inherited ones"** is unsurprising given code: no regression check on `create` (`:273-298`) and `retire` deletes (`:315-321`) based on one LLM call.
- Memory: paper says from-scratch memory is "authored but rarely consulted". Code confirms the mechanism: the Refiner is told "Be conservative" and only sees a tree overview (titles) (`:483-500`); there is no read-tracking at all (recent-access set is for display ordering only, cleared each render `base_store.py:239`).
- The paper's "bootstrap-frozen / bootstrap-updating / from-scratch" are implemented as CLI flag combos (README) over `bootstrap.py`, matching.

## 4. Mechanisms worth adopting into custom-harness (ranked by expected value)
1. **Same-model tool-less Refiner invoked on a schedule + on-demand `evolve_harness` meta-tool, with change summary injected into the agent's next context** (`harness_evolver.py:98-148`, `PokeAgent.py:2229-2252`). Our L6 (`evolve/loop.py`, `evolve/propose.py`) is generation-batched only; PLAN.md L6 "Mid-episode refinement" is a one-line placeholder. Adopt as **L6 mid-episode channel**: (a) adaptive cadence (dense early, sparse later — `:26-33`), (b) agent-callable request-refine tool with a reason string (agent-initiated demand signal is free diagnosis input), (c) post-edit "what changed and why" notice to the agent. Effort S-M. Reimplement (our typed edits differ); concept only.
2. **Component-typed stores with per-entry `mutation_history` diffs, importance, path-hierarchy and `source` provenance** (`base_store.py:82-133`, `skills.py:17-31`). Cheap, auditable; maps directly onto our records/lineage (L2) and L5 memory. Our PLAN wants read-audit and lineage; their `source` tag (orchestrator/evolved/bootstrapped) + old/new field diffs is a good minimal schema. Effort S. Copy-OK (MIT) but reimplement atop our SQLite store.
3. **Skills as inline executable code with a *fixed, documented sandbox API* (`tools[...]`, `args`, `result`) and a skill tree in the prompt that marks executable skills** (`harness_evolver.py:372-383`, `skills.py:58-63`, `PokeAgent.py:421-518`). Evidence in shipped artifacts: 13 BFS-style skills with up to 7 successive code revisions (`bfs_move` mutation_history len 7) — repair-in-place by diffing works. For us this is the "tool add/modify" edit type; run in our Docker sandbox, not `exec` (see §6). Effort M.
4. **Anti-pattern trigger: repeated disposable `run_code` with 0 `run_skill` => force "promote to skill"** (`harness_evolver.py:341-357`). A concrete, cheap trace-detector that maps to our trace-grounded diagnosis (`evolve/` diagnose). Effort S. Copy-OK/reimplement.
5. **Bootstrap-with-sanitization**: carry stores forward under a `bootstrapped/` namespace and LLM-strip run-specific state from the evolved prompt (`bootstrap.py:62-129,166-175`). Directly supports our L5/L6 "transfer priors", plus the three experimental arms (scratch / frozen / updating) are exactly the controls we need for the harness-science ledger (§8.10). The evolved prompt in the repo shows why sanitization is needed (it contains "Current Objectives (Defeating Lt. Surge)", `EVOLVED_ORCHESTRATOR_POLICY.md`). Effort S-M.
6. **Capability-floor as a first-class measured result** (paper: Flash-Lite <20%, README "below the minimalist baseline on Flash-Lite"). Not code; the repo has no floor detector. We should implement the *detector* they lack: before enabling mid-episode refinement, run a cheap competence probe and disable L6 mid-episode editing below the floor (fits our "inverted U" ledger §8.13). Effort M, novel.
- NOT worth adopting: whole-prompt rewrite (no diff, drifts), un-gated apply, DAgger/PRM (no code to adopt).

## 5. Things custom-harness already does better (with evidence)
- **Typed, statically-checked, diffable edits** (JSON-pointer ops, protected nodes, leakage patterns: `src/custom_harness/evolve/edits.py`) vs. their free-form JSON dicts and whole-prompt replacement with no validation beyond JSON parse (`harness_evolver.py:269-321`).
- **Gating**: racing, paired CI, held-out gate, rejected-candidate lineage (`evolve/selection.py`, `evolve/loop.py`) vs. none at all in Continual Harness; every proposal is live immediately (§2 step 6). This is exactly why their paper sees sub-agent regression (acknowledged limitation 4).
- **Predicted effects + proposer calibration** (`evolve/propose.py`; PLAN §8.5) — theirs has only free-text "analysis".
- **Trace-grounded diagnosis with full event-sourced traces and exact checkpoints/fork** (`runtime/`) vs. their 300-char truncated tool results and two string heuristics (`prompt_optimizer.py:273-318`).
- **Sandboxing**: Docker no-network non-root (`sandbox/`) vs. in-process `exec` (§6 B3).
- Atomicity/safety of persistence: SQLite append-only store (`store/`) vs. whole-file JSON rewrite each mutation (`base_store.py:306-316`).

## 6. Pitfalls, bugs, or anti-patterns seen in their code (cite) that we must avoid
- **B1 — Refiner drops skill code on create.** `_evolve_skills` `add` branch calls `store.add(path,name,description,effectiveness,importance,source)` but never passes `spec["code"]` (`harness_evolver.py:431-438`) even though the prompt asks for `code` (`:405`). Executable skills created by the Refiner are descriptions only; `run_skill` then returns "has no executable code" (`PokeAgent.py:435-440`). Only `update` carries code (`:444-452`).
- **B2 — Return-type bug masks successes.** `BaseStore.add()` returns the entry id string (`base_store.py:82-108`), but the evolver treats it as an object: `entry.id`/`entry.name`/`entry.title` (`harness_evolver.py:295-296,439-440,542-543`). This raises AttributeError AFTER the entry was stored; the except logs "Failed to create ..." (`:297-298,441-442,544-545`) and the id is never appended to `result["created"]`. So evolution logs, `_inject_evolution_summary` (agent never sees newly created items listed as "new") and `evolution_log.jsonl` under-report creations. Also `_save_evolution_log` reads `store._entries` (`:616-618`), but the attribute is `entries` (`base_store.py:73`) -> AttributeError swallowed by `except Exception: pass`, so `store_counts` is never recorded. [inference, from reading code only; not run.] Lesson: their paper's component-attribution counts may be derived from stores/other logs, but the evolution log in this version is unreliable. Never swallow exceptions around the audit log.
- **B3 — "Sandbox" is `exec` with `__import__` exposed.** Skill/`run_code` sandbox gives `__builtins__` incl. `"__import__": __import__` and `type` (`PokeAgent.py:482-497` and run_code equivalent ~`:590-600`) => trivially escapes to os/subprocess/file access; LLM-written code runs in the agent process. For arbitrary skill code we must use Docker/gVisor (we have it) — never port this.
- **Un-gated, un-rollbackable live edits** (§2 step 6). One bad prompt rewrite or subagent retire persists; the only history is `mutation_history`/meta_prompts files, with no automatic revert. Authors' own limitation 11 (positive-feedback risk) is unmitigated in code.
- **Prompt contamination/drift**: Refiner prompt asks to "reinforce successful patterns" and "add learned lessons" with no length/structure constraint; the shipped evolved policy contains transient state and effusive praise ("Outstanding Work! You brilliantly navigated ...") and a leading literal artifact "IMPROVED BASE PROMPT:" (`EVOLVED_ORCHESTRATOR_POLICY.md` line 1; `bootstrap.py:60-61` special-cases it). Prompt bloat + state leakage into reusable harness => needs our leakage critic and a "state vs. policy" split.
- **Heuristic false alarm baked into the prompt**: the "Movement attempted but coordinates unchanged" flag (`prompt_optimizer.py:310-311`) is wrong when facing objects; the evolved prompt had to tell the agent to ignore it ("FALSE ALARMS"). Hand-coded diagnostic flags must themselves be gated/tested.
- **Skill bloat/no dedupe**: the shipped bootstrap has 13 near-duplicate navigation skills (navigate_to, move_to_coords, walk_to, bfs_move, safe_navigate, travel_to, go_to_coords, city_nav, ...) with one-off variants (diglett_nav). No merge/consolidation or usage-based retirement for skills (only subagents have `retire`, skills have no remove path in the evolver).
- **Un-validated skill code persisted**: 1 of 13 shipped skills (`navigate_to`) fails `compile()` — its latest `code` has literal `\n` escape characters ("unexpected character after line continuation character"; checked by compiling each entry with Python, not by running them). No syntax check/dry-run before saving an update (`harness_evolver.py:444-452`).
- `run_skill` extracts args by regex from free-text reasoning as a fallback (`PokeAgent.py:442-455`) — brittle implicit coupling.
- Whole-file JSON rewrite per mutation and a process-global singleton store (`base_store.py:306-316`, `skills.py:78-87`) — not multi-worker safe.
- Refiner sees only the last N steps (default 50) — no long-horizon credit assignment; memory pass sees titles only.
- `should_evolve` ignores its `frequency` arg (`:104`); dead parameter, README misleading.
- Duplicate evolve trigger code in two branches (`PokeAgent.py:2043-2068` vs `2104-2129`).

## 7. Verifier / evaluation / safety handling
- No verifier for harness edits: success is measured externally by milestone completion/cumulative button presses (paper), with game state read from emulator memory; `utils/anticheat.py` exists (not read; name suggests it blocks game-state cheating — [inference]). The Refiner receives no explicit reward signal; it reasons from trajectories only (`_format_trajectories_for_analysis`). There is no held-out evaluation or paired comparison of harness versions inside the run.
- Safety on edits: tool-name whitelist for subagents (`harness_evolver.py:277-280`, falls back to `press_buttons`), `max_turns<=50` (`:287`), 12k-char caps (`subagents.py:142-157`), built-in subagents undeletable (`:208-213`). Skill/run_code: in-process `exec` with restricted-looking but escapable builtins (B3); `run_code` is explicitly forbidden game actions (`PokeAgent.py` run_code builds only get_game_state/get_map_data tools).
- Knowledge restrictions ("NO walkthrough or wiki", `harness_evolver.py:210-212`) are prompt-level plus tool removal for the scaffold (`registry.py` scaffold filtering), not enforced against the Refiner.
- Capability-floor evidence: paper table (Flash-Lite <20% across variants; Flash 80% vs 77% minimalist; Pro 100% at $130 vs minimalist 98% at $215) and README caveat only; repo contains no experiment results, configs, or analysis scripts to re-check (the repo bundles benchmark code; checked directory listing: `scripts/` has only scaffold smoke-test shells). Treat as paper-reported, unverified by code.

## 8. Bottom line
- Real, small, MIT-licensed mid-episode refiner: periodic same-model JSON-CRUD over prompt/subagents/skills/memory stores with no gate/rollback — good idea for our L6 mid-episode channel, but we must wrap it in our typed edits, gate, and sandbox (PLAN already restricts mid-episode to low-risk edit types; this code is the unrestricted version).
- DAgger + PRM weight co-learning is NOT in the repo (README sentence only); nothing to adopt for L8 beyond the paper's design.
- Several real bugs (skill code dropped on create, `add()` return misuse, wrong `_entries` attr, escapable `exec`, invalid persisted skill code) mean their reported component counts/log are not trustworthy from this code alone.
- Adopt: adaptive cadence, agent-callable refine tool, change-notice to agent, mutation_history diffs + source provenance, run_code->skill antipattern trigger, bootstrap-with-sanitization experiment arms, and add a capability-floor probe they lack.
