## 1. What the code actually does (architecture map)
Two generations live side by side:
- **v1** (`src/autosaddler/v1`): a fork of GEPA (`core/engine.py` is the GEPA engine; `strategies/batch_sampler.py` says "Based on GEPA"). `proposer/autosaddler/proposer.py::AutoSaddlerProposer._run_iteration` (line 514) runs three Claude-Agent-SDK sessions per iteration inside a forked git worktree. This is almost certainly the code behind the paper's numbers (Claude Opus 4.6, `configs/v1/meta_are.yaml`: `claude_agent_sdk_model: claude-opus-4-6`, `max_metric_calls: 3000`, `train_minibatch_size: 3`) [inference: the paper summary names Opus 4.6; I did not read the paper].
- **v2** (`src/autosaddler/v2`): a clean rewrite, event-sourced and resumable (`docs/v2-architecture.md`). Ports-and-adapters: engine (`core/engine.py::AutoSaddlerEngine`) depends only on protocols (`core/ports.py`); scenario plugin supplies harness space (git-worktree or component-map), evaluator, evidence builder, prompt pack; provider adapters (claude/codex/copilot/fake) give the optimizer session; policy bundle (`core/policies.py::PolicyBundle`) supplies task selection, acceptance, dev gate, ranking, budget. `events.jsonl` is the source of truth; manifest/EvoDAG/metrics are projections (`docs/v2-architecture.md` "Events, Replay").
- Three optimizer sessions (v2 schemas in `plugins/meta_are/prompt_pack.py`): `evolve` (pick parent + optional component sources; JSON schema `_evolve_schema`, line ~120), `diagnose_patch` (edit the repo in a workspace, return `intent/diagnosis/expected_effect/changed_paths`), `reflect` (return `lessons[{scope,statement,evidence_case_ids}]`).
- Harness = a git repo (Meta-ARE default agent). Candidate = content-addressed git revision. Mutable surface = an allowlist (`writable_paths` in `configs/v2/meta_are_full.yaml`: default_agent dir, agent config, `agent_user_interface.py`, `hook.json`), with a `forbidden_paths` list (validation, scenarios, benchmark, tests...), enforced by `GitHarnessSpace._require_writable` (`harness/git.py:434`).

## 2. Core loop, step by step (v2, with citations)
Per iteration, `engine.py::_run_iteration` (line 214):
1. Sample a fixed-size TRAIN mini-batch with `EpochShuffledTaskSelectionPolicy` (`policies.py:39`); `configs/v2/meta_are_full.yaml` sets `batch_size: 3`, v1 config also `train_minibatch_size: 3`. Batch is persisted as a `BatchSampled` event (engine ~233) so resume is deterministic.
2. **Evolve session** (engine ~250): LLM sees history bundle and returns `parent_ids` (first = base) and `component_sources` {file -> source candidate}. `_selection_plan` (line 1274) validates: parents must be in the ACCEPTED set, unique, every extra parent must supply a component. If any component_sources, `harness_space.compose(plan)` (engine 268; `harness/git.py:288`) builds the working parent: git worktree at base revision, overwrite listed files with the same file from other parents' revisions (`git.py:318-330`). Composition unit = whole files only; the prompt `prompts/evolve.md` says so explicitly.
3. **Measure parent on this batch** (engine 283, purpose `train_before`). Parent is re-run EVERY iteration on the new batch; there is no cross-iteration rollout cache in the engine [I found none; `_ensure_evaluation` caches only by operation id, i.e. per-iteration, line 1056].
4. **Early exit**: if every observation of the parent is `success`, the iteration ends with outcome `no_training_failures` (engine ~288-296). No diagnosis, no child, no further rollouts.
5. Build evidence (`MetaAREEvidenceBuilder.build`): per-case, per-repetition record with disposition, score, judge rationale, full interaction trace, usage, plus a `consistency` label (`consistent_pass | consistent_failure | intermittent`, `evidence.py` `_consistency`). Written to `.autosaddler/training_evidence.json` in the optimizer workspace.
6. **Diagnose+patch session** (engine ~310): an agentic Claude/Codex/Copilot session with read/edit/run-commands tools in a worktree copy, plus a history bundle under `.autosaddler/history/` and skills. It must edit files and then return a JSON whose `changed_paths` must EXACTLY equal the observed git delta (`_workspace_delta_failure_reason`, engine 1315). Retries are durable (`session_retries: 2`).
7. **Verifier gate before any rollout is spent** (`MetaAREVerifier.__call__`, `verification.py`): compile every changed .py; parse/validate `hook.json`; if phase is steering and any .py changed -> reject (`steering_scope`, line ~50); anti-cheating: reject if any changed text file contains a TRAIN case id string (`anti_cheating`, ~line 65); run an import check in `uv run` for python changes. Failure -> `MutationRejected` event, iteration ends (engine ~340-385); child never evaluated.
8. **Measure child on the SAME batch** (engine 399, purpose `train_after`).
9. **Acceptance** = `MatchedValidStrictImprovement.compare` (`policies.py:102-135`): both are train evaluations over identical ordered case ids; restrict to (case, repetition) keys where BOTH observations are valid (`disposition in {success, task_failure}`; infra errors/invalid attempts are excluded, `domain.py:180`); accept iff mean(child) > mean(parent) strictly on that matched set. No CI, no threshold, no multiple-comparison correction.
10. **Dev gate**: `FullOnAcceptDevelopment` (`policies.py:138`): evaluate the child on the whole development split iff accepted (engine 443). This is the only time dev rollouts are spent. The dev score does NOT feed back into accept/reject (see section 3).
11. `EvolutionRecorded` event; accepted child is appended to `accepted_candidate_ids` (`run_state.py`, `EvolutionRecorded` with accepted true) and becomes selectable.
12. A deferred `reflect` obligation is scheduled (engine 465); it runs at the start of the next iteration (`_drain_deferred`, line 596) and emits lessons into an `ExtensionStateChanged` event; lessons are validated to cite only current train case ids (`_validate_lesson_case_ids`).
13. End: `MeanDevelopmentRanking` (`policies.py:146`) picks the accepted candidate with max dev mean (ties -> later). Test split is never opened by the engine.

**Rollout accounting** (this is the whole "10x" story; section 4.1): per iteration = 2*b*reps (b=3) when a patch is attempted, 1*b*reps when the batch has no failures, plus |dev| (65 cases in the full config per its own comment) only on accepted children. Seed dev eval once. `BudgetPolicy` caps `attempted_rollouts` and iterations (`policies.py:166`; full config 30000/2000 — these are caps, not what the paper used).

### v1 differences (the code that likely produced the paper)
- v1 acceptance: `sum(after) <= sum(before)` -> skip (`v1/core/engine.py:532-535`), i.e. same strict mean improvement; but missing/failed scenarios silently score 0.0 (`evaluator.py::compute_pass_rate`, `results.get(sid, {}).get("score", 0.0)`), so an infra crash is a "failure" and can fake a fix or a regression. v2 replaced this by matched-valid.
- v1 selection is NOT schema-constrained: Session 0 is a free-form agent that edits the new worktree (rsync / cherry-pick / revert) before the "before" measurement (`proposer.py:~600-640`, `session0_candidate_selection.md`: "Regressions identified here must be reverted in THIS session"; "prefer diff-level precision over copying entire files"). So v1 composition is line-level and unverifiable, v2 is whole-file and schema-checked.
- v1 default base parent = the non-abandoned DAG node with the highest iteration (`proposer.py:544-550`; `dag.py:518-520`). `abandoned` is set only on session failure/verify failure/all-passing (`proposer.py:674,723,731`), NOT on acceptance-gate decline. So a declined patch's worktree is forked as the next base unless Session 0 reverts it [fact from code; effect on results is inference]. v2 fixes this: only accepted candidates are selectable parents (`engine.py::_selection_plan`).
- v1 phase: `capability_phase_iterations` or `capability_phase_epochs` x iterations-per-epoch (`proposer.py:272-284`; config default 1 epoch). v2: explicit `capability_phase_iterations` (25 in the full config).

## 3. Paper/summary vs code discrepancies
(Summary = `autoresearch_survey/2608.23041.md`; I did not read the PDF.)
1. **Generalization-aware selection is not a gate in the code.** Summary: "patches causing regression on development sets are rejected even if they improve training" and calls this the biggest ablation effect (+11.4 pp). In both v1 and v2 the accept/reject rule uses only the 3-case train mini-batch (`policies.py:102-135`; v1 engine 532-535). Dev is measured after acceptance and never un-accepts anything (`DevelopmentDecision` only decides *whether to measure*, `policies.py:138-143`). What "generalization awareness" really is: (a) dev data hidden from the optimizer as case-level evidence (aggregates only; `prompting/methodology/system/optimizer-invariants.md` "Evidence And Generalization"), (b) the evolve/Session 0 LLM is told to choose parents by dev score and revert regressions, (c) reflection lessons, (d) final ranking by dev mean. The effect is mediated by an LLM following a prompt, not by a deterministic rule. The ablation "w/o reflection and dev evaluation" removes all four at once, so the 11.4 pp cannot be attributed to a gate.
2. **Patch taxonomy is a prompt convention, not typed/enforced.** No enum/type of patch exists in code (grep for patch_type/new_tool found nothing). What exists: two phases, a skill per phase (`capability-patch`, `steering-patch`), a table of "Patch Type -> Skill" in the prompt (`v1 prompt_builder.py:206-232`), and the "Common Patterns" list inside `capability-patch/SKILL.md` (New Tool Addition, Argument Modification, Implementation Fix, Infrastructure Change, Agent Loop Logic Change). The only mechanically enforced rule is v2's "steering phase may not touch any .py file" (`verification.py` `steering_scope`). v1 only "discourages" cross-phase changes in prose. The per-type acceptance rates in the summary (New Tool 83%, Loop Change 71%...) therefore must come from post-hoc labelling of diffs, which is not in the repo [inference]. Also the summary's claim that the taxonomy "prevents collapse to 91.5% steering" is implemented purely by the phase schedule + prompt: capability phase first.
3. **"10x fewer rollouts" is two different numbers.** Summary: total executions ~1,000 vs ~2,800 (2.8x) and traces-at-peak 147 vs ~1,400 (~9.5x). The 10x is the trace-at-peak figure. Code explains why traces are scarce: traces are captured only for TRAIN evaluations (`engine.py:1097 capture_traces=split == "train"`), mini-batch of 3, and dev evals are untraced. See 4.1.
4. **Benchmarks**: repo contains only the Meta-ARE/GAIA2 plugin; SWE-Bench Pro and Terminal-Bench are "coming" (README line 124) though the README headline table lists them. README says SWE-Bench Pro +9.6 pp, the summary says +8.4 (README line 21 vs summary). Cannot reproduce 2 of 3 headline results from this repo.
5. **EvoDAG**: summary frames it as a rich graph enabling "non-linear recombination". In code, v2's EvoDAG is just the accepted-candidate parent edges plus multi-parent whole-file composition (`git.py:288-348`); v1's `dag.py` is a larger data structure (nodes, base and cherry_pick edges with per-scenario impact, lessons, scenario registry) but selection among nodes is an LLM reading `evo-dag show history`, there is no algorithmic traversal/UCB/Pareto policy over the DAG. GEPA's Pareto frontier machinery exists in v1 state (`frontier_type: instance`) but the AutoSaddler proposer does not use it for parent choice (it forks the latest node) [inference from proposer.py:544-550].
6. "Phased patch scheduling" = a single hard switch at iteration N (v2: `iteration + 1 <= capability_phase_iterations`, `prompt_pack.py:46`), no schedule shape, no adaptive trigger.
7. "Three repeated runs at test time", cross-model transfer, etc.: nothing in the engine; test evaluation is out of band (`purpose == "test"` exists in `domain.py` but the engine never runs it).

## 4. Mechanisms worth adopting into custom-harness (ranked by expected value)
Our current code: `evolve/propose.py::diagnose` (single-shot digest), `evolve/selection.py::race` + `gate`, `evolve/loop.py::evolve_generation`.

### 4.1 Cheap-first, two-stage evaluation with an early exit — the exact mechanism behind the rollout saving (Value: highest; effort S-M; reimplement)
What it is: spend 2*b rollouts on a tiny TRAIN batch (b=3) that is *resampled each iteration and also serves as the diagnosis evidence*; skip the iteration entirely if the parent already passes the batch (`engine.py:288`); run the candidate on the big dev split ONLY if it clears the mini-batch gate (`policies.py:138`, `engine.py:443`); verifier-reject bad patches before any rollout (`verification.py`). Traces (the expensive artefact for the diagnoser) exist only for the small train batch. That is the mechanism; there is nothing cleverer (no surrogate model, no bandit, no caching: the parent is re-run each iteration).
Why better than ours: `evolve_generation` (loop.py) evaluates the parent on ALL evolve units each generation, races K=3 candidates on all of them, then evaluates the survivor on all gate units, and the parent too (gate_diffs recompute parent scores; they are cached, but candidate gate evals are full-split). Our unit of search is the whole split, theirs is a 3-case mini-batch plus a dev check only for winners. Their cost per attempted patch is ~6 rollouts vs ours ~|evolve|*(K+1)+|gate|.
Where: L6 (evolve loop) + the §6.4 allocator. Add a "minibatch stage" before `race`: draw b tasks from the evolve split (epoch-shuffled, deterministic, persisted), measure parent only on those, feed *those* traces to `diagnose`, `no_failures -> skip` (a free early exit we lack), then candidate on same units, promote to the full evolve+gate procedure only if matched improvement. Caveat in 4.2 about the noise this creates.
Copy vs reimplement: reimplement (small; MIT permits copy of `EpochShuffledTaskSelectionPolicy` with attribution).

### 4.2 Do NOT copy their acceptance rule as is; but copy "matched-valid" pairing (Value: high; effort S; reimplement)
Their rule is `mean(child) > mean(parent)` on b=3 cases (`policies.py:122`). With b=3 and 0/1 scores this accepts on a single flip and on pure noise (winner's curse), and nothing downstream rejects it (section 3.1). The paper's own ablation is evidence that this noise needs the dev check; but their dev check is advisory. Our `gate()` (selection.py) is strictly better for the final decision (paired bootstrap CI on evolve split + non-regression CI on a never-shown gate split). The correct synthesis: their cheap mini-batch rule as a *pre-filter* (promotion), our CI gate as the *decision*. What to take from theirs: restrict the paired comparison to units where BOTH runs were valid, excluding infra errors/timeouts (`policies.py:110-113`, `domain.py:180`). Our `score_state` returns 0.0 for non-completed runs (`evolve/evaluate.py:score_state`), so a sandbox flake counts as a failed run and biases both the diagnosis digest and the paired differences. Add a `disposition` (valid / infra_error) to `RunOutcome` and drop invalid units from pairing, but report their count.
Where: L6.5 gate, `evolve/evaluate.py::RunOutcome`.

### 4.3 Deep, agentic diagnosis with staged evidence and a mandatory causal procedure (Value: high; effort M-L; reimplement)
What it is (code facts): the diagnoser is a tool-using session in a writable workspace, not a prompt. Inputs staged as files: `.autosaddler/training_evidence.json` (per case, per repetition: score, judge rationale, full interaction trace, consistency label), `.autosaddler/history/manifest.json` (+ summary, lessons, candidate diffs), `session_context.json`. Mandatory skill order `history-analysis -> diagnose -> {capability|steering}-patch -> patch-verification` (`prompt_pack.py` `skill_paths`; `v2 prompting/methodology/prompts/diagnose-method.md`). The method forces: required vs actual behaviour, FIRST divergence point, what the agent could observe/do there, trace through the controlling surface (prompt/description/schema/config/impl/hook), compare repetitions, cross-check prior attempts, classify the cause (behaviour/description, missing capability, implementation, configuration, infrastructure) (`skills/causal-diagnosis/SKILL.md`). "An evaluator rationale is a lead, not a root cause." Output must contain `diagnosis`, `expected_effect`, exact `changed_paths` and it is cross-checked against the real diff (`engine.py:1315`). The paper attributes +4.2 pp to this depth (6.2 more tool calls and 5.8 more file accesses per step; summary, not verified in code).
Ours: `propose.py::diagnose` (line 20) clusters normalized error strings and attaches <=2 examples of 1500 chars, containing only step `error` / `run_error` fields, then one LLM call with `digest[:12000]` and the last 15 ledger rows `[:4000]` (`build_prompt`). Consequences: (a) failures with no exception (the research harness's common failure: runs that complete but do not beat baseline, wrong claims, leakage) have no signature at all except the `give_up` route; (b) the proposer cannot open the code/spec or a trace beyond the excerpt; (c) truncation by character slicing (`[:12000]`, `[:4000]`) can cut JSON mid-structure; (d) no repetition-consistency signal; (e) the proposer never has to produce a first-divergence step, only `evidence: list[str]`.
Where: L6.1. Concretely: give the proposer a read-only sandbox workspace with `traces/<run_id>.jsonl`, `spec.json`, `history/` (lineage+ledger including rejects), and tools to read them, then require a structured diagnosis (`divergence_node`, `controlling_surface`, `cause_class`, `repetition_consistency`) before `edits`. Our Codex-CLI backend is already an agent harness (STATUS.md) so a workspace-reading proposer is feasible, but at ~16k input tokens/call and 13-15 s/call it is expensive; start with a deterministic "evidence file bundle" + one agent session per generation, not per candidate.
Copy vs reimplement: prompts (`diagnose-method.md`, `causal-diagnosis/SKILL.md`, `history-analysis/SKILL.md`, `verification-baseline/SKILL.md`) are MIT and directly reusable with attribution after adapting nouns (prompt/tool -> node/contract). Engine code reimplement.

### 4.4 Phase-gated edit types, enforced by the static checker (Value: medium-high; effort S; reimplement)
Their verifier makes the "capability then steering" schedule a hard constraint (steering: no executable change; `verification.py` `steering_scope`) plus "no train-case ids in candidate text" (`anti_cheating`) and a loadability check before measuring. Our `evolve/edits.py` already has typed `EditType` (CONTRACT, HOP, CONTROL_FLOW, CONTEXT_POLICY, TOOL, SUBAGENT_ROLE, MEMORY_POLICY, PROMPT_TEXT, BUDGET_POLICY, ROUTING, PARAMS) and static checks (protected nodes, leakage patterns), which is a stricter taxonomy than theirs. Missing: a schedule over types. Add `allowed_types(generation)` to `EvolveConfig` (structural types first: CONTRACT/HOP/CONTROL_FLOW/TOOL/ROUTING; later PROMPT_TEXT/PARAMS) and reject edits outside the active set in `apply_edit`/static check, and log the share of each type per generation so we can test the "steering collapse" claim (their ablation: 91.5% steering without constraint) on our own proposer. Cheap and testable; we already have the ledger (`store.append_record("harness_edit", ...)` has `type`).
Also copy the train-id leakage check literally: reject edits whose serialized value contains any evolve/gate task_id or name (our "leakage patterns" check should be confirmed to cover task ids).

### 4.5 Selectable-parent discipline + whole-component composition (EvoDAG as code) (Value: medium; effort M; reimplement)
What it is: only ACCEPTED candidates are selectable; declined/rejected are "negative evidence, never selectable" (`optimizer-invariants.md` "Terminology"). The evolve session returns `parent_ids` + `component_sources: {unit -> parent}` where the schema's `enum` per unit lists ONLY candidates that actually changed that unit (`engine.py:243-248` builds `component_source_options` from each accepted candidate's `change.changed_units`; `_evolve_schema` uses it as an `enum`), so the LLM cannot hallucinate a composition; invalid plans are rejected and the session is retried (`result_validator`, engine ~255). The composed child is a real new candidate, finalized and recorded (`CandidateFinalized kind=composition`, engine ~268), and is measured by the usual machinery, i.e. composition is not trusted, it is just another proposal. Fork/backtrack comes for free because candidates are content-addressed.
Ours: `evolve/loop.py` is strictly sequential: each generation starts from the single `parent` passed in; `HarnessSpec` has a spec hash and `add_harness_version(spec.id, ..., parent_hash=...)` records lineage (loop.py), but there is no multi-parent composition and no choosing an older parent. Our edits are JSON-pointer ops on node paths, so composition granularity is finer than their files: `component_sources` could name JSON-pointer subtrees (/nodes/implement) with the same enum-from-diff trick. This is the "branching" feature in PLAN L6.6/§8, and the schema-constrained composition prevents invalid merges.
Where: L6.6 / L7. Effort M. Reimplement.

### 4.6 Lesson store from before/after attribution with evidence-id validation (Value: medium; effort S-M; reimplement)
Reflection categorizes each train case as fixed / regressed / still-failing / still-passing / uncertain (`reflect-method.md`) and emits lessons whose `evidence_case_ids` are validated against the current batch (`engine.py::_validate_lesson_case_ids`, 1364); v1 also auto-builds good/bad pattern lists and a per-scenario registry with categories `consistently_failing | volatile | stable_passing | recently_fixed | recently_broken` (`lesson_manager.py::_classify_scenario`, 123). Reflection runs deferred, after the dev score is known, and gets matched per-case before/after scores (`DeferredWorkScheduled` payload, engine 465).
Ours: `store.records("harness_edit")` ledger holds predicted vs actual delta and proposer calibration (`proposer_calibration`) which they lack, but no per-task fixed/regressed attribution and no lessons. Add `fixed/regressed/still_failing` per task unit to the `harness_edit` record (we already have paired scores, so this is nearly free) and feed "regression-prone nodes" to the next diagnosis. Our calibration (MAE and sign agreement) is something worth keeping and reporting; they do not measure whether their `expected_effect` predictions are right.

### 4.7 Event-sourced run state with replay and durable operation ids (Value: medium for long campaigns; effort L; reimplement ideas only)
`RunState.replay(events)`, stable `operation_id`s per (iteration, step), crash-safe resume that reuses completed sessions and evaluations, fork-from-sequence (`docs/v2-architecture.md` "Resume And Fork"). Our `Evaluator.cache` (loop.py) is in-memory only (keyed by spec_hash, task, seed) — lost on crash; evidence store (SQLite) has runs but evolution progress is not resumable mid-generation. Worth doing before long scorecard campaigns (STATUS "Next" #2). Do after 4.1-4.5.

## 5. Things custom-harness already does better (with evidence)
- **Acceptance statistics**: `selection.py::gate` uses paired bootstrap CIs on both an evolve split (`elo > 0`) and a never-shown gate split with a non-regression bound; theirs is a bare strict mean comparison on 3 cases (`policies.py:122`) with dev only advisory. This is exactly the failure their own ablation shows (regression rate rising without a dev check).
- **Candidate comparison/allocation**: `race()` (successive halving with paired CI) compares K candidates per generation; their loop tries ONE patch per iteration, no tournament and no per-candidate budget allocation; they have no notion of paired uncertainty at all.
- **Typed, programmatic edits**: `edits.py` JSON-pointer ops on a typed `HarnessSpec` with protected nodes and predicted effects; theirs is free-form git diffs of arbitrary Python plus advisory prompts. Ours is statically checkable and exactly forkable; theirs relies on compile/import smoke tests (`verification.py`).
- **Proposer calibration + harness-science ledger** (`loop.py::proposer_calibration`, `store.append_record("harness_edit")`): they log intent/diagnosis but never score the prediction.
- **Objective integrity**: our objective is 0 unless the integrity audit passes (`evaluate.py::score_state`, "no audit = no credit"). Their objective is the GAIA2 judge score, with a benchmark where the judge/oracle is outside the optimizer's write scope; fine for them, not a research-integrity design.
- **Verifier tiers / sealed split / sandbox**: our L3 tier policy and sealed split are not present in AutoSaddler at all (see section 7).
- **Cost accounting**: budget ledger in provider-neutral units (`budget.py`); theirs counts rollouts and tokens but the paper's own limitation list says no per-component cost breakdown.

## 6. Pitfalls, bugs, or anti-patterns seen in their code that we must avoid
1. Acceptance on b=3 with strict `>` (`policies.py:122`): high false-accept rate, and an accepted noise patch becomes a selectable parent forever. Fix by pre-filter + CI gate (4.2).
2. The parent is re-measured on every new batch and its before-score is thus a fresh noisy sample each iteration (`engine.py:283`); no pooling of parent measurements across iterations. We should cache and pool parent scores per (spec_hash, unit) — our `Evaluator.cache` already does; keep that.
3. v1: treating a missing scenario result as score 0.0 (`evaluator.py::compute_pass_rate`) conflates infra failures with task failures. v2 fixed it; do not reintroduce it (our `score_state` partly does, see 4.2).
4. v1: base parent is the latest non-abandoned node, including declined ones (`proposer.py:544-550`), relying on a free-form Session 0 LLM to revert. Declined code leaks into the lineage. Do not select parents by recency.
5. v1: free-form Session 0 does rsync/cherry-pick and edits code before the "before" measurement, so the "before" score belongs to a different program than the selected parent: the paired comparison parent->child is no longer a comparison of one patch. v2 fixed this by composing through the engine, hashing, and measuring `parent` as the composed candidate. Keep composition outside the proposer's free-form control.
6. Dev "quarantine" is by convention only: artifacts are written to `<run>/quarantine/dev/...` (`engine.py:1087`) inside the same run directory that the optimizer's workspace was copied from, and providers run with broad permissions (`providers/claude.py:23` `permission_mode: "bypassPermissions"`, `copilot.py:147` `PermissionHandler.approve_all`; codex has a `workspace-write`/`danger-full-access` choice, `codex.py:26-30,162`). Absolute paths to the run dir are not blocked [inference: I did not read the workspace/cwd isolation beyond `_prepare_session_attempt_workspace` (engine 1225), which copies the mutation workspace into an attempt dir but does not hide the run dir]. A proposer with `run_commands` can in principle read dev traces. Our L0 sandbox design must run the proposer in an isolated filesystem without the evidence store mounted.
7. Anti-cheating is a substring test for train case ids (`verification.py` `anti_cheating`): trivially evaded by paraphrase/derived constants; it protects only against literal id leakage. Use it as a cheap tripwire, not a safeguard.
8. Steering rule is enforced only for `.py` suffix (`steering_scope`); a prompt string inside a `.py` file is blocked, but a `.json`/`.yaml`/`.md` config can still change loop behaviour (e.g. iteration limits in config) in the "steering" phase [inference].
9. Optimizer sessions are expensive and sequential: `diagnosis_patch_timeout_seconds: 18000` (5 hours per session, `meta_are_full.yaml`); retries 2. Their cost per attempted patch is dominated by the session, which the paper acknowledges. Do not assume the "10x fewer rollouts" implies cheaper campaigns in dollars.
10. Dev-best-of-N selection: final `MeanDevelopmentRanking` picks the max dev mean over all accepted candidates (`policies.py:146`), reselecting on the same 65 dev cases used to steer the evolve LLM; mild selection bias on dev, which is why they need a third test split. Same issue for our `gate` if we reuse it for both selection and acceptance; keep sealed separate (we do).
11. Resume complexity: v2's engine is 1.4k lines, mostly event/operation-id bookkeeping (`_ensure_session` ~300 lines). Adopt the idea selectively.

## 7. Verifier / evaluation / safety handling
- Evaluator: GAIA2/Meta-ARE benchmark with an LLM judge model (`judge_model` in configs); score from the benchmark result jsonl normalized by `MetaAREResultNormalizer` (`evaluator.py`): strict coverage check (duplicate/unexpected/missing (case, repetition) keys raise), finite-score check. Evaluator fingerprint is part of observation identity (`Observation.create`, `domain.py`) and resume rejects a changed plugin environment (`docs/v2-architecture.md`).
- Splits: train / development / test disjoint, retaining visibility (`docs/v2-architecture.md` "Safety Invariants"); test never opened by the engine; dev traces not captured (`capture_traces` only for train). Provenance: pinned source commits, dataset manifest hashes, demo-filesystem digests (`configs/v2/*.yaml` fields).
- Mutation safety: writable/forbidden path lists with overlap check (`git.py:66-77`), isolated git worktrees, exact-delta capture, declared `changed_paths` must equal observed (engine 1315), import check via `uv run` with timeout (`verification.py`). Forbidden paths include validation, scenarios, benchmark, tests, data, checkpoints.
- Exploit handling: no exploit detection of the optimized agent's behaviour (e.g. reward hacking the judge); relies on the forbidden-path list and prompt invariants ("Do not modify evaluation, benchmark, test, or protected data", `optimizer-invariants.md`). The training evidence includes judge rationale, which the optimizer reads; the judge itself is a fixed LLM and is not perturbed/quarantined.
- Sandbox of the optimizer: none beyond the workspace copy and provider permission flags (point 6 in section 6). Agent execution of the harness in benchmark runs is done by Meta-ARE's own runner (`runner.py`, not read).
- Run-level safety: `RunFailed` / `RunInterrupted` events; `ObservabilityDegraded` events; provider trace exports contain prompts and tool outputs and "should be treated as sensitive" (docs).

## 8. Bottom line
1. The "10x fewer rollouts" is a design pattern, not an algorithm: 3-case train mini-batch that doubles as diagnosis evidence, skip if no failures, verifier-reject before measuring, and spend full dev evals only on mini-batch winners (`engine.py:283-296,443`; `policies.py:138`). Adopt it as a promotion stage in front of our race/gate.
2. Their acceptance rule is too weak (strict mean on 3 cases; dev advisory) and the paper's "generalization-aware selection" is mostly an LLM prompt convention; our paired-CI + never-shown gate split is better, keep it and add their matched-valid pairing (exclude infra errors).
3. Their real edge is diagnosis depth: an agentic workspace with full per-repetition traces, history bundle, a mandatory first-divergence causal procedure, and diff-vs-claim cross-check. Our `propose.py::diagnose` is a 1500-char error-string digest; upgrading it is the highest-value change, and their MIT prompt assets can be reused.
4. Patch taxonomy is just a phase schedule + advisory skill text (hard rule only: no .py in steering); EvoDAG is accepted-only parents + enum-constrained whole-file composition. Cheap to copy as typed-edit scheduling and component-source composition; neither is a proven mechanism (no ablation of EvoDAG in the paper summary).
5. Only GAIA2 is in the repo (SWE-Bench Pro/Terminal-Bench "coming"), and the quarantine/sandbox of the proposer is weak; do not treat the reported numbers as reproduced or the safety design as a model.
