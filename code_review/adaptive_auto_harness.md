## 1. What the code actually does (architecture map)
- Entry point `solve_all_with_evolution.py` is a batch loop: route tasks -> solve in parallel -> evaluate -> `Observer.collect` -> evolve -> commit. Launchers `scripts/{poly,ctf_dojo,futurex}_hypothesis.sh` all pass `--temporal-reveal`; the paper's headline cell "H4_multi_nav" = `--navigation` + config `orchestrator: structured_navigation` (`scripts/ctf_dojo_hypothesis.sh:158-162`, `experiments/*/configs/structured_navigation_evo.yaml`).
- Harness tree = ONE git repo that IS the solver workspace (`prompts/system.md`, `skills/`, `tools/`, `infra/`, `memory/`, `README.md`). `VersionControl` wraps the git CLI (`engine/versioning.py`: init/commit/tag/rollback_to_tag/create_branch/checkout_branch/rebase_branch/sync_paths_from/branch_exists, lines 22-392). Tags `evo-N`, `pre-evo-N`, `evo-N-build-<target>-<attempt>` etc. Tree metadata (`StrategyTree`/`BranchInfo`: name, created_at_cycle, last_routed_cycle, total_tasks, total_passed, description, failed_checkouts) is serialized to `tree_state.json` (`types.py:124-176`, `solve_all_with_evolution.py` persist block near 807).
- Solve-time adaptation is a pluggable `Adaptation` protocol (`protocol/adaptation/base.py:206-239`: `select` per task, read-only, parallel; `materialize` once per key mutating the workspace; `prepare`; `project`). Operators: `whole_store`, `tree_routing` (`algorithms/navigation/adaptation.py:32-82`), `retrieval` (dense top-k), `agentic_filter` (`operators.py:32-162`). Registry at `registry.py:104-111`.
- Evolver = `NavigationEngine` (`algorithms/navigation/engine.py`) delegating to a template. The paper's 4-role evolver is `StructuredNavigationTemplate` (`templates/structured_navigation.py`): Analyst -> Researcher(s, up to 3 parallel) -> Builder -> Verifier, per-target (main first, then each branch), then "guardrails". Each role is the same Opus model driven by a different system prompt with a single `workspace_bash` tool in a Docker container (`_evolver_tools.py:EvolverSandbox`), mounts `/solver_workspace`, `/evolver_workspace`, `/trajectories:ro`.
- Persistent cross-cycle evolver state lives in a sibling dir `evolver_workspace/` (`_evolution_workspace.py:17-23`): `task_board.md`, `research_log.jsonl`, `architecture.md`, `insights.jsonl`, `strategy_tree.md`, `tests/`, `evolution/`.

## 2. Core loop, step by step (with file:line citations)
Per batch (`solve_all_with_evolution.py`):
1. `adapter.prepare(...)` (line ~397), then if branches exist, `adapter.select(ws_dir, task)` for every task via a thread pool of up to 10 workers (`:412-414`). Else all tasks -> "main".
2. `TreeRoutingAdaptation.select` builds a context from `Task ID`, metadata keys `category/event/challenge/year`, plus full `task.input` (`adaptation.py:47-57`) and calls `NavigationEngine.navigate` (`engine.py:138-201`).
3. `navigate`: returns "main" if no branches; filters to "viable" branches (in git AND `failed_checkouts <= 2`, `:204-219`); reads, per branch, ONLY `description` and `README.md` via `git show` (`_read_branch_leaves`, `:317-343`); prompt is README truncated to 1000 chars each (`prompts.py:build_navigate_prompt`, `readme[:1000]`); one zero-temperature, `max_tokens=256` JSON call `{"branch","confidence","reason"}` (`engine.py:176-189`). Non-main branch with `confidence < 0.7` -> main (`:190-198`). Any exception is swallowed (`except Exception: pass`, `:199-200`) and returns "main".
4. For each group: `adapter.materialize` = `git checkout <branch>` (fall back to main and bump `failed_checkouts`, `adaptation.py:59-73`); `agent.reload_from_fs()`; `backend.build_prompts` captures the harness state "while on the branch"; `infra/*.py` serialized into args; futures submitted (`solve_all_with_evolution.py:440-505`). After all groups are submitted the working tree is checked out back to main (`:504-508`). Solvers therefore run from captured strings/files, not live git state.
5. Evaluate in-worker (`run_eval`), collect `batch_results` with per-task timeout/crash fallbacks (`:510-590`). `strategy_tree` stats updated: `b.total_tasks += 1; b.total_passed += r["success"]` (`:640-650`) and a `RoutingEntry` appended.
6. Temporal reveal gate: watermark = MIN `creation_date`/`timestamp` of the NEXT batch (`:714-729`); `observer.set_batch_timestamp(watermark)`, `observer.collect(observations)`, `observer.update_reveal_state(cycle, watermark)` (`:729-736`). See mechanism below.
7. `routing_log.jsonl` appended per task with `properties`, `branch`, `cycle`, and `success` ONLY if `observer.is_revealed(iid)` (`:739-757`).
8. `versioning.commit("pre-evo-N: score=<batch_score>")` (`:758-761`; label omitted only if `trajectory_only`), then `evolve_with_navigation` (`engine.py:345-386`): snapshot, apply `observer.filter_batch_for_evolver(batch_results)` (strips `success/score/detail/feedback/feedback_detail` for unrevealed tasks), then `template.execute`.
9. `StructuredNavigationTemplate.execute` (`:79-130`): update `strategy_tree.md` from routing stats -> Phase 1 Analyze (`:132-300`) -> Phase 2 Research -> Phase 3+4 Build/Verify per target -> guardrails.
   - Analyze: Opus with bash over `/trajectories`, writes `task_board.md`. Output must match a strict regex format ("- tag: N tasks fail ... PRIORITY: X -> TARGET: main|branch/<name>", `_evolution_workspace.py:validate_task_board` ~106-148); one repair attempt (`:210-238`), then no-bash fallback. Prompt `analyst_nav.md` instructs branching by CAPACITY CONTENTION (system prompt hard cap `MAX_PROMPT_CHARS = 10_000`, `_guardrails.py:25`), ROUTABILITY, VOLUME (>= ~15 tasks).
   - Research: top-3 gaps parsed from the task board by regex (`_extract_gaps`, `:497-545`), parallel research agents write JSONL to `/evolver_workspace/tests/research_<gap>.jsonl`; code parses JSON blocks from file + chat text, `setdefault`s most required fields incl. `tested=True` (`:470`), validates the 15-field schema, appends to `research_log.jsonl`. Dedup of effort = agents are told to read the log; failed approaches are kept (`get_failed_approaches`).
   - Build/Verify (`:551-690`): main first; then each branch target from the task board: `create_branch(name, "main")` + `BranchInfo(description=", ".join(regimes[:3]))` (`:578-585`), rebase onto main if main mutated, fallback `sync_paths_from("main", ..., ["tools/","infra/","tools/registry.yaml"])` (`:588-598`). Up to 3 build attempts; each: `_run_llm(builder)` -> `git commit` (no commit => stop) -> `_verify` -> if pass, mark mutated; else `rollback_to_tag(pre_build_tag)` and retry with `builder_retry.md` containing `report[:500]` (`:690-745`).
   - Verify (`:805-860`): one LLM agent with bash, prompt `verifier.md` ("Test the tools and infra pipelines ... Sample query ..."), `cutoff_date="2026-01-15"` hard-coded (`:821`), verdict = substring search for `VERDICT: PASS` or `VERDICT: PARTIAL` in the LLM text; PARTIAL counts as passed (`:832-839`). `isolate_to` is parsed (`:846-851`) but never consumed (grep: only that file).
   - Guardrails (`:870-925`): strip search-count caps from prompt, truncate `prompts/system.md` to 10k chars, run `infra/search_pipeline.py` smoke check (`verify_pipeline`) — FutureX-specific; bundle infra on main.

### Temporal-reveal feedback: exact mechanism
`engine/observer.py`. Two flags: `trajectory_only` (never expose labels) and `temporal_reveal` (per-task, overrides trajectory_only).
- Archive: in temporal mode EVERY task's label+`resolution_date` is appended to `feedback_archive.jsonl` (`:257-280`).
- In-batch gate: `_label_revealed(obs, batch_ts)` (`:43-59`): a task with NO `resolution_date`/`resolved_at` in `task.metadata` is revealed immediately; with a date it is revealed iff `resolution <= batch_ts`; `batch_ts=None` -> hidden. Revealed tasks get label fields written in `batch_NNNN.jsonl` and join `_revealed_ids` (`:282-312`); unrevealed ones are written without labels.
- Later reveal: `update_reveal_state(cycle, watermark)` scans the archive each cycle, for any task not in `_revealed_ids` with `resolution <= watermark` appends the label to `observations/revealed_supplement.jsonl` (`:369-440`) and logs an ASCII reveal table (`render_reveal_update`, `:62-109`). `get_recent_logs` overlays the supplement onto older batch records (`:453-495`).
- Watermark choice (driver, not observer): MIN creation_date of the NEXT batch, i.e. a label is visible only if it resolved before the first task of the upcoming batch was posed (`solve_all_with_evolution.py:714-729`, comment explains the leakage rationale).
- Enforcement points: (a) `filter_batch_for_evolver` strips label fields from in-memory batch dicts before any template builds a prompt (`observer.py:347-367`, called at `engine.py:366-370`); (b) routing_log gating (`:753`); (c) Docker bind-mount of `/dev/null` over `feedback_archive.jsonl` in both workspaces (`_evolver_tools.py:178-190`); (d) `/trajectories` mounted read-only containing only conversation + patch (`observer.py:213-220`). The evolver is TOLD only the unrevealed-as-"pending" semantic via missing keys (e.g. `"pending"` in index, `:739`).
- Unrevealed tasks keep behaviour visible (turns, conversation), only labels are removed.

## 3. Paper/summary vs code discrepancies
1. "Router reads each branch's workspace and selects best match" (summary). Code: router sees only `description` + first 1000 chars of `README.md` (`engine.py:317-343`, `prompts.py`). The `_read_branch_leaves` docstring itself claims it reads "system prompt, skill names, and tool registry" — it does not.
2. Branch README is destroyed every cycle. `builder_branch.md` tells the builder to write a README with a mandatory "When to route here" section and says the router "only sees the README". But after the build, `structured_navigation.py:609-611` unconditionally overwrites it with `# <branch>\nSpecialization: <regimes[:5]>`. The router system prompt says branches without a clear "When to route here" section are "low-confidence candidates — prefer main" (`prompts.py`). So in the paper-config template every branch is a low-confidence candidate by construction. This is the strongest code-grounded explanation of why the deployed router is far below oracle (see 4.1/4.2). [inference: that this caused the reported 50.2 vs 87.7 gap; the code shows the mechanism but there are no router logs in the repo to confirm.]
3. "Router training": there is none. The router is a zero-shot, temperature-0, single-call LLM prompt with no examples, no branch performance history, no learning from routing outcomes, no held-out routing evaluation. `grep -ri oracle` over code/config/scripts returns nothing: the 87.7% oracle number cannot be reproduced or inspected from this repo, and no per-task per-branch counterfactual runs are implemented. The `agentic_filter`/`retrieval` operators (embedding, `catalog.py`) are alternatives, not trained routers either.
4. "Branches pruned by the verify gate (a branch that fails to beat main on its own regime is dropped)" (analyst prompt `analyst_nav.md`, STEP 4). Code: verify is an LLM tool-smoke test with no comparison against main, PARTIAL passes, and no code deletes branches. `promotion_threshold` and `staleness_window` exist in `config.py:79-80` but are referenced nowhere else (grep). Matches the summary's "Not automated: branch pruning", but contradicts the prompt text given to the analyst.
5. Verifier "tests builder outputs against benchmark tasks" (summary). Code: verifier gets ONE sample query (`_extract_sample_query`, not read) and a hard-coded cutoff date `2026-01-15` (`:821`), writes its own tests, and emits a free-text verdict. No benchmark-task replay, no regression gate, no baseline comparison. For branches, regime tasks are selected by `reg in task_id.lower()` (`:807-812`) — regime tags are category names and task ids are `event_market_snapshot` (polybench) so this almost always falls back to the whole batch.
6. "Verified" research: `works` and `tested` are self-reported by the research LLM, and `tested` defaults to True when absent (`:470`); the builder only builds from `works==True` records (`get_verified_approaches`). Nothing independent verifies a research claim.
7. Temporal reveal on PolyBench is a no-op by construction (my finding, from code): `PolyBenchBenchmark.get_tasks` deliberately withholds `resolved_at` from `Task.metadata` (`polybench.py:90-93`, ground truth kept in `_ground_truth`), but `Observer._label_revealed` reads exactly `metadata["resolution_date"]` or `["resolved_at"]` and treats a missing date as "revealed immediately" (`observer.py:50-54`). `update_reveal_state` also skips records with no resolution_date (`:398-400`). `grep resolution_date` shows only FutureX injects it (`benchmarks/futurex/futurex.py:36`). So for PolyBench and CTF all labels are revealed immediately (CTF is intentional per observer docstring; the `config.py:44-47` comment saying CTF labels "remain hidden" contradicts the observer code). Also `config.py:43` says watermark = `max(creation_date)` while code uses `min`. PolyBench rows are sorted by `resolved_at` (`polybench.py:250`) so batches are ordered by resolution time, not creation. [inference: unless the PolyBench task dict gets a resolution date from elsewhere I did not read, the paper's "temporal-reveal ablation hurts on all benchmarks" cannot be testing the gate on PolyBench.]
8. Summary numbers inconsistent (not code): "oracle 87.7 vs 60.2 baseline (no branching)" but "deployed router ~50.2" which is below 60.2; and Figure 7 text says deployed captures partial headroom. If no-branching is 60.2 and full system is 50.2, branching hurt on CTF-Dojo. Cannot be resolved from the repo. Treat the 37.5-point "headroom" claim skeptically. [inference] An oracle that picks the best of N noisy single-run branch outcomes per task is upward-biased by selection (pass@N effect), not a true achievable ceiling.
9. Human-in-the-loop: implemented (`human_interface.py`: stdin/Telegram/Slack; `request_human_action` tool, `_evolver_engine.py` `_run_llm`) but all three `structured_navigation_evo.yaml` have `hitl_enabled: false` and the tool is gated on `config.extra["human_in_the_loop"]`; credential supply and task-board steering from the summary are not exercised in the shipped configs.
10. Evolver network: research prompt says "You can utilize Full network access if available" but PolyBench and CTF configs set `evolver_sandbox_network: none` (only FutureX is `bridge`). Research on those two benchmarks therefore cannot reach external services.

## 4. Mechanisms worth adopting into custom-harness (ranked by expected value)
Our current state: `STATUS.md` says branching/routing is "Next #5" and nothing exists; `evolve/` has typed edits, racing, held-out gate, lineage, ledger; there is no `branch`/`router`/`reveal` in `src/` (grep of src).

1. **Adaptation seam with `select` (read-only, no feedback) / `materialize` split** (`protocol/adaptation/base.py:206-239`; `registry.py`). Why better: lets us swap router types (whole-store, branch-routing, per-task retrieval) behind one tiny interface and A/B them on the same tasks; invariant "selector never sees reward" is stated in the docstring. We have nothing; PLAN L6.6 needs exactly this. Layer: L6.6 (+ L0 harness spec materialization). Effort: S. Reimplement (tiny; MIT copy possible with attribution but our spec is a graph interpreter, not a file tree).
2. **Temporal-reveal as archive + watermark + supplement overlay** (`observer.py:43-59, 193-320, 369-495`). Mechanism worth copying: store full labels in a sealed archive, expose only labels with `resolution <= min(creation of next batch)`, expose late labels via an append-only supplement overlaid at read time, and a reveal log. Our PLAN §6 line 177 just names the mode. Layer: L2 evidence store + L3 verification + L6 (diagnosis input filter). Effort: M. Reimplement; fix their flaws (section 6): single choke point, sealed archive not just a masked file, no aggregate-score leaks, fail-CLOSED when the date is missing.
3. **Root-cause-first branching protocol keyed on capacity contention** (`analyst_nav.md`, `build_capacity_signal`/`scan_regime_accretion` in `_evolution_workspace.py:380-550`, not read in detail). Idea: branch when the shared harness is at/over a hard size cap and a regime has a self-contained rule cluster, is routable from a task property, and has volume (>=15 tasks), rather than when pass-rate is low (they explicitly say outcomes are confounded by composition/luck). Complements our planned "frontier-coverage voting (MoB)" (PLAN line 172). Layer: L6.6. Effort: M. Reimplement as a deterministic trigger on our typed harness spec (we can measure prompt/spec token budget exactly, no regexes over markdown).
4. **Persisted structured research log with negative results + schema gate** (`research_log.jsonl`, `REQUIRED_RESEARCH_FIELDS` `_evolution_workspace.py:30-37`, `validate_research_record`, `get_failed_approaches`). Matches our PLAN L5 "negative memory / dead-ends". Take: 15-field record incl. `does_not_cover`, `complementary_to`, `credential_needed`, `works`; read-before-test rule. Do NOT take: self-reported `works`/default `tested=True`. Layer: L5. Effort: S. Reimplement with `works` derived from a recorded T1 evidence id, not LLM claim.
5. **Build->verify->rollback-to-checkpoint retry with failure report fed forward** (`structured_navigation.py:690-745`, tags `evo-N-pre-build-<target>`). We already have exact fork/backtrack (STATUS L0), so adopt only the pattern: max 3 attempts, rollback between, verifier report in retry prompt. Layer: L6. Effort: S. Reimplement.
6. **Task-board output contract with validator + one repair pass** (`validate_task_board`, repair prompt `analyst_repair.md`, `:210-238`). Our contracts with bounded retries already do this at L0; their trick of tying every failure bullet to a TARGET (main vs branch/<regime>) is the useful part for typed edits (`routing rule` edit type, PLAN line 163). Effort: S.
7. **Branch viability filter + routing fallbacks** (`_viable_branches`, `_resolve_branch_name`, `_sanitize_branch_name`, `engine.py:204-300`): only offer branches that exist and have not failed checkout >2 times; coerce LLM names to legal refs. Cheap robustness. Effort: S. Reimplement.
8. **Capability-bundle/regime README as the routing interface** — the idea (each branch publishes "When to route here / NOT applicable / Strategy / Known limitations", `builder_branch.md:27-60`) is sound; the implementation is broken (finding 3.2). For us: generate the routing descriptor deterministically from the branch's own gate results (which regimes it beat the parent on, with CIs) instead of asking an LLM to write prose. Effort: M.
9. **Reveal-aware dashboards**: per-cycle ASCII reveal table and stratified outcome x property tables sorted worst-relative-to-mean (`render_reveal_update`; `build_stratified_outcome_table` named, not read). Low priority. Effort: S.

Not worth adopting: git-as-store (our spec is typed and has exact fork/backtrack already); regex-parsed markdown task boards; LLM-written README as the only routing signal; substring "VERDICT: PASS" parsing.

## 5. Things custom-harness already does better (with evidence)
- Verification: ours has tiers T0-T6, bootstrap CIs, paired test-example bootstrap, held-out hidden-test verify and non-regression gates (`STATUS.md` L3/L6, `verify/`, `evolve/`). Theirs: LLM substring verdict, PARTIAL=pass, no baseline comparison, no CI (`structured_navigation.py:832-839`).
- Typed, bounded harness edits with static checks (protected nodes, leakage patterns) vs their free-form "builder writes whatever to the workspace via bash" and size-cap truncation of `prompts/system.md` after the fact (`_guardrails.py:142`).
- Budget accounting (L1 ledger, hard caps) — theirs has timeouts and an output cap only; paper reports 100-365M tokens/run with no in-code budget gate (grep: no budget ledger).
- Sandbox: ours is non-root, read-only rootfs, caps, optional gVisor; theirs is `alpine` + `docker run --user uid:gid` with default capabilities and read-write bind mounts, forwards `SERPER/JINA/EXA` API keys into the container (`_evolver_tools.py:204-208`), and uses `os.getuid()` (Linux only, `:168`).
- Evidence/claims: ours claims only from evidence with content-addressed blobs (L2); theirs trusts LLM-written JSON `works` flags.
- Private-data guard in prompts (`runtime/template.py`) vs their leakage handled by masking one file path.

## 6. Pitfalls, bugs, or anti-patterns seen in their code (cite) that we must avoid
1. **Silent router failure modes**: bare `except Exception: pass` -> "main" (`engine.py:199-200`); router only runs if `self.llm` is a `BedrockProvider` (`:176`), else silently always "main". Never degrade routing silently; log + count fallbacks.
2. **README overwritten after build** (`structured_navigation.py:609-611`) negating the very interface the router depends on. Lesson: the routing descriptor must be a build artifact validated by a test ("router can pick this branch for its own regime's held-out tasks"), not free text.
3. **Stats leak in non-structured templates**: `b.total_passed += r["success"]` uses the UNGATED label for current-batch tasks (`solve_all_with_evolution.py:640-650`) and `inline.py:48-51` prints `total_passed/total_tasks` into the evolver prompt. [inference: inline template leaks under temporal reveal; structured_navigation instead parses the gated routing_log.]
4. **Aggregate-label leak through git**: commit messages `pre-evo-N: score=<batch_score>` and `evo-N: skipped (score=..)` (`solve_all_with_evolution.py:758-761`, `~865`) are written in the repo that is bind-mounted to the evolver; the evolver has bash + git (`_evolver_tools.py` mounts, `Do NOT run git` is only a prompt rule in `builder_system.md`). Only `trajectory_only` suppresses them. So the current batch's score (computed from labels the gate hides) is readable. Also `evo_trigger_threshold` uses the immediate `batch_score` to decide whether to evolve (`:~770`), default 0.0 (off).
5. **Task metadata written ungated**: observer records `task.metadata` unconditionally (`observer.py:246-250`); FutureX puts `expected_output` (ground truth) into metadata (`futurex.py:42`) and the evolver mounts `/solver_workspace/evolution/observations` when the observer dir is inside the solver workspace (it is, unless `orchestrator == "structured_evolution"`, `solve_all_with_evolution.py:262-270`; for `structured_navigation` evo_dir = `ws_dir/"evolution"`). The mask only covers `feedback_archive.jsonl` (`_evolver_tools.py:178-190`). [inference: FutureX ground truth is reachable by the evolver in the paper-config run; I did not run it.] Leakage defence by masking one filename is brittle; seal labels in a separate store the evolver can never mount.
6. **Missing-date => revealed** (`observer.py:50-54`): fail-open. A benchmark that hides resolution date from metadata (PolyBench) silently disables the gate (3.7). Fail closed and assert at startup that every task has a resolution date when `temporal_reveal` is on.
7. **Dead config / dead stats**: `promotion_threshold`, `staleness_window`, `isolate_to`, branch pruning — declared, never used. Branches only grow; stale branches keep being offered to the router. `last_routed_cycle` is set but never read.
8. **Branch drift**: rebase onto main frequently conflicts (both edit `prompts/system.md`); on failure only `tools/` and `infra/` are synced (`:588-598`), so branch prompts/skills never inherit main's later general improvements. Our branches must carry explicit lineage and re-gate after parent change.
9. **Regex-parsed LLM markdown as control plane** (task board bullet regexes, `_extract_gaps`, `extract_targets_from_task_board`, branch slug sanitizer) — fragile, needed repair/fallback paths. Use typed JSON via our contract layer.
10. **Hard-coded benchmark constants in the generic template**: verifier `cutoff_date="2026-01-15"` (`:821`), `verify_pipeline` requires `infra/search_pipeline.py`, `MAX_PROMPT_CHARS=10_000`, news-RSS seed hints (`_guardrails.py`). Not portable to research tasks.
11. Path built from LLM output: `/evolver_workspace/tests/research_<gap>.jsonl` where `gap` is an LLM-emitted tag (`:455`) — constrained by `\w` regex in `_extract_gaps`, so low risk, but pattern to avoid.
12. Loose name resolution: `name.endswith(stripped)` match in `_resolve_branch_name` (`engine.py:~262`) can route `branch/x` to `branch/prefix-x`.
13. Two workers/processes switching the same working tree by `git checkout` is the concurrency model; they mitigate by capturing prompts before returning to main (`:~447-503`), but `reload_from_fs` mutates shared `agent` state; correctness depends on ordering. Do not use checkout-as-materialization with parallel solvers; use read-only snapshots/worktrees (they have `checkout_branch_worktree` in `versioning.py:169` but the solve loop does not use it).

## 7. Verifier / evaluation / safety handling
- Evaluation of solver outputs is benchmark-side and deterministic: PolyBench scores accuracy + simulated order-book fill return with a confidence gate 0.6 (`polybench.py:135-226`); ground truth kept in a private dict, not in `Task.metadata` (`:76-93`) — good practice. FutureX/CTF use benchmark-specific graders (FutureX embeds `expected_output` in metadata, see 6.5).
- Evolver verification = LLM verifier as described (3.5); no held-out gate, no exploit/quarantine concept, no reward-hacking checks (an evolver that reads `/trajectories` could overfit; unrevealed labels are the only protection). Branch quality is never tested against main.
- Sandbox: Docker `alpine` + bash/git/python libs, `--network none` by default, runs as host uid, no `--cap-drop`, no read-only rootfs, no CPU/mem limits, bind-mounted workspaces writable; 60 s per command, 100 KB output cap with head+tail truncation (`_evolver_tools.py:78-99, 248-262`). API keys (SERPER/JINA/EXA) are forwarded in env (`:204-208`). `make_workspace_bash` raises if Docker is unavailable ("no insecure fallback", `:~318-326`) — a good rule we share.
- Evolver-written tools later run in the solver sandbox (`agents/*/sandbox.py`, not read).
- Human gate: optional stdin/Telegram/Slack tool, disabled in shipped configs.
- Reproducibility: temperature 0 for solver/evolver, resume via `tree_state.json`, `history.jsonl`, `results.jsonl`; no seeds recorded; no committed result logs (db file empty), so none of the paper numbers can be checked against artifacts in this repo.

## 8. Bottom line
- Real, MIT-licensed code, but the interesting part (git-branch tree + LLM router + 4-role Opus evolver) is thin: the router is a zero-shot README-reading prompt with no training and the oracle number is not in the repo.
- The deployed-vs-oracle gap has a concrete code cause: branch READMEs are overwritten with a one-line stub (`structured_navigation.py:609`) while the router prompt demands "When to route here" or defaults to main; plus no verify-vs-main gate and no pruning. For PLAN L6.6: train/evaluate the router on a held-out split against per-task oracle, and build routing descriptors from gate evidence, not prose.
- Temporal reveal is a good mechanism (archive + min-next-batch watermark + supplement overlay) but leaky and fail-open in code (PolyBench no-op, git commit scores, ungated metadata); adopt the mechanism, fail closed, seal labels outside the evolver's mounts.
- Adopt: adaptation seam (select/materialize), capacity/routability/volume branching trigger, negative-result research log; avoid: regex-parsed markdown, LLM-verdict verifier, checkout-based materialization, self-reported "verified".
