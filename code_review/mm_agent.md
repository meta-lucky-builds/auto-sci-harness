## 1. What the code actually does (architecture map)
A strictly **sequential, deterministic, single-pass pipeline of LLM prompts** (no tool-use agents, no self-modification, no cross-run memory). Entry: `MMAgent/main.py:11 run()`.
- Stage 1 `utils/problem_analysis.py:37 problem_analysis`: dataset summary (LLM) -> problem analysis actor/critic/improve (`agent/problem_analysis.py:381`) -> high-level modeling actor/critic/improve (`:401`) -> decompose into `tasknum` subtasks + refine each (`agent/problem_decompse.py:355`) -> dependency analysis + DAG (`agent/coordinator.py:111`).
- Stage 2 `utils/mathematical_modeling.py:380`: per subtask: task analysis -> HMML retrieval (top-k methods) -> formulas actor + critic/improve loop -> modeling-process actor (`agent/task_solving.py:98-106`).
- Stage 3 `utils/computational_solving.py:282`: if the problem has a dataset (`with_code = len(problem['dataset_path']) > 0`, `utils/problem_analysis.py:62`), generate code, run via `subprocess`, debug loop; else skip code. Then LLM-written "result", "answer", and chart prose.
- Stage 4 `utils/solution_reporting.py` (LaTeX paper): **commented out as "optional"** in `main.py:28-31`; it is not part of the default run.
- Config `config.yaml`: `top_method_num: 6, problem_analysis_round: 1, problem_modeling_round: 1, task_formulas_round: 1, tasknum: 4, chart_num: 3`. So actual critic rounds by default = 1 each (code defaults to 3 for problem analysis/modeling, `agent/problem_analysis.py:381,401`, but config overrides).
- Memory = two in-process dicts on `Coordinator` (`memory`, `code_memory`, `coordinator.py:64-65`), keyed by task id, filled in `computational_solving.py:306,318`; dependent tasks get prior tasks' description/method/result/code-structure injected as text (`mathematical_modeling.py:325-377`). Nothing persists across problems.
- LLM layer `llm/llm.py`: one OpenAI-compatible client, fixed temp 0.7, usage tokens accumulated; **errors are returned as the string `"An error occurred: ..."`** (`llm.py:93-94`).

## 2. Core loop, step by step (with citations)

### 2a. Hierarchical modeling-method library (HMML) and retrieval
- Library is a **markdown file, not a learned/curated structure with metadata**: `MMAgent/HMML/HMML.md` (323 lines). Headers `##` = domain, `###` = subdomain, sometimes `####` = sub-subdomain, `- name: description` bullets = leaf methods. My count with grep: 5 `##`, 18 `###`, 12 `####`, 97 `-` bullets (paper summary says 5 / 17 / ~98: roughly matches, not identical; the actual 5 domains are Operations Research, Optimization Methods, Machine Learning, Prediction, Evaluation Methods — the summary's domain names ("dynamics modeling", "statistical inference"...) do not match the file).
- Parsed at every `MethodRetriever.__init__` by `utils/convert_format.py:markdown_to_json_method` into nested dicts (`retrieve_method.py:206-218`); the constructor **rewrites `HMML.json` on every construction** (`:216-218`) and a new `MethodRetriever` (which also loads the HF embedding model `Alibaba-NLP/gte-multilingual-base` with `trust_remote_code=True`, `embedding.py:25`) is built **once per subtask** (`mathematical_modeling.py:382`).
- Scoring `retrieve_method.py:145-203 MethodScorer`: top-down tree walk. At each level, score *all siblings in one call* (embedding mode: cosine*100 of query vs `"method: description"`, `embedding.py:60-85`; LLM mode: `METHOD_CRITIQUE_PROMPT` rating Assumptions/Structure/Variables/Dynamics/Solvability 1-5 per method, `retrieve_method.py:220-228`, template.py:87). Leaf score = `0.5*mean(ancestor scores) + 0.5*leaf score` (`:189-190`; ancestors = only scored non-root nodes, so the top-level domain is excluded — `current_score` is None for roots, `:174`). All leaves are flattened, sorted, top-k returned as `**method:** description` text (`:233-241`). Default is `method='embedding'` and **the LLM-critique scorer is never called by the pipeline** (`mathematical_modeling.py:391` calls with default). Query text = task description + task analysis (`:390`).
- Note: it is **not pruned/hierarchical search**: every node at every level is scored, then leaves ranked globally. The hierarchy only contributes the parent-score prior. [inference] With embeddings this costs one embed call per internal node, cheap.
- `rag=False` mode returns the *entire* markdown (`:243`), i.e. the paper's retrieval ablation is a one-line switch.

### 2b. Actor-critic modeling refinement
- Fully in `agent/task_solving.py:98-106 modeling()`: `formulas = actor(...)`; `for i in range(round): critique = critic(formulas); formulas = improve(formulas, critique)`; then `modeling_actor(formulas)`. Default `round=config['task_formulas_round']=1`.
- Same actor/critic/improve pattern at problem level (`problem_analysis.py:381-407`).
- The critic prompt (`template.py:339-385`) asks for critique on Accuracy/Rigor, Innovation/Insight, Applicability, and explicitly says **"without offering any constructive suggestions"**; the improvement prompt (`:386-411`) consumes critique + prior text and is told "DO NOT mention any previous formulas content". Critic and actor are **the same model with the same temperature**, no external signal, **no convergence test or score**: it runs exactly `round` times, always accepting the rewrite (no accept/reject, no comparison vs. previous version).
- The modeling-process critic/improve loop is **commented out** (`task_solving.py:112-126`) though `TASK_MODELING_CRITIQUE_PROMPT` still exists (`template.py:436`). Paper summary says critic covers "model adequacy ... until convergence or max iterations"; code has no convergence.

### 2c. "MLE-Solver" — what it actually stands for
- **The string "MLE" appears in the repo code nowhere except inside unrelated words** (grep over `template.py` hits only inside words like "exaMpLE"/"simpLE" matches; no identifier, class, or file named MLE). The only definitional mention is `README.md:178`: "Autonomously generates and iteratively improves code using MLE-Solver". It is **never expanded in the repo**; there is no class `MLESolver`. The survey summary's expansion "Maximum Likelihood Estimation Solver" is **not supported by the code** (nothing computes a likelihood). [inference] The name is borrowed from the MLE-bench / "MLE-Solver" module of Agent Laboratory ("ML Engineer" solver, Schmidgall et al. 2025), i.e. **MLE = Machine Learning Engineering**; the paper's own text may say so but I did not open the paper. Treat "Maximum Likelihood" as wrong.
- What it really is: `task_solving.py:194-213 coding()` = `for try in range(5): for iteration in range(3): iteration 0 -> coding_actor (fresh generation); iterations 1,2 -> coding_debugger (feeds code + execution output back)`. So up to 5 independent restarts x (1 gen + 2 debugs) = **max 15 LLM calls/task**. Note each new "try" re-generates from scratch with no memory of previous failures (iteration==0 path, `:201-202`).
- Execution `execute_script` (`:28-75`): `subprocess.Popen("CUDA_VISIBLE_DEVICES=0 python -u script", shell=True, cwd=work_dir)` — **no timeout, no sandbox, no resource limit, runs in the same Python environment**, output truncated to the first 2000 *characters* (comment says "last ~2k tokens", code keeps the first 2000 chars, `:151-153`).
- Success test = **absence of the substrings** `"Traceback (most recent call last):"`, `"SyntaxError: invalid syntax"`, `"IndentationError"` in the observation (`:204,209`). Note `execute_script` returns **stdout only if return code is 0, else stderr** (`:65-68`); a crash that does not print "Traceback" (e.g. OOM kill, `sys.exit(1)`, timeout) would be counted as success. No check that the produced numbers exist, are finite, or match anything.
- Failure is silent for the pipeline: if all 15 attempts fail, `coding()` returns `(code, False, None)`; `is_pass=False` is stored in the task dict (`computational_solving.py:300`) but downstream continues with `execution_result=None`.

## 3. Paper/summary vs code discrepancies
1. **MLE-Solver expansion**: summary says "Maximum Likelihood Estimation Solver"; code has no such component or expansion; it is a generate-run-debug loop (see 2c). [inference: ML Engineering]
2. **Execution result never reaches the result-writing prompt (real bug)**: `computational_solving.py:293` calls `ts.result(task_description, task_analysis, formulas, method, execution_result)`; signature is `result(self, task_description, task_analysis, task_formulas, task_modeling, user_prompt='', execution_result='')` (`task_solving.py:215`). The 5th positional arg is bound to `user_prompt`, so `execution_result==''` and the **no-code prompt** `TASK_RESULT_PROMPT` is used with the run output pasted into the `{user_prompt}` slot. So `TASK_RESULT_WITH_CODE_PROMPT` is effectively dead code in the default path; numbers do get seen but as an "extra instruction", framed as user guidance. (Verified by reading both lines.)
3. **Iterative refinement "until convergence"**: fixed `round` count, default 1 (config.yaml); modeling-process critic disabled (`task_solving.py:112-126`).
4. **Stage 4 report generation is not in the default run** (`main.py:28-31` commented out as optional).
5. **Domains/subdomains**: file has 5/18(+12 third-level)/97, with different domain names than the summary lists.
6. **Retrieval described as "similarity + alignment with parent subdomain"**: matches the 0.5/0.5 parent-child mix (`retrieve_method.py:189-190`), but the parent score excludes the top domain and it is a flat global top-k, not hierarchical narrowing.
7. **Benchmark evaluation rubric vs code**: see section 7; the judge is fed an *empty background/requirements* due to a loader bug, and Analysis Evaluation (AE) only reads `task_description`, not the problem analysis.
8. **Human expert score 7.91, baselines (DS-Agent, ResearchAgent, Agent Laboratory)**: nothing in the repo reproduces them (no baseline adapters, no human-solution scores). Only a GPT-4o rubric script and 2 example solutions exist. Unverifiable from the code.
9. **Policy-only problems skip code**: implemented only via `dataset_path` emptiness (`utils/problem_analysis.py:62`), i.e. "has dataset" is the proxy for "quantitative"; a no-dataset problem that needs simulation gets no code at all.

## 4. Mechanisms worth adopting into custom-harness (ranked by expected value)
Our current state (from `STATUS.md`, `PLAN.md` §4): L4 research loop v0 has hypotheses -> tournament (`research/modules.py:151`, Bradley-Terry in `verify/ranking.py:18`) -> implement/fix loop -> hidden-test verification. No method library, no retrieval, no task-dependency DAG, no rubric-judge. MM-Agent is soft-verifier (T5) territory, so the value is in structure, not rigor.

1. **Hierarchical method library with parent-prior scoring as a hypothesis/method prior (L4 step 4, L5)** — what: tree of method families, score each level, final = `0.5*parent_mean + 0.5*leaf` (`retrieve_method.py:145-203`), top-k injected into the proposal prompt (`mathematical_modeling.py:391`). Why better than ours: we have no method memory feeding `hypothesize` (STATUS "Next" item 3 is only negative memory). Cheap, deterministic scoring (embedding cosine) = "code decides" (P7). Extend: attach to each leaf *usage stats and verified outcomes* (win/loss per task type, from our Evidence store) so the library is learned, which MM-Agent does not do. Layer: L5 (memory kind `playbook`) + L4 step 4. Effort: M. License: GPL-3 -> **reimplement from the idea** (algorithm is ~60 lines; do not copy code or the HMML.md text unless we accept GPL on the data; the HMML.md content is also authored by them, so build our own taxonomy).
2. **Task-dependency DAG with typed hand-off of prior-task artifacts (L4 step 1/7)** — what: LLM emits adjacency JSON, code topologically sorts it (`coordinator.py:68-98`), falls back to a linear chain on 5 failed parses (`:115-127`), and each task receives only its dependencies' description/method/result/code-structure/output-file list (`mathematical_modeling.py:325-377`; `CODE_STRUCTURE_PROMPT` extracts functions/classes/file_outputs, `task_solving.py:226-246`). Why better: our runtime is a fixed graph; multi-stage research problems that decompose into dependent experiments have no analogue. Adopt with Evidence-record refs instead of pasted text, and validate acyclicity/fallback in code (theirs already does). Layer: L4 + L0 (graph runtime). Effort: M. Reimplement.
3. **Rubric decomposition for T5 judging, with fixed 1-10 anchors per sub-criterion and `<reason>/<score>` tags (L3 judge panel)** — what: four rubrics with 2 sub-criteria each (e.g. 1.1 Problem Definition, 1.2 Scope; 2.1 Assumptions, 2.2 Rationality; 3.x Practicality/Scientificity; 4.x Result/Bias), anchor bands "1-2 = ..., 9-10 = ..." (`MMBench/evaluation/prompts.py:145,154,220,...`). Useful as a *template* for our judge panel, but only if fixed (see section 6/7): pairwise + position-swap + multi-family (our P5/C4). Layer: L3. Effort: S. Reimplement the rubric structure (the wording is theirs; GPL).
4. **Code-structure extraction for cross-task reuse (L5 / L4 step 7)** — `extract_code_structure` records script path, classes, functions, produced files with descriptions (`task_solving.py:248-267`), and later tasks are told to *reuse files from "Other Files" instead of recomputing* (TASK_CODING_PROMPT, template.py:512+). Our fork/snapshot already preserves state; this adds a *semantic index of artifacts*. Effort: S. Reimplement.
5. **Per-problem-type decomposition principles** (`prompt/decompose_prompt.json`, keyed by contest problem letter A-F and subtask count, used `problem_decompse.py:342-344`). Marginal for us; as an idea: seed decomposition with type-specific templates, and let L6 evolve them as typed `contract`/`prompt text` edits. Effort: S, low value.

## 5. Things custom-harness already does better (with evidence)
- **Execution safety**: theirs is `shell=True` subprocess in the host env, no timeout, no network control (`task_solving.py:33`); ours has Docker sandbox with no network, caps, non-root, read-only rootfs (`sandbox/docker.py`, STATUS L0), and refuses unisolated runs without explicit env var (`sandbox/local.py`).
- **Success criterion**: theirs = absence of 3 substrings (`task_solving.py:204`); ours = hidden-test verification, trusted T1 metrics, T2 bootstrap CIs (`verify/metrics.py`, `verify/stats.py:65`).
- **Ranking/judging**: theirs = one absolute rating, one sample at temp 0.7 from one model (`run_evaluation.py:131`); ours = K-way ranking -> Bradley-Terry (`verify/ranking.py`, `research/modules.py:151`).
- **Provenance/cost**: theirs = global token counters with 3 hardcoded price points for `gpt-4`, `gpt-4o`, `gpt-3.5-turbo` (`MMBench/evaluation/model.py:80-89`); ours = ledger + per-step trace + checkpoints + failed attempts costed (`budget.py`, `runtime/`).
- **Typed, diffable harness + held-out gating**: they have none; every "improvement" is a prompt rewrite accepted unconditionally (`task_solving.py:99-102`).
- **Error handling**: theirs returns exception text as model output (`llm.py:93-94`); ours uses contracts with bounded retries (`runtime/`).

## 6. Pitfalls, bugs, anti-patterns seen (must avoid)
1. **LLM errors become content**: `llm.py:93-94` returns `"An error occurred: ..."` as a normal answer; it would be fed to critic/improve/report prompts silently. Also class-level shared `usages = []` (`llm.py:34`) is shared across instances.
2. **Argument-order bug** that dropped the execution-result prompt (`computational_solving.py:293` vs `task_solving.py:215`). Lesson: keyword-only args for prompt builders; contract-validate template fields.
3. **Evaluation loader bug**: `load_solution_json` returns only `{task1: ..., task2: ...}` (`MMBench/evaluation/utils.py:262-268`) but `generate_*_prompt` call `solution_data.get('background', 'None')` and `.get("problem_requirement", [])` (`prompts.py:16-17,91-92,165-166,254-255`). So the judge is always told Background: None, Requirements: []. [inference: this makes scores insensitive to problem fit; I did not run it.] Also the `for task_key, task in solution_data.items()` loop would break on string values if those keys were ever added. Strong anti-pattern: judge that cannot see the problem.
4. **Unsafe/fragile execution**: no timeout (`task_solving.py:33-63`: `while process.poll() is None and selector.get_map()`, plus blocking `readline`), `input("Ah oh, Got stuck! Press any key to continue.")` on exception (`:156,190`) which would hang an unattended run, and `observation`/`new_content` can be unbound if all 5 format retries fail (`:131-143`) or exception (`:146-158`).
5. **Truncation comment/code mismatch** (keeps first 2000 chars, claims last ~2k tokens, `:149-153`): the traceback tail, which is the most informative part, is cut off.
6. **Pipeline continues after failed code** with `execution_result=None` and prose written as if results existed (`computational_solving.py:291-300`) -> fabricated-results risk. Our I1/I4 integrity audit exists precisely to catch this.
7. **Critic told not to propose fixes + unconditional acceptance** of the rewrite: no check the rewrite is better; a rewrite can lose content. Use accept/reject by pairwise judge + tier policy.
8. **Reloading model and rewriting HMML.json on every task** (`mathematical_modeling.py:382`, `retrieve_method.py:216-218`): wasteful and writes into the source tree (relative path `'MMAgent/HMML/HMML.json'` requires running from repo root).
9. **Parsing by `split('---')`, `strip('```json\n')`** (`problem_decompse.py:346`, `coordinator.py:119`): `str.strip` with a char set, not prefix removal — can eat legitimate leading/trailing characters. Use schema-validated outputs (we have strict-schema conversion).
10. **Hardcoded device 0 and `python`** (`task_solving.py:30-32`), API key passed on CLI `--key`, and `trust_remote_code=True` for the embedding model (`embedding.py:25`) = remote code execution surface from the HF hub.

## 7. Verifier / evaluation / safety handling
- **No verifier for correctness.** Code success = no traceback strings. No ground truth, no numeric checks, no test suite, no sanity checks (units, finiteness, constraint satisfaction). Everything is T5/T6 in our ladder.
- **MM-Bench**: 111 problems (JSON, fields background/problem_requirement/dataset_path/dataset_description/variable_description/addendum per `MMBench/README.md`; 22 dataset folders in `MMBench/dataset`). The repo ships **no reference solutions or ground truth** to compare against. Evaluation is a **single-judge, single-sample, absolute LLM rubric**: `run_evaluation.py:65-75` issues 4 prompts to gpt-4o at temperature 0.7 (`:131`), regex-extracts `<reason>`/`<score>` pairs (`:14-36`); if counts mismatch, the whole section is returned as `{}` (`:21-27`), and **batch averaging skips missing sections silently** (`run_evaluation_batch.py:calculate_average_scores`: `sum(scores)/len(scores) if scores else 0`), which biases averages and can score 0. Only `analysis_evaluation[0]` of n=1 is used. The four "metrics" are the mean of 2-ish sub-scores each (1-10). The rubric dimensions: AE = problem definition + scope/coverage (fed `task_description` only, `prompts.py:23`); MR = assumptions + rationality (fed `task_analysis`, `:98`); PS = practicality (+ scientificity/innovation; fed `mathematical_modeling_process`, `:172`); RBA = result + bias analysis (fed `subtask_outcome_analysis`, `:261`). Each dimension reads a **different field**, so a solution can be judged on prose quality of one section. No position/length controls, no self-preference control (the evaluator is the same family as the generator, GPT-4o), no inter-judge agreement, no CI. The 8.85 vs human 7.91 claims therefore hinge on an LLM judge that favors long fluent text. [inference, not tested]
- **Safety/sandboxing**: none (see 2c, 6.4). Executes generated code with host privileges and the dataset copied to `output/.../code` (`utils/problem_analysis.py:67`).
- **Exploit handling**: none. Nothing prevents generated code from writing fake outputs, since success is judged by absence of tracebacks and the LLM later writes prose around whatever was printed.

## 8. Bottom line
- Small, clean, readable pipeline whose real contributions are (a) a parent-prior tree scoring over a method taxonomy and (b) a task-DAG with typed hand-offs; both are cheap to reimplement and fit L4/L5. Neither is evidence-verified.
- "MLE-Solver" is not Maximum Likelihood; the code has no such component. It is a plain 5x3 generate/run/debug loop with a substring-based success test, no sandbox, no timeout. [inference: MLE = ML-Engineering, borrowed from Agent Laboratory.]
- The actor-critic loop is 1 unvalidated rewrite per stage with the critic forbidden from suggesting fixes; no gate. Our gated, CI-based accept rule is strictly stronger.
- MM-Bench is useful as a *task set* (111 real MCM/ICM problems + datasets) but its evaluator has bugs (empty background to judge) and no ground truth; GPL-3.0 means reimplement ideas and write our own rubric/judge, do not copy code or HMML.md.
