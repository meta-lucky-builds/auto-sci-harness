## 1. What the code actually does (architecture map)

One worker = one `LnrSolver` (`solver/lnr/solver.py`), a long-lived LLM agent loop over a host workspace directory. The paper's four concepts map to code as follows.

| Paper concept | Code |
|---|---|
| Recoverable executable state | Stage Snapshot: content-addressed file objects plus a manifest (`workspace_snapshot.py`), wrapped by `SnapshotStore` (`snapshot_store.py`), which adds a metadata sidecar (`.logs/lhr_snapshot_meta.json`), a copy of agent memory, and stage logs. |
| Stage Gate | `gates/service.py` normalizes a "result signal" into a `MetricEvent`. `gates/policy.py:GateManager` (fail-closed plugin registry) decides accept/retry/reject. Accepted results become a Stage: an append-only ledger card (`stage/stage_ledger.py`) plus a snapshot capture. |
| ESTRA | `solver.py:_ask_estra` (LLM decision), `_set_pending_estra_from_decision` (builds the pending transition), `_restore_pending_estra` (executes it). |
| Memory add/fold/unfold/assemble | `stage_memory.py` (folds ledger cards into summaries, cached in `.agent_memory/stage_memory`), `solver.py:_rebuild_memory_after_estra`, `core/mem/memory_context.py` (4.6k lines, not read). |
| Evidence-aware execution control | `solver/lnr/resource_runtime/` (admission, GPU leases, observer, arbiter, kill gates) plus `safety/resource/`. It runs inside the same Python process as the agent, hooked into the bash tool, not in a separate service. |
| Multi-worker | `core/parallel_runner.py` launches workers. Workers read each other's stage-performance rows (`stage/peer_context.py`) and merge finals (`global_merge/`). `estra_magent` (sidecar helper agents) is off by default (`settings.py:345-352`). |

There is no real sandbox. The agent runs bash on the host with regex and AST guards (`safety/code_guard.py`, `safety/leakage_detector.py`, `core/tools/bash/guards.py`). `core/executor/sandbox.py` only holds data-truncation helpers.

## 2. Core loop, step by step (with citations)

### 2a. Stage capture: how a recoverable state is created
1. The agent runs a full-run command. A "result signal" (a metric event) is turned into a candidate by `gates/service.py` (~130-190). A candidate is stage-eligible only if the metric is finite, `validation_ok`, `selection_eligible` and not a "pilot" run. Row-subsampled runs are rejected by a regex over the bash command env (`_non_full_result_reason`).
2. `GateManager.decide_with_trace` (`gates/policy.py:179`) runs core invariants first, then the named policy (`DefaultGatePolicy` checks metric present, direction known and validity rank; `OptimizationFeasibilityGatePolicy` adds a constraint-violation bound). Any exception, unknown policy or malformed decision becomes a reject (fail closed, `policy.py:~193-230`).
3. The agent writes a stage card into `.run_results.md`. The ledger is append-only and exactly one new card must be added (`stage/stage_ledger.py:155-178`, `validate_append_only_stage_commit`). A prepared/committed/rolled-back transaction manifest backs the ledger write (`solver.py:7014-7054`).
4. `solver.py:~7260` calls `snapshot_store.capture(stage_id, metric_value, ..., memory_cut=_count_memory_records(), node_uid, lineage_id)`. It is preceded by a workspace-git auto-checkpoint (`~7190`) and the metric-validity adjudication.
5. `SnapshotStore._capture_workspace_snapshot` (`snapshot_store.py:715`) calls `WorkspaceSnapshotStore.capture` (`workspace_snapshot.py:140`). That walks the workspace, skips excluded dirs (`.git`, `.logs`, `logs`, `tmp`, `.agent_memory`, `dataset/` contents, and so on), stores each file as a sha256 object under `objects/` (write temp, fsync, hard-link to the final path, chmod 0444, `workspace_snapshot.py:384-413`), and writes a manifest `{rel: {kind, digest, size, mode, mtime_ns, fingerprint}}` atomically. Symlinks are recorded by target. Escaping relative symlinks are skipped and unlisted absolute ones raise (`:415-436`).
6. Dedup trick: a file is not re-hashed if its (size, mtime_ns, ctime_ns, inode, device) fingerprint equals the previous manifest's entry and the object still exists (`workspace_snapshot.py:176-190`). This is the delta mechanism behind the paper's 91.4% footprint reduction (see §3).
7. The sidecar copies the agent memory directory into `<snapshot>/.logs/memory` (`snapshot_store.py:~790`) and the stage logs, then writes the metadata JSON. A snapshot record carries `stage_id`, `node_uid` and `lineage_id`.

### 2b. ESTRA: the exact re-anchoring mechanism
7. Triggers: after a stage capture when `estra_trigger_stage_count` (default 2, `settings.py:160`) is met and the observation key changed (`_estra_trigger_allowed`, `solver.py:5845`). Also forced after N stages (`force_estra_after_stage_count`, default 0 = off), on a text-only agent reply, on a context-limit event, and on a context-hygiene event.
8. Candidate set (important): `candidates = [stage ids in the CURRENT ledger that have a snapshot in self.stage_snapshots]` (`solver.py:5389-5392`, `5839`). `switch_candidates` is `candidates` minus the latest stage (`_estra_switch_candidates`, `5173`). Abandoned-lineage stages are pruned from the active view (`_prune_active_stage_snapshots_to_ledger`, `4601`). They stay on disk and in an `archived_stage_snapshots` index keyed by `node_uid`, so the same visible id `S03` can exist in several lineages (test `test_snapshot_store_discovers_same_visible_stage_across_lineages_by_node_uid`).
9. The decision is one LLM call returning one JSON object (`_ask_estra`, `5388-5640`). It appends an ESTRA prompt to the main agent's own context (`estra_use_main_agent_context=True`), tools disabled. The prompt contains the folded Stage Memory View, per-stage checkpoint context, peer-route evidence and a backtrack reflection. If that fails to parse, it retries in an isolated call. If that also fails, the decision is `keep_current` (`5521-5610`). A deterministic variant exists (`_deterministic_estra_decision`, `2614`: switch to the best-metric candidate if it is not the latest).
10. The two axes are normalized to three actions (`5182-5232`): `switch_stage` = (previous_stage, continue), `keep_but_redirect` = (current_workspace, redirect), `keep_current` = (current_workspace, continue). The paper's 4-cell grid (archived+redirect) has no distinct code path: `previous_stage` always maps to `switch_stage`, and `_estra_axes_from_action` forces intent to continue for it. The `intent` field only travels in `estra_fields` into the resume prompt text. [inference: archived+redirect is expressed only through prose in that prompt.]
11. `_set_pending_estra_from_decision` (`5772`) builds `pending_estra`: target stage, `target_node_uid`, a 1.2k-char synthesized summary of the abandoned tail (an LLM call, `_synthesize_estra_archive_summary`), the full terminal ledger text, and a deterministic "state packet" (`_build_lhr_state_packet`, `2705`).
12. Execution happens between agent runs (`solver.py:10108-10110`: LLM clients are closed, then `_restore_pending_estra`). `_restore_pending_estra` (`8704-8860`):
    - Resolve the snapshot by (stage, node_uid).
    - `snapshot_store.restore(snap)` (`snapshot_store.py:1054`) first captures a "terminal archive" of the CURRENT workspace (`_capture_terminal_archive`, `561`) using the same content-addressed store. Then it restores the target manifest (`workspace_snapshot.py:249`), which pre-flights every object (exists and sha256 matches, `_preflight_restore_entries:307`) BEFORE clearing the target. It clears the target but preserves `.git`, `.logs`, `logs`, `.memory`, `.agent_memory`, `stage_memory`, `tmp` and so on (`runtime_paths.py`), moving undeletable items to `.restore_trash`. It then copies objects back, restoring mode and mtime. If anything throws, `_restore_terminal_archive` re-materializes the pre-restore workspace (`snapshot_store.py:~1120-1136`).
    - Then it re-links the dataset symlink, appends an "Archived Trajectory before estra" block to the ledger (`stage_ledger.py:~330`), prunes active snapshots to the restored ledger, and rebuilds agent memory. The solver additionally rolls back the stage map and the terminal archive if the "unfold transaction" fails (`8780-8822`).
    - A new lineage id is started (`_start_new_lineage`). `keep_*` actions do the same memory rebuild without touching the workspace (`8727-8765`).

### 2c. What is actually restored (see §3)
- Workspace files: byte-exact, with mode and mtime (but not `.git`, `dataset/` contents, `tmp`).
- Ledger: restored because `.run_results.md` lives in the workspace and is not a preserved path, then a summary of the abandoned branch is appended.
- Agent conversation memory: NOT restored to its state at that stage. `_rebuild_memory_after_estra` (`solver.py:2833`) takes the base stage (S01) memory records (`_base_stage_agent_memory_dir`, `2439`, reading `<snapshot>/logs/memory/ScienceAgent`), selects prefix-safe records (or a minimal task prefix under `strict_context_limit`), and appends ONE synthesized user prompt (`build_estra_resume_prompt`) carrying the summary, state packet, a parallel-worker snapshot and resource context. The memory directory is deleted and rewritten.
- Resource records and logs: live `logs/` is preserved, so accounting stays cumulative, as the paper says. They are not rolled back.

### 2d. Resource controller
- Admission (`resource_runtime/admission.py`): a rule-based result with actions `RUN_NOW | OBSERVE_THEN_RUN | PENDING | REPLAN`. An isolated "ResourceAdmissionArbiter" LLM is consulted only for blocked/low-confidence cases (`should_request_admission_llm:28`). `normalize_admission_decision` (`:116`) downgrades any LLM start to `PENDING` unless the rule layer already holds an atomically acquired or grantable lease (`:131-141`). The LLM can only veto or defer, never grant beyond the rule layer.
- Online review (`review/arbiter.py`): proposal types (`kill_proposal`, `periodic_efficiency_review`, `quick_probe_review`, `deadline_finalize_review`, GPU-share reviews) each have an action allowlist (`allowed_actions_for_proposal:~68`; enforcement downgrades anything else to `OBSERVE_MORE`). An isolated Resource Arbiter LLM returns `outcome KILL | NO_ACTION | TIMEBOX` with a `clear_on` condition (the arbiter may not choose a timebox length). Valid arbiter actions are listed in `arbiter.py:~20-40`.
- Kill gate (`arbiter_gate.py:507 enforce_arbiter_kill_gate`): a kill is downgraded to `OBSERVE_MORE` unless (a) arbiter confidence is high, (b) no conflict between the owning agent's advisory and machine-observed facts, (c) not protected by an imminent phase end (<=300 s with high-confidence ETA) or by a live best-metric job, and (d) there is support: hard safety (boundary, OOM, orphan, runaway), deterministic evidence (repeated failed proof windows, quick-probe overrun with no value signal, unaffordable finish under a deadline, resource idle with CPU busy for 30+ min), or a high-confidence owning-agent stop advisory (`arbiter_gate.py:~290-330`, `~560-640`). `review/kill_intent.py` snapshots and revalidates the evidence just before the kill, which guards against a time-of-check/time-of-use race.
- State persistence: `UnifiedResourceStore` writes `resource_state.json` atomically (tempfile then `os.replace`) under `fcntl.flock`, plus an append-only `resource_events.jsonl` (`unified_store.py:~15-95`). Leases, waiters, pressure and cooldowns therefore survive a process restart.
- Budget handling: wall-clock only (`settings.py:116 wall_clock_budget_sec`, default 3600). The controller sees `deadline_remaining_sec`, `remaining_useful_budget_sec` and `finish_feasible` per job (`observer/controller.py` around `5084`, `7591`, plus the gate's `proposal_has_unaffordable_finish_without_output`). Token/USD costs are tracked (`settings.py:94-95` price tables, `tests/test_cost_tracker.py`) but I found no dollar cap enforced in the loop. [inference: from grep of `max_cost|usd|budget` in `settings.py` and `resource_runtime`; I did not read all of `observer/controller.py`.]

### 2e. Durability across crashes and a 10-day campaign
- Task-level resume (`core/parallel_runner.py:1288-1330`): `state.json` stores `charged_elapsed_sec`; on resume the remaining budget is `logical_budget - charged` (`_check_resume`). Time lost to external LLM failures is not charged (`_charged_elapsed_for_resume:616`, `resume_budget_policy: external_llm_failure_not_charged`, `:1505`). There is also a `fresh` policy.
- Agent-level resume (`solver/lnr/resume/`): reloads persisted agent memory and, if the tail is an assistant tool call without a result, re-executes that single pending tool call (`continuation.py`, README). Multiple pending calls are detected but not replayed. This is state-based, not process-based: a half-run training job is simply re-issued.
- `scripts/lnr_kill_resume.sh` kills and resumes a workspace. The repo has no 10-day config or run. The KTTSP task exists (`tasks/opt_solver/kttsp/task.yaml`) but the "10-day campaign / 79.6% objective reduction" claim is not backed by any shipped artifact or script I could find. It is a paper claim only.
- LLM-side durability: multiple API keys and base URLs with sticky failover per worker (`core/key_pool.py`, `solver.py:~8640-8700`).
- POSIX-only locking (`fcntl` at `unified_store.py:7`, `gpu_lease_store.py:15`, `history_store.py:15`), so the controller will not import on Windows.

## 3. Paper/summary vs code discrepancies
1. "Restores full state: workspace, memory, validation evidence, resource records." Code: workspace and ledger are byte-restored. Agent conversation memory is rebuilt from the S01 prefix plus a synthesized summary and state packet (`solver.py:2833-2925`), not restored to the stage-k memory. A copy of memory is stored in each snapshot (`snapshot_store.py:~790`) but is read only for the base stage (`solver.py:2439`). Resource logs are preserved live, not archived and restored (this matches "cumulative").
2. "Four outcomes (current|archived) x (extend|redirect)". Code has three actions. (archived, redirect) has no separate path, and `intent` is cosmetic for `switch_stage` (`solver.py:5182-5232`).
3. "Choose to restore a previously archived state". The LLM's candidates are only stages in the current lineage's ledger (`solver.py:5389`, `5839`). Abandoned-lineage nodes are archived and addressable by `node_uid`, but I found no path where the ESTRA prompt offers them. [inference: from reading `_ask_estra` and `_estra_candidates_for_current_ledger` only; I did not read every use of `archived_stage_snapshots`.]
4. "Delta-based storage, 91.4% reduction vs full snapshots". The code is not delta encoding in the diff sense. It is whole-file content-addressed dedup with mtime/inode fingerprint shortcuts (`workspace_snapshot.py:176-190`). Changed large artifacts are stored in full. The 189.2 vs 2204.6 GiB figures cannot be reproduced from the repo.
5. "Controller retains lease allocation, timeboxing, termination" while the agent retains routing. Mostly true, but the controller itself contains two LLM calls (admission arbiter, resource arbiter), and the owning agent's `main_agent_advisory` can serve as the support evidence that unlocks a discretionary kill (`arbiter_gate.py:~228-262`, `_blocked_kill_reason`). So separation is of authority (hard rule gates around LLM judgements), not of "LLM vs code".
6. "Humans review anchor-selection decisions" (summary table). I found no human-approval gate in the ESTRA path.
7. "Fold/Unfold maintain indices for retrieval". Fold (`stage_memory.py`) summarizes older cards in two layers (L and G summaries) and keeps recent, best and verification cards raw. Whether any LLM-driven "unfold" retrieval exists beyond the ESTRA prompt's checkpoint context was not verified.
8. The 10-day KTTSP campaign, MLE-bench numbers and the ablation are not reproducible from the repo, and nothing I read ships results. Treat them as unverified.
9. The "no skill by default" claim is consistent with the README, not checked in code.

## 4. Mechanisms worth adopting into custom-harness (ranked by expected value)

1. **Crash-safe, verifiable restore: preflight, then rollback archive.** What: `WorkspaceSnapshotStore.restore` validates every referenced object (exists, sha256 matches) before touching the target (`workspace_snapshot.py:307-325`). `SnapshotStore.restore` first archives the live workspace and re-materializes it if the restore throws (`snapshot_store.py:561-637, 1054-1136`). Why better: our `restore_snapshot` does `shutil.rmtree(workspace)` first, then writes files (`sandbox/snapshot.py:25-34`). A missing blob or crash mid-restore leaves the user's workspace destroyed or partial. Layer: L0. Effort: S. Reimplement (about 30 lines: verify all `blobs.has`/`get` first, take a throwaway snapshot, restore, on exception restore the throwaway).
2. **Incremental snapshot capture via stat fingerprint.** What: skip re-hashing unchanged files using (size, mtime_ns, ctime_ns, inode, dev) from the previous manifest (`workspace_snapshot.py:176-190`), tested with a 50 GB sparse file (`tests/test_workspace_snapshot.py:63`). Why: `take_snapshot` reads and hashes every file in full at every `snapshot_after` node (`sandbox/snapshot.py:14-20`), which is unusable once an ML workspace holds checkpoints. Caveat: their test `...same_size_and_mtime_gets_new_object` (line 112) exists because the shortcut is fragile. Include `ctime_ns` and inode as they do, and keep a periodic full-hash audit. Layer: L0. Effort: S-M. Reimplement.
3. **Preserve-list and mode/mtime/symlink fidelity.** What: manifest stores `mode`, `mtime_ns`, symlink targets (validated), and a `RESTORE_PRESERVED_DIR_NAMES` set that restore never deletes (`runtime_paths.py`, `workspace_snapshot.py:249-305`). Why: our snapshot drops symlinks (`not path.is_symlink()` at `snapshot.py:18`), loses the exec bit and mtimes (`write_bytes` only, `snapshot.py:34`), and wipes everything, so an ML task relying on `chmod +x` scripts, mtime-keyed caches or a dataset symlink will not be byte-identical. Layer: L0. Effort: S. Reimplement.
4. **Cumulative-across-fork accounting as a first-class rule, persisted.** What: on restore the live `logs/` and resource state are preserved, so wall-clock/resource accounting never rewinds, and resume computes `remaining = budget - charged_elapsed` from `state.json` with a separate "provider outage not charged" policy (`parallel_runner.py:616, 1288-1311, 1505`). Why better: our `Budget` (`budget.py`) is an in-memory object (`spent: Cost`), has no persistence and no wall-clock deadline, and `Engine.fork` does not carry spend explicitly (`engine.py:99-118`). After a crash the campaign budget silently resets. Layer: L1. Effort: M. Reimplement: persist the ledger in the evidence store with the run record, add a `deadline_s` unit, and mark provider-fault time as `uncharged`.
5. **Controller authority = fixed allowlists + LLM can only downgrade + intent revalidation.** What: per-proposal action allowlist (`arbiter.py:~68`), kill gate with explicit support classes (`arbiter_gate.py:507-640`), admission where an LLM can never exceed the rule layer's atomic lease (`admission.py:131-141`), and a kill-intent snapshot revalidated before termination (`kill_intent.py`). Why: this is a concrete, tested pattern for PLAN P7 ("LLM proposes, code decides") that our L1 lacks (`budget.py` only caps). Adopt the pattern, not the 9.6k-line implementation. Layer: L1. Effort: M. Reimplement (ideas only; the MIT code could be copied with attribution but is entangled with their bash tool).
6. **Archived-state addressing by (stage, node_uid, lineage).** What: every capture has `node_uid` and `lineage_id`, and the same visible stage id can exist in many lineages without collision (`snapshot_store.py:136-148`; test line 123). Why: ties directly to PLAN §8.9 (revivable dead-ends point to exact snapshots). Our `Engine.fork` addresses `(run_id, step_index)` which is already unique, so this is only needed if we add a "visible stage" abstraction. Layer: L5/L0. Effort: S. Reimplement.
7. **Two-axis re-anchoring decision (anchor x intent) with a fail-safe default.** What: decide (current|archived) separately from (continue|redirect), with an invalid or failed decision defaulting to keep_current (`solver.py:5182-5232, 5521-5610`). Why: we have exact fork but no policy deciding when and where to fork. Their evidence offered to the decider (stage cards with metric validity, selection_eligible, source commit, peer-route evidence, "backtrack reflection") is a good template for our L7/L6 loop. Layer: L4/L7. Effort: M. Reimplement.
8. **Append-only stage ledger with a validator and transactional commit (prepared/committed/rolled_back).** (`stage_ledger.py:155-178`, `solver.py:7014-7054`). Aligns with our records table (`store/evidence.py`) and L2 immutability. We already have append-only evidence, so this is low priority. Layer: L2. Effort: S.
9. **Stage-gate admission rules (what NOT to snapshot).** Pilot or row-subsampled runs cannot become Stages (`gates/service.py:~190-205`). Worth a rule in our gate so cheap proxy runs never become anchor states (PLAN §6.4: proxies prune, never accept). Layer: L3/L6. Effort: S.

## 5. Things custom-harness already does better (with evidence)
- Snapshot granularity: we checkpoint after every node, including state, next node and workspace ref (`runtime/engine.py:160-175`) and can fork from any step (`engine.py:99-118`). ScienceFlow snapshots only at gated Stages (`solver.py:~7260`), so recovery granularity is coarse and there is no deterministic replay of the agent.
- Exactness of the agent state: our fork restores the exact graph state `cp["state"]` (`engine.py:109-113`). ScienceFlow's re-anchor reconstructs the agent's context from S01 plus a lossy 1.2k-char summary (`solver.py:2833-2925`), so the "exact" restore is only for files.
- Blob integrity on read: `BlobStore.get` re-hashes and raises on corruption (`store/blobs.py:~28-31`), with atomic temp-and-replace writes. ScienceFlow verifies at restore preflight, which is equivalent, but its object store is plain files with no content check on dedup reuse (it trusts the previous manifest if the object file exists, `workspace_snapshot.py:183-186`).
- Typed, small, testable core versus an enormous string-and-dict-typed solver: `solver.py` has 10k lines, `observer/controller.py` 9.6k lines, and routing is by parsing LLM JSON text. Our harness is a typed spec with deterministic routing (`research_v0.yaml`).
- Verifier tiers, claim graph and held-out gates: ScienceFlow has none of these. Its metric comes from agent-visible stdout (`safety/execution_policy.py:491-520 final_validation_score_contract_error`, `_extract_metric_from_stdout`) for the legacy ML profile, and from a hidden `evaluator.py` only for task packages (`tasks/opt_solver/kttsp/task.yaml:11-13`).
- Real sandboxing: ScienceFlow runs agent code on the host (see §7). We ship Docker with gVisor and a network-off default (STATUS.md).
- Platform: we run on Windows via the local sandbox. Their controller needs `fcntl`.

## 6. Pitfalls, bugs, or anti-patterns seen in their code that we must avoid
- Monolithic god-objects: `LnrSolver` is 10,174 lines and `observer/controller.py` is 9,663 lines. Behavior is encoded as hundreds of string reason-codes and prompt sentences (`arbiter.py:~125-190` builds a ~3k-char instruction paragraph per call). Any single behavior is hard to test or ablate. Our typed-edit design should stay small and typed.
- "Exact" restore claimed but memory is rebuilt lossy (`solver.py:2833`). If we call something state-exact, document exactly what is excluded (they exclude `.git`, `dataset/` contents, `tmp`, `.logs`, `.memory`, `.venv`-style env state). Note `dataset/` and environment are not part of their snapshot and are re-linked after restore (`solver.py:~8785 _prepare_dataset_symlink`), so a changed dataset or an installed package is not rolled back.
- mtime/inode fingerprint reuse can silently stale a digest if a file is edited in place within the same ns timestamp and size (`workspace_snapshot.py:176-190`). They added a test, but it is a heuristic. A restore later "verifies" only objects, not that the manifest matches the content at capture time.
- ESTRA decider is the same LLM context that made the mistakes (`estra_use_main_agent_context=True`, `solver.py:5440-5460`). That biases the choice. Calibrate proposer/decider separately (PLAN §8.5). Their "5/7 optimal, zero median regret" analysis is replayed on only 7 decision points (paper), so treat it as anecdotal.
- LLM-in-the-controller: two LLM arbiters in the resource path add latency, cost and non-determinism to termination decisions. They mitigate with allowlists and gates, but the arbiter's own prompt contains policy ("KILL_AND_REPLAN requires confidence=high ...") duplicated by the code gate. Keep policy only in code.
- Metric trust: legacy ML scoring parses "Final Validation Score" from agent-written stdout and detects "row-subsample" by regexing the bash command (`gates/service.py:_non_full_result_reason`; `execution_policy.py:~407-520`). This is spoofable. Our T1 trusted-metrics path (`verify/metrics.py`) is the right design.
- Leakage detection is regex/AST heuristic with stated "allow false negatives" (`safety/leakage_detector.py` docstring).
- POSIX-only `fcntl` locks for the resource store; breaks on Windows (`unified_store.py:7`).
- Wall-clock-only budgets: no token/dollar cap in the loop; cost is observed, not enforced. Our `Budget` already caps USD, tokens and quota units. Add wall-clock and persist.
- Snapshot sidecar copies the whole memory directory into every snapshot (`snapshot_store.py:~790`), but restore reads only the base stage's copy, so the other copies are write-only storage. Our own L5 read-audit idea (PLAN §4) is the countermeasure.
- Resume replays at most one pending tool call and only logs multi-call tails (`resume/README.md`). A long training job interrupted mid-run is restarted, not resumed (consistent with our "state-exact, not process-exact").

## 7. Verifier / evaluation / safety handling
- Evaluators: `gates/evaluator/backends/task_package.py` and `artifact_command.py` run a task-package `evaluator.py` (hidden from the agent: `visible_to_agent: false` in `tasks/opt_solver/kttsp/task.yaml`), producing a normalized `MetricEvent` with `metric_validity` (low/medium/high). The gate requires "high" by default (`policy.py DefaultGatePolicy`). `GateManager` is fail-closed on unknown policy, invalid config, exceptions and malformed decisions.
- Stage admission refuses pilot and subsampled results (`gates/service.py`).
- Exploit handling: none specific to reward hacking. MLE-bench-style submission checks exist (`gates/evaluator/providers/mlebench/submission_checks.py`). Validation-leak detection is heuristic (`safety/leakage_detector.py`, `safety/code_guard.py`), plus a stdout-hostility checker (`safety/stdout_checker.py`).
- Sandbox: none. Agent code runs on the host through a bash tool with guards (`core/tools/bash/guards.py`, `core/agent/tools/tool_guards.py`) and resource controls. Process-kill safety uses a lifecycle classifier (`safety/resource/process_lifecycle.py`, `safe_to_terminate_pid`). The restore path hardens file ops (symlink validation, `.restore_trash`).
- Controller safety: kill gates, intent revalidation, phase-completion and live-best-metric protection, advisory-vs-fact conflict check (`arbiter_gate.py`).
- I did not verify the paper's 70.22% MLE-bench, ablation or KTTSP numbers, and the repo does not contain results to check them against.

## 8. Bottom line
1. License is MIT, so ideas and small pieces are copyable with attribution, but the core files are monolithic and tangled with their agent, so reimplement.
2. Adopt now (S effort, concrete holes in `sandbox/snapshot.py`): restore preflight plus a rollback archive, mode/mtime/symlink fidelity, and a stat-fingerprint incremental capture. Keep blob-verified reads.
3. Adopt in L1: persisted cumulative budget with a wall-clock unit and an "uncharged provider outage" rule, and the "LLM may only downgrade, code gates kills, revalidate intent" controller pattern (`arbiter_gate.py`, `admission.py:131`).
4. Their "exact recoverable state" is files-exact only: agent memory is rebuilt lossily, the ESTRA grid is 3 actions not 4, and the 10-day / 91.4% / MLE-bench claims are not reproducible from the repo. Our per-step exact `fork` of full graph state is already stronger on recoverability and weaker only on fork policy (when and where to re-anchor).
5. Avoid: LLM-in-controller as policy, stdout-parsed metrics, host-run agent code, and single-file god objects.
