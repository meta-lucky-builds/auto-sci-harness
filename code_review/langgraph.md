## 1. What the code actually does (architecture map)
- Pregel/BSP model: a graph = named `nodes` + `channels`. Nodes are triggered by channel version changes, not by edges (`versions_seen[node][channel]` vs `channel_versions`; `apply_writes` _algo.py:232-342). StateGraph edges compile down to channels.
- One superstep = `PregelLoop.tick()` (_loop.py:614) -> run all ready tasks concurrently via `PregelRunner.tick` (_runner.py:177) -> `after_tick()` (_loop.py:698) applies all task writes at once with `apply_writes`, then `_put_checkpoint({"source":"loop"})`.
- Checkpoint (checkpoint/base/__init__.py:93-125): `{v,id,ts,channel_values,channel_versions,versions_seen,updated_channels}`; metadata (`:39`): `source in input|loop|update|fork`, `step`, `parents`, `run_id`. IDs are monotonic so sorting by id = time order (:98-101). Checkpoints form a parent chain; threads are keyed by `thread_id` + `checkpoint_ns`.
- Pending writes ("checkpoint_writes") are a second table: per-task writes of the in-flight superstep, stored against the *parent* checkpoint id (`put_writes` _loop.py:430, sqlite put_writes INSERT OR REPLACE for special channels / INSERT OR IGNORE otherwise, checkpoint-sqlite __init__.py:463-465).
- `BaseCheckpointSaver` interface (base:177-): get/get_tuple/list/put/put_writes/delete_thread/delete_for_runs/copy_thread/prune + async twins + `get_next_version`. Implementations: in-memory, sqlite (WAL, journal_mode pragma :141), postgres.

## 2. Core loop, step by step (file:line)
1. Entry: `_first()` (_loop.py:860) decides fresh-run vs resume by heuristics: resuming iff checkpoint has channel_versions AND (input is None OR input is `Command` OR same `run_id` as checkpoint metadata) (:869-884).
2. Fresh input: unfinished tasks of the prior checkpoint are DISCARDED (`discard_tasks`, :1062-1083) and the input written via `apply_writes`, then an `"input"` checkpoint is saved (:1117).
3. `tick()` (:614): `prepare_next_tasks` -> if none, status "done"; if `drain_requested`, status "draining" (:650); on resume, `_reapply_writes_to_succeeded_nodes` (:772) copies saved outputs of finished tasks onto the new in-memory tasks so the runner (which runs only tasks with empty `writes`) skips them; then `interrupt_before` check (:664) raising `GraphInterrupt`.
4. Runner executes tasks in a thread pool; each task wrapped in `run_with_retry` (_retry.py:573). When a task finishes, `commit()` (_runner.py:575) immediately calls `put_writes` -> checkpointer (async submit) UNLESS durability == "exit" (_loop.py:488). So partial-superstep progress is persisted per task. Interrupts are persisted as `(INTERRUPT, ...)` writes (_runner.py:583-592); errors as `(ERROR, exc)` writes (:599-607).
5. First failing (non-handled, non-interrupt) future cancels siblings (`_should_stop_others` :618, `_panic_or_proceed` :652) and re-raises; siblings that already finished keep their persisted writes. Multiple interrupts in a step are aggregated into one `GraphInterrupt` (:693-694).
6. `after_tick()`: `apply_writes` — tasks sorted by task path (not completion order) so reducer application is deterministic (_algo.py:253-256); per channel `channel.update(list_of_writes)` (:315-323); channel_versions bumped; pending writes cleared (_loop.py:731); checkpoint saved (:735); `interrupt_after` check (:737).
7. `_put_checkpoint` (:1142-1283): checkpoint put is submitted to a thread, chained after the previous put future so checkpoints reach the saver in order (:1262-1269, `_checkpointer_put_after_previous` :1596). `new_versions` (only channels whose version changed) is passed to `put` so savers can store per-channel blobs rather than whole state (:1255-1258).
8. Step limit: `step > stop` -> status "out_of_steps" -> `GraphRecursionError` (_loop.py:621; main.py:3070-3080). Default recursion_limit is a config key (value not verified by me).

Durability modes (types.py:98-104): `sync` (persist before next step), `async` (persist while next step runs; DEFAULT, main.py:2672), `exit` (persist only when graph exits; `_suppress_interrupt` :1383-1397 writes checkpoint + pending writes at exit).

Interrupts (types.py:893-): `interrupt(value)` raises `GraphInterrupt` on first call; on resume the node is RE-EXECUTED FROM ITS START, and the Nth `interrupt()` call returns the Nth stored resume value, kept in a `RESUME` write scoped to the task (docstring + body: `scratchpad.resume` list, asserting `len(resume)==idx`). Static alternatives: `interrupt_before/after` by node. Resume with `Command(resume=...)`; with >1 pending interrupts you must pass a map keyed by interrupt id (xxh3-128 hex) (_loop.py:1018-1030). Resume requires a checkpointer (:1019-1023).

Send / fan-out: `Send(node, arg)` objects written to the `TASKS` channel become PUSH tasks in superstep n+1 (`prepare_push_task_send` _algo.py:938-1000). Task id = hash(checkpoint_id_bytes, ns, step, node, PUSH, idx) (:990-997) -> deterministic per checkpoint, which is what makes reapplying saved writes on resume possible. Per-Send `timeout` supported (types.py:754-806). Reducers: `BinaryOperatorAggregate.update` (channels/binop.py) folds `operator(current, v)` over the step's writes in sorted task-path order; `Overwrite` bypasses the reducer; two Overwrites in one superstep raise `InvalidUpdateError`. Non-reducer channels (LastValue) raise on >1 concurrent write [inference from the error code ErrorCode.INVALID_CONCURRENT_GRAPH_UPDATE; LastValue file not read].

Retries: `RetryPolicy(initial_interval=0.5, backoff_factor=2, max_interval=128, max_attempts=3, jitter, retry_on)` (types.py:427-446). `run_with_retry` clears the task's partial `writes` before each attempt (_retry.py:615), sleeps `min(max, init*factor**(n-1))` plus `uniform(0,1)` seconds if jitter (:665-674). `default_retry_on` retries only ConnectionError and HTTP 5xx; most programmer-error types (ValueError, TypeError, RuntimeError, OSError...) are listed as NON-retryable (_internal/_retry.py:1-26; truncated at line 26 of my read, but list head shows the intent). Retry is transient-infra only; there is no notion of cost or budget in retries.

Time travel / forking: every superstep checkpoint is addressable; `get_state_history` (main.py:1510), `update_state`/`bulk_update_state` (:1615-) create `source="update"` checkpoints `as_node` (must name a node, ambiguity raises, :1963-1981); re-invoking with a past `checkpoint_id` replays: nodes are re-executed (not cached) and `forks` logic writes a `source="fork"` checkpoint so the new branch gets its own head (_loop.py:1021-1052, 1128-1139). On time-travel, stored RESUME writes are dropped so `interrupt()` re-fires (:918-934). `copy_thread` (base:351) copies a whole parent chain to a new thread_id.

Other: error handler nodes (`ERROR_SOURCE_NODE`, _loop.py:785-850, new), `drain` control (:650), `DeltaChannel` (append-only channel stored as writes + periodic snapshot; metadata `counters_since_delta_snapshot`, snapshot every N updates or 5000 supersteps, base:46-66), `UntrackedValue` channels never persisted (_loop.py:451-466), `TimeoutPolicy` (async only; sync nodes rejected at compile time, _retry.py:580-583).

## 3. Paper/summary vs code discrepancies
I read the survey file `autoresearch_survey/web_langgraph.md` only by size (18 KB), not its content, so this section is limited. Observed facts that commonly mismatch folklore:
- Default durability is "async", not sync: a hard crash can lose the most recent checkpoint put (it is submitted to a thread and only awaited before the next put / at exit). Task-level writes are also async. [see §6]
- "Resume continues where it left off" is only true at node granularity; `interrupt()` re-executes the whole node (types.py docstring). Side effects before the interrupt call run again.
- Checkpoints store graph channel state only, not filesystem/env (matches PLAN §13 rationale; nothing in checkpoint Checkpoint TypedDict beyond channels).

## 4. Mechanisms worth adopting into custom-harness (ranked)
Our engine: runtime/engine.py (258 LoC) is strictly sequential, one node per step; single `state` dict; per-step content-addressed checkpoint `{state,next,workspace}` (engine.py:164-169); `fork()` (:99-117) starts a NEW run from a checkpoint; no resume of an interrupted run; no interrupts; no parallelism; retries only at LLM contract level (:236-254); run status stays RUNNING if a non-caught exception escapes (`_loop` catches only BackendError/KeyError/ValueError/OSError, :150) and no `try/finally` sets status.

1. **Resume-the-same-run after crash/kill (`Engine.resume(run_id)`)** — LangGraph resumes from last checkpoint + pending writes (_loop.py:860-). We have the data (checkpoint_ref on every step, engine.py:169) but no entrypoint, and runs hang in RUNNING forever after a crash. For a multi-day research run this is the #1 gap. Layer L0. Effort S (load last step with checkpoint, continue `_loop` with `start_index=last+1`, reuse run_id; mark RUNNING runs with no live owner as `crashed`). Reimplement (trivial). Also wrap `_loop` in try/finally to set FAILED on any exception.
2. **Human-in-the-loop interrupt/resume as a first-class node outcome** — PLAN §L0 and tiers.py:39 mention human approval but runtime has none (grep for interrupt/pause: no hits in src). Reimplement as: node returns/raises `Interrupt(payload)`; engine persists a checkpoint with status `PAUSED` + pending-interrupt record, returns; `engine.resume(run_id, answer)`. Adopt LangGraph's two good ideas: (a) the resume answer is stored in the checkpoint keyed by interrupt id (deterministic, replay-safe), (b) require schema for the answer (`response_schema`, types.py:893-). Make the interrupt a SEPARATE node kind (`ApprovalNode`) instead of LangGraph's re-execute-the-whole-node-on-resume semantics, which silently repeats side effects (an LLM call or a sandbox exec before `interrupt()` is billed twice). Layer L0/L9. Effort M.
3. **Per-task write persistence inside a step + deterministic task ids** (_loop.py:430, _runner.py:575, _algo.py:990). Needed only once we add parallel branches; then a crash mid-fan-out must not re-run (and re-pay for) K-1 finished branches. Use ids = hash(run_id, step, node, branch_idx) and store each finished branch's output as a trace step with checkpoint_ref. Effort M with fan-out.
4. **Fan-out/map (`Send`) + reducer-merge with deterministic ordering** — our tournament K-way (research/) is presumably done inside a module node, serialized and opaque to checkpointing [inference; not read]. LangGraph's lesson: run branches concurrently, but apply writes sorted by task path, not completion order (_algo.py:253-256), so replays are reproducible. Add a `MapNode(over="state.hypotheses", node=..., reducer="append|merge|custom")` to the spec so the evolver (L6) can edit branching width as a typed edit. Reimplement. Effort M/L. Budget must be charged per branch before launch (their runner has no budget concept).
5. **Reducers declared in the spec** (binop.py): explicit per-key reducer (`append`, `max`, `merge`, `overwrite`) with an explicit `Overwrite` escape hatch and an error on conflicting concurrent writes. Our `state.update(out)` (engine.py:158) is last-writer-wins and fine only because we are sequential; add reducers at the same time as fan-out. Effort S. Copy-able (MIT) but trivial to reimplement.
6. **Retry policy with error classification + backoff** (types.py:427, _retry.py:644-679): ours retries only schema failures; transient backend errors (`BackendError`, engine.py:150) go straight to FAILED/`_last_error`. Add `RetryPolicy` to nodes, retry only transient classes, and — our advantage — charge each failed attempt to the budget (LangGraph doesn't). Effort S.
7. **Durability knob** (`sync|async|exit`, types.py:98). We are effectively `sync` (blob + step written before next node). Keep sync as default for expensive steps; consider `exit`/batched for cheap tool-heavy loops. Low priority. Effort S.
8. **Checkpoint dedup: store only changed channels, by version** (_loop.py:1255-1258, put(..., new_versions)). Our engine writes the whole `state` dict per step as one blob (engine.py:164): 50 steps x large state (data profiles, code, traces in `_module_llm_calls`) is O(steps x state). Split state per top-level key into content-addressed blobs and checkpoint = {key: blob_ref}. Effort S/M, high value for storage on long runs. Reimplement.
9. **Time-travel UX**: `get_state_history`, `update_state(as_node=...)` (main.py:1510, 1615): edit state "as if node X produced it" and fork. We have fork-from-step but no state-edit-and-fork, which is what a human or an evolver needs ("same checkpoint, different hypothesis"). Add `fork(run_id, step, state_patch=..., as_node=...)` recorded as lineage with source tag `update` (their `source` metadata is a good model, base:42-50). Effort S.
10. **Drain/graceful stop** (_loop.py:650): cooperative "finish this superstep, checkpoint, exit" so campaign schedulers can preempt. Ours has only budget/step limits. Effort S.
11. **Recursion/step limit raised as an explicit status** — ours already does (RunStatus.STEP_LIMIT). No gain.

## 5. Things custom-harness already does better (with evidence)
- Budgets in units, enforced before/after every step (engine.py:129-131,173-176; budget.py:44-60). LangGraph has only a step cap (`recursion_limit`) and no cost/token/wall budget at all in the loop (searched _loop.py/_runner.py/_retry.py; none seen).
- Failed attempts are costed and stored in the trace (engine.py:142-149); LangGraph retries silently, with `task.writes.clear()` (_retry.py:615) and no cost record.
- Workspace snapshot in the checkpoint (engine.py:162-165, 106-107): LangGraph checkpoints channels only; sandbox FS/process side effects are not part of replay/time-travel, so forking a LangGraph run after tool execution gives inconsistent state.
- Typed, closed spec with `extra="forbid"` and static graph validation (spec.py:283-362): conditions are data (`Condition`), not Python callables, so L6 can diff/edit/hash them (spec_hash, :364). LangGraph conditional edges and nodes are arbitrary Python functions (e.g. `add_conditional_edges(START, continue_to_jokes)` in the Send docstring), unhashable and un-diffable.
- Error routing explicit: errors only follow edges that test `_last_error` (engine.py:191-201); unmatched edges = FAILED, never silent success. LangGraph's error handler nodes are newer and optional (_loop.py:785).
- Content-addressed blobs + append-only trace with full inputs/outputs/provenance (engine.py:166-169) vs LangGraph's checkpoint table being the only record (traces are LangSmith, a separate product).
- Private-state guard against prompt leakage (template.py `_private*`): no LangGraph equivalent (state is passed whole to nodes).

## 6. Pitfalls, bugs, or anti-patterns in their code that we must avoid
- **Resume semantics inferred from heuristics, not an explicit API.** `_first()` is ~280 lines of branching on input type, `run_id` equality, `RESUMING` config flags, time-travel vs resume vs fork, subgraph namespaces (_loop.py:860-1140, with comments admitting special cases for "LangGraph Studio"). Passing new input to a thread with pending tasks silently discards them (:1062-1083). Our resume/fork must be two explicit methods with distinct run records.
- **Default `async` durability** (main.py:2672): the loop continues before the checkpoint is durable; crash window loses last step(s) while the user's mental model is "checkpoint after every node". Our default must stay sync for expensive nodes.
- **Re-execution on interrupt resume** (types.py docstring: "re-executing all logic"), with order-based matching of resume values to `interrupt()` calls (assert `len(resume)==idx`). Any nondeterminism or conditional `interrupt()` before the call breaks the mapping. Avoid by making interrupts node boundaries.
- **Task ids depend on the checkpoint id**, so any fork changes all task ids and stale INTERRUPT writes must be manually purged (_loop.py:1031-1035 comment). Key our branch ids on (run_id, step, node, idx) and keep per-run tables.
- **Mutable/parallel state with per-task partial writes + async puts** produces a large correctness surface: ordering futures (`_checkpointer_put_after_previous`, :1596-1613), delta-channel visibility invariant (:1285 docstring), exit-mode special cases (`exiting = metadata is self.checkpoint_metadata` identity trick with a TODO, :1142-1154). Keep one writer, ordered, simple.
- **`prune(keep_latest)` can silently corrupt DeltaChannel state** (base:375-415 warning: "silently reconstruct as empty (no error raised)"). Never add delta/incremental state encoding without a verification on read.
- **Serialization safety**: JsonPlusSerializer default is PERMISSIVE msgpack (all types allowed with a warning) unless `LANGGRAPH_STRICT_MSGPACK=true` (jsonplus.py:107-115) and has an opt-in `pickle_fallback` (:100, 269-288). Deserializing checkpoints from a shared DB = code-execution surface. Ours stores JSON blobs (engine.py:164 `put_json`), keep it JSON-only.
- **Retry defaults**: `max_attempts=3` counts the first try; jitter is additive `uniform(0,1)` seconds regardless of interval (_retry.py:671) — not proportional. Sync timeouts unsupported (`sync_timeout_unsupported`, :580). No budget/cost awareness: a retried LLM node pays repeatedly with no accounting.
- **`INSERT OR IGNORE` for ordinary writes** (checkpoint-sqlite __init__.py:465): a replayed task's differing output for the same (task_id, idx) is ignored, so saved vs recomputed outputs can diverge silently [inference from SQL semantics; I did not trace the exact replay path].
- Complexity cost: `main.py` 4.4k lines with sync/async duplicates (`atick`, `arun_with_retry`, `AsyncPregelLoop`) — the reason we chose a thin core is justified; do not grow engine.py toward this.

## 7. Verifier / evaluation / safety handling
LangGraph has none of this: no sandbox, no evaluation, no result verification; it executes arbitrary Python nodes in-process. Safety hooks present are limited to: checkpoint serializer allowlist (strict msgpack opt-in, jsonplus.py:92-125), an `EncryptedSerializer` in checkpoint/serde/encrypted.py (existence seen in dir listing, not read), recursion limit, and human-approval via interrupts. Nothing to borrow for L3/L4.

## 8. Bottom line
- Our thin engine is the right call for typed, diffable, budgeted harnesses; LangGraph's semantics are mostly about durability + concurrency, which we have not built.
- Highest-value gaps: (1) resume-same-run after crash + FAILED-on-any-exception, (2) explicit PAUSED/interrupt node with checkpointed answers, (3) parallel `MapNode` with per-branch persisted outputs, deterministic merge order and declared reducers, (4) per-key checkpoint blobs, (5) transient-error retry policy charged to budget.
- Copy ideas not code: the useful pieces are small (sorted-by-path reducer application, per-task pending writes, deterministic task ids); MIT allows copying if wanted.
- Avoid: heuristic resume detection, async-by-default durability, re-execute-node-on-interrupt, pickle/permissive deserialization, delta-encoded checkpoints.
