## 1. What the code actually does (architecture map)
- **Kernel** (`src/orchestrator/iteration/graph_runner.py`, 686 lines incl. subprocess worker code; paper says ~600): `GraphRunner` runs an `IterationGraph` loaded from YAML (`graph.py:IterationGraph.from_yaml`). Nodes carry `module`, `depends_on`, `params`, `input_mapping`, `output_mapping`, `routes`, `timeout`, `retry` (graph.py:IterationNode). Everything is stringly-typed dicts.
- **Module contract** (`adapters/base.py:BaseModule.execute(inputs)->dict`): reserved keys `_route`, `_routes`, `_score`, `_metadata` consumed by the runner (graph_runner.py:501-520) and stripped before downstream (line 506). `LLMAgentModule` wraps progress-reporting.
- **Registry** (`registry.py`, 67 lines + `modules/__init__.py`, 1381 lines): `ModuleSpec` with free-text input/output schemas; `_ADAPTERS` table maps name to (dotted module path, class). I counted **161** entries; every referenced file and class exists (scripted check), so "130+/140+" is understated, not overstated. Instantiation is lazy and falls back silently to a `PlaceholderModule` on ImportError/AttributeError (`modules/__init__.py:_lazy_import`, `_create_placeholder`).
- **Persistence**: three SQLite files (`db/connection.py:8-10`: knowledge_store.db, papers.db, artifacts.db) plus small registries (`code_analyzer/analysis_registry.py`, `code_link_extractor/downloaders/repo_registry.py`). Paper says five SQLite DBs; I found three main plus two registry DBs [inference: that is how the five are counted]. Neo4j holds the KG (`knowledge_graph/store.py`, vector + fulltext indexes created in init_schema per kg_config.yaml comments).
- **Providers** (`llm_provider/factory.py:LLMFactory._providers`): openai, anthropic, local, minimax, glm, mock = 6, matching the claim. Plus `llm_dispatcher/` (concurrency guard, RPM limiter, retry policy per provider slot, dispatcher.py:ProviderSlot._dispatch).
- **Pipelines**: 38 YAML in config/pipelines (README says 38; paper says ~50/53; the count that includes `*.smoke/*.test/*.prod100` variants is already in 38).
- **Agents**: "six cognitive roles" exist as `idea_agents/{reader,analyst,connector,contrarian,synthesizer,critic}.py` plus ~12 more (hypothesis, theory, etc.), wrapped as `*_agent` adapters. Experiments are delegated to an external CLI agent (`opencode run ... --dangerously-skip-permissions`) rather than a native sandbox.

## 2. Core loop, step by step (with citations)
1. `GraphRunner.run` builds `_TopologyContext` (graph_runner.py:651), merges graph config into shared config (:190), calls `_execute_graph`.
2. `_topological_levels` (:605-643): Kahn's algorithm over `depends_on` plus `input_mapping` `output.<node>` references. **Nodes in cycles are dropped from the levels with only a log warning (:637-642).** Initial `ready` = level 0 only (:247).
3. Loop `while ready and round_num < max_rounds` (:249; default max_rounds=100, :244): run all ready nodes concurrently via `asyncio.gather` (:486-488), optional `max_parallel` semaphore (:357).
4. Each node: dependency check (:369), retry loop with optional backoff (:379-484), then either a **fresh `multiprocessing.Process` per node execution** (:396-404; result via Queue, `os._exit(0)` in child, :142) or in-process when `max_workers=0` (:429-447). Timeout: queue.get timeout then terminate (:409-416) or `asyncio.wait_for`.
5. `_process_node_result` (:494-520): extract `_route`/`_routes`/`_score`/`_metadata`, store filtered outputs, bump per-node iteration count.
6. `_resolve_next_ready` (:272-333): successor = `routes[_route]` if present, else `routes["default"]`, else every node that lists it in `depends_on`; plus all `_routes` fan-out targets. A successor becomes ready only if all its `depends_on` are in `completed_nodes`. Because `completed_nodes` is never cleared, loops work only when the loop-target's dependencies were completed once and stay "complete" (re-entering a node re-runs it, but a node waiting on a not-yet-run dep may trigger running that dep, :323-331 hack).
7. Loops are expressed as route-back edges, e.g. auto_idea_to_paper.yaml: `accumulate` routes `need_more: paper_retriever`; `round_control` routes `continue: paper_retriever`. **Loop state (retry counters, accumulator, round count) is kept in JSON files on disk**, not the kernel: `state_file: output/auto_idea_to_paper/round_state.json` etc. (YAML lines 38-69; `experiment_success_gate.py:_load_state/_save_state`). Reruns of the pipeline inherit stale state unless files are deleted.
8. Inputs are resolved by string prefixes `config.` / `output.<node>.<field>` (graph_runner.py:543-571). No type checks at runtime; typing is only a lint script (`scripts/validate_pipeline.py`) comparing INPUT_SPEC/OUTPUT_SPEC dicts offline.

## 4. Mechanisms worth adopting into custom-harness (ranked)
1. **Per-node process isolation with hard kill on timeout** (graph_runner.py:102-142, 396-416). Why: frees GPU memory and kills hung native threads; our engine (`custom_harness/runtime/engine.py`, 266 lines) runs modules in-process. Layer L0. Effort S-M. Reimplement (no valid license; and our sandbox layer already covers untrusted code; only adopt for heavy GPU/PDF modules). Caveat: they `os._exit(0)` after queue put, losing exceptions in cleanup; keep tracebacks.
2. **Persistent paper corpus schema with typed extraction sub-tables** (papers_schema.py: papers, authors, pdf_extractions, paper_sections with order/type/page, paper_tables, paper_formulas, paper_images with bbox, paper_artifacts; provenance of downloads). Our L2 store (`store/evidence.py`) has no literature layer (STATUS.md: "I3 n/a until literature module exists"). Layer L5/literature (PLAN §4). Effort M. Reimplement (design idea only), and make FTS actually work: use FTS5 with triggers or a contentless table populated on insert, unlike PARNESS (see §6).
3. **Provider dispatch layer: per-provider concurrency guard + RPM limiter + retry with jitter** (llm_dispatcher/dispatcher.py:ProviderSlot: guard, limiter, retry order). Our `gateway/` has registry and BYOS gating but I did not verify rate limiting there. Layer L0 gateway. Effort S. Reimplement.
4. **KG construction recipe**: chunk to nodes, embedding link threshold, struct edges from FKs, semantic edges via LLM with `min_confidence`, random-walk "remote relation" discovery with visit-frequency threshold (random_walk.py:_run_walks/_filter_candidates; kg_config.yaml `random_walk`, `indexing`), protected-relation pruning with decay (pruner.py). Useful as a cheap serendipity source for hypothesis generation. Layer L5 memory/literature. Effort L (needs Neo4j or a SQLite+vector substitute). Reimplement; do not take Neo4j as a hard dependency. Caveat: no evidence it improves ideas; treat as an ablation candidate, not a default.
5. **Pre-flight static pipeline validation of cross-node field contracts** (scripts/validate_pipeline.py checks: node exists, field exists in upstream OUTPUT_SPEC, type match, required coverage, dangling ref). We already have typed `HarnessSpec` (runtime/spec.py, pydantic `_Strict`), so this is a lower priority; adopt only the idea of validating `input_mapping` field existence against module output schemas at load time. Effort S.
6. **Fan-out / `_routes` + `_score` in a four-field return contract**: a minimal, easy-to-explain agent contract. Our contracts are richer (bounded retries, typed edits), so adopt only if we add multi-successor routing (STATUS next item 5, MoB-style). Effort S.

## 5. Things custom-harness already does better (with evidence)
- **Typed, strict spec vs stringly-typed dict DSL**: `runtime/spec.py` (`_Strict` pydantic models: LLMNode, ToolNode, ModuleNode, Condition, Edge, BudgetSpec) versus `IterationNode` dicts with unvalidated `routes`/`input_mapping`; PARNESS silently ignores unknown keys and dead edge fields (§3).
- **Exact traces, per-step checkpoints, fork/backtrack** (STATUS L0). PARNESS has no checkpoint/resume in the kernel (state in ad-hoc JSON files per module, `experiment_success_gate.py:_save_state`) and `completed_nodes` is a plain set with no replay.
- **Budget ledger with hard caps** (`budget.py`). PARNESS has no token/cost accounting: `BaseLLMClient.chat` returns `str` only (llm_provider/base.py), so usage, cost, and finish reasons are lost.
- **Verified outcomes**: our tiers/verify (T0-T6, bootstrap, hidden-test) vs. PARNESS gate based on `"ERROR" in log` (experiment_success_gate.py) or an LLM-agent verdict.
- **Sandboxing**: Docker with no network, caps, read-only rootfs (`sandbox/`) vs. `--dangerously-skip-permissions` CLI agents (experiment_runner_cli/run.py:93, experiment_verifier_cli/run.py:99).
- **Private-data guard, secret redaction, provider BYOS registry** have no counterpart in PARNESS.
- **Self-improvement exists in ours** (`evolve/`: typed edits, static checks, racing, held-out gate, lineage) while PARNESS has none (§3).

## 6. Pitfalls, bugs, anti-patterns (must avoid)
- **Silent placeholder fallback**: `_lazy_import` returns a `PlaceholderModule` that returns `{"placeholder": True, "message": "Module not implemented", ...}` on any ImportError/AttributeError (modules/__init__.py `_lazy_import`). A missing dependency becomes a "successful" node and the pipeline continues. Our engine must fail closed.
- **Failed experiments flow into the paper**: in auto_idea_to_paper.yaml, `experiment_gate` routes both `pass` and `skip` to `experiment_report`; after 3 failures the gate resets its counter and "skips" onward (experiment_success_gate.py end of execute). Failure is not terminal; negative results can be written up as if complete. Contradicts our integrity audit (I1, I2, I4).
- **Weak default success heuristic**: success = non-empty results and no substring "ERROR" in the log (experiment_success_gate.py:47-49). Gameable by an agent that writes `results.json` with fabricated numbers. The generating agent also writes the results.json format and prediction/label arrays (executor.py `_build_prompt`), i.e. the same agent produces both the metrics and the labels.
- **Verifier is another LLM CLI with permissions disabled** (`opencode run --agent verifier --dangerously-skip-permissions`, experiment_verifier_cli/run.py:99). `.env` keys are loaded and passed into the child env (run.py ~75). Verdict is a file the agent writes (`verdict.json`); missing verdict only prints a warning (run.py ~120).
- **Cycle handling is a log warning**: nodes inside cycles via `depends_on` are dropped from topological levels (graph_runner.py:637-642); loops only work because routing bypasses levels. Easy to build graphs that silently never run a node. `max_rounds` default 100 is the only loop guard (:244).
- **`completed_nodes` never cleared** so loop re-entry semantics are implicit; a node on a loop sees stale outputs of its deps. Retry counters/accumulator state in global JSON files (shared across runs and parallel runs).
- **Dead DSL**: `condition`, `feedback_key`, `priority`, `backtrack` on edges parsed, never executed (§3), yet advertised in README:101.
- **Anthropic client bug**: `AnthropicClient.chat` passes `model=`, `max_tokens=` explicitly and also `**kwargs` (anthropic.py:~31-37); any caller supplying `model` or `max_tokens` in kwargs raises `TypeError: multiple values for keyword argument`. Also `response.content[0].text` ignores non-text blocks; system prompt only keeps the last system message; no usage returned.
- **Unusable mock for realistic tests**: `MockLLMClient` sleeps `delay=10.0` seconds per call by default (mock.py `__init__`), and picks canned output by substring-matching English/Chinese prompt fragments (`_DETECTION_RULES`); an edited prompt silently yields `{"result":"mock response"}`. Fragile and slow. Our `gateway/mock.py` should stay schema-driven.
- **Search index never populated**: `paper_sections_fts` external-content FTS5 with no sync (§3). The documented persistent full-text index would return nothing.
- **Copy of secrets into child processes**: `llm_api_key` rides in shared config dict pickled into subprocess args (graph_runner.py:385-404, adapters/base.py:_get_llm_client).
- **Swallowed errors**: KG phases (`rebuild.py:556`), DB-level processing (`rebuild_all`) record errors in stats and continue; also many `except Exception: pass` in the worker (graph_runner.py:89-98). Success flag in `PipelineResult` is just "no failed nodes".
- **Repo hygiene**: no tests directory, no LICENSE file though README claims MIT, vendored AGPL code (PDF-Extract-Kit) next to MIT claim, committed output artifacts under `papers/`.
- **Quality of the main loop is unmeasured**: no benchmark, no ablation of the KG or role agents; the paper itself reports none.

## 7. Verifier / evaluation / safety handling
- Idea quality: LLM scorers (`idea_evaluator`, `idea_judge`, `idea_reviewer`; mock rules mention "ICLR Area Chair"), thresholds in YAML (`score_threshold: 7.0`) and controllers (iteration_controllers.py: threshold/patience/improving/LLM/multi-criteria) feeding `_route`. Same model family judges and generates; no panel or agreement stats [inference from config; not all judge code read].
- Experiments: generated and run by an external coding agent in a temp workdir (executor.py: `tempfile.mkdtemp(prefix="opencode_exp_")`, `asyncio.create_subprocess_exec`), timeout 3600s, no container, no network restriction, permissions skipped. Results read from `results.json`. Verification by a second agent session over the plan and the runner workspace (`experiment_verifier_cli`), reward/exploit handling beyond that is not present (no perturbed evaluator, no hidden test, no seed repeats).
- Gate: heuristic fallback plus "authoritative" upstream verdict override (experiment_success_gate.py:44-48); on exhausted retries, proceed anyway.
- Citation/reference integrity: README lists an Integrity Checker and Gap Analyzer (5 reference-management modules); I did not read them.

## 8. Bottom line
- A large, practical, YAML-driven pipeline toolkit (161 modules, 38 pipelines) with a thin 686-line kernel; engineering breadth is real, scientific rigor is thin.
- Worth borrowing as ideas: per-node process kill/timeout, typed literature corpus schema, provider dispatch (RPM/concurrency/retry), KG random-walk discovery as an ablation. Do not copy code: no LICENSE file, and the vendored PDF parser is AGPL.
- Paper claims that the code does not support: tests (none in repo), scenario-sliced KG feeding the six role agents, any self-improvement, working persistent SQLite FTS, backtrack edges.
- Anti-patterns to avoid: placeholder-on-import-failure, failed experiments flowing to the report, "ERROR" substring success, agent-run verifier with skipped permissions, loop state in global JSON files.
- LoC verification: 65.7k py lines (56.0k non-blank) excluding vendored code, 72.9k with it; 62.2k is in the right range, but "13.4k test LoC / 553 tests" is unverifiable because the tests are not in the repo.
