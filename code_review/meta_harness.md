## 1. What the code actually does (architecture map)

Meta-Harness in code is a thin Python outer loop that shells out to the `claude` CLI as the proposer, then evaluates whatever Python files the proposer wrote into `agents/`. There is no spec, no DSL, no edit algebra: the "harness" is a single arbitrary Python file (a `MemorySystem` subclass for text classification; an `AgentHarness(Terminus2)` subclass for TB2).

Components (text_classification/, the paper's main reference loop):
- `meta_harness.py`: outer loop (Phase 0 baselines, then N iterations of propose -> import-validate -> benchmark -> update frontier -> append summary). Final test eval only via separate `--test` invocation (`finalize_run`, :286-357).
- `.claude/skills/meta-harness/SKILL.md`: the ENTIRE proposer prior (workflow, anti-parameter-tuning rules, anti-overfitting rules, file formats). This is what makes the proposer behave; the Python is plumbing.
- `claude_wrapper.py`: builds the `claude -p ... --dangerously-skip-permissions --output-format stream-json --model opus --effort max --setting-sources "" --strict-mcp-config --disable-slash-commands` command (:115-168) and logs each proposer session to `logs/<run>/claude_sessions/<ts>_iterN/{meta.json,response.md,events.jsonl,tools/NNN_Tool.txt}` (log_session :322-424).
- `benchmark.py`: sweep orchestration; computes per-dataset best and aggregate Pareto frontier over (accuracy, context chars) (`compute_pareto_frontier` :274-293, `print_frontier` :611-710) and writes `frontier_val.json`.
- `inner_loop.py`: the single (memory system, dataset, model) evaluator that writes `log.jsonl` (per-step events: `logger.log("eval_step", ...)` etc., :166-405), `val.json`, `memory.json`.
- `config.yaml`: datasets (USPTO, Symptom2Disease, LawBench), split sizes (200 train / 50 val / 100 test, with overrides), baselines (`no_memory`, `fewshot_all`).
Terminal-Bench-2 variant (terminal_bench_2/): same skeleton; evaluator is `harbor run -d terminal-bench@2.0 ... --n-attempts N` via scripts/run_eval.sh:79-87; candidate = `agents/<name>.py` with class `AgentHarness` subclassing Harbor `Terminus2`, parent = `agents/baseline_kira.py` (KIRA).
Also: `experimental/harbor_meta_harness/` (pilot where the OUTER agent is itself a Harbor agent with an `evaluate_harness` tool; see section 7).

### What the proposer actually sees (this is the central question)
1. Working directory = the experiment dir (`cwd=str(EVOLVE_DIR)`, text_classification/meta_harness.py:169-179; TB2 propose_claude at terminal_bench_2/meta_harness.py:431-446). Tools: Read, Glob, Grep, Agent, Write, Edit, Bash (PROPOSER_ALLOWED_TOOLS :39-47), with `--dangerously-skip-permissions`. So it is a full coding agent with an unrestricted shell in the experiment directory. That directory contains every prior candidate's source (`agents/*.py`), `logs/<run>/evolution_summary.jsonl`, `frontier_val.json`, per-(dataset,system,model) `log.jsonl` traces and `val.json`, `reports/`, and the prior proposer sessions (`logs/<run>/claude_sessions/`, so it can read its own earlier reasoning and tool calls). For TB2: `jobs/` (Harbor trial dirs: per-trial result.json, agent logs) and `logs/`.
2. The task prompt is tiny (render_task_prompt, text_classification :136-146; TB2 :530-545): "Run iteration N", number of datasets/tasks, and the paths to summary/frontier/reports and where to write `pending_eval.json`. No digest, no excerpts, no failure clusters are injected. The proposer must discover everything by Read/Grep/Bash. This is the opposite of our `diagnose()` digest.
3. SKILL.md instructs the discovery procedure. Text-classification: Step 0 write <=30-line reports for any past iteration lacking one (a proposer-maintained memory layer, SKILL.md:46-48); Step 1 read `evolution_summary.jsonl`, `frontier_val.json`, `config.yaml`, "recent" `log.jsonl` traces (:50-58); Step 2 MANDATORY prototyping in /tmp against real logged examples, 2-3 variants (:60-69); Step 3 copy a top-performing agent and edit (:71-80), self-critique "is this a new mechanism or a parameter variant?" (:77). Explicitly "do NOT delegate to subagents" (:8) in the text-classification skill, but the TB2 skill does the opposite: Step 1 launches ONE general-purpose Agent subagent to read state files and "deep-read failed AND successful trajectories", Step 2 another subagent to implement (TB2 SKILL.md:70-99). The claim "median 82 files read per iteration / >20 prior candidates referenced" in the paper is not computed anywhere in the repo; the only instrumentation is `files_read`/`files_written` in meta.json (claude_wrapper.py log_session) [inference: that is where the figure was derived].
4. What the proposer does NOT get: a pre-selected parent (it picks), a score-per-candidate leaderboard beyond `evolution_summary.jsonl` rows (avg_val, delta vs frontier, axis, hypothesis, components) and `frontier_val.json`. TB2 summary rows also carry per-task pass rates and `rollout_metrics` (cost, tokens, turns) (terminal_bench_2/meta_harness.py:396-428), and the printed per-task delta vs the per-task best.

## 2. Core loop, step by step (with file:line citations)

text_classification/meta_harness.py `run_evolve` (:360-579):
1. Load config, resolve run dir `logs/<run_name>` (:375-388). Refuse to continue a run once `finalized.json` status is complete (:395-402).
2. Phase 0 (:413-441): benchmark baselines (`no_memory`, `fewshot_all`) on val, write frontier.
3. For each iteration (:445): print frontier; delete stale `pending_eval.json` (:467-468); call `propose_claude` (:164-189): pop `CLAUDECODE` and `ANTHROPIC_API_KEY` env (use subscription auth), run Opus at `--effort max`, timeout 2400 s default (:595-598); success = exit 0 AND `pending_eval.json` exists.
4. Read `pending_eval.json` candidates (EXACTLY 3 required by the skill: "MUST implement 3 new memory systems every iteration", SKILL.md:14-17) (:482).
5. `validate_candidates` (:192-215): only an import check (`python -c "from text_classification.agents.<name> import *"`, 30 s). No behavioral/smoke test in this loop (TB2 adds one, below).
6. Benchmark each valid candidate on val for all datasets via `benchmark.py --memory <name>` (:511-527), then `--frontier` (:527) which rewrites `frontier_val.json` from ALL results.
7. Score = mean over datasets of val accuracy (:530-541). `update_evolution_summary` (:218-254) appends one JSONL row per candidate with delta vs. current Pareto head (`pareto[0].val_accuracy`, :229).
8. "NEW BEST" is just printed (:563-568). THERE IS NO ACCEPT/REJECT STEP: all candidates stay in `agents/` forever and remain visible; selection is implicit (the proposer chooses parents from the frontier) and explicit only at the end (Pareto set + per-dataset bests are what `finalize_run` sends to test, :301-308).
9. Finalization (separate command `--test`, :286-357): writes `finalized.json` (in_progress), evaluates baselines + Pareto systems + per-dataset best systems on TEST once, writes complete state. After this, evolution under that run name is refused (:395-402).

TB2 loop (terminal_bench_2/meta_harness.py `run_evolve` :573-895):
- Baselines: kira-baseline and terminus2-baseline are evaluated with cached/validated results (:600-668), frontier seeded from them (:660-667).
- Per iteration: propose (1 candidate only, TB2 SKILL.md:14), `validate_candidate` import check (:459-480), `smoke_test` = 1 trial on task `extract-elf` (:481-527; failure on any errors in result.json `n_errors`), then full benchmark: `harbor_run` of all 89 tasks x `--trials` (default 2) at concurrency 50 (:158-207; run_eval.sh uses `--ak temperature=0.7`, :79-87).
- Scoring: per-trial reward read from each trial's result.json; missing/corrupt/errored trials count as 0 (parse_job_results :210-253, explicitly "ground truth"); candidate avg = total_passes/total_trials (compute_pass_rates :256-271); `update_frontier` (:373-393) keeps best per task plus `_best` (best avg). Strictly greater-than, no CI, no noise handling.
- `--full-eval` optional: best agent re-run with 5 trials on the full dataset (:862-895); the 5-trial run is on the SAME 89 tasks.
- No parent/child accept gate at all.

## 3. Paper/summary vs code discrepancies

(Summary = autoresearch_survey/2603.28052.md; I did not read the paper PDF itself, only the survey summary and the repo.)
1. "Proposer ... evaluates candidates and logs results back" / "Proposer decides when to stop and returns Pareto frontier" (summary "Core Idea", "Level of Autonomy"). Code: the proposer explicitly does NOT run benchmarks ("You do NOT run benchmarks", both SKILL.md:10) and is forbidden to stop ("Do NOT write 'the frontier is optimal' or 'stop iterating'", SKILL.md:15). Iteration count is a CLI int (`--iterations`, default 20, text_classification :584); stopping is human/budget only. The outer loop evaluates; the Pareto frontier is computed by `benchmark.py`, not the proposer.
2. "k candidates per iteration": k=3 for text classification (SKILL.md:14,17) but k=1 for TB2 (TB2 SKILL.md:14).
3. Pareto frontier: only text classification builds a (accuracy, context-chars) Pareto set (benchmark.py:274-293). TB2 has NO Pareto: just best-per-task and best-average (`update_frontier`). Cost/turn data is logged and shown to the proposer but never enters selection.
4. "Environment bootstrapping reduces turns by 2-4 steps; inject uname, python --version, package managers" (summary). Code (artifact agent.py `_gather_env_snapshot` ~873-970 per diff): runs ONE compound shell command collecting `pwd`, `ls -la /app/`, versions of python3/gcc/g++/node/java/rustc/go, pip3/pip/apt-get, `free -h`. There is no `uname`. Output is truncated (>25 ls lines -> first 20 + "... N more") and appended to the initial prompt as "[Environment Snapshot]" (agent.py ~985-992); any failure returns "" silently. The "2-4 turn saving" claim is unverifiable from the code (only a `_total_time_saved` accumulator exists, ~line 276, that I did not trace to a metric).
5. "Held-out generalization / separate test sets" is true for text classification (val-only evolution; test only via one-shot `--test`), but for TB2 search and final eval are the same 89 tasks (README.md "Terminal-Bench 2"; summary itself admits it). The repo's own text: "The test data is included in this public repository, so this is operational isolation, not access control" (text_classification/README.md). Proposer has an unrestricted shell in a directory that contains `data/*/test.jsonl` [verified: files exist at text_classification/data/<ds>/test.jsonl], and the SKILL.md anti-leak rule is only prose ("No dataset-specific hints", :36-40). So held-out isolation is by instruction, not by mechanism, in the shipped code. ONBOARDING.md tells users to "Keep final test data and results outside its accessible workspace" - the reference example itself does not do this.
6. "Discovered harness" vs repo: the shipped TB2 reference does not contain the discovered harness; it lives in the separate artifact repo, whose README says only "More details coming soon" on method. No search history, no candidate lineage, no evolution_summary or traces from the paper's run are published in either repo [verified by file listing]. The paper's claims about iteration counts, files-per-iteration and Mtok/iter cannot be audited from the code.
7. Paper-reported ablation "scores only / scores+summary / full filesystem" is not implemented as a switch anywhere in the repo (no config for restricting proposer visibility) [grep-level; I did not find one].

## 4. Mechanisms worth adopting into custom-harness (ranked by expected value)

All of Meta-Harness's value is in what the proposer can read and how it is instructed; the code is small. License of the main repo is MIT, so reimplementation-with-attribution is fine; most of this is ideas (reimplement).

1. Give the proposer a real filesystem workspace of history instead of a 12 KB digest (HIGHEST VALUE).
   - What: proposer runs as an agent with Read/Grep/Glob/Bash over a directory holding every candidate's source, `evolution_summary.jsonl`, `frontier_val.json`, per-run traces, and its own past session logs (text_classification/meta_harness.py:164-189; SKILL.md:50-58). Tiny prompt with only paths.
   - Ours: `evolve/propose.py:67-92` `build_prompt` injects `digest[:12000]` (clusters with <=2 examples x 1500 chars of ONLY error/run_error fields, propose.py:19-42, 30-34) plus `ledger[-15:][:4000]`; it is a single `backend.complete` call with a JSON schema (propose.py:98-100): no tools, no grep, no trace browsing, no look at successful runs. `diagnose` only excerpts steps with errors, so it can never reveal why a "completed but wrong" run failed.
   - Where: L2 (evidence store export) + L6.1. Concretely: materialize `store` to a read-only directory tree per generation (spec_<hash>.yaml, per-run `trace/<run_id>/<node>.json`, `lineage.jsonl`, `ledger.jsonl`, `reports/gen_N.md`), launch a tool-using proposer (our Backend with a Read/Grep/Bash sandboxed tool set, or `claude -p` as they do) with cwd at that tree, and keep the typed-edit JSON as the OUTPUT contract. Retain our digest as an index file in that tree (cheap orientation), not as the only evidence.
   - Effort: M. Reimplement (idea; their wrapper is MIT but tied to the claude CLI).
2. Proposer-maintained post-eval reports (memory layer). Step 0 of SKILL.md:46-48: each past iteration lacking a report gets a <=30-line report (what changed, which datasets improved/regressed and why, takeaway). Reports are written into `logs/<run>/reports/` and become the cheap first-read for later iterations. Ours: `store.records("harness_edit")` ledger is structured numbers only (loop.py:244-249), no causal narrative. Where: L6.7 harness-science claims / L3 memory. Effort: S. Reimplement.
3. Mandatory prototyping before commit + self-critique "new mechanism vs parameter variant" (SKILL.md:60-80). Their report that parameter sweeps "almost always regress or tie" (SKILL.md:21) motivates it. Ours already prefers structural edits in prose (propose.py:87-88) but has no prototype stage; our edits are cheap to apply but we do not let the proposer dry-run a candidate on logged inputs before spending evals. Where: L6 propose stage; with typed edits the analog is "replay the edited node on stored node inputs from past traces" (we store traces in EvidenceStore). Effort: M. Reimplement.
4. Proposer sees rich per-candidate evaluation metadata including cost, tokens and turns, and per-task pass-rate deltas to the per-task best (TB2 `update_evolution_summary` :396-428; run printing :786-826). Ours: `GenerationResult`/lineage records carry scores and CI but proposer sees only last 15 ledger rows truncated to 4000 chars. Where: L6.1 workspace files. Effort: S.
5. Cheap validity gates before expensive eval: import check -> single-task smoke run counting `n_errors` (TB2 :459-527). Ours: static `apply_edit` checks only (edits.py), then straight into the race. A smoke run of a candidate on one cheap task catches runtime-broken specs before the evolve split is spent. Where: L6 gate stage 0. Effort: S.
6. Explicit one-shot finalization with frozen run state: `--test` writes `finalized.json`, records the system set evaluated, refuses further evolution on that run (text_classification :286-357, 395-402). This is the procedural form of "select before looking at test". Ours: sealed split is simply filtered out of `evolve()` (driver.py:139-140) with no finalization artifact; there is no code path or record proving selection preceded the sealed look. Add: `finalize` command that pins the selected set hash, evaluates sealed once, writes the freeze file, blocks further generations. Where: L6/L9. Effort: S. Reimplement.
7. Trust-boundary design for generated code (experimental pilot): candidate source is staged by a short-lived trusted subprocess, never imported by the long-lived controller; AST-checked for required class/method; substring denylist of benchmark references (`validate_source`, controller.py:144-175, `UNIVERSAL_FORBIDDEN` :22-28, per-task `forbidden_references` in task.toml :127-141); bounded `evaluate_harness` tool with a fixed eval budget and append-only history (agents/meta_harness.py:33-39, 53-92). Relevant to us only if we ever allow code-level edits (PLAN L6 "tool add/modify"). Our `_LEAK_PATTERNS` in edits.py:~58 is the same idea but only 4 regexes and only on ops; per-task forbidden-reference lists derived from the actual task files would be stronger. Effort: S-M.
8. Concurrent baseline caching and "failed/timeouts count as 0" scoring rule (parse_job_results :210-253) so partial results never inflate a candidate. Ours: `score_state` already gives 0 on non-completed (evaluate.py:74-77); fine.

Adopt only the parts above that fit our typed-spec design; do NOT adopt the free-code search space wholesale (see 5/6).

## 5. Things custom-harness already does better (with evidence)

- Statistical acceptance. Theirs: strictly-greater average on val, no CI, no repeated-measure noise handling, 1-2 trials (TB2 `update_frontier` :373-393; text_classification `improved = any(v > best)` :563-567; config `seeds: [42]`). Ours: paired bootstrap CIs, successive-halving race against parent, require CI lower bound > 0 on evolve and non-negative on gate (selection.py:283-369; loop.py:226-243).
- Real accept/reject gate with a held-out gate split the proposer never sees, per-edit. Theirs: no gate; every candidate is kept and the proposer self-polices overfitting via prose rules (SKILL.md:36-40; TB2 SKILL.md:17-22). The text-classification val set is the same set the proposer reads traces from. Ours: evolve/gate/sealed task splits (evaluate.py:7-8; loop.py:194-199, 238).
- Typed, auditable, protected edits: protected `verify`/`audit`/`setup` nodes, audit must be the only terminal, spec-validity check (edits.py `apply_edit`, `check_edit`). Theirs: proposer can rewrite ANY method of the agent including how reward-relevant behavior (e.g. completion confirmation, command execution) works, subject only to subclassing Terminus2 (TB2 SKILL.md:24-28 "anything that's expressible in Python is fair game"). Nothing prevents a candidate from reading the verifier/test dirs inside the sandbox (only prose guidance); the experimental pilot is the only place with a denylist.
- Predicted-effect calibration: ours records predicted vs actual delta per edit and computes MAE/sign agreement (loop.py:244-265). Theirs records only a free-text `hypothesis` string (update_evolution_summary :235-245), no machine-checkable prediction.
- Edit lineage with rejects: ours logs malformed/rejected_static/no_op/raced/accepted/rejected_gate with reasons (loop.py:209-253). Theirs logs only evaluated candidates; failed-import candidates are logged with outcome "failed" and avg 0 (text_classification :498-499) but without a reason.
- Evaluation cost control via racing (`evaluations` vs `evaluations_fixed_k`, loop.py:228, selection.py:304-341). Theirs: every candidate on every dataset/task every iteration (TB2: "roughly $500 per iteration", README Runtime And Cost).
- Cache keyed by (spec hash, task, seed) so parent results are reused (loop.py:167-185). Theirs: result caching is only file-existence on val.json (`_has_usable_result`) per system/dataset.
- Honest objective with an integrity audit hard-zero (evaluate.py:74-87); Theirs: raw accuracy / pass rate, no integrity notion at the evolution level.

## 6. Pitfalls, bugs, or anti-patterns seen in their code that we must avoid

1. Held-out isolation by convention only (see 3.5): test data lives in the proposer's cwd tree; `--dangerously-skip-permissions` + Bash. Anything we build with a tool-using proposer MUST mount only the evolve-split evidence read-only and keep gate/sealed data and results on a path the proposer sandbox cannot see (not just un-mentioned). Their README concedes this.
2. TB2: search set = final eval set (89 tasks), `--full-eval` re-runs the same tasks. The reported 76.4% is in-sample w.r.t. selection (acknowledged in paper limitations, not fixed in code). Avoid: always keep a gate+sealed split disjoint from evolve.
3. Selection by max over noisy 2-trial pass rate (TB2 default `DEFAULT_SEARCH_TRIALS = 2`, run_eval.sh temperature 0.7) with strict ">" and no CI means winner's-curse; across many candidates the "best" is partly noise.
4. `update_evolution_summary` computes `delta` against `pareto[0]` (highest-accuracy Pareto point, text_classification :228-229) and in TB2 against `best_avg`, but both are read BEFORE the new frontier is written in the loop that follows; with `best_val` of 0 the delta is None (:241). Minor, but it means the proposer-visible delta can be stale/None on the first iteration. Do not copy this bookkeeping.
5. Candidate failure is silent in a key place: when no candidate is valid, `update_evolution_summary(iteration, candidates, {}, ...)` writes rows with avg 0/"failed" (text_classification :498-500), mixing broken-code failures with real regressions in the history the proposer reads. Distinguish "invalid" from "evaluated and worse" (we do: loop.py status values).
6. Fixed candidate count and "never stop" prompting (SKILL.md:14-17) forces 3 candidates per iteration even when nothing is promising; combined with exploitation/exploration axes rotation (:34). Cost per iteration is paid regardless. We should keep our budget-aware racing and allow "no edit" (we do: decision "no valid candidates").
7. Prompt-only anti-overfitting ("Never mention dataset names in system code, prompts, or comments", SKILL.md:36-40; TB2 :17-22). The proposer can still encode dataset-specific logic without naming datasets (e.g. hard-coded label sets, per-class thresholds). The experimental pilot's substring denylist has the same weakness (controller.py:144-150: `lowered` substring match only). A leakage critic (our PLAN RRSI idea) is needed on top.
8. Proposer subscription-auth hack: strips `ANTHROPIC_API_KEY` from the env so the CLI bills a subscription (text_classification :166-181; TB2 :431-457). Also `os.environ.pop("CLAUDECODE")`. Not something to copy; it couples cost accounting to an unmetered channel (their cost-per-iteration for the proposer is therefore not recorded as dollars except `cost_usd` in meta.json when the CLI reports it).
9. Not tested beyond import ("verifying that it runs", README). Tests in the repo are provider-free contract tests (test_evolution_contracts.py, test_meta_harness.py) covering interface/timeout wiring, not the search quality.
10. `run_cmd` swallows candidate crash details into truncated stderr[:200] prints (text_classification :213-214, 424); failure reasons are not persisted into the proposer-visible history.

## 7. Verifier / evaluation / safety handling

- Verifier: fixed, outside the candidate. Text classification: task evaluators in `data/evaluators.py` (not read), accuracy from `inner_loop.py`. TB2: Harbor verifier reward per trial (`verifier_result.rewards.reward`, parse_job_results :232-250); passes counted as `reward > 0`. The proposer is told not to modify `meta_harness.py`/`claude_wrapper.py` or existing agent files (TB2 SKILL.md:56-60) but this is prose; the sandbox permits it (full Bash + Write/Edit, skip-permissions).
- Exploit handling: none in the loop. No audit of whether a candidate reads test files, tampers with the verifier, or special-cases tasks. Only prose rules. The experimental pilot adds denylist substring checks (`/tests`, `verifier`, `/solution`, `task.toml`, `test_outputs` + per-task forbidden strings) and AST structure checks and a "never import candidate code into the long-lived process" rule (controller.py docstring :1-5; :144-175; agents/meta_harness.py).
- Code sandboxing: candidates are executed inside Harbor environments (Runloop or Modal, `HARBOR_ENVIRONMENT`, run_eval.sh:23-28) for TB2; for text classification the memory system is plain Python run in the benchmark subprocess (no isolation) with an LLM API call as its only external effect. The proposer runs on the host with a permissive shell.
- Timeouts: proposer 2400 s per iteration (text_classification :164, 595-598); Harbor 8 h (TB2 :97, README); smoke test 1800 s; returncode 124 on timeout -> candidate treated as failed, partial results not parsed (harbor_run docstring :158-162).
- Held-out handling summary: text classification = val-only evolution + one-shot `--test` finalization with freeze file (strongest piece, but not access-controlled); TB2 = no held-out.

### What the discovered TB2 harness actually changed vs the baseline harness
I diffed meta-harness-tb2/agent.py against meta-harness/reference_examples/terminal_bench_2/agents/baseline_kira.py (the KIRA baseline the search started from). Findings:
- The prompt template `prompt-templates/terminus-kira.txt` is byte-identical to the baseline's; `anthropic_caching.py` is byte-identical.
- The single behavioral change: environment bootstrap. New method `_gather_env_snapshot` (diff lines ~873-970) runs one compound shell command (cwd, `ls -la /app/`, python3/gcc/g++/node/java/rustc/go versions, pip/pip3/apt-get versions, `free -h`, 15 s command timeout, 20 s outer timeout, silent "" on failure), parses `@@SECTION@@` markers, truncates `/app` listing to 20 entries, and appends "[Environment Snapshot] ..." to the initial prompt in `_run_agent_loop` (~985-992). ## 8. Bottom line (5 lines max)
1. Meta-Harness's one real idea is filesystem-as-memory for a tool-using coding-agent proposer with a tiny prompt; the loop itself is trivial (propose -> import check -> eval -> best-so-far, no gate, no CI, no accept/reject).
2. Our propose.py is the weak link versus them: a one-shot completion over truncated error-only excerpts (propose.py:19-42, 82) vs their unrestricted Read/Grep/Bash over full code, traces, scores and past proposer sessions; port that into L2/L6.1 while keeping our typed-edit output contract.
3. Our selection/gate/held-out/calibration machinery is substantially stronger (paired CI racing, gate split, protected nodes) - their TB2 result is in-sample (same 89 tasks) and their held-out isolation is by convention not mechanism.
4. The discovered TB2 harness = KIRA + one env-snapshot injection (identical prompt template); do not over-weight the paper's "emergent code-search" narrative from this artifact.
5. Concrete adopts: workspace export + tool-using proposer, proposer-written per-generation reports, smoke-run gate, one-shot `finalize` freeze for the sealed split; cost reference: ~$500/iteration and 4-6 h on TB2 at 89x2 trials (their README), which our racing is designed to cut.
