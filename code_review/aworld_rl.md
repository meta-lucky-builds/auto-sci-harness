## 2. Core loop, step by step (EnvTuning; the only RL environment with code)
1. verl calls `MultiTurnFunctionCallInteraction.start_interaction` (`new_multi_turn_fc.py:45`): builds a model instance set and a separate ground-truth instance set (`instance_id + "_ground_truth"`) of the BFCL API classes, via `execute_multi_turn_func_call` (`bfcl_env/multi_turn_utils.py:34`). State is held in a module-level `globals()` dict keyed by instance name (`multi_turn_utils.py:~76-95`).
2. Each model reply goes to `generate_response` (`new_multi_turn_fc.py:93`): parse, special cases, execute, decide.
   - Parse is a strict format gate, `parse_model_response` (`interaction/utils.py:22-125`): exactly one `<think>`, exactly one of `<tool_call>`/`<answer>`, no text outside the tags, valid JSON inside. Violation returns the error text to the model as feedback with reward -3.0 (`new_multi_turn_fc.py:130`).
   - Turns whose ground-truth call list is empty (BFCL "miss func/miss param" turns) are handled at `new_multi_turn_fc.py:136-146`: an `<answer>` earns 1.0, a tool call earns 0.0 plus a system-warning hint and the turn is force-quit.
   - Execution (`execution_manager.py:32-92`) runs each call by `eval()` over instance methods (`multi_turn_utils.py`, the `eval(func_call)` line) after a name denylist (`kill, exit, quit, remove, unlink, popen, Popen, run`). Results come back as a user message "Here are the function's execution results..." with per-step reward -1.0 (ok) or -2.0 (error) (`execution_manager.py:94-114`).
   - Max 5 attempts per turn (`max_step_limit = 5`, `new_multi_turn_fc.py:37`); beyond that the turn is force-advanced (`turn_manager.py:420`).
3. Turn-end scoring (`turn_manager.advance_to_next_turn`, `turn_manager.py:357` -> `score_calculator.calculate_turn_score`, `score_calculator.py:207-242`): 0.0 if the model produced nothing; else re-executes the GT calls on the GT instances and requires BOTH `state_checker` (every public attribute of every instance equals GT, `multi_turn_checker.py:~173`) AND `response_checker` (GT execution outputs are an unordered subset of the model's accumulated outputs, `multi_turn_checker.py:~242`) -> 1.0 else 0.0. So the per-turn reward is binary but outcome-based (state + output equality), not text matching.
4. Trajectory reward = sentinel-coded list `user_turn_rewards`, where values mean {1, 0 = turn graded; -1 = tool call ok; -2 = tool call errored; -3 = format error}. `bfcl_reward.compute_score` (`bfcl_reward.py:1-34`): `score = progress = mean of the 0/1 entries only`; format and tool-call ratios are returned as diagnostics, not in the score. `format_reward.compute_score` (`format_reward.py:1-29`): `score = is_tool_call * (format_reward + tool_call_reward)`, with `progress` returned separately.
5. Curriculum = which YAML/script is run (`scripts/run_multi_turn_fc_grpo_stage{1,2,3}.sh`). I diffed them: stage 1 uses `format_reward.py`, `max_response_length 10000`, batch 16 and `bfcl_train_base.parquet`; stage 2 switches to `bfcl_reward.py`, response length 24576, batch 32, same base data; stage 3 swaps only the data file to `bfcl_train.parquet` (config identical to stage 2, `diff` empty). The model name in each script's EXPERIMENT_NAME changes (Qwen2.5-7B stage 1, watt-tool-8B stage 2/3), which looks like leftover experiment labels (inference).
6. GRPO hyperparameters (all three YAMLs, `multi_turn_fc_grpo_stage1.yaml:20-55`): lr 1e-6, low_var_kl loss coef 0.1, clip ratio 0.2 low / 0.28 high (DAPO-style asymmetric clip), `loss_agg_mode: seq-mean-token-mean`, `adv_estimator: grpo`, `max_turns: 100`, sglang rollout.

## 3. Paper/summary vs code discrepancies
- **RODS (the survey's headline item): not in code at all** (see section 0). Every RODS claim (variance detector, boundary partitioning into mastered/boundary/hard, five-stage synthesis, dual-control replay buffer, +33.87, 20x fewer trajectories) is unverifiable from this repo. The README numbers are self-reported.
- **"Four-stage curriculum" (README) vs three stage configs/scripts.** README says "Four-stage"; Quick Start lists stage 1-3 (and the README's own data list says "Stage 3 & 4" for `bfcl_train.parquet`). Stage 3 is config-identical to stage 2 apart from the training parquet.
- **"Actionable environment augmentation" is not wired into the training interaction.** `bfcl_env/func_source_code/` is the augmented simulator (e.g. `travel_booking.py` adds explicit `Invalid airport code(s)... use list_all_airports` hint errors; diff vs `func_source_code_wo_aug/`), but `execute_multi_turn_func_call` selects the augmented classes only when `is_augmented=True` (`multi_turn_utils.py:~52`: `CLASS_FILE_PATH_MAPPING if is_augmented else CLASS_FILE_PATH_MAPPING_WO_AUG`) and the default is False. A repo-wide grep for `is_augmented` finds it only in `multi_turn_checker.py` and `multi_turn_utils.py`; none of `execution_manager.py`, `score_calculator.py`, `new_multi_turn_fc.py` pass it. So, as released, the interaction code trains on the NON-augmented classes. Either the verl fork passes it (not verifiable, submodule empty) or the released code does not reproduce the paper's central ablation. I did not check whether `utils.py` in `interaction` injects hints elsewhere; I grepped `env_tuning/` for "augment" and found no match. The only "hint" text in training code is the generic prompt in `format_execution_response` and the missing-function warning.
- **"Fine-grained progress rewards ... by turn and by execution outcome"**: the actual reward is the mean of binary per-turn graded outcomes (`bfcl_reward.py:9-10`); the finer per-call signals (-1/-2/-3) are excluded from `score` in stage 2/3. Progress is fine only in the sense of "fraction of turns correct", not partial-credit within a turn.
- **Data**: README says data cannot be released, repo ships parquet anyway (`data/*.parquet`); content not inspected.
- The survey summary says "Qwen2.5-4B" for FunReason-MT; the root README table says Qwen3-4B (README line ~219). Minor, and not code-verifiable.

## 4. Mechanisms worth adopting into custom-harness (ranked)
Most of AWorld-RL's value for us is design ideas for L8 and L3, not code. Our repo has no L8 yet (`STATUS.md` lists L0-L4, L6 only; "Weights" not started) and PLAN §A4/C7 defers L8 to post-M2, so nothing here is urgent.

1. **Reward-variance boundary selection (the RODS idea) for L8 data selection.** What: per-task rollout reward variance as a zero-cost "is this task informative" signal; GRPO group advantage vanishes when all samples in a group get the same reward, so tasks with mixed success/failure carry the gradient (README "Method" and "Introduction", Popoviciu bound argument; **README only, no code**). Why better: our PLAN §4 L8 currently says "synthetic data targeted at reward-variance gaps (AWorld-RL RODS)" with no concrete selection rule; this gives one. We already compute per-task multi-rollout outcomes in `evolve/` racing, so the variance statistic is a one-liner over data we have. Layer: L8 (and arguably L7 stall detection: low variance across the frontier = saturated task suite). Effort: S for the selector (reimplement from description: p-hat per task, keep 0 < p-hat < 1, optionally weight by p(1-p)); M-L for the synthesis pipeline (not available, must design ourselves). Copy-vs-reimplement: reimplement (nothing to copy; MIT anyway). Caveat: variance estimated from few rollouts per task is noisy; use a CI/Beta posterior rather than raw variance [inference].
2. **Turn-level outcome verification by state-diff plus output-subset against a replayed ground-truth instance (L3 T1 pattern).** What: `score_calculator.py:207-242` + `multi_turn_checker.py` `state_checker`/`response_checker`: run the model's calls on one instance, the reference calls on a twin instance, compare all public attributes and require GT outputs to be a subset of the model's outputs (unordered, because parallel calls). Why better: gives a deterministic executable verifier with graded partial credit across turns, instead of a single end-of-task pass/fail; matches PLAN §3 "T1 executable exact" and ScienceIDE-style invariants. Our `verify/` has stats (`stats.py`) and trusted metrics but no state-diff verifier. Layer: L3 (also usable in L4 experiment checks when a reference solution exists). Effort: S-M. Reimplement (BFCL itself is Apache-2.0; their checker derives from BFCL).
3. **Sentinel-coded per-step reward channel with diagnostics separated from the optimized score** (`bfcl_reward.py:4-35`, `format_reward.py`): one trajectory-level list encodes graded turns (0/1), tool-ok (-1), tool-error (-2), format-error (-3), and different reward functions are swapped per curriculum stage while the same diagnostics are always logged. For L8 we should log the same decomposition (format validity, tool success, outcome) for every trajectory so that a reward change never destroys diagnostics, but I would use a typed record, not magic numbers (see pitfalls). Layer: L8 plus L3. Effort: S.
4. **Format-first then outcome curriculum (stage 1 reward = format+tool-call validity, stage 2 = outcome progress)**; README's single-stage ablation claims instability and collapse without it (claim only; the plot is an image, not checked). Applicable if we ever run GRPO on a small open model for the L4 roles. Layer: L8. Effort: S (config-level). Reimplement.
5. **Strict output-grammar gate returning the exact error text to the model** (`utils.py:22-125`, error text feeds back to the policy with -3 reward). For our L0 contracts (we already have contracts with bounded retries) this is conceptually the same as what we have; worth borrowing only the "negative reward channel for format violations during RL training" part. Layer: L8. Effort: S.
6. **Dual-instance replay for exact-state comparison and per-instance cleanup** as the model for our sandbox-backed T1 verifier when tasks are stateful (our snapshots are state-exact per PLAN B4). No code to copy; concept only.
7. (Low priority, outside our current plan) StressWeb's perturbation injectors (`website_simulatior/inject_*_perturbation.py`: random failure with probability 0.3 at `inject_failure_perturbation.py:17`, popups, layout chaos, semantic conflict) are a ready-made source of ideas for PLAN §8.4 "exploit quarantine under perturbed evaluator" and robustness testing of web-using research agents. Only the idea transfers; the code is web-specific. Skimmed only.

What is NOT useful for us: V2P (GUI visual grounding, a vision model training recipe), RAG-R1 (multi-query search RL on KILT with exact-match reward, vendored verl), StressWeb as a benchmark (web-GUI agents; our target is ML research), the FunReason pipelines (no code). BFCL-specific simulators (`func_source_code*/`) are irrelevant to research tasks.

## 5. Things custom-harness already does better (with evidence)
- Statistical rigor of verification: `src/custom_harness/verify/stats.py` has seed bootstrap and paired test-example bootstrap CIs; AWorld-RL reports single numbers with no CIs, seeds or variance (README tables), and says nothing on seeds in code.
- Gated, auditable evolution: our `evolve/` has typed edits, racing, held-out gate, lineage including rejects, calibration (STATUS.md L6). AWorld-RL has no harness-level self-improvement; each stage is a human-run script (`scripts/*.sh`).
- Evidence plane and claim provenance (STATUS L2/L4): nothing comparable in AWorld-RL.
- Safe code execution: our Docker sandbox (no network, caps, non-root, read-only rootfs) vs. their in-process `eval()` with a 8-name denylist (see section 6).
- Private-data guard and hidden-test verification (STATUS L4): their ground truth lives in the interaction state next to the model's instances, protected only by process separation.

## 6. Pitfalls, bugs, or anti-patterns seen in their code
- **Unsandboxed `eval()` of model-generated call strings inside the training process** (`multi_turn_utils.py`, `func_call_result = eval(func_call)`), guarded by a denylist of 8 names checked via `split("(")[0]` / `split(".")[1]` string slicing. Nested expressions, attribute access (`a.f(x=__import__(...))`), or any non-listed name bypass it; `_process_method_calls` regex-rewrites calls to the instance, which makes injection easier. Avoid; our Docker sandbox is the right model.
- **Reward-hackable / loophole behaviours in the verifier**:
  - Turns with empty GT: any `<answer>` earns 1.0 (`new_multi_turn_fc.py:140-141`), so the policy can learn "always answer immediately" on any turn with missing GT and that is rewarded. Also an empty model response on a GT turn scores 0.0 but on a no-GT turn the "call a tool" branch scores 0.0 and force-quits, which is intended.
  - State check requires equality of ALL public attributes (`state_checker`), so the model gets no credit for correct-but-different incidental state (e.g. extra file listing counters); conversely, the response check is only a subset check, so redundant extra calls are free. No penalty for step count except via the 5-attempt cap.
  - `score` for stage 1 = `is_tool_call * (format + tool_call_reward)` rewards making any tool call at all (`format_reward.py:49`); intended as a warm-up only.
- **Magic sentinel numbers in one list (`-1/-2/-3` mixed with `0/1`)** (`bfcl_reward.py:4-23`): mean over `s == 0 or s == 1` only; a bug in producers silently changes semantics. Also `calculate_overall_score` in `score_calculator.py:303-318` divides by total length but sums only non-negative scores (inconsistent with `bfcl_reward`); it appears to be dead code (`calculate_score` at `new_multi_turn_fc.py:174` returns 0.0 constant).
- **State leak / wrong key in cleanup**: `await self.finalize_interaction(instance_id=entry_id)` (`new_multi_turn_fc.py:121`) passes the dataset `entry_id` not the `instance_id`, so `self._instance_dict` entries are likely never freed on that path; meanwhile model/GT instance objects live in the module `globals()` forever (`multi_turn_utils.py`), keyed by name; long training runs accumulate memory (inference from code reading; not executed).
- **Mutating the question queue**: `_prepare_next_question` pops from `state.processed_question` (`turn_manager.py:414-416`); state is per instance so OK, but there is no replay/determinism guarantee if a rollout is retried [inference].
- **Incomplete repo for reproduction**: trainer submodule empty, data withheld, the augmentation switch apparently off, stage configs partly duplicated. Treat reported numbers as "as reported", not reproducible from this repo.
- **Hard-coded `max_step_limit = 5`**, hard-coded Chinese comments/log strings, `print` for error handling (`score_calculator.py:281,300`): swallowed exceptions in the verifier return `False` (reward 0) rather than failing loudly, which would silently turn infrastructure bugs into "model got it wrong".
- Hygiene: `V2P/src/V2P/__pycache__/*.pyc` committed to the repo; API key config file `StressWeb/authorization.py` is a template to be edited in place (risk of committing keys).

## 7. Verifier / evaluation / safety handling
- Ground truth: BFCL V3 multi-turn data; verifier is outcome-based (final state of simulated APIs + execution outputs), executed in-process in Python with a name denylist (see section 6). No container, no timeout/resource limits I saw in the files I read (`execution_manager.py` wraps in a bare `try/except Exception` and treats exceptions as `has_error=True, should_continue=False`).
- Exploit handling: none beyond the denylist and the format gate. No held-out check that rewards correlate with the real BFCL score during training, no perturbed-evaluator re-run. The README's evaluation split is "half of each BFCL V3 multi-turn split as train, the rest as test" (README step 3), i.e. train and test are drawn from the same benchmark distribution; OOD checks (BFCL V4, ACEBench, tau2-bench) are reported in the RODS README only.
- Rewards for RAG-R1: exact-match on extracted last `<answer>` (`verl/utils/reward_score/qa_em.py:62-110`; grep-level reading only), a standard rule-based reward.
- StressWeb: per-query evaluators parse the final HTML with regexes (`evaluator/calendar_query1.py`), which is brittle but deterministic; ground truth from the generator pipeline. Not assessed further.

## 8. Bottom line
- RODS, the item the survey emphasised, is README-only in this repo (no variance detector, synthesis pipeline or replay buffer); same for FunReason-MT. Do not plan to copy code from it; take only the idea (variance-selected tasks) and re-derive it ourselves in L8.
- The only real code of value is EnvTuning's executable multi-turn outcome verifier (state-diff plus output-subset against a replayed GT instance) and its stage-wise reward swap; both are small and reimplementable (MIT allows copying with attribution, but the verifier sits on the unsafe `eval()` design).
- Released EnvTuning code does not appear to enable the paper's "actionable augmentation" (`is_augmented` default False, never set), and the trainer/data are missing, so its numbers are not reproducible from here.
- Relevance: low-to-moderate and almost entirely L8 (selection rule + reward decomposition) and L3 (stateful T1 verifier); nothing for L4/L5/L6/L7; V2P, RAG-R1, StressWeb are off-target for ML-research harnesses.
- Safety lesson (negative): in-process `eval` plus a denylist and "answer on empty-GT turn gets 1.0" are examples of exactly the verifier exploits our PLAN §8.4 quarantine should catch.
