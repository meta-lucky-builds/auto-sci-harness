## 1. What the code actually does (architecture map)

Pipeline entry: `launch_scientist_bfts.py` (main at :182) → loads one pre-generated idea JSON (`--load_ideas`, :191-195) → `perform_experiments_bfts(config)` (:256) → `aggregate_plots` (:265, LLM-written plotting script run by `subprocess.run`, `perform_plotting.py:114`) → citation gathering + LaTeX writeup with VLM reflection → LLM paper review (:304-319) → process cleanup (:321-359).

Experiment engine (the part you asked about) has three layers:

1. `AgentManager` (`treesearch/agent_manager.py`): a **fixed 4-stage state machine**, not a free-form "manager agent". Stages are hardcoded: 1 initial_implementation, 2 baseline_tuning, 3 creative_research, 4 ablation_studies, with hardcoded goal prose (`agent_manager.py:143-167`) and per-stage iteration caps from config (`bfts_config.yaml`: 20/12/12/18). The LLM is used only for yes/no completion checks and to name/describe *sub-stages* (`_generate_substage_goal`, :552-636; `_create_next_substage`, :638-662).
2. `ParallelAgent` (`treesearch/parallel_agent.py`): per sub-stage, picks N nodes (N = `num_workers`, capped at GPU count, :1168-1180) and submits each to a `ProcessPoolExecutor` worker (`step`, :2053-2190). Each worker runs `_process_node_wrapper` (:1410-1796): generate code (draft/debug/improve/hyperparam/ablation) → execute → LLM review → LLM-written metric-parsing script → LLM-extracted metric → LLM-written plotting script → run → VLM plot analysis.
3. `Journal`/`Node` (`treesearch/journal.py`): the tree. A `Node` holds plan, code, term_out, exception info, `metric` (`MetricValue`), `is_buggy`, `is_buggy_plots`, VLM analyses, parent/children (:44-118). `Journal` is a flat list plus helpers: `draft_nodes` (parent None, :380), `buggy_nodes`, `good_nodes` (:390-407), `get_best_node` (:420-502).

Config knobs that define the search (`bfts_config.yaml`): `num_drafts: 3`, `debug_prob: 0.5`, `max_debug_depth: 3`, `num_workers: 4`, `multi_seed_eval.num_seeds: 3`, `exec.timeout: 3600`, coder = Claude 3.5 Sonnet, feedback/VLM/selection = gpt-4o.

## 2. Core loop, step by step (with file:line citations)

**Outer loop** — `AgentManager.run` (:692-829):
1. For each (sub-)stage create a `ParallelAgent` (:703, `_create_agent_for_stage` :274-329). Stages 2/3/4 are seeded with the previous stage's best node, deep-copied with parent/children cleared (:538-550, :705-718), and that carried-over node is appended to the new journal as node 0.
2. Inner `while True` (:721): `agent.step()` once, then `_check_stage_completion` (:410-536), then, if the main stage is not complete, `_check_substage_completion` (:343-408), which **makes an LLM call every step**.
3. Main-stage completion rules: stage 1 = at least one good node (:434-442) or fail the whole run at max iters (:414-429); stage 2 = best node differs from node 0 (i.e. beat the carried-over node) and an LLM says complete from VLM text + datasets list (:444-498); stage 3 = best differs from node 0, plus an "runs too quickly, scale it up" exec-time feedback rule written onto the last node (:500-530); stage 4 = run to max iterations (:531-533).
4. On main-stage completion, `_run_multi_seed_evaluation(best_node)` then `_run_plot_aggregation` (:738-756) re-run the winning code with seeds 0..2 and LLM-aggregate plots. This happens **after** the winner was already selected, so seeds affect reporting only, not selection.
5. Sub-stage completion (LLM says goals met) creates a new sub-stage with an LLM-written name and goals and `num_drafts=0` (:779-804, :638-662).

**Node selection** — `ParallelAgent._select_parallel_nodes` (:1931-2051). For each of N worker slots:
- If fewer than `num_drafts` roots exist → `None` = new draft (:1952-1954).
- With probability `debug_prob` (:1964): choose a *random* buggy **leaf** with `debug_depth <= max_debug_depth` (:1980-1993; `debug_depth` = consecutive buggy ancestors, `journal.py:202-212`). Tree-diversity guard via `processed_trees` so parallel workers do not all hit the same tree (:1998-2004).
- Stage 4: always the single `best_stage3_node`; Stage 2: always the single `best_stage1_node` (:2009-2015). These two stages are **not tree search**: every iteration expands the same base node with a new LLM-proposed idea (hyperparameter in stage 2, ablation in stage 4) generated in the main process to avoid duplicates (:1798-1919, :2096-2113).
- Stages 1 and 3: **greedy best-first**: take `journal.get_best_node()` (the single best good node), else the best node from an unprocessed tree (:2016-2049). If there are no good nodes, draft again (:2020-2022). There is no UCT/bandit, no value estimate, no explicit backtracking; "backtracking" is just "the global best may be in a different subtree".

**Node expansion** — `_process_node_wrapper` (:1486-1522): parent None → `_draft` (:453-492); parent buggy → `_debug` (:494-521, prompt includes previous code, term_out, VLM feedback, exec-time feedback); parent good → `_improve` (:523-547) or the stage-2 hyperparam / stage-4 ablation generator (:557-656). Seed re-runs reuse the parent code (:1480-1485).

**Node evaluation** (all in the worker):
- Execute code in an `Interpreter` (`interpreter.py`, see §7) (:1526).
- `parse_exec_result` (:683-718): LLM function-call `submit_review` returns `is_bug` + summary; `node.is_buggy = response["is_bug"] or node.exc_type is not None` (:713).
- Metric: **another LLM writes a script** that loads `experiment_data.npy` and prints metrics (:1555-1594), the script is executed (:1597), and **a third LLM call extracts the numbers** from the printed text into `MetricValue` (:1608-1637). Failure anywhere → `WorstMetricValue` and `is_buggy=True` (:1642-1666). Seed nodes reuse the parent's parse script (:1541-1552).
- Plotting: LLM writes plotting code (:720-833), executed with up to 3 retries on exception (:1669-1711); PNGs moved into `logs/.../experiment_results/` (:1745-1760).
- VLM: `_analyze_plots_with_vlm` (:894-1033): if >10 plots an LLM picks 10 (:910-980); VLM returns per-plot analyses, `valid_plots_received`, and a summary (schema :103-133). `is_buggy_plots = not valid_plots_received` (:1020-1023). Then an LLM decides which datasets were "successfully tested" (:835-892).
- **A node counts as good only if `is_buggy is False and is_buggy_plots is False`** (`journal.py:405-407`, strict `is False`). A node whose plotting failed or produced no plots has `is_buggy_plots=None` and is never good, so the VLM/plot step is an implicit validity gate on the search.

**Best-node choice** — `Journal.get_best_node` (`journal.py:420-502`): for >1 good nodes it asks an LLM (default `gpt-4o` temp 0.3 unless `cfg.agent.select_node` set, :470-475) to pick by id from a text list of `ID` + `str(metric)` (seed nodes excluded, :453). Fallback on exception or unknown id: `max(nodes, key=metric)` (:497, :502). `MetricValue.__gt__` compares the **mean of `final_value` over all metrics and datasets** (`metric.py:171-189, 302-324`) with direction taken from the **first** metric only (:191-204). This is called on every search step, every completion check, and in reporting.

**Memory** — `Journal.generate_summary` (:504-548): an LLM call over all good + buggy nodes (plan, analysis, metric, error type, debug depth) producing "patterns of success/failure/recommendations", regenerated every step (`step`, :2072-2081) and injected as `Memory` into draft and improve prompts (:463, :530) but not into debug prompts.

**Report assembly** — `overall_summarize` (`log_summarization.py:299-366`): stage 1 and 2 report best node + seed nodes + aggregation node; ablation stage reports every good leaf with an `ablation_name` (:333-335, no seeds).

## 3. Paper/summary vs code discrepancies

(The paper itself was not read; "claim" below is from `autoresearch_survey/gh_SakanaAI_AI-Scientist.md` lines 141-150, 211-215, and the README.)
1. "Experiment manager agent orchestrates exploration dynamically" (summary l.147). Code: stage names, order, goals and completion rules are hardcoded (`agent_manager.py:143-167, 410-536`). The LLM only answers yes/no checks and writes sub-stage goal strings. Dead experiment-manager code exists but is never called: `_create_stage_analysis_prompt` (:831, also references an undefined `stage_number` at :888), `_evaluate_stage_progression` (:1151), `_get_response` (:978), top-level `stage_config_spec`/`stage_progress_eval_spec` (:21-75).
2. "Backtracking when experiments hit dead ends" (summary l.146). Code: no backtracking operator. Buggy leaves are retried only while `debug_depth <= 3` with probability 0.5 per slot; deeper dead ends are simply never selected again. New roots appear only when `len(draft_nodes) < num_drafts` or there are zero good nodes (`parallel_agent.py:1952, 2020`).
3. "Tree search" for all stages. Code: stages 2 and 4 expand one fixed base node (`:2009-2015`), i.e. a fan of siblings, not a tree. Stage 1/3 is greedy best-first.
4. Stage bookkeeping bug: `_create_next_substage` sets `stage_number=current_substage.stage_number + 1` (`agent_manager.py:661`) and `_create_next_main_stage` sets it likewise (:679), but completion logic branches on `stage.stage_number == 1/2/3/4` (:434, :444, :500, :531). After any sub-stage is created the counter no longer equals the main-stage number, so later stages can be evaluated with the wrong completion rule. This is derived from reading, not from running it.
5. Per-node summaries and stage notes silently never run: `hasattr(node, "_agent")` guards (`agent_manager.py:1054`, `journal.py:573`, `perform_experiments...:113`) but `_agent` is never assigned anywhere (grep over `ai_scientist/` finds only reads).
6. `_check_substage_completion` has unreachable tail code and returns a bare `False` where callers unpack a tuple (:397-408); after a successful LLM call all branches already returned.
7. Multi-seed: config comment says `num_seeds` "should be 3" and `_aggregate_seed_eval_results` hardcodes `seed_nodes[0..2]` (`parallel_agent.py:2316-2324`); any seed failure or `num_seeds != 3` raises inside a bare `except` (:1406) and aggregation is silently skipped.
8. README itself states v2 has lower success rates than v1 and is exploratory (README l.22), consistent with the weak selection/verification design below.

## 4. Mechanisms worth adopting into custom-harness (ranked by expected value)

Licensing note first: the repo license permits derivative works but (3.1) requires shipping the license, (3.2e) forbids generating/disseminating manuscripts without a prominent machine-generated disclosure, and (3.3) requires the restrictions to be embedded in downstream legal agreements (`LICENSE`). It is not MIT/Apache and is not compatible with our Apache-2.0 decision (PLAN A3) if we copy code. **Verdict: ideas only; reimplement from scratch; copy nothing.** (We should disclose machine generation in reports anyway.)

Baseline of ours for all comparisons: `examples/research_v0.yaml` is a one-shot ranked hypothesis queue (`tournament` → `next` → `implement` → `run` → optional `fix` ×2, `edges` from line 99; `run` params `max_attempts: 6, max_fixes: 2` at line 94), and `research.run_candidate` (`src/custom_harness/research/modules.py:175-213`) only returns routes fix / next / verify / give_up. There is **no improve-from-a-working-candidate operator**, no candidate tree, and a successful candidate is never refined.

1. **Candidate tree with three operators (draft / debug / improve) and deterministic best-first selection** (v2: `parallel_agent.py:453-547, 1931-2051`; `journal.py:202-212, 380-407`).
   - Why better: our loop cannot compound gains; a hypothesis that works at 0.71 is never pushed to 0.75. v2's `improve` operator reads parent code plus feedback (`:523-547`).
   - Take the structure but fix its flaws: pick the parent by **dev score computed by code**, not an LLM (see §6); keep selection RNG seeded from `state["_seed"]` as our `tournament` already does (`modules.py:126`) so runs are replayable.
   - Where: L4 step 7 (PLAN §4 "tree search over experiment code"); node table lives in graph state / Evidence store with lineage (parent_id, op, debug_depth, dev_score, code_ref), implemented as a new module `research.select_node` that outputs `route ∈ {draft, debug, improve, verify, give_up}` plus `parent`; existing `implement`/`fix` nodes become draft/debug prompts and we add an `improve` LLM node. The runtime already supports loops (`max_steps: 60`, yaml line 5), so no L0 change is needed.
   - Effort: M. Reimplement.
2. **Debug-depth cap and "buggy leaf" bookkeeping as an explicit, evolvable policy** (`journal.py:202-212`; `parallel_agent.py:1964-1993`; config `max_debug_depth: 3`, `debug_prob: 0.5`).
   - Why better: ours is a flat `max_fixes: 2` per hypothesis and a global `max_attempts: 6` (yaml line 94). Depth-per-lineage plus a probability of returning to old failures is a richer search policy.
   - Expose `max_debug_depth`, `debug_prob`, `num_drafts` as typed edit surfaces for L6 (PLAN §4 L6 `control-flow`), so the evolver can tune them. Effort: S. Reimplement.
3. **Stage curriculum with stage-specific operators: baseline → tune → creative → ablation** (`agent_manager.py:143-167`; hyperparam generator with a "tried" list `parallel_agent.py:1798-1858`; ablation generator `:1860-1919`).
   - Why better: our v0 ends at "beats baseline on hidden test". v2's ablation stage yields attribution evidence (which component produced the gain), which maps directly onto PLAN L4.8 (Socratic critic: "which control is missing?") and a stronger T2 claim. Stage 2's "first check training longer, then LR/batch size, then model-specific" ordering (`:1805-1811`) is a cheap, useful prior for our ML/DL domain (PLAN §13.3).
   - Where: L4 stages 7-8; encode as sub-graphs in the harness spec, each with an entry criterion computed by code (our `_better`, `modules.py:73`), not an LLM. Effort: M. Reimplement.
4. **Failure/success memory fed to prompts** (`journal.py:504-548`, used at `parallel_agent.py:463, 530, 2072-2081`).
   - Why better: our `implement` prompt (yaml lines 46-66) sees only the current hypothesis; it learns nothing from the earlier attempts' errors or scores. PLAN L5 lists this as not built (STATUS "Next" #3).
   - Do it as a **deterministic digest** (best score, per-attempt error class, tried ideas) rather than a per-step LLM summary (v2 pays one LLM call over the full history every step). Where: L5 playbook/negative memory read by L4. Effort: S. Reimplement.
5. **Exec-time feedback and "valid output" gate on candidates** (`agent_manager.py:510-530`; `journal.py:405-407`).
   - Take the idea of a deterministic validity predicate (ran, produced scoreable output, within timing band) that gates "good" status. We already have scoreability in `run_candidate` (`modules.py:186-190`); add timing/budget feedback to the next prompt. Effort: S.
6. **VLM figure review loop in the write-up stage** (`perform_icbinb_writeup.py:1013-1160`; `perform_vlm_review.py:389-444` duplicate-figure detection; per-figure caption/figref review prompts `perform_vlm_review.py:35-110`).
   - Worth adopting later for PLAN L4.10 (report/paper): compile → VLM reviews each rendered figure vs caption and in-text references → detect duplicates → page-limit-aware figure triage → revise. **Condition**: every revision must re-pass our integrity audit I1/I4 (`modules.py:320+`), which v2 lacks (see §6). Low priority for tabular M1 tasks (D1). Effort: M-L. Reimplement.
7. **Stage-gated parallelism + GPU slot manager** (`parallel_agent.py:1091-1139, 1178-1183`): one worker per GPU with `CUDA_VISIBLE_DEVICES` pinning (:1443-1448). Trivial; matches PLAN B8. Effort: S. Reimplement.
8. **Idea generation as a tool loop with Semantic Scholar search and reflection rounds** (`perform_ideation_temp_free.py`, `tools/semantic_scholar.py:101-138`). I only skimmed this; relevant to PLAN L4.3 literature module. Effort: M. Defer.

Not adopting: LLM-picked best node, LLM metric extraction, in-host execution (see §6/§7).

## 5. Things custom-harness already does better (with evidence)

- **Held-out verification separate from search.** v2 selects the winner and reports on the same single-run metric the winner was chosen by; seeds run after selection (`agent_manager.py:738-751`). Ours scores candidates on a dev split and verifies the winner on a hidden test split with 3 seeds, seed-CI **and** paired example-bootstrap CI both excluding zero, against an identically re-run baseline (`modules.py:216-286`). There is no hidden-test notion in v2 at all.
- **Metric provenance.** v2's metric is the output of three LLM hops (code writes npy → LLM-written parser prints → LLM function call extracts numbers; `parallel_agent.py:1555-1637`). Ours scores predictions with code-implemented metrics (`modules.py:64-71`, `verify/metrics.py`) and records T1 Evidence (`modules.py:249-252`).
- **Private-data guard.** `_private*` state cannot render into prompts (STATUS L4). v2 gives the LLM the full dataset directory and the executing code access to everything in the process environment.
- **Deterministic routing** (`modules.py:201-211`, PLAN P7). v2 routes by LLM judgments at every decision point: bug detection (`:701-713`), best-node (`journal.py:476`), stage completion (`agent_manager.py:364, 473`).
- **Claims only from Evidence + audit** (`modules.py:281, 320+`). v2's writeup is an LLM over summaries; "Do not hallucinate" is a prompt line (`perform_icbinb_writeup.py:1079`); I found no programmatic check linking numbers in the paper to results.
- **Sandbox posture.** Ours refuses to execute unisolated (`_require_isolation`, `modules.py:34`; Docker with no network, caps, read-only rootfs per STATUS). v2 executes on the host (§7).
- **Replay/determinism.** Our tournament and routing are seeded (`modules.py:126`); v2 uses unseeded `random` for debug choice (`parallel_agent.py:1964, 1993`) and shuffles the package list in every prompt (`:289`).

## 6. Pitfalls, bugs, or anti-patterns seen in their code (cite) that we must avoid

1. **LLM chooses the "best" node and it is re-asked constantly** (`journal.py:436-502`): nondeterministic, non-replayable, costs a call on every step and every completion check, and its prompt lists only `ID` + metric string, so it cannot see code or per-seed variance. Operator precedence in `candidate_info` (:454-466) means a node with a falsy metric loses its `ID` line. Also the fallback `max(...)` compares mean-over-metrics-and-datasets with direction from the first metric (`metric.py:191-204, 302-324`), mixing losses and accuracies. We must keep selection in code (P7).
2. **Winner's curse / selection-reporting overlap.** With ~60 nodes per run (20+12+12+18 iters) chosen by single-run metrics, the best node is biased high; seeds are run after selection (`agent_manager.py:738-751`). With a tree search ours needs racing/CI on dev (PLAN §6.4) and the hidden test touched only for the winner, otherwise more nodes = more dev overfitting.
3. **Unreachable/dead code and silent failures**: stage-number conflation (:661, :679 vs :434-531), dead manager methods (:831, :978, :1151), bare returns (:408), `_agent` never set (:1054), hardcoded 3 seeds swallowed by bare `except` (`parallel_agent.py:2316-2324, 1406`). Pattern: many `except Exception: print(...)` that degrade quietly. Our typed spec + contracts already avoid this; keep it that way and never swallow errors without recording a failed-attempt Evidence record.
4. **Prompt placeholder bug**: `final_reflection_prompt` is not an f-string, so the literal text `{reflection_page_info}` is sent (`perform_icbinb_writeup.py:1195`). Also, `perform_imgs_cap_ref_review_selection` etc. depend on regex-extracted LaTeX with no compile-success gate after the last revision.
5. **Unsafe global cleanup**: at exit it SIGTERM/SIGKILLs **any process on the machine** whose command line contains `python`, `torch`, `mp`, `bfts` or `experiment` (`launch_scientist_bfts.py:347-359`). Never do this; track child PIDs/containers by label instead.
6. **Timeout handling can leak work**: the parent waits with `future.result(timeout=...)` (`parallel_agent.py:2152`) but a `ProcessPoolExecutor` task cannot be cancelled once running, so a timed-out worker keeps running; the inner interpreter's timeout is SIGINT-based (`interpreter.py:284`), which generated code can catch (`except BaseException` in user code) and which does not exist on Windows (`signal.SIGINT` to a child pid is not equivalent there); hard kill only after +60 s (:287-293). Use container-level wall-clock kill (we have Docker caps) instead.
7. **Prompts that invite unverifiable data**: "Make sure to create synthetic data if needed" (`parallel_agent.py:473`), and stage 2/3 goals demand "TWO/THREE HuggingFace datasets" (`agent_manager.py:158, 163`) in a loop that nothing verifies has network or real data. No exploit/quarantine checks exist; the agent chooses its own metric (`parallel_agent.py:1194-1222`) and its own evaluation code, so it can grade itself. Avoid; our fixed task spec + hidden test prevents this.
8. **Cost blow-up**: per step: one summary call over full history (:2072), one best-node call (≥1 per `_select_parallel_nodes` loop, :2025), one sub-stage completion call (`agent_manager.py:775`), per node: review, metric-parse code, metric extraction, plot code (+≤3 retries), plot selection, VLM, dataset determination. v2 has `token_tracker` but I did not read it, and I saw no budget enforcement in the loop (no cap besides iteration counts and 3600 s timeouts). We have a budget ledger (STATUS L1); keep every LLM judgment off the hot path.
9. **Shared mutable global node state across stages**: stage journals are seeded by deep-copying the previous best (:538-550, :711), and `len(journal.nodes) >= max_iterations` counts that copied node and all seed/aggregation nodes (`journal.py:374-377`), so budgets are not exactly what config says.
10. **License trap** (see §4): copying their code would pull their use restrictions into our Apache-2.0 project.

## 7. Verifier / evaluation / safety handling

- **Verifier tier (PLAN §3 scale):** effectively **T5/T6**. "Bug" = LLM review OR Python exception (`parallel_agent.py:713`). "Metric" = LLM-extracted from LLM-written parser output (:1555-1637). "Good" = LLM said not-bug and VLM said plots valid (`journal.py:405-407`). "Best" = LLM pick (`:476`). "Stage complete" = LLM over VLM text (`agent_manager.py:364, 473`). The one non-LLM signal is the exception / timeout flag and presence of `.npy` output (`parallel_agent.py:1535-1539`, which only logs a warning). The paper-review step (`launch_scientist_bfts.py:304-319`) is again an LLM, run post hoc, and does not feed the search.
- **VLM role in the search loop:** (a) validity gate on nodes, (b) feedback text injected into debug/improve prompts (`parallel_agent.py:505-506, 531-532`), (c) evidence for stage completion (`agent_manager.py:331-341, 351-361, 456-470`). It is not a verifier of claims and nothing checks that VLM descriptions are right (the prompt only says "Never make up plot analysis", :991-995).
- **Seed handling:** the winner is re-run for seeds 0..2 by prepending a seeding header to the code (`parallel_agent.py:1285-1288`); the code can ignore or override it. Results go to LLM aggregation plots, not to a statistical test.
- **Code execution / sandbox:** `Interpreter` runs LLM code via `exec(compile(code...))` in a `multiprocessing.Process` on the host, with working directory change and stdout redirect only (`interpreter.py:111-161`). No network, filesystem, memory, or privilege restrictions. The only safety text is the README caution to "run this within a controlled sandbox (e.g., Docker)" (README l.26) and `copy_data: True` to protect the original data (`bfts_config.yaml`). Per-worker workspace directories exist (`parallel_agent.py:1434-1441`) but are not enforced boundaries. The LLM-written plotting aggregator is also run unsandboxed via `subprocess.run([sys.executable, script])` (`perform_plotting.py:114`).
- **Exploit/reward-hacking handling:** none found. Self-chosen metric (`:1194`), self-written evaluation and parsing code, LLM judges with no held-out data. v2 is therefore fully exposed to the failure modes in PLAN P9/§8.4.
- **Resource handling:** one GPU per worker via `GPUManager` and `CUDA_VISIBLE_DEVICES` (:1091-1139, :1443-1448); CPU fallback; 3600 s timeout per execution (config).

## 8. Bottom line
- The "tree search" is greedy best-first (stages 1, 3) plus fixed-parent fan-out (stages 2, 4), with a debug-depth cap and a hardcoded 4-stage curriculum; the "experiment manager" is a state machine with LLM yes/no checks, and several documented behaviors are dead code or buggy.
- Adopt the structure (draft/debug/improve operators over a node tree, debug-depth policy, tune→creative→ablation curriculum, failure-memory digest) as typed, code-selected, replayable L4 modules; our linear implement/fix queue cannot compound improvements.
- Do not adopt their judging: LLM best-node, LLM metric parsing, VLM-as-gate, same-run selection and reporting, host execution; our hidden-test T2 verify, deterministic routing and Docker isolation are stronger.
- Licensing: custom restrictive license, so reimplement from ideas only; copy no code.
- Biggest new risk for us if we add a tree: dev-set overfitting from many more nodes, so pair it with racing/CI (PLAN §6.4) and keep the sealed hidden test for the winner only.
